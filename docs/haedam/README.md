# 해담시청 저장소 분리 준비

2026-10-19 사용자 결정: 서비스 이름은 **해담시청 민원포털**, 소개 문구는 **시민의 목소리를 담다, 해담시청**이다. 프론트와 백엔드는 별도 저장소에서 개발한다.

이 문서와 `scaffolds/`는 새 저장소를 위한 문서·폴더 스켈레톤이다. 아래 두 비공개 저장소를 생성했다. 초기 스켈레톤을 반영하며 앱 구현·의존성 설치·외부 도구 연결은 아직 하지 않았다.

**10/19 집 세션 후속:** 사용자가 김명준 + Codex의 포털 프론트·백 구현과 React + Flask를 선택했다. 별도 두 저장소에 로그인·민원 신청/조회/처리·관리자 계정 기능을 구현했다. [포털 API](PORTAL-API.md), [작업 brief](MVP-TASK-BRIEF.md), 각 저장소 README가 실행 기준이다. 위 스켈레톤 설명은 초기 생성 시점의 기록이며 외부 관제 연동 완료를 뜻하지 않는다.

실제 업무 흐름을 평가한 뒤 입력 이탈 경고·항목별 오류·검색 조건 복원·모바일 가독성을 개선했다. 최신 검증과 다음 작업은 [사용성 개선 핸드오프](../../work-log/2026-10-19-portal-usability-improvements.md)를 따른다.

후속 [MySQL 브라우저 통합 핸드오프](../../work-log/2026-10-19-mysql-browser-integration.md)에서 실제 MySQL 12건·앱 서버 재시작 2회·DB 직접 감사와 재현 명령을 확인한다. 팀 서비스 VM 배포·두 PC 관제 인수와 구분한다.

팀원 독립 재현과 PR 리뷰에는 [검증 체크리스트](REVIEW-CHECKLIST.md)와 [복사해서 전달할 리뷰 요청문](REVIEW-REQUEST.md)을 사용한다. 작성자 실측을 참고하되 검토자가 실제 결과·미실행 범위를 직접 기록한다.

- 프론트: https://github.com/NoBugs-Aleph/haedam-portal-frontend
- 백엔드: https://github.com/NoBugs-Aleph/haedam-portal-backend

두 레포를 초기화할 당시 공통 규칙 원본은 capstone의 미커밋 작업 트리에 있었다. 초기 복사본은 `docs/SOURCE.json`에 그 기준 HEAD와 실제 파일의 SHA-256을 기록했다. 원본·준비 파일은 이제 `codex/haedam-handoff-1019` 인수인계 브랜치에 함께 게시한다. 양쪽 새 레포의 초기 출처 기록은 자동 갱신되지 않으므로, 원본 커밋으로 출처를 맞추는 후속 PR이 필요하다. 초기 기준 HEAD에 새 규칙이 포함돼 있었다고 소급하지 않는다.

## AI 지침 구조

각 저장소는 `AGENTS.md`를 규칙 진입점으로 사용한다. `CLAUDE.md`는 `@AGENTS.md`를 불러오고, `CODEX.md`는 공통 지침을 안내하는 보조 문서다. 모델·개인 전역 설정은 포함하지 않는다.

공통 제약 원본은 **이 저장소의 `docs/haedam/PROJECT-RULES.md`** 한 곳이다. 스켈레톤과 새 저장소의 `docs/PROJECT-RULES.md`는 배포용 복사본이다. 저장소별 `AGENTS.md`에는 담당 경계와 확인 절차만 추가한다.

공통 규칙을 변경할 때:

1. 이 저장소 원본을 고치고 두 스켈레톤의 복사본을 함께 갱신한다.
2. 각 새 저장소에 원본과 동일한 `docs/PROJECT-RULES.md`를 반영하는 PR을 만든다.
3. 각 저장소 README에 적용한 capstone 커밋을 기록하고, 양쪽 반영 여부를 확인한다. 서로 다른 버전을 조용히 섞지 않는다.

이 복사본은 `tools/sync_ai_assets.py`의 관리 대상이 아니다. 이 도구는 기존 `.agents/skills/`·`ai/roles/`의 어댑터만 관리한다.

## 새 저장소로 옮기는 방법

프론트는 `scaffolds/haedam-portal-frontend/`의 **내용 전체**를 새 저장소 루트에 복사한다. 백엔드도 대응하는 폴더의 내용 전체를 복사한다. 숨김 파일과 빈 폴더 유지용 `.gitkeep`도 포함한다. capstone의 `.git`, `.venv`, 원본 로그와 개인 설정은 복사하지 않는다.

복사 후 다음 항목을 채운다.

- 실제 저장소 URL, 작업자·리뷰어, 적용한 공통 규칙 원본 커밋
- 프론트 기술·런타임, 백엔드 Python 버전·의존성 잠금, 개발·검증 명령
- API 계약 원본 커밋, 개발 주소, 로그인·CSRF·오류 형식
- DB·마이그레이션 및 합성 테스트 데이터 초기화·정리 방법

현재 파일에는 실행 가능한 앱과 잠금 파일이 없다. 존재하지 않는 `npm run`·Flask 실행 명령을 완료된 환경처럼 안내하지 않는다.

## 실행 배치 기준

레포 분리는 PC 분리가 아니다. 프론트와 백엔드는 공격·서비스 PC의 서비스 환경에 배치하고, Graylog·Wazuh·n8n·보안 대시보드와 티켓은 관제 PC 측에서 운영한다. Suricata는 합의한 pfSense 패키지 배치를 따른다. 이들은 **설계 기준**이며 실제 설치·연결 완료를 뜻하지 않는다.

레포 분리를 이유로 HTTP 프록시를 자동 도입하지 않는다. 초기 기준은 현재 기획서의 프록시 없는 요청 경로다. 프론트의 빌드 결과를 서비스 VM의 Flask 앱에서 API와 함께 제공하는 구성을 먼저 검증한다. 개발용 별도 origin이 필요하면 허용 origin·쿠키·CSRF 정책을 계약 단계에서 확정한다. 세부 IP·VMnet·포트는 기획서와 망 담당의 최신 허용표를 기준으로 하고 새 값은 임의로 확정하지 않는다.

현재 구현은 React/Vite, 서버 저장 세션·CSRF, 개발용 Vite 5173·Flask 5000, MySQL 계획·로컬 SQLite, Alembic이다. 실제 배포 주소·관리망은 망 담당이 정한 허용표를 따른다. 향후 HTTP 프록시를 도입하려면 신뢰할 접속 경로·전달 헤더·404 이벤트·망 로그 매핑을 별도 설계하고 S1·S8·S10을 재검증한다.
