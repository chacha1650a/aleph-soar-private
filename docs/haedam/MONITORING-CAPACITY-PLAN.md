# 관제 처리량·가용성·복구 검증 계획

2026-10-20 사용자 요청으로 추가한 H05 검증 계획. **상태: 계획 작성, 실제 두 PC 관제 시험 미실행.** Kafka 도입보다 현재 구성의 처리 한계와 회복을 먼저 측정한다. 기존 포털 [독립 체크리스트](REVIEW-CHECKLIST.md)의 T1~T4 결과와 별도로 기록한다.

## 1. Kafka를 쉽게 이해하기

Kafka는 여러 프로그램에서 발생한 기록을 받아 보관하고, 필요한 프로그램들이 각자 읽도록 전달하는 이벤트 스트리밍 플랫폼이다. 로그 흐름에서는 중간 물류창고에 비유할 수 있다. Graylog는 받은 로그를 검색·분석하고 탐지 규칙을 실행하는 역할이다.

```text
현재 계획: 포털·보안 장비 → Graylog → 탐지 이벤트 → n8n → 대응·티켓
Kafka를 쓰는 구성 예: 로그 발신자 → Kafka → 수집 연동 → Graylog → 탐지·대응
```

두 번째 줄은 설명용 예시다. Kafka 연결에는 발신·수신 연동과 운영 설정이 필요하다. Kafka에는 보존 기간·용량 안에서 기록을 다시 읽거나 여러 소비자가 독립적으로 읽는 기능이 있다. 저장·복제·확인 설정에 따라 내구성이 달라지며, 추가만으로 로그 무손실이나 가용성이 보장되지는 않는다.

예를 들어 초당 1,000건이 들어오고 300건만 처리하면, 10초 동안 적체가 7,000건 늘어난다. 입력이 초당 100건으로 줄고 처리는 300건을 유지하면, 이 적체를 비우는 데 이론상 35초가 더 필요하다. 실제로는 자원·색인·재시도로 달라진다. 이 예시는 계산 설명이며 실측값이 아니다.

우리 기획서의 구성은 Graylog + OpenSearch + MongoDB이며 별도 Kafka 브로커는 없다. Graylog 자체 저널은 처리 대기 메시지를 저장하지만, 발신자부터의 전달 보장과는 구분한다. 현재 포털의 GELF UDP 전송에는 수신 확인이나 자동 재전송이 없다. 로컬 JSONL도 자동 재전송 큐가 아니며 디스크 쓰기 실패가 가능하다.

## 3. 시험 전 준비와 보강 후보

- [ ] 공격·서비스 PC와 관제 PC의 CPU/RAM, VM·WSL 상한, 컨테이너 메모리·JVM 힙, 저장 볼륨·여유 용량을 기록한다. 호스트·WSL·컨테이너 수치를 구분한다.
- [ ] 관리 화면은 계획대로 관제 PC 내부에 두고, 로그 수집 포트는 실제 발신 장비·필요 포트 중심으로 허용한다. 대역 전체 허용을 좁힐 때 pfSense·Suricata·Wazuh의 실제 발신 주소를 먼저 확인한다.
- [ ] Graylog 저널, 검색 인덱스, 포털 JSONL, Docker 로그 각각의 용량·보존·회전 설정을 기록한다. 포털 JSONL 회전·전달 재시도는 실제 구현 여부를 확인하고, 없으면 후속 작업으로 남긴다.
- [ ] Graylog 밖의 관측 PC/호스트에서 포털 업무 요청, 컨테이너 생존·재시작 횟수, 마지막 시험 로그 확인 시각을 기록한다. Graylog 검색 실패도 별도 관측 장애로 남긴다.
- [ ] 발신 장비·관제 PC·VM·WSL 시계를 맞추고 오차를 기록한다. 기획서 초안의 허용 오차 1초를 넘으면 시각 차 기반 지표는 무효로 표시한다.
- [ ] 시험 출발지와 정상 시민 출발지를 분리하고, 시험 중단·차단 해제 경로를 확인한다. 관리망을 부하 발신자로 사용하지 않는다.
- [ ] DB·로그 볼륨 백업/보존, 중단 기준, 시험 경로·요청량·지속시간·최대 동시성을 실행 기록에 먼저 채운다. 응답 지연 시 동시 요청을 무제한 누적하지 않는다.

입력 제한은 방화벽·발신자·수집 입구에서 먼저 검토한다. Graylog 처리 규칙에서 버리는 것만으로 네트워크·수신·저널 과부하까지 막힌다고 판단하지 않는다. 제한·샘플링을 적용하면 제외 건수와 보안 신호 누락을 별도로 기록한다. 탐지 임계값은 처리량 개선을 위해 임의로 완화하지 않는다.

## 4. 측정 지표와 출처

| 지표 | 측정·계산 | 출처·주의 |
| --- | --- | --- |
| 요청량 RPS | 실제 완료/시작 요청 수와 시험 시간, 동시성, 응답 코드별 건수 | 부하 실행기. HTTP 요청 수와 이벤트 수를 같다고 보지 않는다 |
| 발신·수신 EPS | 초당 발신 이벤트 수, Graylog 입력·처리·색인 수 | 발신 요약과 Graylog 지표를 구분. UDP send 성공은 수신 성공이 아님 |
| 검색 가능 지연 | 이벤트 원본 시각 → 해당 ID가 최초 검색된 시각의 p50/p95/최댓값 | 검색 간격 5초와 시계 오차를 함께 보고. 정확한 내부 수신 시각으로 부르지 않는다 |

| 적체 | 저널 사용량·미처리 건수, 입력/색인 처리량 차이 | 5초 간격 표본. 저널 바이트와 이벤트 건수를 섞지 않는다 |
| 자원·장애 | RAM/CPU, 디스크 여유·쓰기 지연, OOM·재시작 횟수, 검색 저장소 상태 | Graylog 밖의 호스트 기록 포함. 화면 정상만으로 통과시키지 않는다 |
| 정상 시민 업무 | 성공률, p95 응답시간, 타임아웃, 신청→답변→조회 결과 | 시민 경로와 관리망 health를 따로 측정. 합성 계정·민원만 사용 |

| 서비스 복구 시간 | 추가 부하 종료 → 정상 출발지 연속 K=3회가 사전 기준선 안인 시각 | 기존 기획서 5.4·5.9와 연결. 관제 복구, 대응 MTTR과 별도 보고 |

포털 JSONL의 `event_id`와 Graylog에 보존된 ID 필드를 시험 전에 실제 한 건으로 대조한다. GELF `_event_id`가 수신 후 어떤 필드로 저장되는지 확인한다. `web.request`와 로그인·404 등은 한 요청에서 함께 생길 수 있다. health 요청도 로그를 발생시키므로 관측용 요청을 발신 집계에 포함하거나 명시적으로 분리한다.

시험 시간·발신 장비·계정·원본 이벤트 ID 목록으로 집합을 고정한다. 스키마에 임의의 `run_id`를 추가하지 않는다. 수신 집합은 실험 종료 뒤에도 회복 관측을 이어가며 수집한다. **종료 후 5분**을 초기 관측 기한 후보로 두고 시험 전에 확정한다. 기한 내 미도착과 이후 도착한 지연 로그를 구분하며, 기한 내 누락을 영구 유실로 단정하지 않는다.

## 5. 시험 순서와 판정

아래 시간·배수·중단값은 초기 실습 제안이다. 실제 장비 기준선을 얻은 뒤 실행 전에 확정해 기록한다. 기획서의 N=5, 정상 업무 T=30분, 회복 K=3 및 최종 기준값을 대신하지 않는다.

1. **수집 경로 소량 확인:** 정상 민원 업무를 한 번 끝내고 발신 ID가 검색되는지 대조한다. 실제 수신 확인 전에는 증속하지 않는다.
2. **정상 기준선:** 합의한 요청 종류·비율·동시성으로 30분 실행한다. RPS·EPS·p95·지연·자원·적체의 정상 범위와 회복 제한 시간을 사전 기록한다.
3. **단계 부하:** 정상 시민 요청은 유지하며 별도 시험 출발지의 요청을 정상 기준 대비 1배→2배→4배까지 단계적으로 증가시킨다. 각 단계 2분, 사전 최대 요청량·동시성 이내. 중단 기준에 닿으면 다음 단계로 가지 않는다. 제한·차단으로 입력량이 줄었다면 실제 포털 도달량과 함께 보고한다.
4. **회복 관측:** 추가 부하만 멈추고 정상 시민 요청과 외부 관측을 유지한다. 관제/서비스 회복 시각, 미도착·늦은 로그, 수동 개입을 따로 기록한다.
5. **수집기 일시 중단·재연결:** 별도 회차에서 Graylog 수집기를 30초 중지하고 재시작한다. UDP 전송 중의 누락, 로컬 JSONL 보존, 복구 후 새 로그 수신, 포털 정상 업무를 확인한다. 인덱스·볼륨은 삭제하지 않는다. JSONL 자동 재전송이 없으므로 중단 중 로그가 자동 복원된다고 기대하지 않는다.
6. **반복·보강 비교:** 먼저 한 회를 사전 시험하고, 유효한 동일 조건 시험을 N=5회 반복한다. 설정 변경은 한 번에 소수 항목만 적용하고 전후 동일 부하로 비교한다. 집계 창·차단·티켓 중복 억제의 이전 실행 영향을 제거한다.

**중단 기준 후보:** 디스크 여유 20% 미만, 저널 사용률 80% 이상, OOM/예상치 못한 재시작, 정상 시민 요청 3회 연속 실패 중 하나면 추가 부하를 중단한다. 호스트 RAM 사용률 90% 이상이 30초 유지되는 경우도 중단한다. 더 엄격한 장비별 기준이 있으면 그것을 적용한다. 중단 직전 수치·시각을 보존하고 무조건 재실행하지 않는다.

**통과·한계 보고:** 수치 기준은 시험 시작 전에 확정한다. 정상 시민 성공률·p95 상한, 검색 지연 p95 상한, 회복 제한 시간, 허용 누락률을 비워 두면 종합 통과 판정을 내리지 않는다. 정상 구간의 누락은 원인을 조사하며, 중단 시험에서 관측된 UDP 누락은 실제 한계·보강 필요로 남긴다. 자동 재시작 성공만으로 로그 회복을 통과시키지 않는다.

측정한 단계 중 모든 사전 기준을 만족한 최고 실제 EPS/RPS와 최초 기준 초과 단계를 함께 보고한다. 2분 단계 시험은 단기 부하 결과다. 지속 처리량으로 보고할 값은 해당 부하에서 별도로 30분 유지 시험을 하고, 유효한 반복별 값과 최저값을 남긴다. 중단 기준까지 도달하지 않았으면 최대 한계는 미확인이다.

## 6. 복구 순서와 결과 양식

추가 부하 중단 → 호스트·디스크·검색 저장소 원인 확인 → 중단했던 수집기 복구 → 입력·색인·새 로그 검색 확인 → 적체·지연 회복 확인 → 정상 시민 업무 확인 → 시험용 차단·계정 상태 원복 순서로 진행한다. Graylog가 내려간 동안 대응이 지연·누락될 수 있으므로 n8n 실행·티켓·대응 상태도 확인한다. 원인을 해결하지 않은 반복 재시작과 미처리 저널 삭제는 복구 결과로 인정하지 않는다.

## 7. 근거·남은 결정

- [Apache Kafka 소개](https://kafka.apache.org/intro/): 이벤트 발행·구독, 보존·재조회, 생산자와 소비자의 분리.
- [Graylog 시스템 알림](https://go2docs.graylog.org/current/making_sense_of_your_log_data/system_notifications.htm): 저널 포화·미처리 메시지 삭제·검색 저장소 디스크 문제. 링크는 현재 버전 문서이므로 설치 버전에서 실제 지표·동작을 재확인한다.
- 기획서 검토 원본: 로컬 `aleph-proposal-cleanup`의 `docs/proposal-submission-cleanup` 브랜치 `team_docs/기획서_합의본.md` 5.4·5.9. 아직 이 문서의 측정 기준이나 기획서 원본을 변경·승인하지 않았다.
- 남은 결정: 실제 배포·수집 연동, 실측 담당/독립 재현자, 정상 요청 프로필과 수치 기준, 시험 범위, JSONL 회전·내구성 있는 전달의 구현 필요성. Kafka 추가 여부는 측정 뒤 병목·재전송·다중 소비자 요구와 자원 비용을 근거로 판단한다.
