# 티켓 12종 구상 · 4인 분담·단계적 구현·다른 팀과의 차별화

기준일: 2026-10-16 · 상태: 사용자 방향 반영, 팀 합의·Claude 검토용 초안. 미구현·미시험

## 1. 최신 방향과 출처

강사 말씀으로 사용자가 전달한 것은 ‘티켓을 4가지 이상 구상할 것. 이유는 팀원 4명이 각자 맡을 수 있게’다. 이는 하한과 분담 취지이며 4종 상한이나 특정 시나리오 지정은 아니다.

사용자는 **‘10종 이상을 구상하고, 4명이 나눠 맡되, 공통 기반부터 단계적으로 구현하자. 그러고 나면 Claude에게 검토받자’**고 지시했다. 이에 S1~S10과 추가 2종, 총 12종을 구상한다. [직전 4종 구성안](28-four-ticket-scope-plan.md)은 논의 이력이며 이 문서가 후속 계획이다. 대표 하나는 첫 통합 확인 순서다.

설계 대상은 12종이며 단계별 구현을 계획한다. ‘구상·실제 연동·증거를 갖춘 통과’를 별도로 표시한다. 일정·자원상 변경이 필요하면 영향과 이유를 기록하고 팀/평가 조건을 확인한다. 조용히 4종만 남기거나 12종 성공을 미리 선언하지 않는다. 실제 기간·장비·실명 담당·서비스의 팀 최종 채택은 미정이다. 기존 사용자 준비 방향은 외주 유지보수 포털이며 MockTel은 팀원 제안으로 구분한다.

## 2. 다른 팀 정보와 차별화

사용자가 이번 대화에서 전달한 정보이며 다른 팀 문서·코드·시연을 직접 확인하지 않았다. 각 항목이 서로 별개의 팀인지도 추가 확인 전 단정하지 않는다.

| 전달된 정보 | 확실성·한계 | 우리 계획에 반영할 판단 |
| --- | --- | --- |
| Kubernetes로 전체를 보는 대시보드 같은 주제 | 사용자가 정확히는 모르겠다고 설명. 대상·기능·복구/대응 범위 미확인 | 기능을 추측해 경쟁 비교하거나 같은 도구를 따라 추가하지 않음 |
| 통신 주제 1팀 | 배경만 전달됨. 서비스·사고·제품·구현 상태 미확인 | ‘통신 주제’만으로 고유하다고 주장하지 않음 |
| 은행 주제 1팀 | 배경만 전달됨. 상세 기능 미확인 | 통신/은행 배경 선택 투표를 다시 시작하지 않음 |

우리의 설명 가능한 차별화 목표는 **사고 유형별 기본/보강 탐지 비교 + 실제 경계 통제 + 승인 후 조치 효과 + 정상 사용자 업무 유지·복귀의 증거**다. 대시보드는 이 증거를 읽는 화면이다. 다른 팀이 이 기능을 하지 않는다고 주장하거나 우리만 구현 가능하다고 말하지 않는다. 12종이라는 개수도 단독 차별점이 아니다.

## 4. 4인 소유권과 공통 기반

A~D는 실명 배정 전 자리다. 주담당은 자신의 사고 입력·기본/보강 비교·분석·티켓·승인·조치·실제 효과·원복·증거까지 책임진다. 공통 기반은 한 번 만들고 12종이 공유한다.

| 공통 영역 | 주관리 제안·연결 | 파일·검증 경계 |
| --- | --- | --- |
| 정상 업무·인증·세션 | A, C는 권한/객체 요구 제공 | `src/aleph_soar/portal/`·계약 후보. 정상 A/B·인가·잠금·기존 세션 검증 |
| 망·WAF·제한/해제 | B, 각 담당이 필요한 경로 요청 | [허용표](26-network-allow-table-s1-s10.md). 배치 파일 위치는 P01에서 지정, 실제 경유·state·프록시 확인 |
| 데이터·권한·직접 감사 | C, A와 객체/API 연결 | 앱 로그와 DB 감사·실제 조회를 구분. 원문 민감값 제외 |
| 관측·FIM·통합 표시/측정 | D, 각 주담당이 자기 규칙·입력·증거 작성 | 수집 설정 위치 미정. `detection/`·`response/`·템플릿의 개별 파일 담당을 따로 지정 |
| 공통 사건 엔진·계약 | 조율 담당 1명 지정, A~D 기여 | `docs/API-CONTRACT.md`, `contracts/`, 소비자·검증·DAG의 별도 정합화 작업 |

A4/B3/C2/D3이라는 개수는 작업량 균등을 뜻하지 않는다. D의 S7/S10/가용성과 공통 관측 부담이 크므로 공통 엔진 전체를 D에게 맡기지 않는다. 각 유형 규칙/입력/증거는 해당 주담당이 쓰고 공통 모듈은 단일 파일 소유자·편집 순서로 작은 작업을 배분한다. 실명·가용 시간에 따라 공통 업무와 유형을 함께 재배분한다. 자기 티켓은 다른 담당이 교차 검증한다.

현재 앱은 스켈레톤이고 계약은 인증 중심이다. 경계·FIM·송신·가용성 입력까지 이미 지원한다고 가정하지 않는다. 기존 DAG 6개 작업과 기술 역할은 개인 티켓 책임과 별개이며 준비 후보는 P01이다. 이 계획만으로 P01 완료·계약/역할/DAG 변경을 선언하지 않는다.

## 6. 실험과 범위의 중요한 조건

- 기본/보강 탐지 설정과 취약/수정 앱 정책은 다른 축이다. 입력·seed·버전·센서·정책을 보존하고 바꾼 조건을 구분한다. 예방 때문에 미도달한 행위를 탐지 규칙 실패로 오판하지 않는다.
- 입력 0회·원본 미수신·탐지 미충족·오탐·중복·조치 실패·효과 미관측·복구 실패를 구분한다. 탐지 시간은 유형 조건 성립→첫 유효 경보, 입력 시작→조건 성립은 별도 기록한다. 목표는 기준선 후 합의한다.
- S7은 운영자가 정한 경로의 무해한 고정 파일과 후속 접근을 연결하는 모사다. 실제 웹셸/임의 업로드 취약점을 추가하지 않으며 전체 침투를 입증하지 않는다. 경로가 없으면 설계 대기와 영향으로 표시한다.
- S6의 관리자 경로·S9의 권한/객체·DB 감사·S10의 실제 계층 식별이 선행이다. 모든 계층에 공격 요청이 도달해야 한다고 가정하지 않는다. 프록시 연결 IP와 신뢰 헤더는 별개 증거다.
- PLAN-11은 인터넷 대신 격리된 사설 수신기를 사용하고 송신/수신/거부를 대조한다. PLAN-12는 부하 상한·중단 조건·정상 출발지를 분리하고, 공격 429와 정상 업무 실패의 분모를 나눈다. 고정 VU는 고정 RPS가 아니다. 서버 장애는 추가하면 독립 실행으로 측정한다.
- 16GB 한 PC에 15GB VM 전부 동시 배치를 기본값으로 삼지 않는다. 단계에 필요한 대상 운용·기존 Docker 재사용·장비 분산은 자원/격리 측정 후 결정한다. 최소 구성도 미측정 상태에서 보장하지 않는다.
- 단일 호스트·LB·DB·관제의 SPOF를 남긴다. Kubernetes·자동 대응·물리 HA는 12종의 전제가 아니다. 수동 승인·조치도 증거와 실제 효과를 검증한다. 복원 전 증거는 스냅샷 밖에 보존한다.

## 7. 공유 문구와 검토 요청

> 강사님 말씀의 4종은 최소 기준으로 이해하고, S1~S10과 추가 후보를 포함해 12종을 구상해 보면 좋겠습니다. 4명이 관련 유형을 나눠 맡고 서비스·네트워크·로그·티켓 기반은 공통으로 만들자는 방향입니다. 먼저 한 종류로 전체 연결을 확인하고, 각자 한 종류씩 완주한 다음 나머지 유형과 연계를 확대하면 좋겠습니다. 유형마다 탐지 비교와 대응·복구 증거를 남기고, 구상한 것과 실제 검증한 것은 구분하겠습니다. 다른 팀과 배경이 겹쳐도 실제 통제·정상 업무 유지·복귀를 증명하는 방식으로 우리 결과를 설명하면 좋겠습니다.

이 메시지는 미발송 초안이다. 다음 작업은 Claude에 유형 중복·4인 부담·선행 조건·측정·타 팀 정보의 불확실성을 독립 검토받는 것이다. 문서 준비만 수행했으며 앱·계약·DAG·망·실제 제품은 변경하지 않았다.
