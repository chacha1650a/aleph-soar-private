# 강사 조언 반영 · 4인 담당 티켓 4종 구성안

기준일: 2026-10-16 · 상태: 사용자 전달 조언 기록·팀 합의용 제안, 미구현·미시험

**후속 사용자 지시:** 4종은 상한이 아니며 ‘10종 이상 구상·4인 분담·공통 기반부터 단계적 구현’으로 진행한다. 최신 계획은 [12종 구성안](29-twelve-ticket-phased-plan.md)이다. 아래의 4종 구성은 이전 제안 이력으로 보존하며 최종 범위를 4종으로 제한하지 않는다.

## 1. 확인된 조언과 해석

사용자가 전달한 강사 말씀:

> 티켓을 4가지 이상으로 구상해 볼것 이유 : 팀원4명이 각자 맡아서 할 수 있게.

확인된 내용은 **4가지 이상 구상**과 **4명 각각의 담당 확보**다. 모든 S1~S10 구현, 특정 네 유형, 담당 이름, 제품 배치까지 강사님이 지정한 것은 아니다. 이 문서에서는 ‘4가지’를 서로 다른 사고 유형의 티켓으로 해석해 제안하며, 실제 제출 범위·채점 기준은 별도 확인한다.

첨부 이미지에는 S1~S10 사례와 ‘문서 153~162’가 보인다. 저장소 [기존 정의](03-scenarios.md)는 ‘자료 167·168’로 출처를 적고 있으므로 쪽 번호 체계를 임의로 같다고 보지 않는다. 유형·신호의 대응을 참고하며 카드의 임계값·대응 번호는 우리 환경에서 검증된 설정이 아니다.

**이전 ‘대표 흐름 하나 먼저 완주’는 최종 범위를 한 종류로 제한하는 추천에서, 첫 통합 확인 순서로 수정한다.** 최종 구상은 최소 4종으로 하고, 공통 경로를 첫 종류로 확인한 뒤 나머지를 연결한다. 팀원 원안의 INC-01~06, 참고 S1~S10, 아래 T01~T04는 서로 다른 번호 체계다.

## 2. 추천 티켓 4종

T 번호는 이 문서의 논의용 표기이며 계약·등록부에 예약하거나 기존 ID를 변경하지 않았다. 이름별 배정은 팀에서 정한다.

| 논의 ID·주담당 | 사고 유형·참고 사례 | 필요한 근거 | 승인 후 대응 후보 | 효과·복구 확인 |
| --- | --- | --- | --- | --- |
| T01 · 팀원 A | 반복 로그인 실패 후 성공, 계정 악용 의심 · S1/S4 | 앱 인증 결과·계정·시각·세션, 실패→성공 순서 | 계정 잠금·기존 세션 무효화 | 신규 로그인·기존 세션 거부, 자격 재설정 후 허용 업무 복귀, 정상 B 유지 |
| T02 · 팀원 B | 웹 탐색 후 인증 공격 · S8 | WAF/웹 탐색 신호 + 앱 인증 실패, 신뢰된 출발지·대상·시간 순서 | 특정 시험 출발지 제한 | 해당 출발지 재시도 거부·경계 로그, 다른 출발지 정상, 제한 해제 후 복귀 |
| T03 · 팀원 C | 비인가 권한 변경과 보호 자료 접근 · S9 | 권한 변경 전후·행위자·대상 계정·객체·인가 결과, 가능하면 DB 직접 감사 | 승인된 권한으로 회수·영향 세션 회수 | 금지 객체 거부·허용 객체 성공, 이전 권한/세션이 재사용되지 않음 |

각 담당은 해당 티켓의 사고 입력·기본/보강 탐지 비교·분석·티켓·대응·원복·증거까지 책임진다. 한 사람은 모든 탐지, 다른 사람은 문서만 맡는 식으로 개인 티켓을 없애지 않는다. 공통 인프라 구현은 한 번만 하고 각 티켓이 이를 사용한다.

## 3. 각 유형의 범위와 선행 조건

- **T01:** S1과 S4는 한 계정 사건의 신호로 묶을 수 있다. 각각을 별도 티켓 2종으로 세지 않는 안이다. 서로 다른 결과 개수만으로 시간 순서를 판정하지 않는다.
- **T02:** 랩에 한정된 요청 수·기간을 정한다. 공유 NAT의 IP는 사용자 신원이 아니므로 차단 범위·정상 사용자 피해를 확인한다. T01과 같은 실행에서 두 조건이 발생하면 공통 사건 아래 탐지 근거로 연결하고 같은 피해를 중복 집계하지 않는다. 유형별 검증은 별도 실행 ID로도 수행한다.
- **T03:** 합성 역할·합성 자료로만 시험한다. 거부된 권한 변경 시도와 실제 권한 변경 성공을 구분한다. 앱이 DB 조회 전에 거부하면 DB 감사가 없는 것이 정상일 수 있다. DB 직접 감사가 확보되지 않으면 앱 로그를 DB 감사로 표시하지 않는다.
- **T04:** 기존 서비스에는 임의 업로드 기능이 없다. 실제 웹셸·업로드 취약점을 새로 구현하는 대신 운영자가 정해진 시험 디렉터리에 무해한 고정 파일을 두고 접근을 대조하는 후보로 제한한다. 이는 실제 웹셸 공격 전체나 업로드 침투를 입증하지 않으며, 일반적인 계정 공격의 필수 후속 단계도 아니다. 정상 배포·승인된 파일 변경을 대조군으로 둔다. 시험 경로·접근 방식은 구현 전 설계한다.

T04의 FIM→웹 경로 연결이 기간·자원·평가 목표에 맞지 않으면 **S5 차단 후 재시도**를 네 번째 유형의 대안으로 검토한다. 이 경우 차단 목록이 적용된 사전 상태에서 독립 실행하고 반복 경계 거부를 티켓으로 묶는다. 4종 수를 맞추기 위해 파일 경보와 무관한 웹 접근을 억지로 상관하지 않는다. HIDS 필수 여부는 평가 조건에 맞춰 별도 확인한다.

## 4. 공통 기반과 수정 경계

공통 서비스 하나·사용자/보호 자산·망·시간 동기화·이벤트 연결 기준·티켓 양식을 먼저 맞춘다. 4종 때문에 포털 4개나 관제 시스템 4세트를 만들 필요는 없다. 서비스는 기존 외주 포털 준비 방향과 팀원 MockTel 중 팀 합의가 필요하며, 네트워크는 [허용표 초안](26-network-allow-table-s1-s10.md)에서 선택한 유형에 필요한 규칙을 고른다.

| 공통 자산 | 소유권·연결 원칙 |
| --- | --- |
| 앱 인증·역할·객체·세션·시험 경로 | 공통 앱 담당 1명을 정하고 T01/T03/T04가 필요한 입력·관측·조치를 요청. 같은 파일 동시 수정은 순서 조정 |
| pfSense/WAF·배치·수집기 설정 | 공통 망 담당 1명을 정하고 T02의 차단·T04 수집 경로와 연결. 담당 티켓과 공통 업무의 부담을 함께 산정 |
| 이벤트·사건·대응 API 계약 | 조율 담당이 변경을 모아 스키마·예시·소비자와 함께 검토. 티켓마다 제각각 API를 만들지 않음 |
| 티켓별 규칙·입력·정상 대조·증거 | 각 티켓 주담당 소유. 별도 파일 경계는 P01에서 확정 |
| 독립 검증 | 다른 팀원이 교차 재현. 본인 담당만 검증하고 끝내지 않음 |

현재 `tools/team.py ready`의 준비 작업은 P01이며 기존 DAG는 6개 작업이다. 기존 역할은 기술 모듈 소유권이고 새 티켓은 사고 유형 책임이므로 서로 바꾸어 세지 않는다. 이 문서만으로 P01을 완료하거나 DAG·역할·계약을 수정하지 않는다.

## 5. 구현 순서와 완료 증거

1. **범위 합의:** 서비스·보호 자산·티켓 4종·주담당·공통 자산 소유자·장비·실제 기간·평가 요건을 기록한다.
2. **공통 경로 시험:** 정상 A/B 업무, 선택한 경계의 허용/거부, 원본→중앙 수신·시간·식별자를 확인한다. 관측 누락은 차단 성공이나 탐지 실패와 구분한다.
3. **첫 통합:** T01 등 가장 준비된 한 종류로 입력→탐지→티켓→승인→조치→효과→복구를 연결한다. 다른 세 담당도 이때 자기 시험 입력·조건을 준비할 수 있다.
4. **나머지 연결:** 유형별 규칙·근거·대응·원복을 공통 경로에 연결하고 정상 대조·보강 전후 비교를 수행한다. 공통 설정 변경 시 기존 유형의 영향도 확인한다.
5. **4종 교차 재현:** 티켓별 실행 ID, 원본/중앙/경보 연결, 분석·승인 시각, 실제 조치와 효과, 정상 사용자 영향, 복구·미검증 항목을 보존한다. 유형별 탐지·복구 시간을 같은 정의로 측정한다.

최종 시연은 독립 티켓 4종을 순서대로 보여주거나, 별도 재현 증거와 일부 통합 시연을 결합하는 안 중 평가 기준에 맞춰 합의한다. 서로 다른 유형이 항상 한 공격의 연속 단계인 것처럼 설명하지 않는다. 자동화·Kubernetes는 4종이라는 이유만으로 추가하지 않는다.

## 6. 팀 공유 초안

> 강사님이 팀원 4명이 각각 맡을 수 있도록 티켓을 4가지 이상 구상하라고 조언해 주셨습니다. 그래서 최종 범위를 한 가지로 줄이기보다는, 공통 서비스와 네트워크 안에서 사고 유형 4종을 나눠 맡는 방향으로 조정하면 좋겠습니다. 예시는 계정 악용, 웹 탐색 후 인증 공격, 권한 변경·자료 접근, 무해한 파일 변경·웹 접근 탐지입니다. 각자 자기 유형의 탐지 비교부터 분석·티켓·대응·복구 검증까지 맡고, 우선 한 종류로 공통 연결을 확인한 뒤 나머지를 붙이면 좋겠습니다. 유형과 실제 담당자는 서비스·장비·기간을 보고 함께 정했으면 합니다.

실제 팀 채팅에 전송하지 않은 초안이다. 작성한 것은 이 구성안과 관련 대화 요약뿐이며 앱·규칙·계약·DAG·망 설정은 바꾸지 않았다. 티켓 성공 결과는 아직 없다.
