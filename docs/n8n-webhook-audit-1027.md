# Webhook 인증 정적 점검 · 2026-10-27 집 작업

## 작업 경계

사람 자리 B·Codex가 검사기/회귀/이 문서를 담당한다. 기술 역할은 coordinator/detection이며 운영 n8n의 소유자 D와 구분한다. 기준 head는 ac6792e다. 수정 대상은 새 읽기 전용 검사기와 테스트, n8n 안내/학원 S1 인수 문서·개인 일지다. 워크플로 원본·생성 JSON·자격 증명·수신/발신 설정·CI 판정은 바꾸지 않는다. PROGRESS는 A 담당을 유지한다.

완료 조건: 현재 10개 수신 노드의 인증 누락을 놓치지 않고, 비활성/disabled·출발지 허용 목록·송신 인증을 수신 인증으로 오인하지 않는다. 잘못된/비어 있는 내보내기는 성공으로 처리하지 않는다. 선택한 인증 방식과 자격 증명 참조가 있어도 실제 인증 검증 완료로 처리하지 않는다. 출력에는 원문·헤더·주소·경로·자격 증명 이름/ID/값을 넣지 않는다.

## 검사와 인수

검사기 [tools/check_n8n_webhooks.py](../tools/check_n8n_webhooks.py)는 로컬 폴더 바로 아래 JSON만 읽는다. 네트워크 호출·자격 증명 조회·워크플로 실행·파일 변경 기능이 없다.

```powershell
# 저장소 후보 검사: 현재 결과는 누락10건이므로 종료1이 예상된다.
python tools/check_n8n_webhooks.py --expected-webhooks 10
# D의 필요한 워크플로만 내보낸 로컬 사본: 경로는 각 PC에서 정한다.
python tools/check_n8n_webhooks.py --folder <저장소_밖_워크플로_JSON_폴더> --expected-webhooks <예상_수신_노드_수>
```

자격 증명 자체/복호화 내보내기를 검사 입력으로 만들지 않는다. 운영 내보내기에는 고정 데이터·민감 본문이 포함될 수 있으므로 저장소 밖 PC 로컬에서만 읽고 커밋/업로드하지 않는다. 이 도구는 비밀값 스캐너가 아니다. 보고서는 파일 정렬 순번·입력 SHA256·워크플로/노드의 1부터 시작하는 순번과 허용된 상태 코드만 출력한다. 파일명·워크플로 이름/ID·URL/path·헤더·자격 증명 ID/이름/값·파싱 오류 원문은 출력하지 않는다. 원본과 보고서는 로컬에서 `Get-FileHash <파일> -Algorithm SHA256` 및 해당 순번으로 맞춘다.

| 종료 | 의미 | 다음 행동 |
| --- | --- | --- |
| 0 | 지원 방식의 인증 선언과 해당 자격 증명 ID 참조가 있음 | 실제 자격 증명 존재·권한·거부/허용 동작은 미검증. 게시 허가로 쓰지 않음 |
| 1 | 미설정/none·미검토 인증 방식·자격 증명 참조 미해결 | 해당 수신 경로의 운영 채택 전 D가 수정/검토 |
| 2 | 읽기/JSON/구조 오류, 입력 없음·수신 노드 없음·예상 개수 불일치 | 누락된 범위부터 확인. 0건/준비됨으로 해석하지 않음 |

비활성/disabled, IP 허용 목록, VPN 접근 제한, n8n 편집기 로그인, 송신 HTTP 노드의 인증은 수신 Webhook 인증 선언을 대체하지 않는다. 인증 방식은 basicAuth/httpBasicAuth, headerAuth/httpHeaderAuth, jwtAuth/jwtAuth의 대응을 검사한다. 동적 표현식·이 검사기가 지원하지 않는 새 방식은 검토 대상으로 남긴다. 이름만 남고 ID가 해결되지 않은 자격 증명도 미해결이다. 참조 ID를 확인해도 비밀값/강도·실제 존재·만료·권한은 검사하지 않는다.

## D가 학원에서 할 첫 작업

1. 최종 통합 head/가져온 JSON 해시와 실제 n8n 버전·게시 버전을 기록한다. 저장소 compose의 이미지 핀은2.39.5지만 실행 중 버전은 확인 필요다. 실제 수신 경로가 Test/Production 중 무엇인지, 현재 인증이 노드/앞단 어느 경계에서 이루어지는지 확인한다. 운영본에 이미 별도 인증이 있다면 그 근거와 우회 경로 여부부터 대조한다.
2. 우선 S1 복제 시험 워크플로와 별도 시험 저장소를 준비한다. 모든 장비/메시지 발송·상태 변경 분기를 끊거나 호출 불가한 시험 대상으로 바꾼다. 단순 dry_run 하나만으로 모든 하위 흐름이 안전하다고 가정하지 않는다. 운영 자동 대응/해제는 켜지 않는다.
3. 권고 후보는 Webhook의 Header Auth와 n8n 로컬 자격 증명이다. D가 Graylog 알림 송신 화면에서 사용자 정의 헤더 지원과 실제 보낼 이름을 먼저 확인한다. 지원하지 않으면 검토된 인증 가능한 전달 경로나 다른 지원 방식을 함께 정한다. 발신을 맞추지 않은 채 수신 설정만 바꾸면 알림이 끊기므로 한 연결로 확인한다. 헤더 이름·기존 키를 추정하지 않는다.
4. 수신용 비밀값은 포털 조치 API 키·C X-Response-Key·Discord 자격 증명과 구분한다. 효과 보고/원복 운영자용 권한과 Graylog 탐지 발신 권한도 나눈다. 값은 n8n/발신자 로컬 비밀 저장소에 두고 JSON·URL query·프롬프트·일지에 쓰지 않는다. 새 키 발급/기존 키 교체는 실제 담당이 노출 여부·발신자 목록·전환 순서·되돌릴 경로를 확인한 뒤 한다. 이번에는 값을 읽거나 교체하지 않았다.
5. 격리된 수신 경로에서 **헤더 없음·잘못된 값은 인증 경계에서 거부되고 하위 조치/티켓 쓰기0**, 올바른 값은 합성 이벤트1개가 기대한 수신/정규화 노드에만 도착하는지 확인한다. Test URL과 Production URL을 구분한다. HTTP 상태·비식별 실행 ID·시각·하위 실행 여부를 각각 남긴다. 앞단/노드 버전에 따라 거부 응답의 세부 모양은 직접 확인한다. 임의 POST를 운영 케이스에 보내 시험하지 않는다.
6. n8n 실행 데이터/디버그 화면·발신 로그·프록시 로그가 인증 헤더 값을 저장/반사하지 않는지 확인한다. 특히 사용자 정의 헤더 자동 마스킹은 가정하지 않는다. 원문 캡처를 외부/저장소로 내보내지 않고 필요한 최소 필드만 비식별화한다. 노출이 확인되면 시험을 중단하고 해당 비밀값 교체를 담당과 진행한다.
7. 수신/발신 설정과 원본 생성기를 같은 정책으로 맞춘 뒤 재생성·정적 검사·실제 격리 거부/허용 검증을 반복한다. 첫 S1 외의 효과/해제 수신부는 각 권한 경계가 확인되기 전 게시하지 않는다. 실해제 live_release_enabled:false는 유지한다.

D는 준비 회신1회에 버전·수신/발신 방식·인증 결과·하위 호출0 근거·남은 조건을 담고 A/B/C와 연결을 직접 대조한다. 이 문서는 메시지 발송이나 학교 설정 적용을 실행하지 않는다.

## 공식 근거와 한계

n8n 공식 [Webhook 문서](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/)는 Test/Production URL과 Basic/Header/JWT 인증을 설명하고, [Webhook 자격 증명 문서](https://docs.n8n.io/integrations/builtin/credentials/webhook/)는 Header Auth에 헤더 이름/값을 사용한다고 설명한다. [공식 노드 선언](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/nodes/Webhook/description.ts)의 방식/자격 증명 타입 대응도 확인했다(10/27 열람). 최신 문서/master는 학원2.39.5의 실제 설정·동작을 확인한 증거가 아니다. 버전 변경·의존성/전역 설정 변경은 하지 않았다.
