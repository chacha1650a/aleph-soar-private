# 주제 심화 후보와 Codex 추천 · Claude 검토용

상태: Codex 제안 · Claude 검토 대기 · 팀 합의 전 · 2026-10-15

## 배경과 판단 기준

사용자는 다섯 팀의 주제가 비슷해질 수 있는 상황에서 더 깊이 있는 주제를 논의하고 싶어 합니다. **다른 네 팀의 주제와 기술은 모른다고 확인했습니다.** 아래 안이 다른 팀보다 독창적이라고 단정하지 않습니다. 우리 팀이 해결할 구체적인 문제와 실행 증거를 먼저 정하고, 다른 팀 정보가 생기면 겹치는 부분을 다시 검토합니다.

확인된 조건은 4인·2주, 계정 이상·자동 대응 / 침해 흐름 관제 / 권한·데이터 접근 추적에 대한 관심입니다. 4계층 필수 여부와 특정 제품·제출일·평가 기준은 미확인입니다. 여기서는 앞선 논의처럼 **4계층이 필수라는 가정**으로 비교합니다.

이 문서는 [팀원 A+B+G 제안 원문](11-team-feedback.md), [4계층 검토](12-four-layer-topic-review.md), [PR #2의 Claude 코멘트](https://github.com/NoBugs-Aleph/aleph-soar-capstone/pull/2#issuecomment-6187601400)를 바탕으로 한 추가 의견입니다. 기존 의견이나 팀 결정을 대체하지 않습니다.

비교 기준은 사용자 문제의 구체성, 어려운 상황 하나를 끝까지 처리하는지, 결과를 반복 시험할 수 있는지, 2주 내 연결 부담입니다. 아래 부담 평가는 구현 실측이 아닌 현재 스켈레톤 기준의 추정입니다.

## 후보 세 가지

아래 서비스와 사건은 모두 가상의 예시이며 실제 개인정보 대신 합성 자료를 사용합니다.

| 후보 | 사용자와 핵심 문제 | 깊이를 보여줄 장면 | 추가 부담 |
| --- | --- | --- | --- |
| ① 고객센터 관리자 계정의 차단·업무 복귀 검증 | 보안 담당자가 조치 후 실제 접근 차단과 안전한 복구를 확인하기 어려움 | 조치 API는 성공했지만 기존 세션 접근은 계속되는 실패 발견 | G를 구체화하므로 현재 제안과 연결이 가장 좋음. 세션·권한·복구 설계는 필요 |
| ② 협력사 임시 권한의 만료·범위 통제 | 승인된 대량 조회와 권한 만료·범위 위반을 구분하기 어려움 | 같은 조회량이어도 유효한 승인은 허용, 만료된 권한은 거부 | 승인·만료 정책, 권한 범위와 관리 입력이 추가됨 |
| ③ 불완전한 로그의 사건 연결 | 로그 누락·지연·중복 때문에 사건 판단을 과신하거나 놓침 | DB 로그 도착 전후 판단 갱신, 확정·추정 연결 근거 표시 | 계층별 수집과 시간·상관·사건 갱신 구현 부담이 가장 큼 |

### ① 고객센터 관리자 계정의 차단·업무 복귀 검증

- 정상: 상담원이 허용된 범위의 고객 주문 정보를 조회합니다.
- 의심: 테스트 계정의 권한이 정책상 허용되지 않은 방식으로 올라간 뒤, 담당 범위를 벗어난 합성 자료를 조회합니다. 대량 조회만으로 침해를 확정하지 않습니다.
- 대응: 계정을 잠그고 신규 로그인 및 기존 세션의 자료 접근을 시험합니다.
- 복구: 정상 사용자는 정해진 재인증 후 원래 업무로 복귀합니다. 의심스러운 권한 변경 이전의 신뢰할 수 있는 상태를 기준으로 하며, 기존 세션은 잠금 해제 후에도 다시 유효해지지 않아야 합니다.
- 핵심 시연: 격리된 시험 조건에서 조치 API가 성공을 반환해도 상태 변경이 적용되지 않는 상황을 주입하고, 접근 재시험으로 대응 실패를 발견합니다.

### ② 협력사 임시 권한의 만료·범위 통제

- 정상: 유효한 승인을 가진 직원이 지정된 프로젝트 자료를 대량 조회합니다.
- 의심: 권한이 만료된 뒤 기존 세션으로 접근하거나 다른 프로젝트 자료를 요청합니다.
- 대응·복구: 위반 범위의 접근을 제한하고 승인·만료 근거를 제시합니다. 재승인된 범위만 복구합니다.
- 핵심 시연: 같은 조회 건수의 정상·위반 사례를 대조합니다. MVP에서는 관리자 입력으로 승인 범위와 만료 시각을 지정하고 복잡한 결재 시스템은 만들지 않습니다.

### ③ 불완전한 로그의 사건 연결

- 정상 대조: 같은 공인 IP를 쓰는 서로 다른 사용자의 활동을 분리합니다.
- 의심: 한 계정의 정책 위반 권한 변경과 후속 제한 자료 조회를 연결합니다.
- 교란: DB 로그 지연·누락, 이벤트 중복을 통제해 입력합니다.
- 핵심 시연: 처음에는 “앱 접근 확인·DB 영향 미확인”으로 기록하고, 추가 증거가 도착하면 판단과 근거를 갱신합니다. 단순 IP 일치만으로 모든 이벤트를 확정 연결하지 않습니다.

## Codex 추천: ① 중심 + 같은 IP의 정상 사용자 대조

잠정 주제명은 **“쇼핑몰 관리자 계정 침해에 대해 실제 접근 차단과 안전한 업무 복귀를 검증하는 4계층 대응 시스템”**입니다. 최종 서비스명·주제 채택은 미정입니다.

팀이 증명할 질문을 세 가지로 좁힙니다.

1. 문제 계정의 신규·기존 세션 접근은 실제로 끊겼는가?
2. 같은 IP를 쓰는 정상 동료의 허용된 업무는 유지되는가?
3. 복구 후 위험한 세션·권한이 되살아나지 않고 정상 사용자가 재인증해 업무할 수 있는가?

②의 승인 시스템과 ③의 일반적인 증거 재평가 엔진까지 함께 구현하지 않습니다. 같은 IP의 정상 사용자 대조는 정상 업무 영향 시험 한 가지로 제한합니다.

### 최소 비교 실험 제안

동일한 앱·계정·입력·초기 상태에서 두 대응 흐름을 비교합니다. 기본 방식도 실제 구현 동작을 측정하며 결과를 미리 성공·실패로 채우지 않습니다.

- 기본 방식: 계정 잠금 API가 성공하면 대응 완료로 기록합니다.
- 제안 방식: API 결과와 실제 접근 검증을 별도로 기록하고, 검증 실패를 처리합니다. 복구도 권한·세션·정상 업무 확인을 거칩니다.
- 차이를 확인할 중심 실험: “성공 응답이지만 잠금 미적용”을 두 방식에 동일하게 주입합니다. 이 한 실험만으로 일반적인 보안 성능 향상을 주장하지 않습니다.

| 시험 | 초기 조건·입력 | 제안 방식에서 확인할 기대 결과 |
| --- | --- | --- |
| T1 정상 업무·같은 IP | 사용자 A·B는 같은 IP, A만 사건 대상. B는 허용된 자료 조회 | A 대응 중에도 B의 업무 성공. IP 전체 차단으로 B를 막지 않음 |
| T2 기존 세션 접근 | A가 잠금 전에 세션 발급, 잠금 후 같은 세션으로 자료 요청 | 신규 로그인·기존 세션 자료 접근 모두 거부 |
| T3 조치 효과 없음 | 잠금 요청 성공 응답, 시험 설정으로 실제 잠금 미적용 | 접근 검증 실패를 발견. 사건을 해결로 표시하지 않고 제한된 후속 처리 |
| T4 중복 조치 | 같은 사건·조치 식별자로 요청 재전송 | 중복 티켓·반복 상태 변경 방지. 확인 근거 기록 |
| T5 복구 후 세션 재사용 | 잠금 전에 발급한 세션을 복구 후 재사용. 정상 사용자는 재인증 | 이전 세션 거부, 정상 재인증 후 허용 업무 성공, 위험 권한 미복원 |
| T6 권한 복구 충돌 | 대응 중 정상 관리자가 권한을 추가 변경 | 과거 값으로 자동 덮어쓰기 중단. 충돌 근거를 남기고 검토 대기 |

T1·T2·T3·T5를 첫 필수 검증으로 제안합니다. T4의 중복 안전성은 대응 설계에 포함하고, T6는 우선 충돌 탐지·자동 복원 중단까지만 구현합니다. 자동 충돌 해결은 제외합니다. 일정이 부족하면 탐지 규칙 수·화면·H를 줄이고 필수 요구사항과 복구 안전 기준은 팀에서 다시 검토합니다.

각 시험에는 입력·예상값·실제값·판정·관련 이벤트/조치 식별자를 남깁니다. 보고할 수치는 정의한 시험의 통과 건수, T3의 실패 발견 여부, 정상 업무 오차단 건수, 복구 상태 일치 여부입니다. 지연을 재면 시작·종료 기준과 반복 횟수를 함께 제시합니다. 소수의 합성 시험 결과를 일반적인 탐지 정확도나 실서비스 효과로 확대하지 않습니다.

### 4계층과 연결하는 범위

| 계층 | 추천안에서의 역할·증거 |
| --- | --- |
| 엣지 | 앱으로 전달되는 테스트 요청의 기록, 별도 WAF 차단 시험. 가용한 식별자와 실제 수집 범위 확인 |
| 네트워크 | 엣지를 우회한 앱 직접 접근과 허용되지 않은 DB 경로 거부. 허용·거부 시험 및 로그 |
| 앱 | 인증·인가·계정 잠금·세션 상태 검사·대응 API·정상 업무 재시험 |
| 데이터 | 앱 DB 계정 최소 권한, 허용·금지 접근 시험, 실제 선택한 DB 감사 경로와 기록 |

엣지에서 차단한 요청과 앱까지 허용한 요청을 구분합니다. 요청 하나의 엣지→앱→DB 연결을 먼저 시험하고, 로그인 실패→성공→권한 변경→조회처럼 여러 요청으로 된 사건은 계정·자산·시간 순서 등 별도 근거로 연결합니다. SQL 주석에 ID를 넣는 방안은 선택한 DB 감사 방식이 실제로 보존하는지 확인하기 전까지 가설입니다.

특정 제품·라이선스·수집 API는 아직 선택하지 않았습니다. 계층별 자동 차단 전체를 MVP로 요구하지 않고 앱 계정 대응 경로를 우선합니다. 샘플 수집과 실제 제어, 앱 조회 로그와 DB 직접 감사를 구분합니다.

### 가장 먼저 할 작은 검증과 축소 기준

주제를 채택한다면 1~2일차에 두 가지를 작게 확인합니다.

1. 테스트 계정의 기존 세션을 잠금 중과 복구 후에 거부하면서 정상 재인증은 허용할 수 있는가? 계정 상태 조회와 세션 버전/서버 측 저장 등 선택한 방식의 실제 동작을 확인합니다.
2. 자료 조회 요청 한 건을 엣지·앱·DB 기록에서 연결할 수 있는가? 요청 ID·감사 형식·신뢰 경계를 확인하고, 불가능한 부분은 추정 연결이나 설계 변경으로 명시합니다.

3~4일차에는 이벤트 1종→규칙 1개→사건→잠금→접근 검증의 첫 통합을 목표로 합니다. 우선 줄일 항목은 전체 쇼핑몰 기능, 내보내기, H 전용 UI, 추가 탐지 규칙, 계층별 추가 자동 대응입니다. 필수 제품의 연결 부담이 크면 가용 시간과 장비를 근거로 인수 기준을 재협의합니다.

- 확인 범위: 변경 문서 로컬 링크와 diff 형식 확인. 실제 결과는 PR 본문·체크에 기록합니다. T1~T6와 4계층 연결은 미구현·미실행입니다.
- 필요한 입력: Claude 검토, 팀원 의견, 실제 수업 요건·장비·가용 시간.
- 다음 담당 첫 행동: 팀원 원문·PR #2 코멘트와 이 문서를 비교하고 위 질문 1~5에 의견을 남깁니다. 채택은 팀 합의 후 [주제 결정 기록](07-topic-decision.md)에 반영합니다.
