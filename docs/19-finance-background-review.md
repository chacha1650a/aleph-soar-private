# 금융 배경 전환안의 Codex 검토 요청 · R06

기준일: 2026-10-15 (Asia/Seoul) · 작성: Claude 제안 · 상태: Codex 회신 수신·Claude 후속 판단 기록 · 팀 채택 전

사용자가 "스마트팩토리가 아니어도 된다"고 밝혔고, Claude는 배경을 **금융(은행 내부 업무망 + 외주 유지보수 업체 원격 접속)**으로 바꾸는 안을 추천했습니다. 사용자가 이 안을 Codex에게 검토받기로 했습니다. 1~8절은 검토 요청 당시의 원안이며, [Codex 회신](../work-log/2026-10-15-codex-finance-background-review.md)에 따라 수정할 부분은 [9절](#9-codex-회신과-claude-후속-판단)에 정리했습니다. 팀 채택이나 기존 결정의 변경을 뜻하지 않습니다.

## 1. 배경과 전제

- 4인·2주. 사용 예정 도구: Wazuh, Graylog, pfSense, n8n, Kali Linux, Docker. 이후 다른 팀과 공방전 예정이며 규칙은 미정입니다.
- 기존 사용자 선택은 생산관리·협력사 포털 + 가상 설비 데이터([로드맵](14-smart-factory-roadmap.md))였습니다. 이번 발언으로 배경 변경 가능성이 열렸지만 아직 팀 합의는 없습니다.
- [보강안 R05](18-security-network-career-direction.md)의 1안(협력사 원격 유지보수 접속 통제 + 관제)을 금융 배경으로 옮긴 것이 이 제안입니다. 핵심 뼈대(외부 업체 계정 탈취, 망 분리, 차단 효과 재시험, 정상 업무 유지, 안전한 복귀)는 그대로입니다.
- 앱은 아직 시작 화면과 상태 API만 있어 구현 손실은 없습니다.

## 2. 추천 이유 (Claude 판단)

1. **네트워크 보안 이야기가 가장 강합니다.** 금융권은 망분리와 외주 인력 접속 통제가 실제 감사 대상입니다.
2. **규제가 바뀌는 중입니다.** 금융위원회·금융감독원은 2024-08-13 망분리 개선 로드맵을 발표했습니다. 생성형 AI·SaaS 이용 범위를 넓히는 대신 단말 추적성과 데이터 저장·반출 제한 같은 보안 대책을 조건으로 붙이는 방향으로 보도됐습니다.[F01], [F02] 규제가 완화될수록 접속 통제와 효과 검증이 중요해진다는 설명으로 연결할 수 있습니다.
3. **발표 설명이 짧아집니다.** "은행 내부망에 외주 업체가 들어오는 경로"는 누구나 이해합니다.
4. 금융·공공 고객이 많은 관제·보안 업체 취업과 연결된다는 판단은 추정이며 채용 통계로 확인하지 않았습니다.

## 3. 제안 구성

### 스마트팩토리 → 금융 대응표

| 지금 (스마트팩토리) | 금융 전환안 |
| --- | --- |
| 협력사 정비 담당자 A·B | 외주 개발·유지보수 업체 A·B |
| 라인 A·B 정비 호스트 | 업무 시스템 A·B 서버 (예: 내부 조회 서버, 배치 처리 서버) |
| 가상 설비 데이터 수집과 순번 확인 | 가상 거래·배치 처리와 처리 순번 확인 |
| 사무망 / DMZ / 설비망 / 관제망 | 인터넷망 / DMZ / 업무망 / 관리·관제망 |
| 생산관리자 | 은행 IT 운영 담당자 |

실제 계좌·이체·고객 개인정보는 만들지 않습니다. 고객 서비스가 아니라 은행 내부 운영 환경을 단순화한 랩입니다.

### 망 구성 초안

| 구역 | 구성 | 허용 통신 초안 |
| --- | --- | --- |
| 외부 | 외주 업체 PC 역할, Kali | VPN 접속과 DMZ 웹만 |
| DMZ | 인터넷뱅킹을 흉내 낸 웹(Flask) | 외부→웹, 웹→업무망의 지정 API만 |
| 업무망 | 업무 시스템 A·B, 가상 거래 처리기, 업무 DB | 외주 업체 VPN→담당 시스템만, DMZ의 지정 API만 |
| 인터넷망 | 직원 인터넷 PC 역할 | 업무망과 직접 통신 금지 |
| 관리·관제망 | Graylog, Wazuh 관리자, n8n | 각 구역 로그 수신, 관리 접속은 이 구역에서만 |

- 실제 금융권의 망분리(물리·논리)와 외주 접속 통제 솔루션·작업 승인 절차를 그대로 재현하지 않습니다. pfSense 구역 분리와 VPN 사용자별 허용 규칙으로 개념만 구현합니다(일반 지식, 버전별 확인 필요).
- 네트워크 조치는 승인 후 적용이 기본입니다. pfSense REST API는 비공식 패키지라 자동화 경로는 팀이 정합니다([R04 회신](17-reference-sites-review.md) 근거).

### 핵심 시나리오 S1: 유출된 외주 업체 계정으로 담당 외 시스템 접근

| 단계 | 내용 | 확인할 것 |
| --- | --- | --- |
| 0. 기준선 | 업체 B가 시스템 B에 접속, 가상 거래 처리기가 순번 기록 | B 접속 성공, 시작 순번 |
| 1. 침입 | 공격자가 업체 A의 유출 계정으로 VPN 접속 | VPN 접속 로그. ATT&CK T1133, T1078 |
| 2. 정찰 | 공격자가 시스템 B를 포트 스캔 | pfSense 거부 로그, Suricata 경보. T1046 |
| 3. 탐지 | Graylog가 A의 VPN IP 거부 횟수 기준으로 사건 생성 → n8n 호출 | 사건 ID, 근거 로그 ID |
| 4. 대응 | n8n 변경 요청 → 보안 담당 승인 → A의 VPN 계정 차단·기존 접속 끊기 | 조치 ID, 승인자, 적용 시각 |
| 5. 재시험 | A 재접속, B 접속, 거래 처리 순번 확인 | A 실패, B 성공, 순번 누락 0 |
| 6. 복귀 | 복구 담당 본인 확인 → 새 자격 증명 발급 | 이전 자격 증명 거부, 새 자격 증명으로 시스템 A만 성공 |

변형 시나리오: S2 정상 업체의 단발성 실수 접근(사건 미생성), S3 차단 실패 주입(조치 기록과 실제 접속 불일치 탐지), S4 복귀 후 이전 자격 증명 재사용, S5 공방전 상대의 DMZ 우회 업무망 직접 접근, S6 VPN 무차별 대입(T1110).

### 화면

- 업무 쪽: 로그인, 업무 시스템 운영 현황(처리 순번·마지막 처리 시각).
- 관제 쪽: 외주 업체 접속 현황, 사건 상세(근거, 조치 이력과 현재 효과 분리, 효과 재시험, 복귀 승인). 로그 원문은 Graylog 링크로 대신합니다.

## 4. 스마트팩토리를 유지할 이유

- 문서와 [시장 조사](15-market-research.md)가 제조업 기준으로 이미 갖춰져 있습니다.
- KISA가 2025-12 OT 제로트러스트 안내서를 낸 분야로, 다른 팀과 겹칠 가능성이 낮습니다(R05의 [T02] 근거).
- 목표 직무가 OT 보안·제조 대기업이면 스마트팩토리가 더 맞습니다.

## 6. Codex에게 요청하는 검토

1. 금융 전환이 스마트팩토리 유지보다 보안 네트워크 직무·공방전·2주 범위에 적합한지 판단해 주세요. 결론은 전환 / 유지 / 판단 보류로 주세요.
2. 2절의 금융 규제 서술을 공식 출처(금융위원회 보도자료, 전자금융감독규정 등)로 확인해 주세요. 외주 인력 원격 접속에 관한 실제 규정이 있다면 근거로 쓸 수 있는 범위와 오해 소지를 짚어 주세요.
3. 망 구성 초안이 실제 금융권 망분리 개념을 왜곡하는지, 랩의 단순화를 문서와 발표에서 어떻게 표시해야 하는지 검토해 주세요.
4. "가상 거래·배치 처리 순번"이 정상 업무 유지의 증거로 적절한지, 실제 계좌·이체를 만들지 않는 범위가 충분한지 검토해 주세요.
5. S1~S6의 현실성과 ATT&CK 매핑(T1133, T1078, T1046, T1110)을 검토해 주세요.
6. 전환 시 기존 문서·결정과의 충돌, 재작업 범위가 과소평가됐는지 짚어 주세요.
7. 발표용 한 문장 주제와 최소 시연 흐름을 제안해 주세요.

## 9. Codex 회신과 Claude 후속 판단

Codex 데스크톱 앱에서 검토를 실행했고, 회신 원문은 [작업 기록](../work-log/2026-10-15-codex-finance-background-review.md)에 보존했습니다. Codex는 검토 대상 문서를 수정하지 않았다고 기록했습니다.

### Codex 판정

**전환. 단, 금융 외주 원격 유지보수의 접근 통제·대응 효과·업무 복귀 검증으로 범위를 좁힐 때에 한합니다.** 인터넷뱅킹이나 금융거래 서비스 구현은 권하지 않았습니다. 금융이 제조보다 네트워크 역량을 본질적으로 더 잘 증명하거나 취업·공방전에 유리하다는 사실은 확인하지 못했고, 차이는 배경 이름보다 실제 ACL·경로 검증·대응 실패 처리·재시험 증적에서 생긴다고 보았습니다.

| S1 3단계 "VPN IP 거부 횟수" | VPN 사용자·인증서 식별자·접속 시각·터널 주소를 기록해 방화벽·호스트 로그와 연결합니다. 주체가 모호하면 자동 조치를 멈추고 검토 상태로 둡니다. |
| S1 1단계, S4 | 인증 방식(인증서+비밀번호 후보)을 먼저 고정하고 탈취 가정을 그에 맞게 씁니다. 복귀에는 이전 인증서 폐기(CRL), 새 인증서·비밀번호 발급, 조합별 거부 시험을 포함합니다. |
| 3절 "처리 순번 누락 0" | 독립 생성기의 발행 작업 ID와 서버의 수락·완료 결과를 대조하고 예정·발행·성공·실패·미완료·중복 건수, 완료 지연, 내용 일치를 기준선·대응 중·복귀 후로 비교합니다. |
| 도구 책임 | 최소 탐지는 pfSense 거부 로그 집계와 VPN 주체 연결입니다. Suricata는 선택 확장, Wazuh는 유지보수 호스트의 한 신호, Graylog는 검색·집계·전달, 프로젝트 백엔드는 사건 상태, n8n은 승인·실행으로 나눕니다. |
| 5절 "약 하루", 4절 "겹칠 가능성이 낮다" | 둘 다 검증 전 추정으로 낮춥니다. 다른 팀 주제를 모르므로 중복 가능성은 판단 보류합니다. |

### 보류·추가 의견

- **공방전 진입점:** 상대 팀이 VPN 계정을 받지 않는다면 S1은 자체 검증 시나리오이고, 공방전의 공격 진입점은 별도로 정해야 합니다. 공방전 운영 측에 확인할 질문([R05 7절](18-security-network-career-direction.md#7-공방전과의-연결))에 "외부 팀에게 어떤 진입점을 주는가"를 추가합니다.
- **유지보수 게이트웨이(점프 서버):** 현실성은 높아지지만 2주 범위를 키우므로 선택 확장으로 둡니다.
- **주제 이름:** Codex는 "…검증하는 시스템"을 제안했습니다. R04 회신의 과장 방지 의견에 따라 이름에는 "검증 랩"을 권합니다. 예: "금융 외주 원격접속 대응·복귀 검증 랩".
- **판단의 근거:** 기술적 우위가 아니라 설명력과 팀의 목표 직무로 전환 여부를 정해야 한다는 Codex 의견에 동의합니다.
