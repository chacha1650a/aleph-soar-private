# 4대 PC 분산 배치 실행안

상태: **2026-10-20 사용자 분산 진행 결정 · 10/20 저녁 팀 VPN 구성·B 호스트 시험 · 10/21 기획서 ③ 반영 · A·C·D 연결 시험 전**.

**10/21 현재.** 10/20 저녁 B가 pfSense에 팀 전용 OpenVPN(TRANSIT 인터페이스 UDP 1195, 터널 10.250.0.0/24, 기본 차단)을 구성하고, B 호스트의 시험 계정 접속과 터널 서버 ping을 확인했다([B 10/20 작업일지](../work-log/members/myeongjundev/2026-10-20.md)). 아래 2.1절의 VPN 후보는 이 구성으로 진행하며, 기획서 ③은 이 실행안을 계획값(포털 VM .10, C .30, D .40)으로 반영했다. A·C·D 접속, 서비스까지의 경로, 출발지 보존은 아직 시험하지 않았다. 아래 본문은 10/20 당시 기록이다.

분산 진행 자체는 사용자 결정이다. 아래 PC별 서비스 배치는 현재 역할과 자원을 기준으로 정리한 실행안이며 팀원들이 동의했거나 실제 배치한 결과가 아니다. 기존 기획서 ③의 두 PC 그림·배치표는 이전 안이다. 장비와 배치가 확정되면 제출본 본문·그림도 함께 갱신한다. A~D의 보안 케이스 책임과 포털 코드 구현 책임은 바꾸지 않는다.

## 2. 추가 장비가 없는 현재 할 수 있는 일

- 사용자가 추가 랜카드·스위치·랜선 등은 아직 없다고 답했다. 물리 분산 연결 완료로 표시하지 않는다.
- A는 자기 PC에서 Ubuntu Server VM·Docker와 포털 배포 파일을 준비한다. B는 현재 pfSense를 유지하고 DB·Kali의 설치 파일과 VM을 준비한다. C·D는 각 PC에 필요한 이미지·설정·데이터 보존 경로를 준비한다.
- 설치·패키지 다운로드 단계에서는 각 PC의 기존 인터넷과 설치용 NAT를 사용할 수 있다. 격리 랩 시험을 시작하기 전에 설치용 우회 연결을 정리하고 실제 연결 경로를 확인한다.
- 현재 B의 VMnet5·6·4·7은 같은 PC 안의 가상망이다. 다른 PC에서 같은 VMnet 번호를 만드는 것만으로 연결되지는 않는다.
- 강의실 공용망으로 공격 시험을 옮기지 않는다. 허가된 별도 연결을 확보한 뒤 통합한다.

### 2.1 추가 장비 없이 연결하는 후보 · 후속 사용자 조건

사용자가 USB 랜카드·분리 스위치·랜선 대여가 어렵다고 답했다. 아래 3절은 보류한 물리 연결안이며, 분산 진행에 반드시 그 장비가 있어야 한다는 뜻이 아니다. 준비 작업은 계속하고 PC 간 연결 방식은 먼저 작게 시험한다.

- 후보: 기존 학원 유선망을 팀 PC 사이 VPN의 전송 경로로 쓰고, VM·서비스의 실습 통신은 팀 전용 터널의 경로·방화벽 규칙으로 제한한다. 이는 새로운 제안이며 사용자·팀의 최종 VPN 방식 선택이나 연결 성공을 뜻하지 않는다.
- B의 유선 IPv4는 이 세션의 읽기 확인에서 192.168.3.4/24, 게이트웨이는 192.168.3.1이다. 사용자 전달 주소와 B에서 실행한 일반 통신 점검은 아래 표에 기록한다. VPN·서비스용 포트와 학원망에서 해당 정상 연결을 사용할 수 있는지는 아직 확인하지 않았다.
- 먼저 B↔팀원 한 PC 사이 정상 연결을 확인하고, 터널 한 개의 연결·라우팅·복원만 시험한다. 포털·로그 입력·관리 API를 학원망 전체에 바로 공개하는 방식으로 대신하지 않는다.
- OpenVPN은 현재 제품에 있는 기능을 새 팀용 설정으로 구성하는 후보이고, WireGuard는 pfSense 버전·패키지 호환성과 설치 가능성을 먼저 확인하는 후보다. 수업용 VPN·키·인증서가 남아 있다는 사실을 팀용 터널 구축 완료로 해석하지 않는다. 설치·업그레이드·터널 설정은 아직 하지 않았다.
- pfSense VM까지 들어오는 외부 연결 경로는 별도 확인 대상이다. 현재 pfSense는 VMnet5·7·6·4에만 연결돼 있으므로, Windows의 학원망 IP가 있다는 것만으로 pfSense가 팀원 PC에서 도달 가능한 것은 아니다. 설치용 NAT의 포트 전달 또는 전용 전송 인터페이스 등 실제 경로를 설계·시험해야 한다.
- 팀원별 경로·VPN 키·라우팅·방화벽·NAT 예외를 맞추고, 공격 대상 서비스가 터널 안에서만 도달되는지 확인한다. 터널 내부 출발지가 중간 NAT·프록시로 바뀌어 S1·S8·S10의 출발지 판정이 깨지지 않는지도 패킷·앱 로그로 검증한다.
- 4절의 물리 브리지·관리 주소 전환표를 이 후보에 그대로 적용하지 않는다. 현재 관리망과 스냅샷은 유지하고, 검증 후 제출본·배치표·규칙·자동화 허용 출발지를 함께 갱신한다.

이 단계에서 DB VM 생성·OS 설치 준비는 계속할 수 있다. PC 간 통합·공격 재현은 정상 연결과 터널 경계 확인 후 진행한다.

**사용자 전달 주소와 읽기 점검(2026-10-20, 이 세션).** 이름 표기 차이로 다른 사람을 재배정하지 않도록 아래는 자리 기준으로 기록한다. 사용자는 .5 자리를 “이상혁”, .6을 김대훈, .7을 반소람으로 전달했다.

| 자리 | 학원 유선 IPv4(사용자 전달) | B에서 확인한 결과 |
| --- | --- | --- |
| B | 192.168.3.4 | Windows의 실제 유선 주소·/24와 직접 연결 경로 확인 |
| C | 192.168.3.5 | Ping 2회 응답 없음. ARP 장치 주소가 확인되고 NeighborState=Reachable |
| D | 192.168.3.6 | 원격 장치 Ping 응답 없음(B 자신이 Destination host unreachable 반환), ARP 장치 주소 미확인·Unreachable. 전원·케이블·현재 IP 확인 필요 |
| A | 192.168.3.7 | Ping 2회 응답 없음. ARP 장치 주소가 확인되고 NeighborState=Reachable |

B→192.168.3.1 게이트웨이 Ping은 2/2 응답했다. A·C의 결과는 같은 링크에서 주소가 식별되는 상태이며 ICMP 차단 등이 원인일 수 있다. 이것만으로 TCP·UDP·VPN 성공이나 실패를 판정하지 않는다. D 점검의 로컬 “Destination host unreachable”을 D의 Ping 성공으로 세지 않는다. 다른 PC의 방화벽을 끄거나 광범위한 포트를 열지 않았고, 터널·서비스 포트 시험과 인증은 미실행이다.

## 3. 보류한 물리 연결안 — 시험 중 기존 유선 포트 재사용

이 안은 **시험 시간에 네 PC의 강의실 유선 연결을 빼고 기존 포트를 랩에 재사용**할 수 있다는 조건이다. 포트 사용 허가와 장비 확보는 아직 확인하지 않았다. 구매 지시나 확보 완료 기록이 아니다.

필요 장비: B용 추가 이더넷 포트 1개(예: USB 랜카드 1개), 강의실 망과 분리된 일반 스위치 1대(3포트 이상 사용 가능), 랜선 총 4개.

```text
외부 시험망(203.0.113.0/24)
  B의 Kali -- VMnet5 -- B의 pfSense WAN(em0)

DMZ(10.10.10.0/24)
  A의 포털 VM -- A 내장 유선 포트 ===== B 내장 유선 포트 -- pfSense DMZ(em2)

업무망(10.10.20.0/24)
  B의 DB VM -- VMnet4 -- pfSense WORK(em3)

관리망(10.10.30.0/24)
  pfSense LAN(em1) -- B 추가 랜카드 -- 분리된 스위치 -- C 내장 유선 포트
                                                 └-- D 내장 유선 포트
```

- 랜선은 A↔B DMZ 직결 1개, B↔스위치·C↔스위치·D↔스위치 3개로 총 4개다.
- B와 A의 DMZ 연결은 각 포트에 특정한 VMware 브리지로 잡는다. A Windows 호스트에는 DMZ IP를 부여하지 않고 VM만 DMZ에 둔다.
- B 추가 포트와 C·D의 유선 포트는 관리망 스위치에만 연결한다. DMZ 케이블·관리망 스위치를 강의실 망에 연결하지 않는다.
- 강의실 유선 인터넷을 계속 유지하려면 이 안보다 추가 포트가 더 필요하다. 위 배치에서 B는 추가 2개, A·C·D는 각 1개로 총 5개 추가 포트가 필요하다. 장비가 없으므로 아직 실행하지 않는다.
- VLAN 스위치를 확보하면 다른 구성을 검토할 수 있지만 Workstation 브리지·Windows NIC 드라이버의 VLAN 전달을 실제 시험하기 전 작동한다고 가정하지 않는다.

## 4. 물리 연결안의 주소·VMnet 전환 계획 — 현재 적용하지 않음

| 대상 | 현재 관찰·설정 | 분산 배치 목표 |
| --- | --- | --- |
| B pfSense WAN / em0 | VMnet5, 203.0.113.1/24 | 유지. Kali도 B VMnet5 |
| B pfSense LAN / em1 | 임시 Host-only VMnet7, 10.10.30.1/24 | B 추가 관리망 포트로 특정한 브리지 |
| B pfSense DMZ / em2 | Custom VMnet6, 10.10.10.1/24 | A↔B 전용 DMZ 포트로 특정한 브리지 |
| B pfSense WORK / em3 | Custom VMnet4, 10.10.20.1/24 | 유지. B DB VM은 10.10.20.10/24 |
| A 포털 VM | 설치·배치 미확인 | 10.10.10.10/24, 게이트웨이 10.10.10.1 |
| B Windows 관리 접속 | 임시 VMnet7 어댑터에 10.10.30.10/24 | B 관리망 물리 포트에 10.10.30.20/24 |
| C Windows 관리망 | 미확인 | 10.10.30.11/24, Wazuh·보안 대시보드 |
| D Windows 관리망 | 미확인 | 10.10.30.10/24, Graylog·n8n |

**주소 충돌 전환:** 현재 B가 쓰는 10.10.30.10은 분산안에서 D에 배정한다. B의 임시 Host-only 주소를 정리하고 B를 .20으로 전환한 뒤 D의 .10을 실제 연결한다. 장비 없는 지금은 VMnet6·7의 모드나 B의 관리 IP를 바꾸지 않는다. 적용은 VMware 콘솔을 확보한 상태에서 진행하고 백업·스냅샷으로 돌아갈 수 있게 한다. B의 VMnet2(172.16.50.0/24)·VMnet3(172.16.10.0/24)는 수업 설정으로 보존한다.

관리망 Windows에는 불필요하게 두 번째 기본 게이트웨이를 추가하지 않는다. B·C·D에서 DMZ/업무망으로 가는 정적 경로는 pfSense 10.10.30.1을 다음 홉으로 정해 설치·시험 때 확인한다. 관리자 브라우저의 포털 접근, n8n의 대응 호출, Wazuh의 agent 호출도 이 경로로 확인한다.

## 5. PC 사이로 분리돼 달라지는 연결

| 연결 | 담당 | 확인할 것 |
| --- | --- | --- |
| A 포털 → B DB | A·B | 10.10.10.10 → 10.10.20.10:3306, DB의 실제 접근 허용·인증, 출발지 보존 |
| A 포털 → D Graylog | A·D | GELF 12201/udp 도착. DMZ의 허용 규칙·D의 Windows 방화벽·Docker 포트 공개 필요 |
| A Wazuh agent → C manager | A·C·B | 1514·1515/tcp 등록·경보 수집. DMZ 규칙·C의 포트 공개 필요 |
| C Wazuh → D Graylog | C·D | 수집 방식·대상 포트·경보 필드를 먼저 정하고 실제 경보로 확인 |
| D n8n → A 포털 / B pfSense | D·A·B | 자동화 출발지·인증·경로, 재시도·상태·실제 효과·원복 |
| D n8n → C Wazuh / 티켓 | D·C | 기존 같은 PC의 localhost/Docker 내부 이름 대신 관리망에서 도달 가능한 주소·포트·허용 출발지로 연결 |

로그 입력과 서비스 간 API는 필요한 관리망 주소에만 공개하고 허용 출발지를 제한한다. Graylog·n8n이 D의 같은 Docker 네트워크를 공유하면 둘의 Webhook은 내부 이름을 사용할 수 있다. API 경로·인증·이벤트 형식을 이 문서에서 바꾸지는 않는다. 실제 계약 변경은 API-CONTRACT·contracts·소비자를 함께 맞춘다.

| L05 수집·대응 준비 | D: D PC의 Graylog·n8n | 입력·정규화·워크플로의 대상 주소·포트·자격 증명 위치 확인. 비밀값은 기록하지 않음 |
| L06 PC 간 연결 | B 책임, A·C·D 각 PC 설정 | 선택한 연결 방식의 선행 확인 후 실행. 물리안은 장비 확보, VPN 후보는 정상 도달성·터널·경로·출발지 보존 시험 필요. 주소·수집 포트·응답 경로 확인 |
| L07 통합 검증 | B 조율, 각 케이스 담당 실행 | 아래 흐름별 실측·정상 대조·원복을 기록하고 미실행은 분리 |

L02~L05의 준비는 각자 할 수 있다. L06은 선택한 방식의 선행 확인과 각 PC 준비가 전제이고, L07은 실제 연결 후에 한다. 이는 새 실행안의 확인 순서이며 기존 orchestration/workplan.json의 완료 ID를 대신하지 않는다. `team.py ready`·`brief P01`은 확인했고 검증하지 않은 완료 ID는 전달하지 않았다. 같은 파일을 여러 명이 고치지 않도록 망·배치 문서 취합은 B가 맡는다.

통합 때 확인할 흐름:

1. 외부 Kali → 203.0.113.1:80 → A 포털. 포털 기록에 Kali의 출발지가 남는지 확인.
2. A 포털 → B DB의 3306 연결 성공, 다른 출발지·불필요 포트 차단 대조.
3. A 앱 로그 → D Graylog, A FIM → C Wazuh → D Graylog의 원본·수집·처리 시각 확인.
4. D n8n → B pfSense 차단·해제 1회. 상태 목록과 실제 공격 차단·정상 출발지 유지·원복을 각각 확인.
5. D n8n → A 잠금/차단, C 파일 복구·티켓 연결. 호출 성공과 실제 효과를 구분.
6. C·D 각각의 자원, 로그 누락·적체·지연·재시작 복구를 측정. 기존 한 PC의 관찰값을 분산 실측값으로 사용하지 않음.

## 7. 현재 증거와 미확인

- 이 채팅의 화면에서 pfSense CE 2.7.2, WAN em0=203.0.113.1/24, LAN em1=10.10.30.1/24, DMZ em2=10.10.10.1/24, WORK em3=10.10.20.1/24를 확인했다.
- 화면에서 HTTP 포워딩(203.0.113.1:80→10.10.10.10:80), 연동 WAN 허용 규칙, 기존 시간표 HTTP 규칙 비활성화, DMZ의 포털→DB 3306 허용·로그, 빈 WORK·Floating, Automatic 모드의 빈 Outbound NAT 목록을 확인했다. 실제 서비스 도착·망 분리는 아직 시험하지 않았다.
- 이 세션에서 Windows VMnet7의 10.10.30.10/24와 VMX의 5/7/6/4 연결을 읽기 확인했고, pfSense LAN 변경 후 10.10.30.1 ping 2/2 및 TCP 22·443 연결을 확인했다. SSH 키 인증 성공까지 확인한 것은 아니다.
- 백업·스냅샷 완료는 사용자 보고다. XML 원문과 스냅샷 복원은 직접 검증하지 않았다.
- 물리 장비, 각 팀원 PC의 실제 설치, Suricata·VPN 재설정, 케이스 탐지·자동 대응·원복, 분산 부하 측정은 미확인이다. 수업 VPN 인터페이스·1194 규칙이 남아 있는 상태를 팀 VPN 구축 완료로 해석하지 않는다.
