# 최종 구현·설치·시연 실행 안내

목표는 A(S1·S4), B(S8·S10), C(S7), D(S12)의 **실제 동작과 다른 환경 재현을 증명하는 패키지**다. 10/30부터 실행, 11/5 리허설, 11/6 본발표다. 집의 코드/합성 시험과 학원의 실측을 구분한다. 이 안내는 전체 설치 완료 보고가 아니다.

## 집과 학원의 작업 경계

| 요구 | 집에서 준비/검증 | 학원에서 완료할 것 |
| --- | --- | --- |
| 6개 시나리오 | 입력·대응·티켓 계약, 생성 워크플로, 정상/실패/중복 테스트 | 실제 입력→수집→탐지→조치→효과→원복 |
| 설치 패키지 | 주소 설정 분리, 버전/해시 목록, 설치 순서·설정 예시 | 새 환경에서 다른 팀원이 설치·6개 범위 재현 |
| 유지보수 | 티켓 DB 백업·새 DB 복원 도구/테스트, 장애별 확인 순서 | 운영 볼륨 백업, 실제 중단/복원·권한/재기동 확인 |
| IDS·사건 ID 실측 | ID 연결 항목과 계산 시작/끝점 고정 | 센서 경보·event_id·n8n 실행 ID·ticket_id 원본 대조 |
| 시각적 전후 비교 | 화면 구성과 비교표 정의, 기존 CSV 집계 도구 | 동일 조건 실측값·실제 화면/티켓 캡처 |
| 한 자리 시연 | 접근 경로·화면 전환 순서·비상 전환 절차 | 발표 PC에서 실제 접속·조작·복구 리허설 |
| 개인 발표/녹화 | 아래 8분 대본 틀·컷 구성 | 각 담당이 실제 실행하고 녹화·재생 확인 |
| UI | 기존 목록/상세/타임라인과 자료 구분을 유지 | 사용자 특강 이미지 수령 뒤 디자인 반영·실측 표시 검증 |

현재 PF/S12 후보는 집에서 코드 검증한 미배포본이다. 타 조 환경에서 설치/작동 검증된 전체 패키지로 부르지 않는다. 새 기능 추가보다 전체 연결과 실측 증거를 우선한다.

## 다른 환경 설치 순서

1. 배포할 capstone/backend/frontend 커밋, 이미지, 워크플로/탐지 규칙 해시를 확정한다. 현재 미커밋 작업본은 최종 배포 커밋이 아니다.
2. 대상 환경의 자산·서비스 주소, VPN/반환 경로, 도구별 포트, 데이터 경로를 대응표로 만든다. 관리자·정상 사용자·공격 시험 출발지를 분리한다.
3. A 포털/DB와 정상 사용자 경로부터 기동·확인한다. 별도 backend/frontend 저장소의 설치 안내를 사용하며 capstone 스켈레톤으로 대체하지 않는다.
4. Graylog/Wazuh 수집을 연결한다. 포털 원본 이벤트 1건을 ID로 대조하고, 단순 포트 연결과 실제 색인을 구분한다.
5. C 티켓 저장소를 설정한다. `services/ticket-store/.env.example`을 `.env`로 복사하고 새 키를 로컬에서 설정한다. `TICKET_BIND_IP`는 해당 환경의 승인된 사설 인터페이스다. 집 격리 확인은 `127.0.0.1`, 학원 기본은 `10.250.0.3`이다. 대시보드는 계속 loopback에만 공개한다.
6. n8n을 기동하고 비활성 워크플로부터 반입한다. 기존 compose는 외부 `n8n_data` 볼륨을 전제로 하므로 새 환경은 빈 볼륨 준비가 필요하다. 기존 볼륨을 삭제/재생성하지 않는다. 자격 증명·암호화 키·웹훅 인증·게시 버전은 D가 별도 인수한다.
7. 포털/PF/Wazuh 조치를 하나씩 단독 검증한다. 정상 대조와 해제/복구를 먼저 확보한 후 시나리오를 활성화한다.
8. 설치를 작성하지 않은 팀원이 같은 안내로 재현하고, 성공한 범위와 미확인 범위를 기록한다. 설치 성공만으로 공격 시나리오 성공을 선언하지 않는다.

## 티켓 DB 백업과 복원 사본

`tools/ticket_db_backup.py`는 Python 표준 SQLite backup API로 일관된 스냅샷을 만들고 integrity_check와 tickets/actions 존재를 검사한다. WAL의 커밋 데이터도 포함한다. 기존 목적지나 원본을 덮어쓰지 않으며 실제 운영 DB를 교체하지 않는다.

DB 파일에 접근 가능한 환경에서, 존재하는 출력 디렉터리의 **새 파일**로 실행한다. 아래 경로는 예시이며 실제 DB/백업 위치로 교체한다.

```sh
python tools/ticket_db_backup.py --source /data/tickets.db --out /backup/tickets-before-demo.db
python tools/ticket_db_backup.py --source /backup/tickets-before-demo.db --out /restore-check/tickets.db
```

컨테이너 환경에서는 같은 데이터 볼륨에 접근 가능한 위치에서 도구를 실행해야 한다. 호스트에 `/data/tickets.db`가 있다고 가정하지 않는다. 백업에는 실제 사건 데이터가 있으므로 저장소/시연 공개 폴더에 넣지 않는다.

운영 복구는 C 담당이 쓰기를 중단한 별도 구간에서 한다. 현재 DB와 WAL/SHM을 함께 보존하고, 새 경로의 검증된 복원 DB를 서비스에 연결해 소유권/권한·조회·기록·재시작을 확인한다. 동작 중인 DB 위로 복사하거나 WAL 파일을 임의 삭제하지 않는다. DB 복원은 PF 차단이나 포털 잠금의 원복이 아니므로 실제 장비 상태를 별도로 대조한다.

| 증상 | 첫 확인 | 완료 판정 |
| --- | --- | --- |
| 티켓 연결 실패 | C 서비스/인증 키·포트·D 경로 | 실제 인증 조회/기록 |
| 대응 후 티켓 누락 | 원래 실행 ID·요청 키·대상 상태 | 중복 조치 없이 기록과 상태 일치 |
| 로그 누락 | 원본 ID·전송·수신·색인 순서 | 같은 회차 원본/고유 수 대조 |
| 차단 해제 실패 | 소유권·활성 티켓·PF journal | 대상 정상 복귀와 다른 정상 사용자 유지 |
| 업데이트 실패 | 이전 이미지/설정·백업·DB 호환 | 이전 버전 재기동 및 연결 재검증 |

## 한 자리에서 시연

발표는 **C PC(`10.250.0.3`)에서 직접 진행**한다. 아래 화면을 탭/창으로 준비하고 담당 실행 터미널을 구분한다. 전체 시험의 실행자는 한 명이고 다른 담당은 관측한다. 공유 화면에 키·쿠키·관리자 자격 증명을 노출하지 않는다.

| 화면 | C PC에서 사용할 경로 | 확인 범위·남은 확인 |
| --- | --- | --- |
| C 보안 대시보드 | `http://127.0.0.1:8089/` · S12 비교는 `/s12` | C의 운영 화면 확인 완료. 실제 CSV 등록과 티켓 대조는 별도 |
| A 포털 | `http://10.250.0.2:5000/login` | C 출발지 TCP·GET 1회 HTTP 200 확인. 로그인·조작 리허설은 별도 |
| D Graylog | `http://10.250.0.100:9000/` | C 출발지 TCP·GET 1회 HTTP 200 확인. 로그인·검색 리허설은 별도 |
| D n8n | D PC 화면 공유 또는 사전 녹화를 C PC에서 표시 | 설정 변경 없는 발표안. 공유·영상 재생과 화면 전환을 리허설에서 확인 |

C 대시보드는 C PC의 loopback 주소로 바로 열고 현재 `DASHBOARD_ORIGIN` 주소/포트를 유지한다. 이 발표 경로에는 C로 접속하는 SSH 로컬 터널이 필요하지 않다. C의 10/30 보고(PC 시계 13:49:48)에서 A 포털과 D Graylog의 HTTP 200을 확인했으며, 14:12 KST 재확인에서도 대시보드(`/`·`/s12`)와 두 화면의 HTTP 200 및 `DASHBOARD_ORIGIN` 유지를 보고했다. 로그인·조작까지 검증한 것으로 확대하지 않는다. 이번 발표 준비에서 B가 PF에 추가하고 저장 설정·실행 규칙을 확인한 허용 범위는 C 출발지에서 A TCP5000·D TCP9000 두 규칙이다. C는 PF 설정을 직접 확인하지 않았다.

D PC의 n8n은 D의 확인 보고에 따라 `127.0.0.1:5678` 게시를 유지한다. 여기서 5678 비공개 유지는 D PC 기준이다. C→D TCP5678 규칙이나 D의 5678 외부 공개를 발표 준비로 추가하지 않는다. C에서 D의 편집기를 직접 조작해야 하는 요구가 생기면 웹훅 접근을 차단하는 프록시 구성을 별도 PR로 검토하고 시험과 분리된 구간에 적용한다. 현재 화면 공유·녹화안과 혼합해 이미 구현된 것으로 설명하지 않는다.

C PC에도 별도의 n8n 컨테이너가 있으며, C 보고상 `0.0.0.0:5678`로 게시돼 있다. 용도와 호스트 방화벽은 확인 중이므로 외부 접속 가능 여부는 미확인이다. C PC의 바인딩 변경은 컨테이너 재생성이 필요하다는 C 보고에 따라 시험 종료 후 별도 작업으로 다룬다. 이 문서 수정으로 C·D의 컨테이너나 방화벽 설정을 변경하지 않는다.

라이브 실패 시 먼저 입력을 중단하고 대상 상태를 확인한다. 사전 녹화로 전환할 때는 ‘사전 녹화, 촬영일/버전’을 명시하고 라이브 성공처럼 설명하지 않는다. 실패 상태가 남은 채 다음 시나리오를 실행하지 않는다.

## 담당별 8분 대본과 녹화 컷

공통 순서: **0~1분 문제/정상 기준 → 1~2분 보강 전 → 2~5분 보강 후 라이브 → 5~6분 티켓/ID/수치 → 6~7분 원복·정상 대조 → 7~8분 설치/운영 가치와 한계**. 긴 관측창은 사전 실측 자료로 보여주고, 짧은 라이브 구간과 구분한다. 5~10분 발표 안에 모든 장시간 정량 시험을 압축하지 않는다.

| 담당 | 이야기와 필수 화면 | 피해야 할 과장 |
| --- | --- | --- |
| A · S1/S4 | 계정 공격과 실패/성공 결합 → 차단/잠금·세션 처리 → 다른 정상 사용자 → 승인 해제. 두 시나리오의 티켓/원본 ID를 구분 | S4를 구현과 다른 ‘5번 실패 뒤 성공’ 순서 규칙으로 설명하지 않음 |
| B · S8/S10 | 웹/인증 신호 결합과 경계 신호 추가 → 앱 차단/S10 PF 차단 → 기존 연결 영향·정상 접근 → PF·앱 원복 | S8/S10의 공유 티켓을 독립 성공 두 건으로 부풀리지 않음 |
| C · S7 | 변조 전후 화면·동일 파일 FIM/접근 신호 → 복구/격리 → 기준 해시 일치·정상 페이지 → 티켓 | AR 전송 성공만으로 실제 복구 성공이라 하지 않음 |
| D · S12 | 정상 기준선 → 장애 구간 → 대응 → 공격 지속 중 정상 사용자 회복 → 티켓·승인 원복 | 부하를 꺼서 회복된 결과나 VPN health만으로 방어 효과를 주장하지 않음 |

각 담당은 정상 화면, 보강 전 증거, 보강 후 실행, 티켓/ID, 정상 대조, 원복의 6개 컷을 녹화한다. 시작에 회차/날짜/버전/실측 구분을 보이고 녹화 종료 후 영상·음성·글자 가독성을 재생 확인한다. 편집 컷 사이 대기시간을 없앴다면 실제 측정 시간은 원본 기록으로 제시한다.

발표 자료의 숫자는 해당 회차의 표본 수·분자/분모·시작/끝점을 함께 표시한다. 실측·합성·담당 보고를 구분한다. 현재 티켓의 탐지→효과 확인 시간을 서비스 전체 원복 시간으로 바꿔 설명하지 않는다.

## 수요일 종료 시 갖출 것

- 6개 시나리오 각각의 실제 티켓·입력/탐지/대응/효과/원복 증거와 ID 연결.
- 지원 환경·3개 저장소 버전·설정 예시·워크플로/규칙·설치/유지보수/백업 복구 절차.
- 다른 담당의 설치/재현 결과와 아직 지원하지 못한 범위.
- 개인 대본/영상 4개와 한 자리 전체 라이브 실행 순서.
- 보강 전후 수치/화면, 발표용 계정/접근 경로, 실패 시 중단·원복·녹화 전환 절차.

목요일은 리허설과 필수 결함 수정, 금요일은 같은 확정본으로 본발표한다. 인터페이스 확장은 기존 계약/자산·로그·대응 매핑을 설명하고, 미구현 어댑터나 임의 타 사이트 호환을 약속하지 않는다.
