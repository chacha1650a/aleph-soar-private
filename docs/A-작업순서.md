## 전체 흐름 한눈에 보기

```
[1 준비] → [2 기획서] → [3 케이스 설계] → [4 공통 기반: 포털 앱·차단 API]
                                              ↓
                  [5 환경 구축: VM·Graylog 연동] → [6 탐지·자동 대응]
                                                        ↓
                                        [7 검증: 3모드·보강 전후·원복] → [8 시연 준비]
```

**핵심 연결 고리 — 내가 만드는 신호가 끝까지 이어져야 합니다.**

```
Kali 공격(scripts/replay/replay.py)
  → 민원 포털(Flask) 로그인 시도 → 앱이 GELF 로그 송신 (rule, username, src_ip)
  → Graylog 수집·정규화 → 이벤트 정의 발동 (S1: login-bruteforce / S4: 실패 뒤 성공)
  → Webhook → n8n
  → S1: 112 출발지 차단(만료 없음, 사람이 해제) + 114 티켓
    S4: 111 계정 잠금 + 기존 세션 회수 + 114 티켓
  → 재시도로 실제 차단 확인 (S1: 같은 IP 새 요청 403 / S4: 계정 잠금 상태(관리자 화면 "잠김"), 기존 세션 거부)
  → 정상 사용자 영향 확인 (S1: 같은 계정의 다른 정상 출발지는 로그인 가능)
  → 해제(원복): S1 출발지 차단 해제 / S4 비밀번호 재설정 뒤 잠금 해제 → 사전 상태와 동일한지 확인
```

앞 단계가 막히면 뒤 단계를 시험할 수 없습니다. 그래서 **4(앱 로그) → 5(Graylog 도착) → 6(규칙·n8n)** 순서를 지킵니다.
