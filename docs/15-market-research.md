조사 기준일: 2026-10-15 (Asia/Seoul) · M01 · 공개 자료 조사 1차 · Claude 검토·Codex 재리뷰 반영 · 팀 검토·고객 검증·채택 전

Claude 수정 5건의 독립 확인과 추가 보완 근거는 [재리뷰 기록](16-market-research-rereview.md)에 있습니다.

대상은 [스마트팩토리 로드맵](14-smart-factory-roadmap.md)의 생산관리·협력사 포털과 가상 설비 데이터입니다. 이 문서는 주제의 필요성과 경쟁 환경을 평가하는 자료입니다. 구현·고객 인터뷰·제품 도입 시험 결과는 없습니다.

## 1. 조사 결론

**주제를 이어갈 근거는 있지만, 자동 탐지·차단 자체를 새로움으로 내세우기는 어렵습니다.** 기존 SOAR·XDR·접근 관리 제품이 이미 탐지 연계, 계정 통제, 세션 관리, 승인과 대응 결과 확인을 제공합니다.[S05], [S06], [S07], [S08], [S09], [S13]

우리 팀에 권하는 초점은 **“협력사 계정 대응 후 실제 접근 거부와 정상 업무·가상 수집의 유지, 승인된 업무 복귀를 한 사건의 증적으로 검증하는 실습 시스템”**입니다. 이는 시장 전체에 없는 기능이라는 주장이 아니라, 특정 포털과 업무 정책에 연결해 직접 재현할 캡스톤의 검증 범위입니다.

## 2. 우리가 속한 시장과 고객 가설

주요 비교 시장은 **보안 운영 자동화(SOAR), 계정 기반 탐지·대응(XDR/신원 보안), 특권·협력사 접근 관리(PAM/원격 접근)**입니다. 제조업은 적용 산업이고, MES·스마트팩토리 구축 시장 전체를 우리 제품의 시장으로 합산하지 않습니다.

아래 고객은 공개 자료에서 도출한 가설이며 실제 수요처를 확보한 상태가 아닙니다.

| 우선순위 | 고객 가설 | 사용자·도입 결정에 관여할 사람 | 확인할 문제 | 주요 대안 |
| --- | --- | --- | --- | --- |
| 1 | 자체 생산관리·협력사 웹 포털을 운영하는 중소·중견 제조사 | IT·보안 담당, 포털 담당, 생산·정비 업무 책임자 | 계정 잠금 뒤 기존 세션이 남는지, 정상 협력사 업무에 어떤 영향이 생기는지 확인하는 부담 | 기존 IAM/XDR, 수작업 대응·접근 시험 |
| 1 | 제조업 포털·MES 구축·유지보수 업체 | 서비스 운영자, 개발 책임자 | 고객별 계정·권한·복구 정책을 연결하고 증적을 남기는 반복 작업 | 자체 스크립트, 기존 SOAR 플레이북 |

첫 인터뷰는 회사 규모보다 **“외부 사용자 계정이 있고, 앱 자체 세션을 운영하며, 대응 후 접근 확인을 사람이 수행하는가”**를 기준으로 찾는 것이 좋습니다. 전담 보안 인력 부족이나 구매 예산은 아직 확인하지 않았습니다.

## 3. 수요와 시장 규모를 뒷받침하는 자료

### 국내 산업 규모: 배경 수치

과기정통부·KISIA의 2025년 정보보호산업 실태조사 발표에 따르면, **2024년 국내 정보보호산업 매출은 18조 5,945억 원**, 그중 **정보보안은 7조 1,244억 원으로 전년 대비 15.9% 증가**했습니다. 전체에는 물리보안도 포함됩니다. 기준 연도는 2024년이며 2026년 매출 전망으로 바꾸어 사용하지 않습니다.[S01]

이 수치는 보안 제품·서비스가 거래되는 산업의 배경입니다. SOAR 단독 규모, 국내 제조업 포털 보안 예산, 우리 팀의 매출 가능 규모를 뜻하지 않습니다. 현재 조사에서는 이 세부 시장의 검증 가능한 금액을 확보하지 못했습니다.

시장 규모를 추후 산정하려면 다음 입력이 필요합니다.

- 전체 대상: 외부 계정이 있는 제조업 포털 운영 사업장·운영사 수와 중복 제거 기준.
- 실제 제공 가능 범위: 연결 가능한 앱·인증 방식, 배치·지원 지역과 운영 인력.
- 초기 확보 가능 범위: 인터뷰·파일럿에 동의한 고객 수와 확인된 계약 단가.
- 연간 매출 가설: 확인된 도입 고객 수 × 검증된 연간 계약 단가. 초기 연결 비용은 반복 매출과 별도 계산.

공장 수·스마트공장 보급 수를 모두 유료 고객으로 간주하거나, 정보보안 매출에 임의 비율을 곱해 시장성을 확정하지 않습니다.

### 제조업의 계정·자료 접근 위험

Verizon의 **2026 DBIR 제조업 자료**(PDF 13~14쪽)를 직접 확인했습니다.[S02]

- 도난 자격 증명 사용의 **관여** 비율은 41%입니다. 취약점 악용 관여는 원문 14쪽 본문에서 41%, 13쪽 Figure 10에서 40%로 서로 달라 확정 인용하지 않습니다. 관여 비율은 상호 배타적이 아니므로 더하지 않습니다.
- **최초 침입 경로**는 취약점 악용 38%, 피싱 13%, 자격 증명 악용 11%입니다. 자격 증명은 침입 뒤 단계에서 자주 쓰이지만 주된 진입 경로는 아닙니다.
- 침해의 75%에 악성코드, 61%에 랜섬웨어가 관여했습니다.
- 제조업 침해의 **제3자 관여는 61%**입니다.
- 모두 글로벌 기여 데이터 기반이며 한국 제조업 전체의 피해율이 아닙니다.

표·본문·그림의 표본 범위를 함께 봅니다. 요약의 확인된 정보 유출은 2,713건이고, Figure 10의 action varieties는 n=2,417, Figure 11의 action types는 n=2,713입니다. 취약점 관여 수치의 차이를 반올림이나 표본 차이 때문이라고 임의 설명하지 않습니다. 최초 침입 경로의 요약표 수치와 자격 증명 관여 수치는 구분해 사용합니다.

2026 DBIR 공식 발표의 전체 산업 제3자 관여는 48%입니다. 발표는 2026년이지만 분석에 사용한 사건은 2025년 데이터입니다.[S03] 제조업 61%와 함께 외부 공급자 의존 위험의 배경이며, “협력사 포털 계정이 침해의 61%(또는 48%)를 일으킨다”는 뜻이 아닙니다.

**시사점(팀 해석):** 협력사 계정과 자료 접근은 침입 뒤 확산과 제3자 경로에 관련된 위협 흐름입니다. 다만 제조업의 주된 진입 경로는 취약점 악용이고 침해의 다수가 랜섬웨어이므로, 이 프로젝트가 제조업의 주요 위험 전반을 해결한다고 주장하지 않습니다. 발표에서는 “주 침입 경로 차단”이 아니라 “자격 증명이 악용된 뒤의 계정 대응과 업무 복귀 검증”으로 범위를 표현합니다.

### 업무 중단과 복구의 실제 사례

Asahi Group의 2026-02-18 공식 조사 발표에 따르면 2025-09-29 사고는 **랜섬웨어** 공격이었습니다. 대응 과정에서 네트워크를 끊고 데이터센터를 완전히 격리했으며, 데이터센터 시스템 전체를 정지해 업무 시스템에 접근할 수 없었습니다. 안전성을 확인한 시스템부터 단계적으로 복구·연결했고, 수주·출하 업무는 수작업으로 처리했습니다.[S04] 2026 DBIR 제조업 자료도 이 사건을 제조업 랜섬웨어 사례로 언급합니다.[S02]

**시사점(팀 해석):** 보안 조치의 효과와 업무 영향을 함께 기록하고 복귀 조건을 확인하는 일은 현실적인 운영 문제입니다. 다만 이 사건은 데이터센터 전체를 격리한 랜섬웨어 사고로, 우리 범위인 계정 단위 대응과 규모·성격이 다릅니다. 협력사 포털 계정 사고로 단정하거나 우리 방식으로 예방할 수 있었다고 해석하지 않습니다. 대규모 사고에는 광범위 격리가 필요할 수 있으므로 계정 단위 대응만으로 충분하다는 근거도 아닙니다.

### 특히 중요한 경쟁 해석

Microsoft 문서는 **앱이 발급한 세션 토큰을 Entra ID가 직접 취소할 수 없으며, 앱 자체 정책으로 접근을 회수해야 한다**고 설명합니다. 그러므로 계정 관리 시스템에서 조치가 성공해도 개별 앱의 접근 종료 시점과 조건은 따로 확인해야 합니다.[S05]

같은 문서는 해결 방법도 안내합니다. 앱 프로비저닝으로 사용자를 해제하고, 비활성 상태가 앱에 동기화되면 앱이 기존 세션을 폐기하도록 구성하며, CAE를 지원하는 앱은 토큰·세션을 취소할 수 있습니다.[S05] OpenID Foundation은 2025-09-02 SSF·CAEP·RISC 1.0을 최종 사양으로 승인했고, CAEP는 `session-revoked` 등 세션 변경 이벤트를 정의합니다.[S17], [S18]

따라서 “IdP 조치를 앱에 전달할 방법이 없다”는 설명은 부정확합니다. 전달·접근 회수 방법은 존재하며 실제 고객의 지원·구성·운영 상태는 별도 확인해야 합니다. 연구할 지점은 **앱이 이런 신호를 받아 실제로 세션을 폐기하는지, 동기화·전달 지연 동안 어떤 접근이 남는지 확인하는 것**입니다.

Entra CAE와 OpenID CAEP는 같은 구현이나 적용 범위를 뜻하지 않습니다. CAEP는 송신자·수신자 간 보안 이벤트 형식을 정의하며, `session-revoked` 이벤트 수신 자체가 우리 포털의 접근 종료나 최대 지연을 보증하지 않습니다. 내부 이벤트로 세션을 폐기·재시험하는 MVP와 SSF/CAEP 표준 구현·상호운용 검증을 구분합니다. 후자는 관련 보안 요구와 송수신 환경이 필요한 추가 후보이며, 이번 조사로 2주 필수 범위에 넣지 않습니다.[S05], [S18]

Cortex XSOAR에는 작업 결과를 조건 분기로 확인하는 공식 예제가 있습니다. Defender도 자동 조치·해제·예외를 제공합니다. 따라서 “기존 SOAR는 명령만 보내고 결과를 확인하지 못한다”, “자동 대응·복구를 우리가 최초로 구현한다”는 설명은 근거가 없습니다.[S06], [S08]

**제품 기능보다 고객별 연결과 검증이 연구할 지점이라는 판단**입니다. 실제 고객의 미충족 요구인지, 기존 제품 설정만으로 해결되는지는 아직 확인되지 않았습니다.

비교 범위의 한계도 있습니다. 국내 SOAR는 이글루·시큐레이어·안랩의 공개 자료만 확인했고, 국내 SOAR 시장 규모와 독립 점유율 통계는 확보하지 못했습니다. 2절에서 비교 시장으로 정한 특권·협력사 접근 관리(PAM/원격 접근)는 OT 설비 접근의 Claroty만 확인했습니다. 국내 PAM·접근제어 제품과 IT 협력사 원격 접근 제품은 비교하지 않았으며 다음 조사 대상입니다.

현재 Splunk 제품 페이지는 SOAR를 Enterprise Security에 통합된 기능으로 안내하면서 SOAR 구독 필요 조건도 명시합니다. 이는 별도 SOAR뿐 아니라 SIEM·대응을 묶은 플랫폼도 경쟁 대안임을 보여주는 사례입니다. 이를 전체 시장의 통합 완료나 기존 계약의 자동 변경으로 확대 해석하지 않습니다.[S09]

## 6. 캡스톤에서 검증할 차별점

제안 주제명: **“스마트팩토리 협력사 포털의 계정 대응 효과와 안전한 업무 복귀 검증”**.

설명 문장: 의심 계정의 자료 접근을 통제하고, 차단의 실제 효과·정상 업무와 가상 데이터 수집의 지속·승인된 복귀를 같은 사건에서 확인합니다.

| 주장할 가치 가설 | 직접 보여줄 결과 | 증거로 부족한 것 |
| --- | --- | --- |
| 계정 조치가 앱에서 실제로 적용됐는지 확인 | 신규 로그인과 기존 세션으로 보호 자료 접근을 각각 재시험 | 잠금 API의 성공 응답만 표시 |
| 대응 대상을 좁혀 정상 업무 영향을 확인 | 같은 IP의 정상 직원 요청 성공, 별도 수집 계정의 데이터 저장 | 전체 IP 차단 뒤 대상 접근만 확인 |
| 복귀가 재침입을 열지 않는지 확인 | 유출 가정 사례의 옛 비밀번호 거부, 옛 세션 거부, 새 인증 허용 | 잠금 플래그를 해제한 화면 |
| 재시도·권한 충돌에도 이력과 상태를 설명 | 동일 조치 재시도의 중복 부작용 방지, 후속 정상 변경 충돌 시 자동 복구 중단 | 티켓 생성 횟수만 확인 |
| 업무 영향과 보안 효과를 함께 설명 | 동일 시험 구간의 접근 성공·거부 결과와 가상 데이터 순번·저장 지연 | 생산량처럼 보이는 화면 애니메이션 |

이 항목은 [기존 로드맵](14-smart-factory-roadmap.md)의 검증 범위를 구체화한 제안입니다. 새 상용 플랫폼 전체를 개발할 계획이나 팀의 채택 결정이 아닙니다.

OT에서는 성능·신뢰성·안전을 함께 고려해야 한다는 NIST 지침을 배경으로 참고합니다. 2026-10-15 확인 시 Rev.3는 final이고 Rev.4는 초안 의견 수렴 중입니다. 우리 시험은 포털과 가상 데이터 수집에 한정하며 실제 PLC·공정 안전·생산 무중단을 입증하지 않습니다.[S16]

## 7. 비교 실험과 측정 지표 제안

기존 제품과 성능 경쟁을 주장하는 실험은 아닙니다. 같은 앱·입력·초기 상태에서 “조치 결과만 기록하는 기준 흐름”과 “접근·정상 업무·복귀를 확인하는 흐름”을 비교합니다. 확인 단계 외 조치 구현은 동일하게 유지하고 실패 주입 조건·정상 대조군도 동일하게 적용합니다.

| 지표 | 계산·기록 방법 | 해석 주의 |
| --- | --- | --- |
| 대응 기록과 실제 효과의 불일치 | 성공으로 기록됐지만 보호 자료 접근이 허용된 시험 건수 / 성공 기록 시험 건수 | 신규 인증·기존 세션·API 경로를 구분 |
| 실제 접근 차단까지 시간 | 조치 시작부터 최초 거부 관측까지, 이후 시험 구간의 지속 거부 함께 기록 | 주기적 검사 간격의 해상도와 시작 기준 명시 |
| 정상 업무 성공률 | 대응 전·중·후 정상 요청 성공 수 / 정상 요청 시도 수 | 같은 IP·다른 계정 대조, 오류 사유 구분 |
| 가상 데이터 누락·지연 | 예정 고유 순번과 저장된 고유 순번 대조, 발생·저장 시각 차이 | 재시도·중복·시험 종료 후 도착 구분 |
| 복귀 검증 | 옛 세션·옛 비밀번호 거부와 새 인증·허용 자료 접근 성공을 각각 판정 | 비밀번호 유출은 명시한 시나리오 가정 |
| 중복·충돌 처리 | 동일 operation_id 재시도의 상태 변화·이력, 정상 권한 변경 충돌 판정 | 동일 조치와 새로운 재잠금 구분 |

횟수·허용 지연·정상 업무 성공률 목표는 장비와 평가 요건을 확인한 뒤 팀이 정합니다. 목표를 먼저 기록하고, 구현 후 결과·실패·관측 한계를 함께 남깁니다. 현재 측정값은 없습니다.

## 8. 실제 고객 검증과 사업화 가설

사업화한다면 기존 보안 도구에 연결하는 **포털별 대응·검증 어댑터와 플레이북 구축·유지보수**를 먼저 검토할 수 있습니다. 초기 연결 비용과 지속 유지보수·증적 관리 비용을 나누는 가설입니다. 판매 가격·지불 의사·도입 고객은 미확인입니다.

가장 가까운 인터뷰 대상은 제조업 포털 운영자, 포털/MES 유지보수 담당, 제조 고객을 관리하는 관제 담당입니다. 실제 연락·메시지 발송은 하지 않았습니다. 팀 안에서 역할을 가정한 답변은 고객 인터뷰와 구분합니다.

| 물어볼 질문 | 남길 근거 |
| --- | --- |
| 가장 최근 외부 계정·권한 문제에서 무슨 일이 있었나? | 익명화한 사건 시점·접근 경로·업무 영향. 일반적 걱정과 실제 경험 구분 |
| 계정 잠금 후 어떤 화면·세션·API를 누가 확인하나? | 현재 절차, 담당 역할, 확인 시간과 누락 사례 |
| 기존 IAM·EDR·SOAR로 어디까지 해결되나? | 제품·연결 상태·추가 설정 가능성. 미도입 사유와 기술 제약 분리 |
| 자동 차단이 영향을 주면 안 되는 업무·계정은 무엇인가? | 정상 직원·협력사·수집 서비스의 범위, 승인 책임자 |
| 누가 어떤 근거로 잠금을 풀고 권한을 되돌리나? | 신원 확인 경로, 권한 기준 이력, 충돌 처리 |
| 이 문제를 해결하려고 시간·비용을 지출한 적이 있나? | 현재 투입 시간·견적·예산 주체. 추상적 호감과 구매 의사 구분 |
| 익명·합성 데이터로 파일럿을 할 수 있나? | 담당자 동의, 연결 API 제공 가능성, 성공 판정 조건 |

**착수 판단 제안:** 실제 절차에서 별도 확인 부담이 존재하고, 시험 가능한 앱 연결과 업무 정책을 확보하면 좁은 범위의 MVP를 진행합니다. 기존 설정만으로 충분하다면 신규 제품 주장보다 해당 설정의 재현·검증 과제로 조정합니다. 고객 접근이 어렵다면 캡스톤 실험으로는 진행할 수 있지만 고객 수요 검증 완료로 표시하지 않습니다.

## 9. 팀 회의에 가져갈 결정

1. 서비스 배경을 유지하고, 발표의 중심을 계정 대응 효과·업무 복귀 검증에 둘지.
2. 협력사의 담당 라인 밖 자료 접근 등 최소 업무 정책과 정상 대조 시나리오를 무엇으로 할지.
3. 첫 고객 검증을 제조사 운영자·구축 업체·관제 담당 중 누구에게 할지.
4. 4계층 실제 연결·필수 제품·샘플 인정·제출 기한을 강사에게 확인한 결과.
5. 기존 [P01](../orchestration/workplan.json)에 시장 조사 결과를 어떻게 반영할지. 이번 조사로 P01을 완료 처리하지 않음.

발표에 사용할 수 있는 서술은 “보안 산업과 제조업의 계정 위험 자료를 근거로, 특정 협력사 포털의 대응·업무 복귀를 검증한다”입니다. 시장 점유율, 국내 제조업 구매 수요, 기존 제품 대비 비용·성능 우위, 실제 생산 무중단은 이번 자료로 입증되지 않았습니다.
