# 탐지·대응 시나리오 목록

아래 값은 **자료 167·168의 참고 정의**이며, 우리 팀의 구현·검증 결과가 아닙니다. 모든 시나리오는 미구현·미검증 상태입니다. `card()`는 원본의 서로 다른 값 개수에 대한 표기입니다.

| ID | 참고 시나리오 | 참고 신호 | 참고 조건 | 시간창 | 묶기 | 대응 후보 |
| --- | --- | --- | --- | --- | --- | --- |
| S1 | 저속 브루트포스 | `login-bruteforce` | `count()>8` | 30분 | username | 계정 잠금 |
| S2 | 심야 로그인 성공 | `night_login` | `count()>0` | 5분 | username | 티켓 |
| S3 | 한 계정 다중 출발지 | `login-success` | `card(src_ip)>1` | 5분 | username | 티켓 |
| S4 | 실패 뒤 로그인 성공 | `login-*` | `card(outcome)>1` 및 `count()>5` | 10분 | username | 잠금·티켓 |
| S5 | 차단 후 재시도 | `blocked-retry` | `count()>19` | 10분 | src_ip | 티켓 |
| S6 | 관리자 API 인증 실패 급증 | `admin-auth-fail` | `count()>9` | 5분 | src_ip | IP 차단 |
| S7 | 파일 생성 후 웹 접근 | `signal_kind` | `card(signal_kind)>1` | 10분 | 원본은 없음 | 티켓 |
| S8 | 웹 탐색과 인증 실패 연계 | `web-scan`과 인증 신호 | `card(rule)>1` | 15분 | src_ip | IP 차단·티켓 |
| S9 | 권한 이벤트와 민감 조회 | `priv-unauthorized-admin`, `gold-access` | `card(rule)>1` | 30분 | username | 권한 회수·티켓 |
| S10 | 여러 계층의 신호 연계 | pfSense·웹·인증 | `card(rule)>2` | 15분 | src_ip | IP 차단·티켓·경계 대응 |

원본의 대응 봇 번호는 108=권한 회수, 111=계정 잠금, 112=IP 차단, 113=통지, 114=티켓입니다. 번호에 대응하는 실제 워크플로는 이 저장소에 아직 없습니다.

## 설계상 확인할 의미

- 서로 다른 결과·규칙의 개수만으로는 ‘실패 뒤 성공’ 같은 시간 순서를 증명할 수 없습니다. S4·S8·S9의 순서 조건과 상관 키를 별도로 정합니다.
- S7은 파일과 접근의 대상 자산·경로를 연결하는 기준이 필요합니다. 전역 집계로 다른 사건이 합쳐지는지 확인합니다.
- S10은 규칙 개수뿐 아니라 실제로 서로 다른 계층에서 왔는지 확인해야 합니다.
- S2의 심야 기준 시간대, S3의 정상 다중 IP 이용, NAT·프록시 환경의 출발지 해석을 정합니다.
- MySQL 감사 신호는 원본에서도 설계 항목입니다. 팀에서 구현한 뒤 별도 증적으로 검증합니다.

## 시나리오별 검증 기록 틀

```text
시나리오 ID / 담당 / 검증 일시 / 코드·설정 커밋:
대상 랩과 사전 상태:
입력 이벤트, 상관 키와 시간 순서:
정상·임계 미만 입력의 예상 결과:
임계 충족 입력의 예상 결과:
실제 로그 / 탐지 이벤트 / 대응 상태 / 티켓:
중복·재시도·다른 사용자 또는 자산이 섞일 때의 결과:
원복 절차와 원복 후 상태:
증적 파일 경로 / 판정 / 남은 문제:
```

먼저 합성 이벤트와 무해한 테스트 파일로 흐름을 검증하는 안을 사용합니다. 실제 장비와 연결하는 절차는 팀 환경과 범위를 확정한 뒤 작성합니다.
