### 한 명령으로 소스 묶음 확인

파일 담당 B·Codex가 준비한 `tools/check_s1_candidate.py`는 이 카드의 **capstone 로컬 소스 묶음**만 검사한다. 기존 lab_check.py의 시험 증적 수집/대조와 별개이며 포털 체크아웃·실제 서비스/이미지·게시본·자격 증명을 직접 조회하지 않는다. 네트워크·Git 실행·파일 쓰기·운영 적용 기능이 없다.

```powershell
python tools/check_s1_candidate.py
```

검사 범위는 n8n 전체 파일 목록/17개 해시·C 코드6개 해시, S1에서 실제 참조하는 워크플로의 전체 연결과 묶음 목록 일치, 미해결/동적 참조·순환·중복 ID·S1 Webhook 누락이다. 인증 선언 분류는 기존 Webhook 검사기를 재사용하며 S1 연결 안의 수신 노드만 집계한다. 비밀값·파일명/ID/본문/경로·파싱 원문은 출력하지 않는다. 다른 소스 사본은 명시한 `--root`, 후속 후보 묶음은 해당 루트 안의 `--packet` 상대 경로로 읽는다. 묶음 내용으로 임의 파일 경로를 선택할 수 없다.

| 종료 | 해석 |
| --- | --- |
| 0 | `SOURCE_MATCH_RUNTIME_PENDING`: 로컬 묶음 일치. 실제 배포/인증/실측은 미확인 |

현재 예상 결과는 소스 오류0·S1 의존성4개·수신 Webhook1개·수신 인증 발견1개다. 전체 Webhook 검사기의10건과 검사 범위가 다르다. `runtime_verified:false`, `deployment_ready:false`와 실제 배포/인증/효과/원복의 pending 목록은 항상 유지한다. 종료0이나 auth_findings=0도 실행 준비 완료/게시 승인으로 읽지 않는다. 이 검사는 메타데이터의 발행자 신원을 인증하는 서명 검증이 아니다. 10/27에는 점검기 신규 회귀25개·기존 인증 검사35개와 전체505 passed/1skip을 확인했다. 10/28 최신 통합 검증은531 passed/1 Windows symlink skip이다. 과거 묶음의480개 결과는 원래 후보9e2ca45의 검증 이력으로 보존한다.

수동 대조가 필요하면 capstone 루트에서 가져온 **원본 파일**을 다음처럼 읽기 전용으로 대조한다.

```powershell
git status --short
git rev-parse HEAD
$s1Versions = Get-Content -LiteralPath 'docs/capstone/evidence/s1-candidate-20261030/versions.json' -Raw | ConvertFrom-Json
foreach ($s1File in $s1Versions.n8n_exports) {
    $s1Hash = (Get-FileHash -LiteralPath $s1File.path -Algorithm SHA256 -ErrorAction Stop).Hash.ToLowerInvariant()
    if ($s1Hash -ne $s1File.sha256) { throw "S1 source bundle mismatch: $($s1File.path)" }
}
'Candidate source JSON hashes match; runtime not verified.'
```

실제 n8n 재내보내기는 ID/자격 증명 참조/설정·순서가 달라질 수 있다. 가져온 원본 해시와 게시본의 별도 해시/버전을 기록하고 변경 이유를 D가 로컬에서 대조한다. 게시본 원문/키를 저장소로 올리지 않는다. 소스 파일 일치만으로 C 이미지·D 게시본까지 일치한다고 보지 않는다.

집의 추가 확인으로 [실제 Flask 포털·C 임시 DB 연결 리허설](s1-portal-rehearsal-1027.md)도 실행했다. 차단/정상 로그인/해제와 유실/실패 경계의 검사이며 실제 Graylog/n8n/망/운영 MySQL/학원 효과 시험을 대신하지 않는다.

## 병렬 준비 · 각자 1회 회신

공통: `준비됨 / 작업 필요 / 미확인`, 확인 버전·근거·남은 조건을 함께 적는다. 자기 범위만 확인하며 미회신을 준비됨으로 보지 않는다.

- **A:** 포털 health와 실제 DB/로그인, 공격·정상 계정 상태, 차단 잔존 여부·동일 키 응답, 배포 버전. 원복 후 확인할 정상 동작 고정.
- **B:** 실제 출발지·경로·정상 대조 준비, PF 차단 없음, 전송/수집 상태, 다른 측정과 영향 구간 분리. PF를 동시에 차단하지 않는다.
- **C:** 수정 서비스·시험 DB 식별, 키 없음/틀림401·올바른 키 조회200, 자원 조회/원복 뒤 새 주기·멱등/충돌/재시작 보존의 로컬 연결 확인. 운영 데이터와 합성 연결 시험 분리.
- **D:** [수신 인증 인수](n8n-webhook-audit-1027.md)의 격리 거부/허용과 하위 호출0 확인, 실제 가져온 S1 정의/알림·n8n 입력 매핑, 포털/C 별도 자격 증명, 401/실패/형식 오류 보류, 기록 실패/terminal 응답 후 호출 중단, 실행 ID/원시 응답 보존 위치. 수동 입력으로 알림 연결을 대체하면 별도 준비 시험으로 기록.

A↔D 포털, B↔D 입력/정상 경로, C↔D 티켓을 직접 대조한다. 관련 준비가 맞으면 본 측정을 시작하며 본 입력을 자동 재전송하지 않는다. 보강 전 S1은 10/22 기존 증적을 재사용한다. B 등 다른 케이스의 보강 전 동결 중에는 영향받는 S1 정의/대응을 켜지 않는다.

## 담당별 첫 확인 · 설정 변경 전에

A는 확인된 포털 URL을 사용해 정상 출발지에서 health를 읽고 `{success:true,data:{status:"ok",...}}` 및 DB 정상 여부를 확인한다. URL 입력에 키를 넣지 않는다.

```powershell
$portalBase = (Read-Host 'A가 확인한 실제 포털 기준 URL').TrimEnd('/')
```

```powershell
docker inspect ticket-store --format '{{.Image}}'
docker port ticket-store
docker inspect ticket-store --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}} {{.Destination}}{{end}}{{end}}'
docker exec ticket-store python -c "import pathlib,hashlib,json; names=('api_n8n.py','core.py','db.py','app.py','dashboard.py','validate.py'); print(json.dumps({n:hashlib.sha256(pathlib.Path('/app/ticket_store',n).read_bytes()).hexdigest() for n in names},sort_keys=True))"
```

마지막 결과를 버전 묶음의 ticket_source_sha256와 대조한다. Dockerfile의 `/app/ticket_store` 기준이며 설정이 다르면 경로부터 확인한다. 코드6개 해시만으로 모든 이미지/의존성/배포를 검증했다고 보지 않는다. 이미지 ID·빌드 출처·DB 마운트와 함께 기록한다. 환경 전체나 .env를 출력하지 않는다. C 대시보드는 C PC loopback을 유지하며 D의 인증 API는 기존 경로/키를 사용한다.

D는 S1의 실제 활성 집계 키(username+src_ip), count()>8·관측창/주기·grace, 401과429의 구분을 화면에서 확정한다. 참고 시나리오 docs/03의 옛 대응 후보(계정 잠금)를 이번 S1 출발지 IP 차단과 섞지 않는다. haedam-40/50의 인증·권한과 독립 근거가 확인되지 않았다면 그 Webhook으로 effect/해제를 대신 시험하지 않는다. 검토된 담당 경로를 사용하고 자동 해제 보류를 유지한다.

## 실행 순서

1. 정상 기준선: 공격 시험 출발지와 별도 정상 출발지의 허용 접근·로그인을 확인한다. 기존 차단·불명확한 티켓/원복 상태가 있으면 시작하지 않는다.
2. 사전 API 시험이 필요하면 별도 ID로 D가 포털 block→조회→같은 키 재전송→unblock을 수행하고, A/B가 실제 403/정상 접근/해제 후 정상 접근을 확인한다. C 기록도 해당 시험으로 분리한다.
3. 본 입력: 카드에 고정한 S1 입력을 한 번 실행한다. A는 원본 event_id/401 수, B는 실제 입력·출발지·시각을 기록한다.
4. D는 원문 도착과 정규화를 별도 대조하고 Graylog 이벤트 생성·알림·실제 n8n 실행·포털 HTTP 응답을 확인한다. condition_met_at / Graylog detected_at / n8n received_at을 구분한다. 없거나 정의되지 않은 시간은 null/미확인이다.
5. C는 해당 티켓의 detected/applied와 자원 조회를 DB로 대조한다(아래 쿼리는 지정 티켓의 읽기 전용 확인). A/B는 같은 출발지 403 IP_BLOCKED와 별도 정상 출발지의 실제 로그인을 확인한다. HTTP200/목록 반영만으로 effect를 true로 기록하지 않는다.
6. 독립 효과 근거가 맞으면 D가 C effect를 기록한다. 원복 전에 자원별 모든 활성 티켓과 실제 동시 작업이 없는지 대조한다. 다른 소유자·불확실한 실행이 있으면 원복을 보류한다.
7. D의 검토된 포털 API로 수동 unblock하고 실제 목록 부재와 공격 시험 출발지 재접근·정상 사용자 로그인을 확인한다. C released 및 마지막 활성 조치 없음/restored를 대조한다. 검증 후 사람이 close한다. 새 공격 주기는 새 이벤트·새 티켓·새 요청 키다.

### C의 해당 티켓 DB 대조

C가 실제 DB 경로가 compose의 `/data/tickets.db`와 같은지 먼저 확인한다. 다른 시험/운영 DB와 섞지 않는다. 아래는 **읽기 전용 연결**이며 파일이 없으면 새 DB를 만들지 않고 실패한다.

```powershell
$trialTicket = Read-Host '이 시험에서 실제 발급된 ticket_id'
docker exec ticket-store python -c "import sqlite3,sys; c=sqlite3.connect('file:/data/tickets.db?mode=ro',uri=True); print(c.execute('SELECT ticket_id,status,seat FROM tickets WHERE ticket_id=?',(sys.argv[1],)).fetchone()); print(c.execute('SELECT bot,via,action,result,applied_verified,effect_verified,duplicate FROM actions WHERE ticket_id=? ORDER BY id',(sys.argv[1],)).fetchall())" $trialTicket
```

행 존재/결과·적용 확인/효과 확인을 별개로 읽는다. missing/오류는0건이나 준비 완료가 아니다. DB 조회는 실제 차단/정상 사용자/원복 효과의 독립 확인을 대신하지 않는다.

## 중단과 최종 회신

**정상 사용자 오차단·예상 밖 조치·비밀값 노출은 즉시 중단한다.** 일반 막힘은 오류를 즉시 알리고 해결되지 않으면20분 안에 `시험 ID·버전·시각 / 마지막 성공 / 기대 / 실제 비식별 응답·로그 / 필요한 도움`을 묶는다.

조회 실패·정의/알림 미연결·필드 불일치·기록 실패·대상 효과 불명·다른 소유자 발견 시 마지막 확인 단계에서 중단한다. 대상 요청 키/현재 상태를 보존하고 DB·예약/영수증을 지워 재시도하지 않는다. 대상 호출 성공 후 기록 실패는 대상 재호출이 아니라 기록/상태 대조부터 한다.

A 원본/앱·DB, B 입력/경계, C 티켓/DB, D 수신·정규화·탐지/n8n을 병렬 대조해 각자 최종 회신을 1회 남긴다. 시험 ID·관측창·event_id·Graylog 이벤트 ID·n8n 실행 ID·ticket_id·효과·정상 대조·원복·미검증·다음 행동을 함께 적는다. 최신 요약은 기존 편집 담당 A가 PROGRESS에 한 번 반영한다.

완료 기준: **실제 로그→탐지→n8n 실제 호출→대상 차단→티켓→독립 효과/정상 대조→원복 후 정상 동작**. dry_run·수동 webhook·보강 전 관측·단순 연결 성공은 각각 별도 결과다. 한 번 완주한 뒤 정상·경계·보강 후 반복 계획을 수행한다.
