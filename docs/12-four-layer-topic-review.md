# 4계층 필수 가정의 주제 검토 · Claude 인수인계

상태: Claude 검토 대기 · 2026-10-15 · 팀 합의 전

사용자가 요청한 것은 **4계층이 필수라는 가정에서 팀원 제안을 검토**하는 것입니다. 수업의 실제 필수 요건이 확인되었다는 뜻은 아닙니다. [팀원 원문과 Claude 메모](11-team-feedback.md)는 그대로 보존하고, 이 문서에 Codex의 추가 검토를 기록합니다. 최종 결정은 [주제 결정 기록](07-topic-decision.md)에 남깁니다.

## 제안

**A(쇼핑몰 관리자 계정 보호)를 서비스 배경으로 삼고, B(자료 접근 탐지)와 G(대응·복구 검증)를 핵심 기능으로 넣는 방향**을 유지합니다. H는 별도 훈련 UI 대신 시연을 반복하는 작은 스크립트로 제한합니다. 쇼핑몰은 관리자 로그인·권한 변경·합성 고객 자료 조회에 집중하며 결제·배송·상품 관리 전체를 구현하지 않습니다.

4계층 실장이 필수라면 엣지·네트워크와 DB 직접 감사는 선택 확장에서 필수 검증 범위로 올려야 합니다. 단, 평가가 요구하는 것이 실제 제어·수집인지, 샘플 수집까지 허용하는지는 먼저 확인해야 합니다. 특정 제품 도입은 아직 확정하지 않습니다.

## 4계층 최소 인수 기준 제안

참고 자료의 엣지–네트워크–앱–데이터 구분을 사용합니다. 수집·관제·자동화는 계층을 연결하는 공통 기능입니다.

| 계층 | 최소 구성 제안 | 완료를 판단할 실행 증거 |
| --- | --- | --- |
| 엣지 | WAF 규칙 1개와 보안 이벤트 수집 | 통제된 요청의 허용·차단 결과, 해당 규칙·시각·대상과 연결되는 로그 |
| 네트워크 | 방화벽으로 앱·DB 접근 경로 제한 | 허용 경로의 연결 성공, 금지 경로의 연결 실패와 방화벽 로그 |
| 앱 | 관리자 인증·권한 검사·계정 잠금 | 정상 접근 성공, 잠금 후 신규 로그인과 기존 세션의 자료 접근 거부 |
| 데이터 | DB 최소 권한과 DB 측 감사 수집 | 허용 작업 성공, 금지 작업 거부, 선택한 감사 방식으로 수집한 DB 측 기록 |

표의 항목은 구현 결과가 아닌 인수 기준 제안입니다. WAF 샘플 재생은 수집 경로 검증으로 표시하며 실제 WAF 차단으로 기록하지 않습니다. 앱의 `data.read`도 DB 직접 감사와 구분합니다. DB 로그에는 비밀번호·원문 고객 자료를 보관하지 않는 방식을 설계합니다.

WAF에서 차단된 요청은 앱에 도달하지 않습니다. 따라서 계층별 차단 시험과 앱까지 허용된 계정 침해 시나리오를 구분합니다. 모든 로그를 IP만 같다는 이유로 한 사건에 합치지 않고, 요청 식별자·시각·자산·계정 등 실제 확보한 연결 근거를 표시합니다. 확보하지 못한 연결은 추정으로 표시합니다.

## 통합 시연과 범위

1. 정상 관리자 로그인과 허용된 합성 자료 조회가 성공합니다.
2. 통제된 계정에서 반복 로그인 실패 → 성공 → 테스트 권한 변경 → 제한 자료 조회를 발생시킵니다.
3. 시간 순서를 확인한 규칙이 사건을 만들고 근거와 타임라인을 보여줍니다.
4. 계정을 잠근 뒤 신규 로그인과 이미 발급된 세션의 자료 접근이 모두 거부되는지 확인합니다.
5. 사전 상태를 기준으로 잠금 해제와 필요한 권한 복구를 수행하고, 정상 업무 복귀를 확인합니다. 원래부터 허용되지 않던 권한은 부여하지 않습니다.
6. 별도의 엣지·네트워크·DB 제어 시험 결과를 증적으로 제시합니다.

B는 자료 조회 규칙 1개부터 시작하고 내보내기는 보류할 수 있습니다. G는 조치 요청·실행 결과·실제 효과 검증·원복 결과를 구분합니다. 재시도는 한도를 두고, 중복 실행의 부작용과 실패 시 중단 조건을 설계합니다. 모든 계층의 자동 차단을 MVP로 요구하지 않고, 우선 앱 계정 잠금 한 경로를 끝까지 검증합니다.

## 현재 스켈레톤과 연결할 때의 보완점

- [이벤트 계약](../contracts/event.schema.json)은 `username`·`src_ip`가 필수이고 이벤트 종류가 앱 이벤트 4종뿐입니다. 계정이나 원본 클라이언트 IP를 확보하지 못한 인프라 로그를 위한 출처별 필드·이벤트 종류·누락 처리 규칙이 필요합니다. 가짜 사용자명을 채워 넣지 않습니다.
- 프록시 뒤의 네트워크 로그에서 보이는 IP가 최종 사용자 IP와 다를 수 있습니다. 신뢰할 수 있는 프록시 경계와 식별자 전달 방식을 먼저 확인합니다.
- [사건 계약](../contracts/incident.schema.json)의 단일 `response_state`만으로는 조치 성공과 실제 효과 확인을 구분하기 어렵습니다. 검증 결과·시도 횟수·사전 상태 참조 등은 계약 변경 때 소비자와 함께 설계합니다.
- 기존 Claude 메모의 “같은 `event_id`면 중복 확인에 걸린다”는 부분은 **향후 구현할 중복 제거 정책**으로 읽어야 합니다. 현재 앱은 시작 화면과 상태 API뿐이며 수집·중복 제거는 미구현입니다. 사건 내 `event_ids`의 중복 금지 스키마와 재수집 중복 제거는 별개입니다.
- H는 새 실행마다 실행 식별자와 이벤트 ID를 발급하고 테스트 상태를 초기화합니다. 같은 ID를 의도적으로 다시 보내는 중복 검증 사례는 별도로 유지합니다.

이 PR은 문서 검토만 담습니다. 스키마·실행 코드·공식 요건·주제 선택을 변경하지 않습니다.

## 4인·2주 진행 제안

담당자 배정은 아직 하지 않습니다. 한 명당 한 계층을 독립 구축하는 방식보다 연결 지점을 포함한 작업 묶음을 제안합니다.

| 작업 묶음 | 주 산출물 |
| --- | --- |
| 인프라·수집 | 엣지·네트워크 제어, 로그 수집, 재현 가능한 환경 |
| 앱·데이터 | 인증·권한·조회·잠금 API, DB 권한·감사, 이벤트 생성 |
| 탐지·대응 | 상관 규칙, 사건 생성, 잠금·효과 확인·원복 흐름 |
| 관제·통합 검증 | 계약 예시 기반 화면, 정상·의심·실패 대조 시험, 증적·발표 |

공통 계약과 통합은 네 명이 함께 검토합니다. AI 도구 보유 수로 역할이나 역량을 단정하지 않습니다.

- 1~2일: 평가 요건·장비·최종 주제 확인, 필수 제품과 감사 방식의 작은 실행 시험, 공통 계약 합의.
- 3~4일: 실제 앱 이벤트 → 규칙 1개 → 사건 → 잠금 → 실제 접근 거부 확인의 첫 통합. 엣지·네트워크·DB 수집은 별도로 병렬 검증.
- 5~8일: 계층별 제어 증거와 타임라인, 자료 조회 규칙, 복구 경로 연결.
- 9~11일: 정상·중복·지연·대응 실패·기존 세션 접근을 검증하고 범위 고정.
- 12~14일: 팀원 환경 재현, 결함 수정, 증적과 발표 준비.

첫 통합이나 필수 계층 시험이 지연되면 H UI·내보내기·추가 규칙을 먼저 줄입니다. 필수 계층을 샘플로 바꾸고 실장 완료로 표시하지 않습니다.
