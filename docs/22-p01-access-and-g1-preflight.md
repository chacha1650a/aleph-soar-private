## 2. 업체·객체 권한표 초안

초기 합성 데이터는 업체 A/B, 자산 A/B, 각 업체의 외주 계정, 운영자, 보안 담당자로 제한한다. 여기서 ‘자기 작업’은 우선 **자기 계정이 신청한 작업**으로 제안한다. 같은 업체 동료의 작업까지 공유할지는 팀 결정 항목이며 그 전에는 허용하지 않는 안이다.

| 행위 | 외주 A | 외주 B | 업무 운영자 | 보안 담당자 |
| --- | --- | --- | --- | --- |
| 작업 신청 | 현재 담당 자산 A의 `health_check` | 현재 담당 자산 B의 `health_check` | 외주 계정으로 별도 신청 | 외주 계정으로 별도 신청 |
| 작업 목록·상세 | 자기 요청만 | 자기 요청만 | 관리 범위의 요청·승인 정보 | 사건과 연결된 최소 메타데이터 |
| 점검 결과 조회 | 자기 요청 + 승인 유효 + 계정 활성 | 같은 조건 | 업무상 승인된 관리 범위 | 조사 권한이 따로 있을 때만 |
| 승인·반려 | 거부 | 거부 | 담당 범위·자산·기간 확인 후 허용 | 업무 운영자 역할이 따로 있을 때만 |
| 다른 업체 자료 조회 | 거부 | 거부 | 관리 범위가 부여된 경우만 | 보안 역할만으로 일반 조회 허용하지 않음 |
| 업체·자산 할당 변경 | 거부 | 거부 | 별도 관리 권한·이력 필요 | 보안 조치로 임의 추가 금지 |
| 사건·원본 증적 조회 | 거부 | 거부 | 업무 화면의 필요 정보만 | 사건 범위·보관 권한에 따라 허용 |
| 계정 회수·재시험·복귀 승인 | 거부 | 거부 | 거부 | 대상·근거·별도 승인 행위 기록 후 허용 |

사람이 여러 역할을 맡는 것과 한 요청에 모든 역할을 허용하는 것은 구분한다. 업무 승인·보안 대응 승인·복귀 승인은 각각 별도 이력이다. 독립된 2인 승인이 필요한지는 팀 정책으로 결정하며 한 사람의 복수 계정을 2인 승인으로 표시하지 않는다.

구현할 때 다음 경계를 계약·소비자·테스트에 같이 반영한다.

- 업체·담당 자산·신청자는 서버의 현재 권한과 인증 주체로 결정한다. 클라이언트가 보낸 업체 ID를 권한 근거로 쓰지 않는다.
- 목록 필터와 상세·결과 조회에 같은 객체 검사를 적용한다. UI에서 링크를 숨긴 것만으로 접근을 거부했다고 판정하지 않는다.
- 타 업체 객체의 존재를 응답으로 드러낼지, 인증/권한/객체 오류를 어떤 HTTP 상태·본문으로 통일할지는 P01 계약 검토에서 정한다. 아직 새 API 응답을 구현하지 않았다.
- 고정 합성 점검 실행자는 서비스 주체다. 임의 명령을 받지 않고 유효한 승인·계정 상태·작업 ID를 확인한다. DB 설정 계정과 분리한다.
- n8n 호출 권한은 내부 경로와 인증된 제한 조치로 설계한다. 외주 세션·사용자 입력 SQL·임의 대상 변경을 관리 권한으로 받아들이지 않는다.

## 3. G1 시험 카드

공통 선행 조건은 실행 위치·대상 소유·관리 접근·담당자 확인, 기존 서비스 용도 구분, 사용할 버전/이미지 digest와 배치 기록이다. IP·포트는 실제 충돌·라우팅을 확인한 뒤 정한다. 아래 시험은 준비 상태이며 아직 실행하지 않았다.

| 순서·ID | 최소 실행과 실패 대조 | 필요한 실제 증거 | 담당 영역 |
| --- | --- | --- | --- |
| 1 · G1-NET | 선택 배치의 허용 연결 확인 → 해당 규칙 제거 후 새 연결 거부 → 기존 연결과 대상 state 회수 시험 분리. 다른 경로의 앱/DB 직접 접근도 대조 | 인터페이스·서브넷·경로, pfSense 규칙/로그·상태, 클라이언트 결과, B 연결 영향 | 망·엣지 |
| 2 · G1-DB | 선택 이미지의 감사 플러그인 확인 → 합성 허용 SELECT·권한 거부 SELECT·없는 테이블 질의 → QUERY/TABLE·클라이언트 결과 비교 → 재시작 유지 | 버전·필터·권한 범위, 원본 감사 줄·출처 키·결과 코드, 별도 연결의 최종 상태 | 업무 앱·DB |
| 3 · G1-WAF | 정상 A/B 요청 → 선택 CRS 규칙의 통제 요청 → 차단 결과·거래 ID 확인. 외부 제공 ID 덮어쓰기와 정상 백엔드 대조 | 엔진 모드·실제 응답, 결정/기여 규칙·점수, WAF 원본, 독립 백엔드 관측·수집 상태 | 망·엣지 + 앱 |
| 4 · G1-LOG | 각 출처의 합성 표식을 원본/중앙에서 대조 → 전달 단절·회전·재전송 입력 → 공백·지연·중복 표시 | 출처별 예정/발생/수신 표식, 시간창·누락·중복 결과, 재연결 이후 상태 | 각 소스 담당 + 중앙 수집 |
| 5 · G1-LINK | DB 연결의 독점 임대·순차 재사용·동시 요청·예외·재시작에서 요청 연결 시험 | 앱 요청/작업 키, DB 기동·연결·질의 키, 표식 구간. 유일하지 않으면 추정/연결 불가 | 업무 앱·DB + 탐지 |
| 6 · G1-HOST | 선택 Linux 호스트의 전용 시험 파일 변경·원복, Wazuh 경보와 중앙 전달 대조 | 호스트/에이전트·경로·전후 해시·원본 경보·수집 시각 | 호스트 소스 + 중앙 수집 |

G1-NET의 실제 라우팅을 확인하기 전 Docker bridge 분리만으로 pfSense 시험을 통과시키지 않는다. 선택 배치가 WAF–앱 경계를 제외하면 검증 범위에도 명시한다. 기존 컨테이너의 재시작이나 DB 계정 변경은 시험 대상과 분리·원복 방식을 정한 뒤 수행한다.

G1-DB의 거부 로그가 없으면 권한·플러그인·필터·실제 버전을 진단한다. 클라이언트 오류만으로 감사 통과 처리하지 않는다. 감사에 자격 증명 변경 SQL이나 민감 리터럴이 들어가지 않는 합성 입력을 사용한다.

G1-WAF에서 앱 로그가 없다는 사실만으로 미도달을 확정하지 않는다. 정상 대조·관측 공백·독립 백엔드 증거를 같이 본다. G1-LOG는 특정 전달 프로토콜을 아직 가정하지 않으며 출처별 실제 설정과 손실 범위를 기록한다.

시험 결과는 `통과 / 실패 / 미확인 / 미실행`으로 구분한다. 원본이나 관측이 부족하면 통과로 내리지 않는다. 현재 여섯 카드의 결과는 모두 **미실행**이다.

## 4. P01의 남은 결정과 변경 순서

| 결정할 것 | 현재 값·상태 | 이어갈 행동 |
| --- | --- | --- |
| 실제 기간·제출물·평가·공방전 규칙 | 미확인 | 사용자/팀의 확인 결과를 주제 결정 기록에 반영 |
| 실행 위치·배치 A/B | 환경 선택 확인 대기 | 대상 VM·NIC·관리 구역 확인 후 배치/허용표 작성 |
| 업체 내 자료 공유·운영자 범위·승인 정책 | 위 최소 권한 초안 | 담당자 검토 후 허용/거부 예시 확정 |
| 제품 버전·이미지·자원 | 기존 컨테이너 태그만 관찰 | 시험 제품을 별도 선정하고 실제 메모리·디스크·로그 경로 확인 |
| 연결 계약 | v1.0 앱 이벤트 4종·단일 response_state 유지 | actor/출처 키/관측/효과/복귀 제안을 스키마·예시·소비자·검증에 함께 반영 |
| 작업 DAG·역할·담당 | 기존 6개 작업 유지, P01만 ready | G1 선행 조건·TEL-* 인수 조건·망/DB 쓰기 경계를 다음 계약 변경과 함께 정합화 |

이 세션의 수정 경계는 이 문서·진입 링크·복구/확인 기록이다. `contracts/`, `docs/API-CONTRACT.md`, 앱, DAG, 역할 원본·생성물은 바꾸지 않는다. 다음 계약 변경은 `aleph-contract-change` 절차를 적용한다. 확인된 선행 결과가 없으므로 `--done P01`을 입력하지 않는다.

실행 위치가 정해지면 G1-NET 대상의 VM 제품·인터페이스·허용 경로부터 확인한다. 경로와 실제 DB 시험 위치를 정한 뒤 G1-DB, G1-WAF를 순서대로 수행한다. 실제 시험을 시작하지 못해도 권한·API·이벤트 초안은 검토할 수 있으나 이를 팀 합의나 G1 완료로 표시하지 않는다.
