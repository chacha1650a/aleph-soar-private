# 보안 네트워크 직무 관점의 주제 보강안 · R05

기준일: 2026-10-15 (Asia/Seoul) · 작성: Claude 제안 · 상태: 팀 논의 전 · 채택 전

[R04 유사 사이트 검토](17-reference-sites-review.md)를 보안 네트워크 직무 취업 관점에서 다시 보고, 포트폴리오에 도움이 되는 방향과 벤치마킹 자료를 제안합니다. 이 문서는 논의 자료입니다. [로드맵](14-smart-factory-roadmap.md)·작업 DAG·API 계약은 바꾸지 않았고, 제품 설치·연동·공방전 시험은 하지 않았습니다.

## 1. 요약

- R04의 참고 사이트는 **화면 설계 참고로는 쓸 만하지만, 보안 네트워크 직무 역량을 보여 주는 참고는 부족합니다.** 네트워크 계층 참고가 없고 국내 기준 문서가 빠졌습니다.
- 제안: 기존 주제(스마트팩토리 협력사·효과 재시험·업무 복귀 검증)를 유지하고, **협력사 원격 유지보수 접속 통제와 관제**로 네트워크 계층을 두껍게 합니다.
- 포트폴리오에는 화면보다 **망 구성도·방화벽 정책표·탐지 규칙과 ATT&CK 매핑·침해사고 보고서·차단 효과 재시험 결과**를 남깁니다.

빠진 것은 두 가지입니다.

- **네트워크 계층 참고:** 방화벽 정책, IDS/IPS, 망 분리, VPN을 다루는 참고가 없습니다. R04 회신에서도 pfSense는 증거 수집 역할로만 남았습니다.
- **국내 기준:** 국정원 국가 망 보안체계(N²SF), 제로트러스트 가이드라인 2.0, KISA OT 제로트러스트 안내서가 없습니다.

## 3. 취업 시장 근거와 해석

과기정통부·KISIA의 2024 사이버보안 인력수급 실태조사(2025-04 보도)에 따르면 다음과 같습니다.[T01]

- 50인 이상 민간기업 중 사이버보안 인력이 필요하다고 답한 곳은 8.7%입니다.
- 인력이 필요 없다는 기업의 이유에는 외부 보안 서비스 이용(25.2%)이 포함됩니다.
- 정보보호 전공 학생의 애로사항에는 실무 경험·인턴 부족(16.1%)이 있습니다.

**해석(Claude 판단):** 신입 채용은 보안 기업, 보안관제(MSSP), 네트워크 보안 업체에 몰려 있을 가능성이 큽니다. 이들이 확인할 것은 망 구성과 정책, 탐지 규칙, 사고 보고서 같은 운영 산출물입니다. 직무별 채용 통계는 확인하지 못했습니다. 팀원이 목표 회사의 채용 공고에서 요구 기술 키워드를 직접 모아 이 해석을 검증하는 것을 권합니다.

## 4. 제안 방향

### 1안 (추천): 협력사 원격 유지보수 접속 통제 + 관제

기존 로드맵의 포털·계정 대응·업무 복귀 검증은 그대로 두고, 협력사가 **VPN으로 담당 라인의 정비 대상에만 접속**하는 네트워크 경로를 추가합니다.

| 구역(제안) | 구성 | 허용 통신 초안 |
| --- | --- | --- |
| 외부 | 협력사 PC 역할, Kali | VPN 접속과 DMZ 포털만 |
| DMZ | 포털(Flask), 프록시·WAF 후보 | 외부→포털, 포털→업무 DB만 |
| 업무망 | 업무 DB, 생산관리자 PC 역할 | 포털과 관리망에서만 접근 |
| 설비망(가상) | 라인 A·B 정비 대상 호스트, 가상 설비 생성기 | 생성기→수집 API, 협력사 VPN→담당 라인 호스트만 |
| 관리·관제망 | Graylog, Wazuh 관리자, n8n | 각 구역 로그 수신, 관리 접속은 이 구역에서만 |

- **정비 대상 호스트:** 라인별 컨테이너 1개로 단순화합니다. 실제 PLC나 설비 제어 기능은 넣지 않습니다.
- **라인별 허용:** pfSense VPN 사용자에게 고정 터널 IP를 주고 방화벽 규칙으로 라인을 제한하는 방식을 후보로 둡니다(일반 지식, 버전별 확인 필요).
- **탐지:** pfSense 거부 로그(담당 외 라인 접속 시도), Suricata 경보(스캔 등), Wazuh(정비 호스트 로그인 실패·파일 무결성), 앱 이벤트를 Graylog로 모읍니다. 같은 협력사 계정의 앱·네트워크 이벤트를 한 사건으로 연결합니다.
- **대응:** 앱 계정 잠금·세션 폐기는 기존 로드맵대로 자동입니다. VPN 계정 비활성화·차단 규칙 같은 네트워크 조치는 **승인 후 적용**을 기본으로 합니다. R04 회신대로 pfSense의 REST API는 비공식 패키지라 자동화 경로는 팀이 정합니다. 기본안은 n8n이 변경 요청과 승인 기록을 만들고, 운영자가 적용하고, n8n이 재시험하는 흐름입니다. 이는 방화벽 정책 변경 승인 절차를 모사합니다.
- **효과 재시험:** 차단 대상은 담당 라인 접속이 실패하고 pfSense 거부 로그가 남아야 합니다. 다른 협력사는 자기 라인 접속이 성공해야 하고, 생성기 수집 순번은 유지돼야 합니다.
- **복귀:** VPN 자격 증명 재발급, 이전 자격 증명 거부, 규칙 원복 뒤 재시험을 합니다.
- **맞는 직무:** 네트워크 보안 엔지니어(방화벽·IPS 정책), 보안관제, OT 보안.
- **공방전:** 방어의 중심이 망 분리와 정책이 됩니다. 단, VPN과 관리망 자체가 공격 대상이 되므로 노출 범위를 먼저 정합니다.

추가 작업은 인프라 담당에 몰립니다. P01에서 담당을 다시 나누고, 필요하면 권한 복구 충돌·DB 감사 상세 같은 다른 범위를 줄일지 함께 정합니다.

### 2안: 미니 MSSP 관제 운영 (1안에 겹쳐 적용 가능)

- 다른 팀 서비스나 우리 구역을 고객사처럼 보고, 탐지 규칙 → 알림 분류(정탐·오탐) → 사건 → 보고서로 운영합니다.
- 규칙마다 MITRE ATT&CK ID를 붙입니다. Wazuh 규칙은 기본적으로 ATT&CK에 매핑돼 있습니다.[T06]
- 맞는 직무: 보안관제 요원.

### 3안: N²SF 등급별 망 설계 (발표 틀로만 권장)

- 업무 중요도에 따라 기밀(C)·민감(S)·공개(O) 등급으로 나누고 통제를 차등 적용하는 개념입니다.[T04]
- 1.0의 보안 통제 항목이 260여 개로 보도돼 2주 범위로는 무리입니다. 1안의 구역을 등급으로 설명하는 발표 틀로만 씁니다.

## 7. 공방전과의 연결

공방전 규칙은 아직 정해지지 않았습니다. CCDC 형식을 참고해 운영 측에 아래를 확인할 것을 제안합니다. CCDC의 세부 규칙은 지역 대회와 연도마다 다릅니다.[T11], [T12]

1. 서비스 가용성을 채점하는지, 채점한다면 어떤 서비스를 점검하는지.
2. 자동 IP 차단을 허용하는지, 상대 팀 출발지가 NAT로 IP 하나로 보이는지.
3. 침해 보고서를 제출·채점하는지, 양식이 있는지.
4. 공격 허용 범위(VPN·관리망 포함 여부).

## 8. 팀이 결정할 것

1. 1안으로 네트워크 계층을 보강할지, 기존 로드맵 범위를 유지할지.
2. 1안을 택하면 VPN 방식과 pfSense 배치(VM 위치·메모리), 라인별 정비 호스트의 형태.
3. 네트워크 조치의 자동화 경로: 승인 후 수동 적용, 또는 비공식 REST 패키지 사용.
4. 2안의 관제 운영 산출물(ATT&CK 매핑·보고서 양식)을 필수로 둘지.
5. 늘어나는 인프라 작업만큼 줄일 범위와 담당 재배정.
6. 목표 직무별 채용 공고 키워드 조사의 담당.

이 결정은 P01에서 다루고, 채택되면 로드맵·DAG·역할 원본에 반영합니다. 이 문서 작성만으로 채택하거나 P01을 완료 처리하지 않습니다.
