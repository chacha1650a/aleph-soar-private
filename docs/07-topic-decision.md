## 2026-10-22 기획서 결정

사용자 김명준이 이 채팅에서 정했다. 반영 위치는 위와 같다.

- **관리망 전용 연결:** 10/19 기록의 미정 항목(USB 이더넷 어댑터)은 4대 분산 배치로 바꾸면서 쓰지 않는다(whiteclover0542 지적). PC 사이는 학원 유선망 위 팀 VPN이다.
- **S4 해제:** 탈취가 의심·확인되면 비밀번호 재설정 뒤 해제하고, 오탐이 확인되면 승인된 관리자가 비밀번호를 유지한 채 해제(unlock)한다. n8n은 잠금·세션 회수까지만 하고 자동 해제하지 않는다. 회수한 세션은 되살리지 않고 해제 사유·처리자를 감사 기록에 남긴다. unlock(`POST /api/v1/admin/users/{id}/unlock`, `auth.account_unlocked`)은 A가 포털 PR #3과 함께 구현한다(A 수락).
- **보강 전 시험:** 케이스마다 그 케이스의 규칙을 넣기 직전에 전체 조건 충족 1회만 돌린다(whiteclover0542의 보강 전·후 시험 안내와 정량평가 리포트의 1회 안 채택). 보강 전 상태는 그 케이스의 로그 수집은 연결되고 탐지 규칙·n8n 대응은 없는 상태다. 시험은 67회(보강 전 6 + 보강 후 61)이며, 통합 스토리라인은 10/19 결정대로 하지 않는다.
- **팀원 리뷰 반영:** chacha1650a의 D 확인 5건(입력 포트 기본안, 포트 공개 범위, `request-observed` ↔ `web.request` 정규화, S12 GELF 유실 기록, 사전 위험 시험 ③ 분리·기준)과 whiteclover0542가 찾은 포털 로그인 속도 제한(429)의 S4 영향을 기획서에 넣는다.

## 2026-10-20 분산 배치로 진행

- [분산 배치 실행안](DISTRIBUTED-LAB-PLAN.md): A 포털, B pfSense·Kali·DB, C Wazuh·프로젝트 보안 대시보드·티켓, D Graylog·n8n을 기준으로 준비한다. A~D 보안 케이스와 포털 코드 구현 책임은 유지한다.
- 추가 장비 대여가 어렵다는 후속 답변에 따라 B 추가 포트 1개·분리 스위치 1대·랜선 4개의 물리 연결안은 보류한다. 기존 학원망 위 팀 전용 VPN을 후보로 검토하되, 팀원 IP·정상 연결·VM까지의 실제 전송 경로·터널·출발지 보존은 미검증이다. 물리 장비를 분산 진행의 필수 조건으로 확정하지 않는다.
- 현재 B의 임시 VMnet7과 가상망을 물리 브리지로 바꾸거나 주소를 옮기지 않는다. 같은 VMnet 번호를 여러 PC에 만드는 것만으로 연결되지 않는다.
- 사용자 화면에서 실제 DMZ는 VMnet6임을 확인했다. VMnet3의 수업 설정(172.16.10.0/24)은 보존했다. 기존 두 PC 그림·제출본 배치표는 장비 확정 후 동기화해야 한다.

- 핵심 방어: 다른 업체 자료 접근 거부, 계정·기존 세션 회수, 정상 B 업무 유지, 승인된 복귀.

- 공방전: 팀별 웹서비스 대상 가능성에 대비하되 실제 대상·계정·규칙·채점은 미정. 웹만으로 핵심 시연을 구성하고 VPN은 선택 경로.
- 실제 프로젝트 기간(2주 여부)·장비·배치·제품 버전·평가 기준·역할은 재확인/미정.
- 다음 행동: [R08 후속 판단](21-telecom-portal-defense-plan.md#11-claude-회신과-codex-후속-판단)을 기준으로 P01에서 계약·예시·역할·작업 DAG 정합화 → G1 실제 경로/WAF/DB 감사 위험 시험. 현재 구현 작업을 완료로 표시하지 않음.

## 잠정 통합 주제

**사내 포털의 계정 이상과 권한 오남용을 연결하는 자동 대응 관제 시스템**

핵심 사용자 가설: 소규모 조직의 서비스·보안 담당자. 서로 떨어진 인증·권한·조회 기록을 같은 사건으로 이해하고, 대응 이유와 결과를 확인하기 어렵다는 문제를 대상으로 합니다. 서비스 무대는 사내 포털을 제안하며, 기존 Flask 실습 코드의 재사용 여부는 검토 전입니다.

시연할 의심 사건 예시:

`반복 로그인 실패 → 후속 로그인 성공 → 예상 밖 권한 변경 → 민감 데이터 조회 → 사건 티켓 → 테스트 계정 잠금 또는 권한 회수 → 원복 확인`

이 흐름만으로 실제 침해를 확정하지 않습니다. 테스트 정책에 따른 의심 근거와 정상 업무 대조 사례를 함께 보여줍니다.

## MVP 제안

1. **이벤트 수집·연결:** 인증·권한 변경·민감 조회의 실제 앱 이벤트를 사용자와 자산 기준으로 연결하고 시간 순서를 확인합니다.
2. **사건 화면·티켓:** 탐지 근거, 타임라인, 관련 데이터 접근, 대응 상태를 한 사건에서 보여주고 중복 티켓을 방지합니다.
3. **대응·원복:** 테스트 계정 잠금 또는 테스트 권한 회수, 사전 상태 기록과 해제·복원 결과를 검증합니다. 대응 종류와 자동 실행 기준은 설계에서 확정합니다.

### 우선 시나리오

- S1: 반복 인증 실패 탐지
- S4: 같은 계정의 실패 이후 성공을 시간 순서와 맥락으로 연결
- S9: 권한 변경과 후속 민감 조회 연결
- 대조 사례: 정상 로그인과 허용된 조회, 서로 다른 사용자의 이벤트 혼재, 중복·지연 이벤트

세 관심사를 한 통합 시나리오에서 보여주되 각 탐지 조건도 별도로 검증합니다. S9와 데이터 추적의 MVP 범위는 앱 이벤트 기반입니다. DB 직접 접근까지 탐지했다고 주장하려면 별도 DB 감사 수집과 검증이 필요합니다.

### 확장·축소 기준

초기 제안은 앱·데이터 접근 흐름에 집중합니다. DB 직접 접근 감사, pfSense·WAF 연동, S1~S10 전체 구현은 별도 확장 후보입니다. 4계층 실장이 평가 필수라면 필수 범위부터 다시 배분합니다. 학습 기반 이상 탐지나 LLM 기능의 필수 도입 여부도 아직 정하지 않았습니다.
