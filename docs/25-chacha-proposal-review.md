## 1. 검토 결론

**판정: 수정 조건을 합의한 뒤 채택을 검토할 수 있는 구체적인 안이다.** 정상 서비스 MockTel, 취약/수정 프로필, HIDS/NIDS/가용성 티켓, 역할·로드맵·증거 보존까지 연결했다. Kubernetes가 없어도 이 안의 핵심 목표는 검증할 수 있다.

현재 제안의 중심은 단일 대역에서 탐지 공백과 보강 효과, 웹서버 장애 시 가용성을 비교하는 보안 실습이다. 기존 통신 외주 유지보수 포털의 구역별 접근·반출·계정/세션 회수 검증과 목표·서비스가 다르다. 어느 안을 채택했는지는 아직 결정하지 않았으며, 검토 때문에 기존 앱·AGENTS·계약·망 설정을 바꾸지 않는다.

채택 전 우선 결정할 것은 ① 서비스·평가 범위 ② 정상/공격 지표 분리 ③ 두 웹서버의 상태 일관성 ④ 실습 자원·NIDS 가시성 ⑤ 첫 필수 시나리오와 실제 담당자다.

## 4. 우선 수정·확인할 지점

### P1-1 · 단일 대역의 호스트 ACL과 구역 분리의 목표를 구분

근거: PDF 1·11·21~23쪽, 네트워크 PNG. 안 자체가 망 분리를 향후 과제로 두고 있다. 같은 /24에서 web-01/02의 HTTP를 LB 소스에만 허용하는 ufw는 접근 통제 실험으로 유효하지만, 라우터/방화벽을 경유하는 서비스·관리·DB 구역 분리와 같지는 않다.

또한 제시한 초기 SSH 허용 범위는 lab-net 전체라 공격자·rogue도 포함한다. 관리 주체만 허용하는 정책으로 좁힐지 명시해야 한다. IP 허용 목록은 장비 인증 자체를 입증하지 않는다.

수정안: 탐지 강화가 목표면 단일 대역의 한계를 유지해 설명한다. 네트워크 구조·접근 통제가 평가 핵심이면 최소 공격/클라이언트·서비스·관리 구역의 라우팅/허용표를 추가 검토한다. 실제 평가 확인 없이 기존 6구역 안 전체를 필수로 강제하지 않는다.

### P1-2 · 공격 차단 응답과 정상 사용자 오류율의 분모를 분리

근거: PDF 2·17~18쪽. 제시한 k6는 하나의 공격 부하 스트림에 전역 `http_req_failed < 1%`를 적용한다. 방어 설정은 같은 공격에 429를 반환한다. k6 기본 성공 판정은 HTTP 200~399이므로 정상적인 방어 거부가 기본 오류율을 높일 수 있다. [k6 응답 판정](https://grafana.com/docs/k6/latest/javascript-api/k6-http/set-response-callback/)

수정안:

- 공격 요청: 기대한 거부·통과·서버 오류·timeout을 별도로 집계한다. 429 전부를 성공 처리해 정상 사용자 피해까지 가리지 않는다.
- 정상 요청: 별도 소스의 정상 사용자/업무 생성기로 실제 본문·권한·기한을 검사한다. 정상 사용자 429는 정상 업무 실패다.
- IP 차단이 있으므로 동일 공격 VM에서 정상 부하를 태그만 나눠 만드는 것만으로는 충분하지 않을 수 있다. 정상/공격의 실제 출발지와 정책 범위를 분리한다.
- 본문을 확인하지 않은 빠른 429의 p95를 정상 업무 성능 개선으로 제시하지 않는다.

`stages`의 100 VU는 100 RPS가 아니다. 수정 버전이 빨라지면 같은 VU에서도 요청량이 바뀔 수 있다. 요청률·지속 시간·총량·중단 조건을 제한하고, 전후 고정 입력 비교가 필요하면 arrival-rate 방식과 실제 발행/미발행 수를 검토한다. [k6 고정 도착률](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/)

페이지네이션·캐시·rate limit·fail2ban·이중화를 한 번에 켜면 보강 묶음의 효과는 비교할 수 있지만 개별 효과는 분리하기 어렵다. 웹서버 1개 장애는 부하 방어와 독립된 시험으로도 측정한다.

### P1-3 · 두 웹서버의 SQLite·세션·보안 상태 일관성

근거: PDF 21·29~30쪽과 하네스 맥락. 각 웹서버에 `/opt/mocktel/data/mocktel.db`를 두고 roundrobin으로 분배하지만, 두 DB와 로그인·잠금·키·수정 프로필의 동기화 방법은 제시되지 않았다.

읽기 전용의 동일 합성 데이터라면 초기 복제된 SQLite로 조회 비교가 가능하다. 그러나 로그인 정보 변경·계정 잠금·비밀번호 변경·쓰기 업무까지 동일 상태라고 가정해서는 안 된다. 쿠키 서명 키·세션 검증 방식도 두 서버에서 일치해야 한다.

수정안: MVP가 읽기 전용임을 제한하고 같은 seed·서명·프로필을 검증하거나, 쓰기/잠금이 필요하면 공통 상태 저장소를 설계한다. 고정 세션만으로 서버 장애 후 상태 연속성이 해결됐다고 보지 않는다. 반복 요청의 `X-Served-By`와 양쪽 인증/인가·변경 결과를 직접 대조한다. 공유 저장소를 선택해도 그 자체가 SPOF임을 남긴다.

### P1-4 · VM 15GB를 16GB 호스트에 그대로 배치하지 않음

근거: PDF 6·21~22쪽. VM 합계는 약 15GB이고 rogue·호스트 OS·하이퍼바이저·추가 관측 자원은 별도다. 현재까지 확인한 PC는 RAM 약 16GB이며 기존 Docker 서비스도 있다.

Wazuh 공식 Quickstart의 1~25 agent 권장값 4 vCPU·8GiB·50GB는 문서와 맞는다. 다만 이 값에 같은 VM의 Suricata와 부하 중 로그 저장 비용까지 충분하다고 보장하지는 않는다. [Wazuh Quickstart](https://documentation.wazuh.com/current/quickstart.html)

‘호스트 전용망이라 한 PC에 구성’(6쪽)과 ‘두 PC에 나눠 배치’(22쪽)는 연결 조건을 맞춰야 한다. PC별 host-only 네트워크가 자동으로 이어지지는 않는다. 분산하려면 별도의 격리된 연결·라우팅·주소·접근 정책이 필요하다. Docker 대체도 메모리 사용과 장애 범위를 실제 측정하고, 기존 Wazuh와 새 monitor의 중복 여부·버전을 결정한다.

### P1-5 · NIDS 관측 위치·원본 전달을 첫 환경 시험으로 확정

근거: PDF 23·30~31쪽. VirtualBox promiscuous 설정 후 캡처 확인, 실패 시 LB에 Suricata를 두는 대안은 이미 들어 있다. 이를 실제 패킷과 경보·Wazuh 수신으로 통과시켜야 한다. VMware에서 이름만 VMnet으로 치환한 것이 동일 캡처 동작을 보장하지는 않는다. [VirtualBox 네트워크](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/networkingdetails.html)

캡처할 방향·VIP/백엔드·원본 출발지·관측 손실을 고정한다. LB 앞뒤를 동시에 세면 요청이 중복 관측되거나 백엔드에서는 LB IP로 묶일 수 있다. 대안으로 Suricata를 lb-01에 두면 eve.json 수집 주체도 monitor의 로컬 파일 읽기에서 LB의 수집 경로로 바뀌어야 한다. ‘모니터 위치만 변경’하고 중앙 수집 설정을 그대로 두지 않는다.

INC-04의 URI/횟수 규칙은 대량 조회 후보를 탐지하는 것이며, 단발 IDOR의 객체 소유권 위반을 판단하는 로직은 아니다. 저속의 타인 객체 조회·정상 본인 조회·대량 요청을 따로 시험한다. 403·429 비율만 보지 말고 알려진 유효 객체의 본문과 서버 측 인가를 검증한다.

### P1-6 · 모의 행위의 탐지와 실제 사고 기법의 탐지 성능을 구분

근거: PDF 8~11·13~18쪽. INC-01의 삭제된 실행 파일·패킷 소켓 관측은 실습 가치가 있다. 그러나 tcpdump의 패킷 소켓 변화만 잡은 결과가 BPFDoor의 필터·트리거·후속 통신을 탐지했다는 증거는 아니다. MITRE T1205.002는 소켓 필터 기반 신호·활성화라는 맥락을 설명한다. [MITRE T1205.002](https://attack.mitre.org/techniques/T1205/002/)

수정안: 발표 제목과 판정은 ‘무해한 일부 행위의 탐지 보강’으로 한정한다. 정상 tcpdump/패키지 업데이트/삭제된 실행 파일의 대조군을 두고 소유자·실행 경로·허가 여부를 확인한다. 임시 경로·소켓 목록 변화 하나로 악성 확정하지 않는다.

Wazuh command monitoring의 기본 rule 530은 level 0이고 맞춤 경보 규칙이 필요하다는 공식 설명은 안의 방식과 맞는다. 다만 rule 533·명령 출력·alias·권한·수집 주기·실제 버전의 규칙 연결은 재현하지 않았다. `wazuh-logtest` 등 로그 입력 검증과 실제 agent→manager→대시보드 검증을 모두 해야 한다. [Wazuh 명령 모니터링](https://documentation.wazuh.com/current/user-manual/capabilities/command-monitoring/configuration.html)

‘기본 A 탐지·B/C 미탐’은 실험 가설로 두고 실제 관찰을 먼저 기록한다. 예상과 다르게 기본 탐지가 성공해도 유효한 결과다. 정상 작업 1시간의 오탐·동일 이상 상태의 반복 경보·사건 중복을 나눠 세고, 모의 3개 입력 탐지를 실제 변종 전체 탐지율로 일반화하지 않는다.

INC-03의 주석/파일 변화는 공급망 공격 전체, INC-05의 ARP/미등록 IP는 펨토셀 기기 인증 자체의 재현이 아니다. 각각 파일 무결성·의존성 점검, 미등록 네트워크 주체 관측의 대체 시험으로 표시한다.

## 5. 범위·역할·지표의 보완

### 정상 서비스·실습 프로필

MockTel을 선택하면 정상 고객은 본인 정보 조회·검색을 하고 관리자는 무엇을 하는지 최소 업무를 정한다. 실제 고객·실제 자격 증명 대신 합성 데이터를 쓴다는 원칙은 유지한다. 기존 외주 유지보수 포털을 그대로 구현한 것이라고 표시하지 않는다.

`SECURE_MODE`는 앱의 취약/수정 비교 프로필이다. 호스트 프로세스·OS 설정·의존성 환경·LB 규칙까지 이 변수 하나로 자동 전환된다고 가정하지 않는다. 프로필별 앱 이미지/패키지·규칙·설정·seed·캐시와 전환 후 실제 상태를 기록한다. 오래된 Jinja2 예시는 최신 Flask와 동시에 설치 가능한지 별도 환경에서 검토하고, 취약 패키지 목록 스캔과 실제 취약점 동작 재현을 구분한다.

INC-02의 로그인 비밀번호 해싱, 재사용 가능한 API/DB 비밀의 코드 분리, USIM 인증키 보호는 서로 다른 문제다. 환경 변수로 옮기는 것은 코드 노출을 줄이는 조치이며 저장 암호화·권한·교체·접근 기록 전체를 대신하지 않는다. grep 출력에 매칭된 비밀 원문을 중앙 경보로 보내지 않도록 경로·위치·판정 위주로 남긴다. 가짜 값 allowlist와 INC-02 탐지용 규칙의 시험 목적도 구분한다.

### 가용성·티켓·증거

- 단일 lb-01과 같은 물리 PC는 SPOF다. web-01 중단 중 web-02가 처리하는 ‘백엔드 장애 대응’과 LB 자체 이중화·물리 HA를 구분한다. health 응답에 더해 인증·권한·실제 조회가 정상인지 확인한다.
- Wazuh 알림·Markdown 티켓·프로세스 정리·취약점 수정·서비스 복구는 서로 다른 결과다. 수동 티켓 자체는 타당하며 자동 등록을 필수로 추가할 필요는 없다. 승인자·조치 실행·효과·복구 재시험·미확인 여부를 티켓에 보강한다.
- 전체 VM baseline 복원 전에 monitor 원본·시간축·티켓·실행 설정·해시를 스냅샷 밖에 보존한다. 이때 같은 PC의 다른 진행 작업이나 경보가 같이 되돌아가는지 확인한다.
- NIC 해제 격리 뒤에도 VM 콘솔 등으로 휘발성 증거를 수집할 수 있는 절차와 중앙 전달 단절 상태를 남긴다. 공유 프로세스 이름 전체를 종료하는 정리 대신 이번 실행의 PID/자식·파일·소켓만 회수하도록 설계한다.
- 6/6은 알려진 티켓의 커버리지이며 모든 하위 시험의 탐지율과 동일하지 않다. 시도별 ID·원본 도달 여부·탐지/미탐·오탐·반복/미완료를 보존한다.

### 역할·협업

PDF 8쪽과 하네스의 담당자 칸은 비어 있다. 역할 분담 초안은 있으나 실제 팀원 이름까지 배정된 상태는 아니다. avail은 앱 뼈대·등록부 연결·패키지 호환·배포·LB·부하·장애 대응을 맡아 초기 병목이 될 수 있다. 네트워크 공통 설정을 docs만 소유하도록 한 부분도 실제 역량에 맞춰 인수 담당을 정해야 한다.

문서 담당이 독립 검증·증거 대조를 함께 소유하고, 각 탐지 담당은 자기 경보의 실제 전달과 정리를 책임지도록 제안한다. 처음부터 6개를 모두 동일 우선순위로 구현하기보다 INC-01·04·06을 핵심 세 축으로 검토하고 02·03은 보강 점검, 05는 장비/망 요건에 따라 선택한다. 실제 기간과 강사 필수 항목이 다르면 우선순위를 다시 정한다.

하네스의 파일 소유권·번호 분리는 참고할 만하다. 다만 현재 저장소의 `src/aleph_soar`, 생성 AI 자산, P01 DAG와 다른 구조이며 루트 AGENTS를 통째로 대체할 상태는 아니다. claim의 main 직접 푸시는 현재 협업 규칙·보호 설정과 먼저 맞춰야 한다. 다른 파일을 올려도 같은 원격 브랜치의 동시 푸시는 거절될 수 있고, 로컬 claim 확인만으로 선점이 완료되지 않는다. 이 검토에서는 기존 브랜치를 바꾸거나 claim·main 푸시를 수행하지 않았다.

## 6. 출처·문서 일관성 보완

- PDF 12·20쪽의 신고 기한 설명 중 ‘2026.10.1 이전에는 즉시’라는 연혁은 재검토가 필요하다. 과기정통부의 2025년 SKT 최종 발표는 이미 2024.8.14부터 24시간 제도를 설명한다. 이번 지적은 문서 간 불일치이며 현행 신고 의무에 대한 별도 법률 안내가 아니다. 제출 전 현행 조문·당시 시행 조문을 구분해 확인한다. [과기정통부 공식 발표](https://www.msit.go.kr/eng/bbs/view.do?bbsSeqNo=42&mId=4&mPid=2&nttSeqNo=1139&sCode=eng)
- ISMS-P 항목은 문서 스스로 KISA 원문 대조 전이라고 적었다. 언론·위키를 근거로 한 사건의 수치·원인·법적 판단과 특정 취약점 매핑은 공식 원문으로 바꾸기 전 확정하지 않는다. 이번 검토는 다섯 사례의 모든 역사적 주장·수치·법적 결론을 검증한 보고서가 아니다.
- PDF 9쪽의 local_rules.xml 편집과 하네스 등록부의 티켓별 XML·local_rules.xml 미사용 방침을 통일한다. PDF 11쪽의 VM 6대와 기본 5대+rogue 조건, PDF 10쪽의 필수 13항목과 실제 티켓 표의 14개 라벨, 6쪽/22쪽의 단일 PC·분산 대안을 같은 기준으로 정리한다.
- `rule 100130이 550을 능가한다` 같은 문구는 규칙의 override/상속·레벨 변경 의도를 정확히 설명하고 선택 버전에서 확인한다. 기대 결과표는 실행 로그가 있는 결과표와 분리한다.

## 8. 팀원에게 전달할 답변 초안

> 제안서 확인했습니다. MockTel 서비스와 보강 전후 비교, HIDS/NIDS/가용성 역할이 구체적으로 정리돼 있어 검토 기준을 잡을 수 있었습니다.
> 시작 전에 정상 서비스 범위, 사용할 PC 자원, 실제 담당자를 먼저 정하면 좋겠습니다.
> 기술적으로는 두 웹서버의 DB·세션 상태를 어떻게 맞출지, 공격 차단 429와 정상 사용자 오류율을 어떻게 나눠 측정할지 보완이 필요해 보입니다.
> 단일 대역은 탐지 실습으로 두고, 망 분리·접근 통제가 평가 핵심이면 구역 분리를 추가할지도 강사님 기준에 맞춰 결정하면 좋겠습니다.
> 처음에는 INC-01·04·06을 중심으로 하나씩 완주하고 나머지를 확장하는 안을 제안합니다. Kubernetes는 현재 목표에서는 추가하지 않아도 될 것 같습니다.

이 문구는 초안이며 실제 팀 채팅으로 발송하지 않았다.

## 9. 실제 검토 범위·변경

새로 작성한 것은 이 검토 Markdown뿐이다. 동봉 PDF/PNG/하네스 원본·루트 AGENTS·앱·계약·DAG·실행 환경을 수정하지 않았다. PDF 34쪽 추출·주요 페이지 렌더 확인·PNG 4장·하네스 Markdown과 공식 문서 검토를 수행했다. PDF의 명령·공격/부하·Wazuh/Suricata 규칙은 실행하지 않았으므로 개별 설정의 성공/실패·탐지/성능 수치는 판정하지 않았다.

검토 문서의 UTF-8·로컬 링크 7개·코드 블록 짝·줄 끝 공백 확인에서 오류가 없었다. 원본 PDF/PNG 5개의 SHA-256이 검토 시작 값과 같은 것을 재확인했고, `git diff --exit-code HEAD`로 기존 추적 파일이 변경되지 않았음을 확인했다. 새 코드가 없어 기능 테스트는 실행하지 않았다.
