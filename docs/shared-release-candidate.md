# 공유 차단 소유권 반납 · 집에서 검증한 정책 후보

사람 담당 B(집 구현)·C/D(정책/운영 API 채택), 시험 `HOME-SHARED-RELEASE-20261024`. **다른 소유자 때문에 서로 해제를 계속 보류하는 상황을 해결할 정책 후보**다. 논리 소유권 반납/유지 재요청/마지막 해제를 모의 구현했다. C 원본 PR·D 워크플로·기존 API 계약·실제 장비는 바꾸지 않았으며, 운영 정책 확정/배포를 뜻하지 않는다.

## 정책 후보와 관찰 구분

1. 소유권 하나는 `(ticket_id, 적용 action_id)`다. 자리 전체·IP 전체를 한 사람으로 묶지 않는다. 같은 자원은 기존 `{asset_id, via, 적용 action, target}` 4개를 쓰며 block/unblock만 모의 지원한다.
2. 소유자가 **반납 요청**하면 별도 장부에 withdrawn으로 기록한다. 다른 active 소유자가 있으면 물리적 차단과 C 티켓의 적용/효과 상태를 유지한다. 반납 의사만으로 C에 released를 쓰지 않는다.
3. 반납했던 소유자가 다시 차단을 유지하려면 **명시적 retain**으로 active에 돌아온다. 물리 해제 준비 뒤에는 retain/새 반납을 받아 진행을 바꾸지 않고 기존 계획을 대조해야 한다. 새 위협을 기존 applied 중복으로 생략하는 호출자도 반납 취소/유지 재요청을 먼저 조율해야 한다.
4. 마지막 active 소유자가 반납하면 모든 withdrawn 소유권의 기록 본문/순서와 물리 해제 요청ID를 한 계획으로 고정한다. 동일 자원 예약 안에서 모의 해제를 **1회** 수행하고 모의 상태가 해제됐는지 확인한다.
5. 그 뒤에만 모든 관련 C 티켓에 released를 기록하고 action_id/범위/결과를 재조회한다. C 자원 활성 조회가 비었음을 확인한 뒤 장부 완료와 예약 정리를 수행한다. 한 티켓의 다른 자원 조치까지 원복했다고 판단하지 않는다.

| 상태 | 물리 모의 차단 | C 티켓/행 | 의미 |
| --- | --- | --- | --- |
| A 반납, D 유지 | 유지 | A/D 기존 verified/applied 유지 | 논리 반납만 수신 |
| 반납 뒤 새 소유자 도착 | 유지 | 새 적용은 별도 소유권 | 새 소유자의 반납 전 해제 안 함 |
| A 유지 재요청, D 반납 | 유지 | 기존 적용 유지 | A가 다시 반납해야 마지막 해제 후보 |
| 마지막 반납·해제 확인 | 해제 | 모든 해당 소유권에 released | 관찰된 물리 해제와 논리 반납을 구분 |
| 해제 응답 불명/일부 C 기록 실패 | 해제됐을 수도 있음 | pending·일부만 갱신될 수 있음 | 예약 유지, 새 적용/해제 차단, 원본 영수증으로 기록만 복구 |

## 집 실행

```powershell
python -m pytest tests/test_shared_claims.py -q
python tools/rehearse_shared_release.py --ticket-source .local/ticket-pr55-final-20261024 --output .local/shared-release-new
```

첫 명령은 장부/경계 회귀17개다. 두 번째는 [고정 C PR55 패치 체크아웃](../patches/ticket-store-pr55/README.md#다른-pc에서-같은-패치-검증)과 Python .venv·Node가 필요하다. 기존 기본 리허설6종에 후보 정책6종을 더해 **12종**을 검사한다. C 응답은 실제 C 패치 코드의 Flask test client와 계약 스키마를 사용하고, 대상은 정확한 SQLite 모의 객체만 받는다. 실제 대상 콜백·허용 플래그·네트워크 POST는 없다. 기존 output을 덮어쓰지 않고 성공 후 report.json/md·manifest를 생성한다.

후보6종은 마지막 소유자 해제, 새 소유자 유입, 반납 취소/유지 재요청, 모의 해제 직후 중단, C 소유자1개 기록 뒤 중단, 장부 완료 뒤 예약 정리 전 중단이다. 장애 뒤 저장소와 C 앱을 다시 열고 기록만 복구하며, 모의 대상 영수증이 증가하지 않는지 확인한다. 이는 객체 재생성 시험이고 실제 장비 재부팅 시험이 아니다.

직접 실행한 합성 증적: [요약](capstone/evidence/shared-release-candidate-20261024/report.md), [JSON·코드 해시](capstone/evidence/shared-release-candidate-20261024/report.json), [manifest](capstone/evidence/shared-release-candidate-20261024/manifest.json). 기존6종과 후보6종을 구분하며 actual_device_calls=0·live_n8n_verified=false를 유지했다.

구현: [장부](../tools/shared_claims.py), [모의 실행](../tools/shared_release_simulation.py), [통합 리허설](../tools/rehearse_shared_release.py), [장부 회귀](../tests/test_shared_claims.py). 기존 [예약/읽기 trial](resource-gate-home.md)과 [기본 모의 리허설](home-rehearsal.md)은 보수적 보류 동작을 유지한다. 기존 guard의 allow_target_call=false도 그대로다.

## 실패·재실행 규칙

- 모든 적용/반납/유지 요청이 동일한 ResourceGate와 장부를 사용한다는 가정이다. 새 C 활성 소유권은 최신 snapshot에서 수입하고, 기존 미해제 소유권이 snapshot에서 사라지면 빈 조회로 간주하지 않고 보류한다. closed에 미해제 조치가 있거나 자원/행 식별이 다르면 보류한다.
- 같은 intent ID 재전송은 장부를 재변경하거나 오래된 해제 계획을 실행 허가로 반환하지 않는다. 다른 소유권/동작에 재사용하면 충돌한다. 완료된 과거 claim ID가 재등장하면 보류하며 새 주기는 새 ticket/action 식별을 써야 한다.
- 마지막 해제 계획은 영속화된다. 모의 해제 이후의 오류는 예약 pending을 유지한다. `repair_records`는 이전 실행 종료 확인·원래 계획·원래 모의 영수증/현재 해제 상태를 확인한 뒤 같은 키/본문으로 C 기록만 복구한다. 재해제나 자동 잠금 탈취는 없다.
- 논리 반납만 이뤄진 요청은 물리 호출이 없으므로 예약을 not_called로 정리할 수 있다. 장부 기록과 예약 정리는 별도 DB이므로 둘 사이 중단/정리 실패는 확인 후 대조해야 하며 원자적 운영 처리라고 주장하지 않는다.
- 해제 계획만 준비되고 모의 영수증이 없는 경우는 자동 재시도/계획 폐기로 처리하지 않고 보류한다. 준비 단계 중단의 취소/재개 API와 운영자의 권한·실행 종료 검증은 아직 없다.

## C/D가 확정해야 할 운영 조건

운영 반영 전 단계로 [소유자 범위·운영자 복구 권한의 로컬 API 참조 구현](shared-control-api-candidate.md)을 추가했다. ticket/action ID는 인증 정보가 아니며 임의 소유자의 반납을 허용하지 않는다. 로컬 참조 구현도 운영 배포/실사용자 인증은 아니다. C/D는 장부/버전·실제 인증·감사·권한·취소/재개 계약과 D 소비자를 함께 채택해야 한다. 새 후보 장부는 v2로만 열고 이전 v1을 자동 이행하지 않는다.

특히 기존 D/수동 적용이 장부를 우회하거나, 반납했던 같은 소유권에 새 위협이 생겼는데 retain을 하지 않으면 잘못된 마지막 소유자 판정이 가능하다. 이 구현은 운영용 가드의 해제 허가를 켜지 않는다. 운영에서는 신규 적용·중복 생략·반납·유지·물리 해제 전체를 같은 조율에 연결하고, 실제 대상의 멱등성/영수증·정상 접근/효과·원복·장애를 검증해야 한다.

티켓 단위 asset_id의 의미/다중 집행 자산, 운영 조율 위치·DB 식별/복원, 실제 n8n 배포/배치 실행, 현장 VPN/방화벽과 팀 운용 속도도 확인 필요다. 팀 메시지·PR 댓글·실제 장비 적용은 하지 않았다.
