# 핵심 범위 합의 준비 · 팀원 제안과 Claude 회신 정리

기준일: 2026-10-16 (Asia/Seoul) · 작성: Codex · 상태: 팀 논의용, 채택·구현·시험 전

최신 사용자 방향은 **10종 이상 구상·4인 분담·공통 기반부터 단계적 구현**이며 [12종 계획](29-twelve-ticket-phased-plan.md)에 반영했다. 이 문서와 다음 4종 구성은 논의 이력이다. 첫 통합을 하나로 시작하되 최종 범위를 하나 또는 네 종류로 제한하지 않는다.

후속 조건: 사용자가 강사의 ‘4명이 각자 맡을 수 있도록 티켓 4가지 이상 구상’ 조언을 전달했다. [4인 담당 티켓 구성안](28-four-ticket-scope-plan.md)에 따라 아래의 대표 흐름 하나는 **첫 통합 순서**로 해석을 수정한다. 최종 범위를 한 종류로 제한하는 추천은 더 이상 적용하지 않으며, 유형별 담당과 최소 4종 구성을 팀과 합의한다.

## 1. 이번 검토의 결론

**실제 통신사 사고에서 얻은 교훈을 바탕으로, 대표 사고 하나의 기본/보강 탐지 비교부터 대응·복구까지 먼저 완주하자.** 네트워크는 그 사고에 필요한 허용·차단·관측 경로를 설명하고 실제 연결과 로그로 검증한다. 사건 개수와 도구 개수를 성과로 삼지 않는다.

이는 범위 축소 추천이지 팀 합의가 아니다. 기존 사용자 준비 방향은 외주 유지보수 포털이며, 팀원이 제안한 MockTel로 바꾸는 결정은 아직 없다. 실제 기간·평가 필수 조건·실행 장비·이름별 담당도 미확정이다.

## 4. 합의할 최소 범위

| 항목 | 우선 합의할 것 | 완료 후 확장 후보 |
| --- | --- | --- |
| 서비스 | 외주 포털 또는 MockTel 하나의 정상 업무·사용자·보호 자산 | 추가 업무 |
| 대표 사고 | 아래 후보 중 하나. 둘 다 필수로 정하지 않음 | 다른 사고·호스트 행위·가용성 실험 |
| 망 | 대표 사고에 필요한 출발·목적·포트·차단점·수집점·관리 주체·시간 동기화 | 평가 요건과 자원에 따른 추가 구역·별도 DB |
| 탐지 | 같은 입력의 기본/보강 결과와 정상 대조. 미탐·오탐·미관측 분리 | 추가 규칙·상관 분석 |
| 대응 | 근거가 있는 수동 티켓·승인·조치·효과 확인·원복 | n8n 자동 등록·제한된 자동 대응 |
| 가용성 | 정상 사용자 업무 유지·복구 결과 확인 | 독립 부하 시험·백엔드 장애 분산 |
| Kubernetes | 현재 필수 범위에서 제외하는 추천 | 재배치·readiness·HPA 실험과 자원이 합의될 때 재검토 |

대표 후보 A는 **계정 악용·권한 밖 조회**다. MockTel이면 본인/타 고객 정보, 기존 포털이면 본인/타 업체 작업·결과를 대상으로 한다. 저속 객체 접근과 대량 조회를 구분하고 서버 측 인가·응답 본문으로 실제 접근 결과를 확인한다. 앱 로그가 객체 권한 판단의 주요 증거이며, NIDS 횟수 규칙만으로 권한 위반을 판정하지 않는다.

대표 후보 B는 **무해한 호스트 행위의 탐지 공백·보강**이다. SKT 사건의 탐지·로그 교훈을 우선할 때 검토한다. 실제 악성코드 없이 일부 행위만 모사하고, 정상 유지보수 대조군·격리 중 증거·서비스 복귀를 포함한다. 실제 BPFDoor 전체 탐지 성능으로 일반화하지 않는다.

두 후보 모두 교육용 합성 시나리오다. 웹 계정 악용·IDOR을 실제 SKT 초기 침투 경로로 단정하지 않는다. 사건 원인·수치·법령은 제출 전에 공식 원문으로 재확인한다.

## 5. 네트워크 초안을 적용하기 전 확인

[docs/26](26-network-allow-table-s1-s10.md)은 규칙 후보와 시험 목록으로 사용한다. 대표 사고가 정해지면 필요한 줄을 추려 순서·예외·실제 인터페이스에 맞게 정리한다.

- NR-10의 ‘각 구역 소스’와 NR-11 외부 거부는 출발지 목록·목적 포트를 좁혀 충돌 없이 정의한다. 등록 포트와 이벤트 전송 포트도 운영/등록 단계에 맞춰 구분한다.
- 관리 구역 내부의 관리 화면·pfSense 관리 접근은 실제 같은 망 경로를 확인한다. 구역 사이 방화벽 표만으로 같은 구역의 모든 접근이 통제된다고 가정하지 않는다.
- 프록시가 연결을 새로 만들면 패킷의 출발지와 앱의 신뢰된 전달 헤더는 별개 증거다. 모든 계층의 패킷 주소가 항상 같아야 한다고 요구하지 않는다. 주소 변환·공유 NAT가 있으면 가능한 식별 수준과 정상 사용자 차단 위험을 기록한다.
- 443 HTTPS를 쓰는 배치에서는 NIDS가 HTTP URI를 볼 수 있는 관측 위치를 별도로 확인한다. 캡처가 되었다는 사실만으로 복호화된 업무 내용을 분석할 수 있다고 보지 않는다.
- n8n→pfSense 443은 관리 연결 후보다. 차단 목록 변경 API·권한·원복 방법이 검증된 자동 대응 경로는 아니다.

HAProxy 뒤 웹서버를 추가하는 것은 백엔드 장애 대응 실험이다. LB 자체 이중화와 같지 않으며, 단일 LB·단일 DB·단일 물리 PC의 SPOF를 별도로 기록한다.

## 6. 최소 완료 조건과 증거

1. 정상 사용자 A/B의 본인 업무가 성공한다. 요청·본문·권한·정상 구간 경보 수를 보존한다.
2. 대표 사고의 입력을 기본/보강 조건에서 반복한다. 실행 ID, 원본 로그, 중앙 수신, 경보를 대조하고 미탐·오탐·미관측을 분리한다.
3. 선택한 경계의 허용·거부가 실제 경로에서 확인된다. 방화벽·앱·수신기 등 필요한 독립 증거와 정상 B 결과를 남긴다. 로그가 없다는 사실만으로 차단 성공을 판정하지 않는다.
4. 근거 경보와 연결된 티켓·승인 후 조치가 있고 실제 효과를 재시험한다. 계정 대응이면 신규 로그인과 기존 세션을, 호스트 격리면 허용된 증거 수집과 금지 통신을 각각 확인한다.
5. 원복 후 허용된 업무만 복귀한다. 이전 세션/자격 증명 등 폐기 대상은 계속 거부되는지 확인하고, 탐지·복구 시간의 시작/종료·안정 관측 기간과 정상 사용자 영향을 기록한다.

목표 시간·반복 횟수·허용 실패율은 기준선 측정과 팀 합의 뒤 정한다. 위 조건은 시험 계획이며 달성 수치가 아니다. 복구 전 증거는 VM 스냅샷 밖에 보존한다.

## 7. 팀원에게 공유할 문구

> 실제 통신사 사고를 참고하고 기본 탐지와 보강 후 결과를 비교하는 방향에 동의해요. 우선 정상 서비스와 대표 사고 하나를 함께 정하고, 그 사고에 필요한 네트워크 허용·차단·로그 수집 경로를 설계하면 좋겠습니다. 계정 악용·자료 조회를 중심으로 할지, 무해한 호스트 행위의 탐지 보강을 중심으로 할지도 같이 정해 보면 좋겠어요. 선택한 흐름의 탐지 비교부터 티켓, 승인 후 대응, 복구와 정상 사용자 확인까지 먼저 완성하고 나머지를 확장하는 순서를 제안합니다. 서비스·대표 사고·최소 망 구성을 정한 뒤 실제 장비와 평가 조건에 맞춰 역할을 나누면 좋겠습니다.

실제 채팅으로 발송하지 않은 초안이다. 먼저 정할 것은 **정상 서비스·보호 자산, 대표 사고, 필요한 최소 망·실행 자원** 세 가지다. 기간·강사 필수 조건은 함께 확인하며, 제품 설치·설정 변경은 별도 구현 단계다.

## 8. 공유 준비와 실제 확인

사용자의 커밋·푸시 요청에 따라 원본 자료 18개(약 3.3MB), 검토 문서·요청·회신과 이 요약을 공유 묶음으로 준비했다. 원본 PDF SHA-256은 docs/25의 값과 동일하며 루트 AGENTS·앱·계약·DAG는 수정하지 않았다. 원본 자료의 AGENTS 등은 별도 제안의 일부로 보존한 것이며 현재 공통 규칙의 대체물이 아니다.

새/수정 Markdown 11개의 UTF-8·로컬 링크·코드 블록 짝·줄 끝 공백 검사를 통과했다. 원본 Markdown과 PDF 2개의 텍스트에서 주요 비밀키 패턴이 검출되지 않았으며, 이는 모든 민감정보 부재를 보증하는 검사는 아니다. AI 자산 14개와 작업 DAG 6개의 검사도 통과했다. 문서·참고 자료만 변경해 기능 테스트·설치·사고 재현·성능 시험은 하지 않았다.

전체 staged 공백 검사에서는 동봉 원본 `security-lab-harness/harness/06-templates.md`의 빈 목록 항목 3곳에 기존 줄 끝 공백이 표시됐다. 원본 보존을 위해 그대로 두었으며, 원본 폴더를 제외한 작성·수정 문서의 staged 공백 검사는 별도로 통과했다.

다음 담당은 서비스·대표 사고·실행 자원을 팀과 먼저 합의하고, 선택한 흐름의 망 허용표와 완료 기준을 구체화한다. 아직 미합의인 구성을 완료 처리하지 않는다.
