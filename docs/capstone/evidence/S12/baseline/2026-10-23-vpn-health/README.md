# S12 기준선 · D→A 팀 VPN 경로 `/api/v1/health` (2026-10-23)

- 담당: D(chacha1650a). 기준선(5.9)의 대응 판정 경로(n8n → 팀 VPN → 포털) 쪽만 잰 것이다. 회복 판정 경로(정상 출발지 → pfSense → 포털)는 아직 재지 않았다.
- 조건: `10.250.0.100`(D PC)에서 `http://10.250.0.2:5000/api/v1/health`(A 포털 VM)로 GET, 간격 2초, 시간 초과 3초, 2026-10-23 14:11:14~14:41:13 KST, 표본 900개. 보강 전 상태(S12 이벤트 정의·n8n 워크플로 없음)에서 쟀다.
- 파일: `s12_probe.py`(측정 스크립트, 표준 라이브러리만 사용), `vpn-health-1023-1411.csv`(원자료: ts_kst, label, status, ms, error).
- 실행 방법: `python -I s12_probe.py --label <이름> --duration 1800 --out <파일>.csv`

## 해석과 한계

- 느린 값이 1초·2초 근처에 몰려 TCP 재전송처럼 보이지만, 이 측정만으로 원인이 네트워크라고 확정하지 못했다. A 세션이 같은 날 VPN 구간 패킷 손실을 따로 재서 0.5~12.5%로 보고했으나 D가 직접 확인한 값은 아니다.
- 기획서 잠정 식 `응답 > max(p95×3, p95+300ms)`는 이 결과에서 약 3,414ms가 되어 시간 초과(3초)와 같아진다. 정상 상태에서 연속으로 넘는 횟수가 임계 2,000ms에서 최대 2이므로, 잠정안은 "응답 2,000ms 이상 또는 실패가 연속 3회"다. 한 번의 측정이라 정상 출발지 경로 기준선과 보강 전·후 시험에서 다시 확인한다.
- 측정 중 Graylog에는 이 요청이 `web.request`로 함께 들어왔다(출발지 `10.250.0.100`). 같은 날 D 로컬 UDP 시험 로그(`host=zz-d-local`)도 `haedam-portal` 스트림에 800건 섞여 있다.
