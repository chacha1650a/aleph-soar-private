## 결정: 지금은 60초 유지

1. 원인은 계획된 VPN 재시작이었고, 아래 체크 항목으로 막을 수 있습니다.
2. 보강 전 #1을 60초에서 측정했습니다. 보강 후 측정까지 수집 설정을 같게 두면 비교에 변수가 하나 줄어듭니다.
3. 값을 너무 짧게 잡으면 C PC 부하가 클 때 정상 연결도 다시 맺을 수 있고, 그때도 송신 중이던 이벤트가 유실될 수 있습니다. 이 값은 `notify_time`(keepalive 주기)보다 충분히 커야 합니다.
4. 이 설정은 VM agent의 `ossec.conf`(`<client>`)에 있어 A가 바꿔야 하고, 바꾼 뒤에는 재시작·Active 확인·FIM 수신 재시험이 필요합니다.

알려진 한계: **VPN이 끊기면 최대 약 60초 동안 agent 010의 경보(FIM 포함)가 유실될 수 있습니다.**

## 시험·시연 전 체크 항목 (A 동의)

1. 시험을 시작하기 전과 도중에 VM VPN을 재시작하지 않습니다.
2. 재시작했다면 VM agent `ossec.log`에 `Connected to the server`가 찍힌 뒤 시작합니다. C에서도 `docker exec wazuh-manager /var/ossec/bin/agent_control -i 010`로 Active를 확인합니다.
3. 판정할 때 시험 구간에 010 재연결이 있었는지 함께 기록합니다. 재연결이 있었다면 그 실행은 재시험합니다.

## 다시 검토할 때 (S7 보강 후 측정 뒤, 공방전 대비)

- 이유: 공방전에서 상대가 네트워크를 흔들면 VPN이 끊길 수 있고, 그동안 FIM 경보가 사라지면 S7 미탐이 됩니다.
- 순서
  1. 바꾸기 전에 VM의 `notify_time`·`time-reconnect` 현재 값을 기록합니다.
  2. A가 VM `ossec.conf`의 `<client>`에 `<time-reconnect>30</time-reconnect>`를 넣고 agent를 재시작합니다.
  3. 같은 방법(VPN 재시작 + 직후 SSH·sudo 몇 줄)으로 유실 구간을 실측해 이 문서의 52·57초와 비교합니다.
  4. 부하가 큰 상태에서 정상 연결이 다시 맺어지는지(불필요한 재연결) 30분 관찰합니다.
