## 임계값

**Q1. 왜 S1은 30분 8회 초과, S4는 10분 합계 5건 초과인가?**
- 11/02 정상 기준선(랩 관측, [정상패턴 5절](A-S1-S4-정상패턴.md#5-정상-기준선-측정-1102-랩-관측)) 결과 정상 키 11개의 최대값이 S1 3회·S4 3건이라 두 값을 그대로 둡니다. 표본이 작은 랩 기록이라는 점은 함께 말합니다.
- 근거는 정상 패턴 정의서의 상한입니다. 정상 사용자는 로그인 한 번에 오타 4회까지, 30분에 로그인 2회로 봐서 실패 8회까지가 정상 범위입니다.
- 임계값 스윕(`python scripts/replay/sweep.py`, **오프라인 룰 재생·실시간 MTTD 아님**)으로 왜 이 값인지 답합니다. 셀 = 탐지(공격 발동/전체), 오탐(정상 발동/전체):

  **S1 (login-bruteforce 실패만):**

  | 창\임계 | >5 | >8 | >12 |
  | --- | --- | --- | --- |
  | 10분 | 탐지 0/1, 오탐 0/5 | 탐지 0/1, 오탐 0/5 | 탐지 0/1, 오탐 0/5 |
  | 30분 | 탐지 1/1, 오탐 2/5 | **탐지 1/1, 오탐 1/5** | 탐지 0/1, 오탐 0/5 |
  | 60분 | 탐지 1/1, 오탐 2/5 | 탐지 1/1, 오탐 1/5 | 탐지 0/1, 오탐 0/5 |

  10분은 저속 공격(24분에 9회) 미탐, >12는 공격(9회)도 놓침, >5는 경계-아래(8회)까지 오탐 → **30분·>8**(오탐은 알려진 경계 F4 1건).

  **S4 (card(rule)>1):**

  | 창\임계 | >5 | >8 | >12 |
  | --- | --- | --- | --- |
  | 10분 | **탐지 1/1, 오탐 1/4** | 탐지 0/1, 오탐 0/4 | 탐지 0/1, 오탐 0/4 |
  | 30·60분 | 탐지 1/1, 오탐 1/4 | 탐지 0/1, 오탐 0/4 | 탐지 0/1, 오탐 0/4 |

  공격이 6건이라 **>5 필수**, >8은 공격도 놓침. 오탐 F3(오타 5+성공)는 임계로 못 떼어 상한(오타 ≤4)으로 관리 — S4 오탐 1건 = 정상 공무원 잠김.
- 위는 합성 패턴 기준 결정적 재생입니다. 실시간 랩의 MTTD·실측 오탐은 보강 후 따로 재어 분리 표기합니다(S1 실측 MTTD는 Q12).

**Q2. 공격자가 30분에 8회씩만 시도하면?**
- 탐지하지 못합니다. 이 규칙의 한계입니다.
- 대신 계정당 30분 8회로 속도가 묶여, 하루 최대 384회입니다.
- 포털 자체 속도 제한(같은 출발지 5분 실패 20건 이상이면 429)이 별도로 있습니다.

**Q3. 여러 출발지로 나눠 공격하면?**
- 묶기 키가 username + src_ip라 S1·S4 범위 밖입니다(합의본 ④).
- 이 키를 고른 이유: 차단할 출발지가 이벤트에 남아야 하고(S1), 다른 출발지의 정상 로그인이 공격 실패와 합쳐져 정상 계정이 잠기면 안 되기 때문입니다(S4).

## 대응 방식

**Q4. S1은 왜 계정 잠금이 아니라 출발지 차단인가?**
- 실패만으로 계정을 잠그면 공격자가 정상 공무원 계정을 일부러 잠글 수 있습니다(합의본 ②).
- 잠금은 실제 로그인 성공이 확인된 S4에만 씁니다.

**Q5. 같은 사무실 IP를 쓰는 다른 직원도 S1 차단에 같이 막히지 않나?**
- 막힙니다. 알려진 오탐 F4로 정의서에 적었습니다.
- 차단은 사람이 해제하며(만료 없음), 해제 시간과 절차를 결과에 기록합니다.

**Q6. S4는 왜 기존 세션까지 회수하나?**
- 공격자가 이미 로그인에 성공했기 때문에, 잠금만 하면 공격자의 세션이 살아 있습니다.
- 세션 회수를 탈취 대응의 완료 조건으로 두고, 원복 때도 되살리지 않습니다(합의본 5.9).
- 회수는 서버 세션 행을 지우는 방식이라, 대응 전 세션은 다음 요청부터 비로그인 상태가 됩니다(`/auth/me`는 401이 아니라 비로그인 200). 10/28 사전 시험(수동 잠금): 잠금 뒤 새로고침 비로그인, 재설정으로 잠금이 풀려도 로그인 없이는 계속 비로그인, DB 세션은 새 로그인 1개뿐([S4-before-03](evidence/S04/before/S4-before-03/README.md)).
- **11/03 S4-after-01(자동 잠금):** 잠금 직후 DB 그 계정 세션 0(15:45:35), 공격자 창 다음 요청 `/auth/me` 200 + 비로그인(B 화면 관측), 재설정 뒤에도 비로그인 유지([S4-after-01](evidence/S04/after/S4-after-01/README.md) 3a·4c).

**Q7. 잠긴 계정에 로그인하면 뭐라고 나오나?**
- 틀린 비밀번호와 같은 401입니다. 계정이 잠겼는지를 공격자에게 드러내지 않기 위해서입니다.
- 잠금 여부는 관리자 화면의 "잠김"으로 확인합니다.
- 10/28 사전 시험: 잠긴 `zz_s4t1` 로그인 401(10:17:59).
- 11/03 자동 잠금 뒤: 공격자가 같은(맞는) 비밀번호로 재로그인 401(15:47:37, `c437552f`), 관리자 화면 "잠김".

## 오탐

**Q8. 오탐은 없나?**
- 있습니다. 정의서에 F1~F4로 적었습니다.
- 가장 현실적인 경우는 F3(오타 5회 뒤 성공 → S4 발동)입니다. 비밀번호를 바꾼 직후나 Caps Lock이 켜진 경우입니다.
- 실제로 겪었습니다(10/28 S4-before-02): 관리자가 비밀번호를 재설정한 직후 정상 사용자가 새 비밀번호를 9번 잘못 입력 → 같은 계정·출발지 401이 30분 안에 10건 → 성공. **S1·S4 조건을 모두 채웠습니다.** 그때는 정의가 반입되지 않아 조치가 없었습니다(D 확인). 해제 직후가 가장 오탐에 취약하므로, 재설정 비밀번호를 정확히 전달하고 첫 로그인을 관리자가 지켜보는 절차를 둡니다(완화책 팀 결정 전).
- 정상 업무 30분 시험의 오탐은 "정의한 정상 패턴 기준"으로 보고합니다. 합성 트래픽이라 실측 오탐률이 아닙니다. **11/02 기준 미측정**입니다. 지금 답할 수 있는 실측은 "S1 보강 후 2회에서 정상 사용자 오차단 0건(다른 계정 `.12`, 같은 계정 `.12`)", "S4 보강 후 1회에서 오잠금 0건(`zz_n1` 로그인·민원 200)"이고, 실제 사용자 로그인 기준선은 랩에 사용자가 없어 측정 범위 밖입니다.

**Q9. S4는 "실패 뒤 성공" 순서를 보나?**
- 보지 않습니다. 10분 창 안에 실패·성공이 함께 있으면 발동합니다.
- Graylog 오픈 버전의 이벤트 정의로는 순서를 판정하기 어렵기 때문입니다(합의본 5.9).
- 그래서 같은 출발지의 반복 로그인(F1·F2)도 발동하는데, 조건은 유지하고 한계로 명시했습니다(10/23 결정).

## 원복

**Q10. 원복은 어떻게 하나?**
- S1: 담당자가 출발지 차단을 해제합니다(`POST /response/ips/unblock`). 그 IP의 정상 요청이 다시 200이면 완료입니다.
- S4 탈취: 비밀번호를 재설정(reset)한 뒤 잠금을 풉니다. 새 비밀번호로 로그인되고, 이전 세션은 계속 무효입니다.
- S4 오탐: 관리자가 비밀번호를 유지한 채 해제(unlock)합니다(backend #4·계약 #45, 10/27 병합, 포털 VM `9507fce` 배포). 화면 버튼 "오탐 해제(비밀번호 유지)"는 frontend #3(10/28 16:15 배포)으로 생겼고 **잠긴 계정에만** 보입니다. 10/28 17:00 수동 잠금으로 확인: 잠금 16:59:02 → 해제 16:59:27(25초, `reason_code: false_positive`) → 기존 비밀번호 로그인 200.
- 실측: S1 해제 17:06:30 → `.11` 200 확인 17:11:36(10/27, n8n 112 사전 시험). S4 잠금 → 재설정 1분 43초(10/28, 수동).
- **11/03 S4-after-01 실측(탈취 경로):** 자동 잠금 15:45:09.670 → C 효과 확인 뒤 A 비밀번호 재설정 15:57:39.444 → 새 비밀번호 로그인 200 15:58:58.630(재설정 → 새 로그인 61초, 사람 입력 포함) → 티켓 closed 16:04:38. 공격자 옛 세션은 재설정 뒤에도 비로그인. 오탐 경로(unlock)는 보강 후 회차에서 실측 전.
- **10/28 S1-after-01 실측:** 해제 3회 모두 차단 목록에서 빠지고 재접근 200. 해제 요청 → 재접근 200은 54.5·79.0·61.0초인데, 대부분이 B가 다음 요청을 보낸 간격이고 해제 자체는 요청 뒤 1.1~1.2초 안에 끝났습니다(`web.ip_unblocked`). 티켓은 released → restored → closed.
- n8n은 잠금·세션 회수까지만 하고, 해제는 사람이 합니다(합의본 10/22 결정).

**Q10-1. 해제는 자동인가?**
- 아닙니다. 사람이 승인한 뒤 해제를 호출합니다. 10/28에는 승인 해제 워크플로(haedam-50)가 `dry_run`으로 고정돼 있어서, D가 승인한 뒤 임시 워크플로로 포털 해제 API(haedam-12)를 직접 부르고 C가 티켓에 released를 기록했습니다. 그래서 결과는 "자동 차단 + 사람 승인 후 수동 해제"로 적습니다. haedam-50의 실제 해제 스위치는 후속입니다.

**Q11. 자동 대응이 관리 PC나 n8n 자신을 막으면?**
- 보호망(`RESPONSE_ALLOWED_CIDRS`) 주소의 차단 요청은 포털이 403으로 거부합니다(backend #2).
- 실측(11/02): 포털 VM의 보호망은 `10.250.0.100/32`(n8n) 하나입니다. n8n 주소로 자기 차단을 요청하면 403이 나오는 것을 배포 코드와 실제 설정에서 확인했습니다(`lab/s1s4/selfblock_check.py` 6/6, 앱 안 호출).
- 한계: 관리 PC(A PC `192.168.145.1`, 관제 PC)는 보호망에 없습니다. 관리자가 같은 계정으로 30분에 9번 넘게 틀리면 그 PC도 차단됩니다. 해제 API는 보호망 안(n8n)에서만 부를 수 있습니다. VM 콘솔의 `127.0.0.1`도 보호망 밖이라 거부됩니다(11/02 확인). 그래서 해제는 n8n을 통해 합니다. 보호망을 넓히면 그 주소에서 오는 공격도 막지 못하게 되므로, 넓힐지는 팀이 정할 일입니다(현재 결정 기록 없음).

## 측정

**Q12. MTTD가 왜 몇 초가 아니라 분 단위인가?**
- 지연 대부분이 Graylog 이벤트 검색 주기입니다. 검색 주기를 결과와 함께 적어 시간 해상도를 밝힙니다(합의본 5.5).
- **10/28 S1-after-01 실측(1분 실행):** MTTD 59.6·53.4·47.3초. 9번째 401이 1분 판정 주기 중 언제 들어왔는지에 따라 0~60초 사이로 달라집니다. 탐지 뒤 차단 완료까지는 1.0·0.57·0.55초로, 자동 대응 자체는 1초 안입니다.
- **10/29 S1-after-02:** 9번째 401이 UDP에서 유실돼 Graylog가 10번째에서 판정 → 종단 MTTD 99.1초(유실 포함), 파이프라인 지연(Graylog가 받은 마지막 신호 → 이벤트) 4.2초, 탐지 → 차단 5.9초. 유실 영향을 숨기지 않고 두 값을 함께 적습니다(Q16).
- MTTD 시작점은 포털 원본의 9번째 401 시각, 끝점은 Graylog 이벤트 생성 시각(`detected_at` = `timestamp_processing`)입니다. Graylog의 `condition_met_at`은 판정 창 끝 시각이라 포털 원본과 약 59초 다르므로 시작점으로 쓰지 않습니다(팀 합의).
- **11/03 S4-after-01(1분 실행):** 성공 로그인(포털 원본) 15:45:02.695 → Graylog 처리 15:45:08.691(5.996초) → 포털 잠금 15:45:09.670(탐지 → 잠금 0.979초). **성공 → 잠금 6.975초.** C 대시보드 MTTR 346.027초는 사람이 효과를 기록한 시각 기준이라 자동 대응 시간과 따로 말합니다. 이번엔 성공 로그인이 Graylog 평가 창 끝(15:45:03.089)보다 0.4초 앞서 들어와 다음 검사를 거의 기다리지 않았습니다. 들어온 시점에 따라 최대 약 1분 더 걸릴 수 있고, 1회 측정입니다.

**Q13. 보강 전후 비교는 어떻게 했나?**
- 보강 전은 규칙·대응이 없는 상태에서 1회 돌렸습니다(10/22). 공격은 성공하고 로그는 15/15 도착했지만, 이벤트·대응·티켓은 0이었습니다.
- 보강 후는 같은 입력으로 5회 + 경계·정상 입력을 돌립니다. **S1 1회차(10/28 S1-after-01):** 같은 zz_a1 공격이 9번째 401 뒤 다음 요청에서 403으로 막혔고(3번), 이벤트·n8n·차단·티켓이 모두 생겼습니다. 보강 전 "공격 성공·미탐·대응 0" → 보강 후 "탐지·자동 차단·티켓". 2회차(10/29 S1-after-02)도 탐지·자동 차단·403·같은 계정 정상 출발지 200·원복까지 통과해 보강 후 2/5입니다. 3~5회차와 경계(8회)는 GELF TCP 조건으로 재예약, S4는 정의 반입 뒤입니다. 수집 조건이 다르므로(1·2회차 UDP, 이후 TCP) 회차별 backend SHA를 함께 적습니다([보강 변경 목록](A-S1-S4-보강변경목록.md)).

**Q14. 서로 다른 PC의 로그 시각을 빼는데 시계는 맞나?**
- 측정 전에 모든 VM·PC를 NTP에 맞추고 오차를 잽니다. 허용 오차는 1초입니다.
- 10/23 실측: A 포털 VM은 +154µs, A PC는 재동기화 뒤 +0.0024초 이내입니다. C·D는 남았습니다.
- 10/28: 포털 VM +7.5ms. A PC는 5일 사이 약 11초 빨라져 있었고(Windows 시간 동기화가 유지되지 않음) 보정 뒤 0.3초 이내. 그래서 증적 시각은 사람이 본 시각이 아니라 포털 VM·Graylog 기록으로 적고, 시험 직전마다 PC 시계를 비교합니다.
- 11/02: 포털 VM NTP 동기화 yes, C 외부 NTP 대비 약 20ms, D 약 -0.06초.
- 10/28 S1-after-01: A PC ↔ 포털 VM -0.08초, 포털 VM NTP 오프셋 -4.0ms, D pfSense 대비 -0.046초. 포털 기록이 B Kali 요청 시작보다 51ms 앞선 경우가 1건 있었는데, 같은 요청임을 확인하고(차단 뒤 그 출발지 요청 1건뿐) Kali 시계 차이로 정리했습니다(B 측정 약 +77ms). 판정에 쓰는 시각(포털·Graylog·n8n)은 서로 1초 안에서 맞았습니다.

**Q15. 포털이 출발지를 속을 수 있나(X-Forwarded-For 위조)?**
- 포털은 연결 주소(`remote_addr`)만 쓰고 X-Forwarded-For는 무시합니다. 위조 XFF를 무시하는 테스트가 통과했습니다(backend #2).
- 코드 위치: backend `src/haedam_portal/common.py` `client_ip()`(배포본 `f3faa1c`). 차단 검사·로그인 횟수 제한·대응 API 허용망 확인·이벤트 `src_ip`가 모두 이 함수를 씁니다. 포털 앞에 프록시가 없는 구성이 전제이고, 프록시를 두면 신뢰할 프록시 주소를 따로 정해야 합니다.

## 수집·재차단 (10/28 추가)

**Q16. 로그가 Graylog에 안 들어오면?**
- 과거엔 포털이 GELF를 **UDP**로 보내 도착을 확인하지 않았습니다. 10/28 S4-before-02에서 포털 401 10건 중 Graylog 9건(10:20:06 1건 유실), 10/23에도 4건 중 1건, **10/29 S1-after-02에서는 하필 9번째(조건 충족) 신호 1건이 유실**돼 탐지가 한 회차 늦었습니다(종단 MTTD 99.1초).
- **대책(해소): GELF TCP 전환.** `GELF_TRANSPORT=tcp`를 추가해 NUL 구분 GELF TCP로 보내고, 연결이 끊기면 같은 프레임(같은 event_id·시각)을 1·2·5초 간격으로 재전송합니다(backend #8 `f3faa1c`). 요청은 큐에만 넣고 데몬 스레드가 보내 포털 응답은 늦어지지 않습니다. 10/30 포털 VM 배포, 11/02 A VM→D TCP 12201 `ESTAB`·재시도 경고 0 확인.
- 남은 한계: 큐(1,000건)가 차면 그때 들어온 메시지는 버리고(경고), 포털을 재시작하면 큐에 남은 메시지는 사라집니다. 연결 직전 프레임이 재전송돼 **수신 중복이 생길 수 있어 D 집계는 고유 event_id 기준**으로 셉니다. 어느 방식이든 송신 성공이 Graylog 처리 증명은 아니고, 포털 원본(`events.jsonl`)이 실측 출처입니다.
- 결과표에는 포털 기록 건수와 Graylog 수신 건수를 함께 적습니다. S1 R1(10/29, UDP)과 TCP 전환 뒤 회차는 backend SHA(`9507fce`→`f3faa1c`)가 다른 별도 회차로 구분합니다. 경계 근처(8~9건)의 유실 1건이 판정을 바꿀 수 있다는 점은 TCP 전까지의 R2·경계 재예약 사유였습니다.
- 10/28 S1-after-01: 포털 401 27건 → Graylog 27건(유실 0, 도착 +0.03~0.05초). 유실이 없는 날도 있으니 건수는 매번 함께 적습니다.

**Q17. 차단을 풀자마자 같은 기록으로 다시 막히지 않나?**
- 막히지 않습니다. Graylog 알림은 같은 username + src_ip에 첫 알림 뒤 30분간 다시 나가지 않고(grace), 첫 알림은 9번째 실패 뒤라 grace가 끝날 때는 그 실패들이 30분 창 밖입니다. 차단 중 요청은 403이라 401로 세지지 않습니다.
- 해제 뒤 같은 출발지가 **실제로 다시 공격**하면 새 티켓으로 다시 막습니다. 티켓 저장소는 해제되지 않은 조치하고만 중복을 비교합니다(#62).
- grace 상태가 Graylog 재시작 뒤에도 남는지는 확인하지 못해, 시험 중에는 Graylog·n8n을 재시작하지 않습니다.
- **10/28 S1-after-01 실측:** 조건이 남아 있는 동안 같은 키로 Graylog 이벤트가 1분마다 16건 생겼지만 n8n 실행은 첫 1건뿐이었습니다(grace). 해제 뒤 30분 관찰(14:44:05~15:14:05) 동안 재차단 0건. 다만 이 구간은 첫 401이 30분 창에서 빠진 13:13부터 조건 자체가 없어 이벤트가 생길 수 없었으므로, 억제의 근거는 "16건 → 1회"로 듭니다.
- 해제 뒤 같은 출발지 재공격(15:16~): 9번째 401 → 재차단, **새 티켓 T-20261028-0003**이 열리고 이전 티켓은 "재차단: 새 회차로 분리"로 자동 종료됐습니다(#62 동작 확인).

**Q18. 같은 계정을 다른 IP에서 공격하면?**
- 묶기 키가 username + src_ip라 IP마다 별도 이벤트이고 각각 차단합니다. 티켓은 username으로 묶여 같은 티켓에 조치 줄이 추가됩니다.
- **10/28 S1-after-01 실측:** 같은 zz_a1을 `.13`에서 공격 → `.13`만 따로 탐지·차단(MTTD 53.4초)되고, 티켓은 새로 생기지 않고 `.11`의 T-20261028-0002에 조치 줄이 추가됐습니다(created:false). 이 동안 `.11` 차단도 그대로 유지됐습니다.
- 그래서 해제는 출발지별로 하고, 티켓이 restored가 되려면 그 티켓의 모든 출발지를 해제해야 합니다.
- 반대로 **같은 계정의 정상 사용자가 다른 IP에서 로그인하면** 막히지 않습니다. 10/29 S1-after-02: `.14` 차단 중 같은 `zz_s1_1029_r1`이 `.12`에서 로그인 200(14:55:39.215, 요청 4개 모두 200), 계정 잠금 없음.
