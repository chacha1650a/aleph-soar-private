# S1 출발지 차단 대응·원복 플레이북 (포털 쪽, A)

> 담당: whiteclover0542(A). 초안 2026-10-27. **S1 이벤트로 낸 차단은 아직 실행 전이다.** 아래 절차와 시각은 10/27 112 사전 시험(D n8n이 포털을 직접 호출)에서 실제로 확인한 것만 적었다.
> 팀 전체의 시험 순서·역할·중단 조건은 B의 [S1 연결 시험 카드](../school-s1-card-1026.md)(#67)를 따른다. 이 문서는 그중 포털 대응 API(112)와 포털 원본 대조를 맡은 A의 실행 절차다.

## 1. 대응 경로와 고정값

```
Graylog S1 이벤트(username + src_ip, count()>8 · 30분)
  → n8n haedam-30 → haedam-12 → POST /api/v1/response/ips/block {"ip": "<src_ip>"}
  → 포털: blocked_ips 1행(만료 없음) + web.ip_blocked 이벤트
  → 같은 출발지의 모든 요청 403 IP_BLOCKED, 다른 출발지는 그대로
해제: 사람이 판단 → n8n(또는 D 수동 실행) → POST /api/v1/response/ips/unblock
```

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 호출 허용 | 출발지 `RESPONSE_ALLOWED_CIDRS=10.250.0.100/32`(D) + `X-Response-Key` | 범위 밖은 키가 맞아도 403(10/26 VM 확인) |
| 본문 | `{"ip": "203.0.113.11"}`, `Content-Type: application/json`. `minutes` 없음 = 사람이 풀 때까지 | [API-CONTRACT](../API-CONTRACT.md) |
| `Idempotency-Key` | `{ticket_id}-112-{ip}-block` / `…-unblock`, 8~100자 | 같은 키 재전송은 첫 응답 재생 |
| 차단하지 못하는 주소 | 허용 대역(대응 호출자) 자신. 차단 요청은 403, 남은 행이 있어도 접근 안 막음 | 단위 테스트(SQLite 59·MySQL 63 passed), 랩 미시험 |
| 시험 출발지 | 공격 `203.0.113.11~19`(실행마다 바꿈), 정상 `203.0.113.100~109`·`.12` | 10/27 17:35 VM 경로 `203.0.113.0/24` tun0 |

## 2. 실행 전 확인 (A, 5분)

1. 포털 VM: 서비스 3개 active, tun0 `10.250.0.2`, 공격·정상 출발지 경로가 tun0, NTP 동기화, health 200, backend 커밋 기록.
2. DB: `blocked_ips` 0행, 공격 대상·정상 계정 잠금 없음. 남은 차단이 있으면 시작하지 않는다(B 카드 1단계).
3. 이번 실행의 `ticket_id`가 사전 시험에서 쓴 번호와 겹치지 않는지 확인한다. 겹치면 포털이 예전 응답을 재생해 **실제로는 차단하지 않는다**(10/27 사전 시험은 저장소 미사용 번호 `T-20261027-9901` 사용).
4. 시작 시각을 C·D에게 알린다. 117·S12 등 다른 시험과 시간을 겹치지 않는다.

## 4. 해제 (사람이 판단)

1. 해제 전: 같은 출발지의 다른 열린 티켓·진행 중 작업이 없는지 C·D와 대조한다(B 카드 6단계).
2. D가 **새 키**(`…-unblock`)로 해제를 부른다. 차단 키를 다시 쓰면 차단 응답이 재생된다.
3. 확인: `web.ip_unblocked`, `blocked_ips` 0행, 공격 출발지 GET 200, 정상 사용자 로그인 유지. 10/27 실제: 해제 17:06:30.233 → 0행 → `.11` 200 17:11:36.327.
4. C가 티켓 released → 사람이 close. 다음 회차는 새 출발지·새 `ticket_id`·새 키로 한다.

## 5. 막혔을 때 (20분 안에 증거 공유)

공유 형식: 실행 버전·시각 / 기대 / 실제 응답·로그 / 필요한 도움.

| 증상 | 먼저 볼 것 | 10/27 사례 |
| --- | --- | --- |
| 400 `VALIDATION_ERROR` | 응답 `error.message`. "JSON 객체를 입력해 주세요."면 본문이 JSON 객체로 도착하지 않음 → 보낸 쪽 설정을 먼저 대조(아래) | 3회 400 → 실제 요청에 `Content-Length: 0`, `Content-Type` 없음 = n8n Send Body 꺼짐(D #79). 추정만 바꿔 재시도하지 말고 실제 전송 설정·본문을 먼저 본다 |
| 같은 키 재시도 결과가 이상함 | 키가 저장됐는지(`response_receipts` 행 수). 400은 키 처리 전에 끝나 저장되지 않는다 | 400 뒤 같은 키 재사용 가능 확인 |
| 403 `FORBIDDEN` | 호출 출발지가 허용 대역인지, 키, 차단 대상이 허용 대역인지 | — |
| 409 | 같은 키로 한 번만 재시도, 다시 409면 멈추고 포털 상태·키 규칙 확인 | — |
| 포털 응답 없음 | VPN(`journalctl -u openvpn-client@team-a`), DB `10.10.20.10:3306` 연결 | 17:46 B 쪽 VPN TLS 실패로 DB 연결 끊김, health 시간 초과 |

요청 대조는 인증값이 화면·파일에 먼저 나오지 않는 방법만 쓴다.

1. D: n8n 실행 기록에서 HTTP Request 노드의 Send Body·Body Content Type·본문 필드를 본다. `X-Response-Key`는 n8n 자격증명(Header Auth)으로 넣어 실행 기록에 값이 남지 않게 한다. 헤더 값을 노드에 직접 적었다면 그 화면은 공유하지 않는다.
2. A: 포털 수신 결과는 `s1_check.py`(또는 `--jsonl`)의 `web.request` 상태 코드로 본다.
3. 패킷 원문 캡처(`tcpdump -A` 등)는 쓰지 않는다. 줄 단위 필터는 TCP 경계에서 나뉜 헤더 값을 가리지 못한다(B 10/28 리뷰에서 분할 헤더로 재현).

## 6. 사람이 판단할 경계

- **공유 출발지:** 차단은 출발지 단위라 같은 NAT 뒤 정상 사용자도 함께 막힌다. 랩에서는 출발지를 나눠 시험하지만 실제 운영이라면 해제 판단에 이 영향을 넣는다(미검증, 악용 점검 항목).
- **해제 시점:** S1은 자동 만료가 없다. 오탐 확인·공격 종료 판단은 사람이 하고, 자동 해제(haedam-50)는 쓰지 않는다.
- **기록:** 비밀번호·`X-Response-Key`·세션 값은 일지·증적·캡처에 남기지 않는다. 원본 이벤트 발췌는 `s1_check.py --jsonl` 출력으로 증적 폴더(`docs/capstone/evidence/S01/after/<run_id>/`)에 둔다.
