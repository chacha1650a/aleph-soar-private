이 문서는 3단계 "공격 시나리오 정리"의 결과물입니다. **공격자가 무엇을 하는가**와 **그 결과 어떤 신호가 나와야 하는가**만 적습니다. 탐지 규칙·대응·원복의 상세는 [A-작업순서](../A-작업순서.md) 6·7단계에 있고, 입력표(정상/경계/창 밖/순서/혼합)도 그쪽을 따릅니다.

## 공통 전제

- **대상:** 해담시청 민원 포털(Flask) 로그인 `POST /api/v1/auth/login`, 본문 `{username, password}`.
- **출발지:** 포털은 연결 주소(`remote_addr`)만 보고 `X-Forwarded-For`는 무시합니다(PORTAL-API 인증·공통). pfSense는 NAT가 없어 Kali 주소가 그대로 `src_ip`로 남습니다. 실행마다 A 대역(203.0.113.11~19)에서 출발지를 바꿉니다.
- **신호:** 로그인 실패는 `login-bruteforce`, 성공은 `login-success` GELF로 Graylog에 갑니다. 두 신호 모두 `username`·`src_ip`를 남깁니다. `outcome` 필드는 두지 않고 rule 값으로 실패/성공을 구분합니다(2단계 결정).
- **잠금 응답:** 잠긴 계정의 로그인은 비밀번호 오류와 **같은 401**입니다(423 아님, PR #20 5.4). 그래서 잠금 여부는 응답 코드가 아니라 **관리자 화면의 계정 상태("잠김")**로 확인합니다.

### 공격 도구 — 열린 항목

가이드의 도구 후보는 Hydra지만, 해담 포털 로그인은 **JSON 본문 + `X-CSRF-Token` 헤더**를 요구하고 로그인마다 CSRF를 회전합니다(PORTAL-API). Hydra의 `http-post-form`은 폼 인코딩 기준이라 바로 맞지 않을 수 있습니다. 두 가지 안 중 3단계 "재현 스크립트 설계"에서 정합니다.

1. **작은 Python 스크립트**(`requests`): `GET /auth/me`로 CSRF 토큰·세션 쿠키를 받고, JSON으로 로그인 시도를 보냅니다. 간격·횟수·출발지를 그대로 제어할 수 있어 저속 S1에 맞습니다. (유력안)
2. **Hydra** + JSON 지원 모듈/프록시: 설정이 더 번거롭고 CSRF 회전 처리가 필요합니다.

어느 쪽이든 비밀번호 목록은 `zz_` 계정 전용 소형 목록이고, 시도한 값은 저장하지 않습니다.

## S1 · 저속 브루트포스 (원본 153, MVP 우선 후보)

**공격자 이야기.** 공무원 계정 하나를 골라, 2분 단위 같은 짧은 창 임계(예: 2분 6회)를 피하려고 **간격을 두고 천천히** 비밀번호를 추측합니다(ATT&CK T1110.001). 짧은 창 규칙만 있으면 놓치는 공격을, 계정 기준으로 30분 넓게 세어 잡는 것이 이 케이스입니다.

**공격 진행(발동 실행).**
1. `zz_` 테스트 계정이 잠금 상태가 아님을 사전에 기록합니다(관리자 화면).
2. 한 출발지(예: 203.0.113.11)에서 같은 계정에 로그인 실패를 **30분 창 안에 나눠** 넣습니다. 한 번에 몰지 않고, 2분당 6회 미만이 되도록 간격을 둡니다.
3. 실패 **8건까지는 미발동**, **9건째**에서 S1 이벤트가 떠야 합니다(`count()>8`).

**나와야 하는 신호.**
- Graylog 검색 `rule:login-bruteforce username:zz_… src_ip:203.0.113.11` → 9건.
- 각 신호에 `username`·`src_ip`가 남고, 묶기 키는 `username + src_ip`(차단할 출발지가 이벤트에 남아야 함).
- 잠긴 뒤의 추가 시도는 `locked=1`로 계속 기록됩니다(이 신호를 S1 카운트에 넣을지는 미정, [A-작업순서](../A-작업순서.md) 미정 목록).

**성공 판정(대응·효과는 6·7단계).** S1 이벤트 1건 → n8n 112가 그 `src_ip`를 차단 → 같은 IP의 새 요청 403 `IP_BLOCKED` → 같은 계정의 **다른 정상 출발지(203.0.113.100~109)는 계속 로그인 가능**.

**흔한 실패(가이드).** 다른 계정 실패가 섞이면 `username`별로 따로 세야 합니다. 짧은 창 규칙(2분 6회)을 같이 쓰면 같은 공격에 두 번 대응하지 않는지 중복도 확인합니다.

## S4 · 실패 뒤 성공 = 계정 탈취 (원본 156, MVP 우선 후보)

**공격자 이야기.** 같은 계정에 여러 번 실패하다가 **결국 비밀번호를 맞혀 로그인에 성공**합니다. 실패만 반복하는 S1과 달리, 실패와 성공이 한 창 안에 함께 있으면 비밀번호가 뚫린 것으로 보고 계정을 잠급니다.

**공격 진행(발동 실행).**
1. 실패만 6건 이상 → 신호 종류가 1개뿐이라 S4 **미발동**(S1으로는 잡힐 수 있음).
2. `zz_` 계정에 **실패 5건 + 성공 1건(합계 6건)**을 10분 창 안에 넣습니다 → S4 발동(`card(rule)>1` 그리고 `count()>5`). 합계 5건(실패 4 + 성공 1)은 경계 바로 아래라 미발동.
3. 성공 뒤 계정이 잠겨 **다음 로그인이 거부(401 + 관리자 화면 "잠김")**되는지 확인합니다.

**나와야 하는 신호.**
- 같은 `username + src_ip`의 `login-bruteforce`(실패)와 `login-success`(성공) 신호(시각 순서는 판정에 쓰지 않음, 아래 "순서 조건").
- S4 이벤트 1건, 계정 잠김, 티켓 1건.

**순서 조건 — 확정(10/21).** `card(rule)>1`은 "실패·성공이 둘 다 있다"만 증명하고 "실패 **뒤** 성공"이라는 순서는 증명하지 못합니다. 가이드·합의본 모두 이 한계를 적습니다(원본 156에 Wazuh 합성 규칙 미발동 기록 있음). **S4는 순서를 요구하지 않고, 10분 창 안에 두 신호가 함께 있으면 발동합니다.** 다만 순서를 안 보면 정상 사용자가 로그인 성공 뒤 다른 출발지의 실패와 합쳐져 잠길 수 있어, **묶기 키를 `username + src_ip`로 확정**했습니다(A 제안, 10/21 김명준 결정 — 제출본 ④ 이벤트 조건·⑤ 5.9). 같은 출발지의 실패·성공만 묶이므로 다른 출발지의 정상 성공은 합쳐지지 않고, 여러 출발지로 나눈 공격은 S4 범위 밖입니다(S1과 같음). 따라서 "순서 반대"(성공 뒤 실패) 입력도 **발동**으로 기대합니다.

**성공 판정(대응·효과는 6·7단계).** S4 이벤트 1건 → n8n 111이 계정 잠금 + 기존 세션 회수 → 대응 전 발급 세션 거부 → 재로그인 401(관리자 화면 잠김) → 티켓 1건. **원복:** 비밀번호 재설정(`/response/accounts/{id}/reset`) 뒤 잠금 해제, 회수한 세션은 되살리지 않음.

## 원복 절차

공통 순서: **IP 차단 해제 → 계정 잠금 해제 → 티켓 종료 → 샘플 로그·규칙 원복** → 사전 상태(1단계 기록)와 같은지 재확인.

- **S1:** `POST /response/ips/unblock {ip}`로 출발지 차단 해제 → 그 IP의 정상 요청이 다시 200. 차단은 만료 없이 사람이 해제(대응호출방식 초안 6절 2번).
- **S4:** `POST /response/accounts/{id}/reset {new_password}`로 비밀번호 재설정과 동시에 잠금 해제 → 새 비밀번호로 로그인 성공. **회수한 세션은 되살리지 않음**(원복 후에도 무효 유지). 재설정 전에는 잠금을 풀지 않습니다.

## 재현 스크립트 설계 — `scripts/replay/S01.sh`·`S04.sh`

도구는 위 "공격 도구" 2안 중 Python 스크립트가 유력안입니다. 각 스크립트는 인자로 모드를 받아 출발지·계정·간격을 바꿉니다. 비밀번호 목록은 `zz_` 전용 소형 목록이고 시도 값은 저장하지 않습니다.

구현: `scripts/replay/replay.py`(stdlib만, Hydra 아님). `replay.py S1 --mode trigger` 식으로 부른다. `--dry-run`·`--self-test`로 랩 없이 모드 정의를 확인한다(통과). 실제 실행·효과 확인은 5·6·7단계.

| 모드 | replay.py S1 | replay.py S4 | 기대 |
| --- | --- | --- | --- |
| `normal` | 정상 로그인 1~2회 | 정상 로그인 1회 | 미발동 |
| `below` | 30분 창에 실패 8회 | 10분 창에 실패 4 + 성공 1 | 미발동 |
| `trigger` | 30분 창에 실패 9회 | 10분 창에 실패 5 + 성공 1 | 발동 1건 |

공통 인자(안): `--src-ip`(출발지), `--user`(zz_ 계정), 모드별 횟수·간격은 스크립트 안에 상수로. 실행 사이 원복과 출발지·계정 변경은 7단계 "반복 시험 초기화"를 따릅니다.
