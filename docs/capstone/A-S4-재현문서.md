## 1. 기대 결과 (이게 나오면 재현 성공)

같은 `username`+`src_ip`로 10분 안에 로그인 실패(401)와 성공(200)이 **모두** 있고 합계 6건 이상이면:
1. Graylog S4 이벤트 1건(`card(rule)>1 & count()>5`) →
2. n8n(haedam-31 → haedam-13)이 그 **username**을 포털 111로 잠금 + 그 계정 세션 전부 회수 + C 티켓 1건 →
3. 공격자 창 다음 요청에서 비로그인, 같은 비밀번호로 재로그인 **401**, 관리자 화면 "잠김" (효과) →
4. **다른 정상 사용자(`zz_n1`, `.100`)는 로그인·민원 업무 200** (오잠금 없음) →
5. 사람이 판단해 비밀번호 재설정(탈취) → 옛 세션 무효 유지·새 로그인 200, 티켓 closed (원복).

## 3. 입력 (B)

- 한 출발지에서 대상 계정에 **401 5회 → 맞는 비밀번호로 200 1회**(합계 6건), 약 60초 간격 → 전체가 10분 창 안.
- 401은 **5회만**. 9회 이상이면 같은 출발지로 S1(30분 9건)까지 채워 출발지 차단이 같이 나간다. 404는 넣지 않는다(S8 조건 회피).
- 200 직후 공격자 창에서 `/auth/me`로 사용자가 보이는지 확인(세션 확보).
- 회차마다 **계정·출발지·run_id·출력 파일을 분리**한다.
- 입력 도구는 B Kali에 있고 저장소 반영 전이다. 손으로 해도 횟수·간격만 지키면 된다.

## 4. 감시·대조 (A, 포털 원본)

GO 직전에 **회차별 새 파일**로 감시를 켠다(기존 파일이면 거부):

```powershell
cmd /c 'ssh haedam@<포털 VM> "cd ~/haedam-portal-backend && python3 -u - /home/haedam/<run_id>.jsonl <공격 src_ip>,<정상 src_ip>" < lab\s1s4\watch_src.py'
```

- `Ctrl+C`는 PC 쪽 ssh만 닫는다. 끝나면 VM에서 `pkill -f 'python3 -u - /home/haedam/<run_id>'` → `pgrep -f 'python3 -u - /home/haedam/'`를 **따로** 실행해 0건을 확인한다(stdin으로 실행해 `watch_src` 이름으로는 안 잡힘. 한 줄로 보내면 ssh 셸이 같이 끝나 확인이 안 됨).
- `auth.account_locked`·`auth.password_reset`은 출발지가 n8n(`10.250.0.100`)·관리자 PC라 감시 파일에 없다. VM `events.jsonl`에서 시각 구간 + username으로 따로 찾는다.
- 잠금 직후·재설정 뒤·종료 때 `s1_precheck.py`로 `(잠금, 세션)` 값을 기록한다.

```powershell
cmd /c 'ssh haedam@<포털 VM> "cd ~/haedam-portal-backend && .venv/bin/python - <대상>,zz_n1 <공격 src_ip>,<정상 src_ip>" < lab\s1s4\s1_precheck.py'
```

- 끝나면 감시 파일을 증적 폴더 `portal-events.jsonl`로 복사하고 SHA256·줄 수를 VM 값과 대조, 민감 문자열(password·token·csrf·cookie·secret·authorization) 0건을 확인한다.

## 5. 단계별 확인·판정 (어느 값이 어디서 나오나)

| 단계 | 어디서 | 기대 |
| --- | --- | --- |
| 조건 충족 | **포털 원본** 성공 `auth.login_succeeded`(6번째 신호) event_id | 시작점. Graylog `condition_met_at`은 1분 평가 창 끝이라 시작점으로 쓰지 않음 |
| 탐지 | D Graylog `detected_at` / n8n `received_at` | S4 이벤트 1건, 키 `username\|src_ip` |
| 자동 잠금 | 포털 `auth.account_locked`(호출자 `10.250.0.100`) · n8n 실행 · DB `locked=1`·세션 0 | 탐지 뒤 1초 안팎 |
| 티켓 | C 저장소 | 새 티켓 1건, 조치 `111/portal/lock/<username>` |
| 효과 | 공격자 창 `/auth/me` **200 + user null**(401 아님), 같은 비밀번호 재로그인 **401**, 관리자 화면 "잠김", 정상 `zz_n1` 로그인·민원 목록 200 | 오잠금 0 |
| 원복 | 관리자 화면 "비밀번호 재설정" → `auth.password_reset` · DB `locked=0`·세션 0 → 공격자 창 여전히 비로그인 → 새 비밀번호 로그인 200 | 새 로그인은 **한 번에 맞게**(오입력이 쌓이면 S4·S1 재발동 가능, grace 10분은 키별) |
| 종료 | C 해제 기록 `111/portal/unlock/<username>`(lock에 연결) → closed, `locked=0`·세션 0, `blocked_ips` 0행 | 사전 상태로 복귀 |

- 오탐이면 재설정 대신 관리자 화면 "오탐 해제(비밀번호 유지)"(admin unlock). 둘 다 회수된 세션은 복원하지 않는다.
- 지표는 **파이프라인 지연**이다. Graylog 검색 주기(1분)를 함께 적는다. C 화면 MTTR은 효과 기록(사람 입력) 시각 기준이라 자동 대응 시간과 따로 적는다.

## 8. 한계 (재현 결과 해석에 함께 적는다)

- 실측 1회뿐. 임계 바로 아래(실패 4 + 성공 1)·한 종류 rule만·정상 업무 30분은 실측 전(오프라인 재생 8/8만).
- 세션 회수의 user null은 B 화면 관측. 포털 `web.request`에는 사용자명이 없어 원본으로는 200만 확인된다.
- 분산 출발지로 나눈 추측(실패와 성공의 출발지가 다름)은 username+src_ip 묶기 밖(미탐).
- 해제는 설계상 사람 판단(자동 원복 아님). 오탐 경로(admin unlock)는 보강 후 회차에서 실측 전.
- 효과 기록은 D 수동이라 C 화면 MTTR(346초)에 기록 지연이 포함된다.
