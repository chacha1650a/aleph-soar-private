## 3. 구현할 개선 사항

### A. 상태와 증적의 역할 정리

- `docs/PROGRESS.md`를 최신 현황 요약의 기준으로 정한다. 행은 작업/사람 담당/상태/남은 조건/다음 행동/근거/확인 시각을 포함한다.
- 개인 일지는 상세 이력, workplan은 정적 의존성·인수 조건, 시험별 기록은 해당 실행의 불변 증적으로 구분한다. 서로 다른 실시간 상태 저장소를 여러 개 만들지 않는다.
- 상태는 최소한 준비·입력 완료·외부 대조 대기·최종 완료를 구분한다. 미확인과 실패, 원인별 0건도 구분한다.
- 사람 보고·직접 측정·코드 검사·합성 시험·실제 연결 결과의 근거 범위를 표시한다.

### B. 기존 스킬 개선

- `aleph-task-plan`: 시작 전 A/B/C/D가 동시에 확인할 선행 조건과 파일 소유자를 정한다. 하나가 대기 중일 때 독립 작업을 구분해 제시한다.
- `aleph-scenario-check`: 시험 번호·출발지·대상·버전·입력 수·실측 구간·예상 원본/대응·관측 정책을 입력 전에 고정한다. 준비·dry_run·본 측정은 구분한다.
- 같은 스킬에서 입력 후 A 원본/앱 상태, B 입력/경계, C 티켓, D 수신/정의/n8n을 병렬로 확인하도록 한다. 담당별 준비 회신 1회·최종 회신 1회를 기본으로 하고 오류·변경은 즉시 알린다.
- `aleph-handoff`: 확인한 범위·미확인·다음 담당·필요한 입력·증적을 짧은 공통 형식으로 전달한다. 이미 확인한 내용을 정보 변화 없이 반복 요구하지 않는다.
- 공통 계약 변경이 필요한 부분에만 `aleph-contract-change`를 적용한다. 우선 기존 스킬을 개선하고 새 스킬 필요성은 중복을 확인한 뒤 판단한다.

### C. 에이전트 역할 개선

- coordinator는 통합 일정·의존성·완료 근거를 관리하고 모든 상세 답변을 대신 전달하는 구조를 줄인다.
- A↔D는 포털 이벤트/대응 API, C↔D는 티켓/Wazuh/인증, B↔D는 pfSense/Suricata 연결을 직접 맞추고 공통 현황에 결과를 남긴다. 실제 메시지 발송은 명시 지시가 있을 때 수행한다.
- backend/detection/dashboard 역할은 자신이 바꿀 파일·제공할 인터페이스·실제 연결 미검증 부분을 명시한다. 사람 담당과 개발 역할의 대응표를 둔다.
- reviewer는 통합 실행의 실제 효과·원복을 독립 확인한다. 로컬 테스트 통과를 외부 연결 성공으로 확대하지 않는다.
- 실제 병렬 에이전트 실행 기능과 역할 문서 개선은 별개다. 이 문서 작성으로 에이전트를 생성하거나 전역 모델·권한을 바꾸지 않는다.

### D. 오케스트레이션 개선

- 현재 `tools/team.py`는 **상태를 저장하지 않는 DAG 검사·준비 후보·brief 도구**다. AI 실행기나 팀 공유 상태 자동 갱신기로 간주하지 않는다.
- 기존 P01/B01/D01 등의 스켈레톤 그래프를 실제 포털 저장소·수집기·Graylog·n8n·티켓·원복 연결과 대조한다. 역사적 작업 ID와 완료 근거를 보존하며 새 작업/메타데이터를 설계한다.
- ‘코드 준비→수신 준비→연결 검증→실측 입력→병렬 대조→효과/원복→최종 완료’ 의존성을 표현한다. 한 담당의 전체 작업 완료를 다른 모든 담당의 선행 조건으로 묶지 않는다.
- 조회·brief에 준비 조건, 미확인 입력, 다음 담당, 독립 진행 후보를 제시하는 최소 확장부터 검토한다. 공유 상태 저장·에이전트 자동 실행까지 한 번에 구현하지 않는다.
- `--done`은 조율자가 검증한 선행 ID 입력이며 실제 공유 완료 상태가 아니다. 명령 입력만으로 증적 없는 완료가 생기지 않게 유지한다.
- 외부 저장소 경로는 현재 검증기의 저장소 내부 경로 제한과 충돌할 수 있다. 기존 경로 검사를 느슨하게 풀기보다 명시적인 외부 참조 표현을 검토한다.

### E. 실제 팀 운용에 연결

- 통합 구간 시작 전 A/B/C/D 준비 상태를 한 번에 수집한다. 준비됨/작업 필요/미확인과 근거를 받는다.
- 실측 중 관련 서비스·경로·파서·대응 변경을 조율하고, 관련 없는 문서/격리 개발은 진행할 수 있게 한다. 버전·경로가 바뀌면 영향받는 준비 조건만 재확인한다.
- 수동 시험은 별도 출발지·시간 구간으로 구분한다. 같은 출발지를 재사용할 때는 기존 측정 구간과 영향 이력을 대조한다.
- 첫 자동 대응 완주 후보는 S8로 제안한다. 원본/필드 대조가 완료된 경로를 활용해 탐지→실제 차단→티켓→해제→정상 사용을 확인하고 S10에 재사용한다. 팀 합의·구현 완료로 표시하지 않는다.

## 8. 추가 검토 · 필요한 포트 3개 포워딩 제안

**사용자 확인: ‘3회’는 3단계 중첩 NAT나 시험 3회가 아니라, 필요한 포트 3개를 포워딩하는 의미다.** 집에서 필요성과 연결 구성을 검토할 과제로 추가한다. 포트 번호·용도·목적지 3개는 아직 지정되지 않았으므로 확정하지 않는다.

### 권고 방향

- 반복되는 연결 준비를 줄이기 위해, 팀이 계속 사용하는 서비스 3개를 선정하고 **담당·주소·프로토콜·포트·연결 시험 방법을 고정하는 안을 검토할 것을 권한다.** 연결할 서비스가 실제 가동 중이고 해당 구간에서 포워딩이 필요할 때 적용 후보로 삼는다.
- 먼저 집→학원 접근인지, A↔D/C↔D 팀 VPN 내부 연결인지, 호스트→VM/컨테이너 연결인지 구간을 확정한다. 서로 다른 목적지에 있는 3개 포트를 하나의 장비에서 모두 포워딩할 수 있다고 가정하지 않는다.
- 포트 포워딩은 패킷의 목적지 주소/포트를 내부 대상으로 변환하는 inbound NAT다. 기존 VPN 경로로 직접 도달하는 연결은 NAT 필요성과 방화벽 허용 필요성을 구분한다. 접근 제한이 필요한 서비스에는 VPN 사용을 우선 검토하는 것이 Netgate의 권고다. [포트 포워딩 공식 문서](https://docs.netgate.com/pfsense/en/latest/nat/port-forwards.html)
- 외부 공개 포트 3개를 임의로 정하는 대신 실제 필요한 서비스부터 선정한다. TCP/UDP도 각 서비스에 맞춰 정한다. 알려진 포트 번호를 후보로 사용할 경우 현재 수신·배치·담당을 다시 확인한다.
- 연결 경로를 고정하는 효과와 앱 미가동·인증·파싱·DB 연결 문제는 구분한다. 이번 추가 제안만으로 통합 속도 향상이나 기존 장애 해결을 확정하지 않는다.
