## 2. 포털 대응 API 공통 규칙 (구현 기준)

포털 대응 API는 backend #1(계정)·#2(IP 차단)에 구현돼 있고(Draft·미병합), 원본 계약은 [PR #19](https://github.com/NoBugs-Aleph/aleph-soar-capstone/pull/19)의 `docs/haedam/PORTAL-API.md` "자동화 경계"입니다. 이 절은 n8n이 부를 때 알아야 할 것만 옮깁니다. 둘이 다르면 PORTAL-API.md가 맞습니다. 원안(관리망 + `X-Automation-Key`, 401/403 구분, 422 `protected_target`, `already_applied`)은 B 답변 1절 표대로 구현에 맞췄습니다.

**호출 조건 (둘 다 만족해야 함)**

1. 출발지가 허용 대역 `RESPONSE_ALLOWED_CIDRS`(관리망 `10.10.30.0/24`, 관제 PC 10.10.30.10, 계획값) 안. 포털은 연결 주소(`remote_addr`)만 보고 `X-Forwarded-For`는 무시합니다.
2. 헤더 `X-Response-Key: <키>`가 일치. 키는 n8n 자격 증명과 포털 환경 변수에만 두고 저장소·로그·티켓에 남기지 않습니다. 대상마다 키를 따로 둡니다(포털 키, 대시보드 키).

둘 중 하나라도 틀리면 **403 `FORBIDDEN`**입니다(어느 검사에서 막혔는지 밖에 알리지 않음).

**`Idempotency-Key` 필수 (8~100자):** 같은 키로 다시 보내면 처음 응답 전체를 그대로 돌려줍니다. 다른 키로 이미 차단·해제된 상태를 다시 요청하면 `changed:false`(원안의 `already_applied`). 같은 키를 다른 요청에 쓰면 409. n8n은 재시도 때 같은 키를 씁니다. 키 규칙 예: `{ticket_id}-{봇}-{대상}-{block|unblock}`(10/24 API-CONTRACT에 확정).

**자기 차단 방지:** 허용 대역 안의 주소를 block하면 403으로 거부하고, 차단 행이 남아 있어도 접근을 막지 않습니다. 포털 자신과 pfSense 주소는 포털에 출발지로 들어오지 않아 따로 막지 않습니다.

**응답 모양:** 성공 `{"success": true, "data": {...}}`, 실패 `{"success": false, "error": {"code", "message"}}`.

```json
{"success": true, "data": {"ip": "203.0.113.11", "blocked": true, "changed": true, "expires_at": null}}
```

```json
{"success": true, "data": {"user_id": 7, "locked": true, "changed": true, "revoked_sessions": 2}}
```

| 상태 코드 | 뜻 | n8n 처리 |
| --- | --- | --- |
| 200 `changed:true` / `changed:false` | 조치 반영됨(새로 반영 / 이미 그 상태) | 효과 확인으로 진행 |
| 400 `VALIDATION_ERROR` | 요청 형식 오류(IP 형식, `Idempotency-Key` 길이 등) | 조치 실패로 기록, 재시도 안 함 |
| 403 `FORBIDDEN` | 키·출발지 문제, 또는 허용 대역 주소 차단 시도(자기 차단 방지) | 조치 실패(거부)로 기록, 설정 점검 |
| 404 `NOT_FOUND` | 없는 계정. 관리자 계정도 대상에서 빠지는데, 그때의 응답 코드는 PORTAL-API.md에 없어 구현 확인 필요 | 조치 실패로 기록 |
| 409 `CONFLICT` | 동시 요청 충돌, 또는 같은 키를 다른 요청에 씀 | 동시 충돌은 **같은 키로 1회 재시도**. 키 재사용이면 워크플로 오류로 기록 |
| 5xx / 시간 초과(5초) | 포털 문제 | **같은 키로 1회만 재시도**, 그래도 실패면 조치 실패 |

**증적:** 포털 이벤트 `web.ip_blocked`·`web.ip_unblocked`(대응 호출자는 `src_ip`, 대상은 `details.target_ip`), `auth.account_locked`·`auth.password_reset`. 키·비밀번호·요청 본문은 넣지 않습니다.

## 3. 경로 (포털, 구현됨)

포털 경로는 모두 `/api/v1` 아래입니다. 본문에 `ticket_id`·`case_id`·`reason`은 넣지 않습니다(원안에서 뺌). 티켓 연결과 MTTR 시각은 n8n이 티켓에 기록합니다.

| 봇 | 메서드·경로 | 본문 | 하는 일 |
| --- | --- | --- | --- |
| 112 차단 | `POST /response/ips/block` | `ip` (`minutes`는 보내지 않음, 6절 2번) | 이 출발지의 모든 요청(화면·정적 파일·API)을 403 `IP_BLOCKED`로 거부 |
| 112 해제(원복) | `POST /response/ips/unblock` | `ip` | 차단 해제. 케이스와 관계없이 그 IP를 풂(같은 IP를 막은 다른 자리의 열린 티켓이 있으면 해제 보류) |
| 112 목록 | `GET /response/ips` | — | 현재 유효한 차단 `{items:[{ip,expires_at,created_at}]}`. 대응 키가 필요해 관제 PC에서만 확인 |
| 111 잠금 | `POST /response/accounts/{id}/lock` | — | 로그인 거부 + 그 계정의 기존 세션 전부 회수. 응답 `revoked_sessions` |
| 111 원복 | `POST /response/accounts/{id}/reset` | `new_password` | 새 비밀번호로 재설정하며 잠금 해제. 회수한 세션은 되살리지 않음 |

- **계정 대상 간극:** 지금은 숫자 `user_id`만 받는데 S4 이벤트에는 `username`만 남습니다. B가 username으로도 잠글 수 있게 백엔드·계약을 고치기로 했습니다(B 추가 항목). 고치기 전에는 n8n이 S4를 자동으로 잠글 수 없습니다.
- **계정 상태 조회 없음:** 잠금 상태는 잠금 응답(`locked:true`)·`auth.account_locked` 이벤트·관리자 화면 "잠김"으로 확인합니다(6절 4번). 필요하면 나중에 `GET`을 추가합니다.
- 잠긴 계정의 로그인은 비밀번호 오류와 같은 401입니다(423 아님).

## 4. 효과 확인을 두 단계로 나눔

n8n은 관리망에서 호출하므로 공격자 IP로 다시 접속해 볼 수 없습니다. 그래서 효과 확인을 둘로 나눠 기록하자고 제안합니다.

| 단계 | 누가 | 무엇을 | 티켓 필드 |
| --- | --- | --- | --- |
| ① 반영 확인 | n8n 자동 | IP는 조치 직후 `GET /response/ips`에 들어 있는지, 계정은 잠금 응답 `locked:true`와 `auth.account_locked` 이벤트 | `applied_verified` |
| ② 실제 효과 | 시험 스크립트(각 자리) | 공격 출발지에서 다시 시도해 403·로그인 거부를 확인, 정상 출발지는 계속 동작하는지 확인 | `effect_verified` |

S12는 n8n이 헬스체크(116)로 회복을 직접 재므로 ②도 자동입니다. ①만 통과한 상태를 "효과 확인 완료"로 적지 않습니다.

## 5. 티켓에 남길 공통 대응 결과 (모든 대상)

포털이든 pfSense·Wazuh든 n8n이 아래 모양으로 바꿔 티켓 저장소(114)에 넣습니다.

```json
{"bot": 112, "target": "203.0.113.11", "via": "portal",
 "result": "applied", "applied_verified": true, "effect_verified": null,
 "requested_at": "...", "finished_at": "...", "detail": "403 confirmed by status API"}
```

- `via`: `portal` / `pfsense` / `wazuh`
- `result`: `applied` / `already_applied` / `failed` / `rejected` / `released` (포털 `changed:true` → `applied`, `changed:false` → `already_applied`, 자기 차단 방지 403 → `rejected`)
- `effect_verified`: `null`은 아직 확인 안 함. MTTD·MTTR 계산은 이 시각들을 씁니다(정량평가 PR #23).
- 지금 `incident.schema.json`의 `response_state`(not_requested·pending·succeeded·failed·restored)와 대응 관계를 계약 변경(1-3) 때 같이 맞춥니다.
