### 8-1. Wazuh → Graylog 연동 방식

| 안 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. syslog 출력(JSON) → Graylog Syslog 입력 (권장)** | Wazuh 매니저 `ossec.conf`의 `syslog_output`을 JSON 형식으로 켜고, Graylog Syslog TCP 입력으로 받음 | 설정 몇 줄, 별도 설치 없음, 알림 JSON이 그대로 필드로 들어와 정규화 쉬움 | 알림이 매니저를 거친 것만 전달됨(원본 로그 아님), 재전송 보장이 약해 TCP 사용 권장 |
| B. Filebeat/Sidecar로 `alerts.json` 수집 | Wazuh 알림 파일을 수집기가 읽어 전송 | 유실에 강함 | 매니저에 수집기 설치·관리, RAM 추가 |
| C. Wazuh 연동(integratord)으로 n8n webhook 직접 호출 | 알림을 Graylog를 거치지 않고 n8n에 전달 | 지연 짧음 | 합의본의 "Graylog가 모든 신호를 수집·상관" 구조와 어긋남, S7 상관(FIM+웹 접근)을 Graylog에서 못 함 |

- 의견: **A**로 시작합니다. S7 상관 판정은 Graylog 이벤트 정의에서 하기로 되어 있어(기획서 초안 ④) 모든 신호가 Graylog를 지나야 합니다.
- 경로 정규화(파일시스템 경로 → 웹 루트 상대 경로)는 Graylog 파이프라인 한 곳에서 합니다([계약안 README](../docs/s7-draft/README.md) 5절).
- 확인할 것: `syslog_output`의 JSON 필드 구성과 레벨 필터, Wazuh 인덱서(OpenSearch)와 Graylog 저장소가 RAM을 같이 쓰는 문제(8GB 권장 Wazuh + Graylog).

### 8-2. 변조 파일 복구: n8n vs Wazuh active response

| 구분 | n8n만 | Wazuh active response(AR)만 | 혼합 (권장) |
| --- | --- | --- | --- |
| 실행 위치 | n8n이 대상 서버에 접근(SSH 등) | 에이전트가 있는 서버에서 로컬 스크립트 | n8n이 판단·기록, AR이 서버에서 복구 |
| 시연 요건 | "n8n 자동 대응" 장면 충족 | n8n 실행 기록이 없어 공지 장면 부족 | 충족 |
| 대상 서버 노출 | n8n에 서버 접속 권한을 줘야 함 | 불필요 | Wazuh API 호출만 필요 |
| 복구 속도 | 상관 판정 뒤 | 규칙 발동 즉시 가능 | 상관 판정 뒤 |

- 의견: **혼합**. Graylog 이벤트 발동 → n8n이 114 티켓 생성 → n8n이 **Wazuh API로 해당 에이전트에 복구 스크립트(AR)를 실행** → 스크립트가 기준본으로 교체하고 해시를 비교 → 결과를 n8n이 받아 기록.
- 이유: 공지가 요구하는 "n8n 자동 대응" 증적과 원복 절차를 모두 남기면서, n8n이 웹서버 SSH 계정을 갖지 않아도 됩니다.
- 복구 스크립트 원칙
  - 기준본은 **감시 디렉터리 밖, 웹 계정이 쓸 수 없는 읽기 전용 위치**에 둡니다(웹 계정이 기준본까지 바꾸면 복구가 무의미).
  - 기준본에 없는 신규 파일(웹셸)은 삭제하지 않고 **격리 디렉터리로 이동**합니다(증적 보존, 되돌릴 수 있음).
  - 복구 후 해시를 기준본과 비교해 결과를 반환합니다.
  - 복구도 파일 변경이라 FIM이 다시 알리므로, 복구 직후 같은 경로의 알림을 "복구 확인"으로 처리해 사건 중복을 막습니다([합의본 점검 2-2](../docs/s7-draft/합의본-S7-점검.md)).
- 위험(미검증): AR 사용자 정의 스크립트의 입력 형식과 Wazuh API로의 호출 방법은 설치 후 확인해야 합니다. 안 되면 n8n → SSH 단독 복구로 후퇴합니다(대안 1).

### 8-3. Docker 안 웹 디렉터리 감시

| 안 | 내용 | 평가 |
| --- | --- | --- |
| **A. bind mount + 호스트 에이전트 (권장)** | 웹 디렉터리(`templates/`, `static/`)를 호스트 폴더로 마운트하고, 호스트(서비스 서버 VM)의 Wazuh 에이전트가 그 호스트 경로를 감시 | 컨테이너를 건드리지 않음, 실시간 감시 설정이 단순, 복구도 호스트 파일 교체로 끝남 |
| B. 컨테이너 안에 에이전트 | 컨테이너에 에이전트 설치 | 이미지 수정·재빌드, 컨테이너 재생성 시 에이전트 등록이 꼬일 수 있음 |
| C. 이미지 레이어 안의 파일 감시 | 마운트 없이 컨테이너 파일시스템 감시 | 호스트에서 경로가 불안정하고 컨테이너 재생성 때 사라짐 → 비권장 |

- 의견: **A**. 서비스 서버 VM에 에이전트를 두고 `docker-compose`에서 웹 디렉터리를 bind mount합니다.
- 보강 전후 비교 소재: 컨테이너에는 코드 디렉터리를 **읽기 전용**으로, 업로드 디렉터리만 쓰기로 마운트하면 같은 공격이 막히거나 업로드 경로로 한정됩니다. 이 설정을 "보강 후"로 쓸 수 있습니다.
- 확인할 것
  - 변경자(who-data) 정보: 컨테이너 안 사용자가 호스트에는 숫자 UID로 보여 `audit_user` 값이 모호할 수 있음 → 필수 필드로 두지 않음(계약안은 선택 필드)
  - 실시간 감시가 쓰는 inotify 한도(`fs.inotify.max_user_watches`) 설정
  - 앱 개발 담당(포털 앱)과 `docker-compose` 마운트 구조 합의 — 앱 코드 위치(`src/aleph_soar/`)와 마운트 대상이 맞는지
