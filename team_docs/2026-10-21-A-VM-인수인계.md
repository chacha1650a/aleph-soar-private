# 반소람(A) 포털 VM 준비·연결 인수인계

작성: 김명준(B)·Codex / 2026-10-20, Asia/Seoul. B가 VM을 구성하며 확인한 정보를 A의 배포 준비에 전달한다. A PC의 설정·접속 성공을 확인한 문서는 아니다. 기존 A의 S1/S4 책임과 김명준·Codex의 포털 코드 구현 담당은 유지한다.

## 1. 소람님이 먼저 할 일

1. 기존 수업 Ubuntu VM 중 포털에 사용할 환경을 확인하고 아래 점검 결과를 B에게 전달한다. 수업 데이터는 보존하고, 필요하면 복제본의 표시 이름을 `Haedam-Portal`로 구분한다.
2. 아래 표의 실제 구현 브랜치·커밋을 확인해 프론트·백 코드를 받는다. 포털 저장소의 현재 main은 초기 스켈레톤이므로 main만 받은 상태와 구현 코드를 구분한다.
3. VM에서 코드·빌드 준비는 진행할 수 있다. B가 A용 VPN과 DB까지의 경로·허용 규칙을 준비한 뒤 원격 DB 연결과 마이그레이션을 진행한다.
4. 프론트 빌드 `dist`의 실제 절대 경로와 agent 등록 정보를 C에게 전달한다. C는 이 배포 경로를 감시한다.

전체 순서와 담당은 [A·C 작업계획](2026-10-21-A-C-작업계획.md), B의 실측 근거는 [10/20 일지](../work-log/members/myeongjundev/2026-10-20.md)를 참고한다.

## 2. B에서 확인한 VM 준비 경험

| 항목 | B의 실제 구성·경험 | A에서 사용할 기준 |
| --- | --- | --- |
| OS | DB VM에 Ubuntu Server 24.04.5 LTS 사용 | 기존 Ubuntu VM 버전·상태부터 확인. 같은 ISO로 재설치할 필요 없음 |
| 자원 | DB VM은 CPU 2코어·RAM 2GB·디스크 30GB | DB의 사용 설정이며 포털의 확정 사양은 아님. 기존 VM 여유·빌드 중 메모리를 확인해 조정 |
| 설치 단계 통신 | 설치용 NAT에서 패키지를 준비하고 DB를 WORK로 전환 | A도 설치·빌드용 인터넷 경로를 먼저 확인. 최종 서비스 통신 경로는 B와 정한 뒤 적용 |
| SSH·Docker | Ubuntu VM 안에 OpenSSH·Docker Engine·Compose 준비 | Windows Docker Desktop과 VM 내부 설치는 별개. 이미 있으면 재사용하고 없는 것만 보완 |
| NIC·주소 | DB의 NIC·netplan을 확인하고 백업 후 전원 종료→VMware 망 변경→재기동 | A의 실제 NIC 이름·MAC부터 확인. B의 ens33·IP·게이트웨이를 복사하지 않음 |
| 관리 접속 | B는 자기 VMnet7에서 pfSense를 통해 DB에 접속 | B 전용 Windows 영구 경로 명령을 A에 그대로 실행하지 않음 |
| 보존 | DB Docker 기반·WORK 전환 후 스냅샷을 남김(사용자 보고) | A도 프로젝트 변경 전 스냅샷·설정 백업 위치 기록. 스냅샷 생성과 복원 시험은 구분 |

학교망의 A 주소는 사용자 전달 기준 `192.168.3.7`이며 내일 재확인한다. 이는 Windows 유선 주소이고 포털 VM 주소가 아니다. VMnet 번호가 같아도 서로 다른 PC의 VM은 연결되지 않는다. B의 DB용 VMnet4나 과거 물리안의 포털 `10.10.10.10`을 A에 먼저 적용하지 않는다.

## 3. 받을 코드와 확인한 제약

2026-10-20 원격 fetch 후 확인한 참조다. 독립 리뷰·최종 배포 승인·A VM 실행 완료를 의미하지 않는다. 배포할 때 변경된 HEAD가 있으면 B와 다시 맞춘다.

| 저장소 | 구현 브랜치 | 확인한 커밋 |
| --- | --- | --- |
| [haedam-portal-frontend](https://github.com/NoBugs-Aleph/haedam-portal-frontend) | `codex/haedam-portal-mvp` | `cac2bed39181d7f9e6d4da82d1d4391f8a852ae2` |
| [haedam-portal-backend](https://github.com/NoBugs-Aleph/haedam-portal-backend) | `claude/portal-ip-block-file-key` | `983dad68baf8478b49bec20a82315575c6c5ae19` |

- 두 저장소를 같은 상위 폴더의 형제 폴더로 둔다. 각 저장소 README·AGENTS와 계약 출처를 읽는다.
- 코드 기준 Python 3.12 이상, 프론트 package.json의 Node 조건은 22.12.0 이상이다. 설치된 버전을 먼저 확인한다.
- 프론트는 `npm ci` → `npm run build`로 `dist`를 만든다. Flask가 화면·API를 함께 제공하는 기준이며 새 nginx 프록시를 임의로 추가하지 않는다.
- 확인한 백엔드의 시작 스크립트 `tools/start.ps1`은 Windows용이다. Linux에서 같은 명령을 실행하지 않는다. 포털용 Dockerfile·Compose 배포 파일도 현재 참조 트리에 없다. Docker 배포 설정·Linux 실행 서비스 보완은 B와 조율할 준비 항목이다.
- 백엔드 `tools/bootstrap.py`는 의존성 설치 후 DB 마이그레이션도 실행한다. 실제 DB 경로·환경 설정을 확인하기 전에 실행하지 않는다. 기본값 SQLite가 생긴 사실을 원격 MySQL 연결 성공으로 처리하지 않는다.
- Linux 앱은 프로세스 환경변수를 읽는다. Windows 시작 스크립트의 `.env` 로딩을 Linux에도 자동 적용된다고 가정하지 않는다. 환경값을 실제 서비스에 주입하는 방법을 정해야 한다.
- 프론트 계약 출처는 capstone `2303265`, 백엔드는 `f42de82`로 서로 다르다. 단독 화면 준비와 별개로 관제 연동 전 B가 원본·복사본·소비자 버전을 맞춘다. A가 새 계약을 임의로 만들지 않는다.

## 4. 포털에 넘길 실제 DB·VPN 정보

| 항목 | 현재 값·확인 범위 |
| --- | --- |
| DB 서버 | `10.10.20.10`, TCP `3306` |
| DB 종류 | MySQL 실제 버전 `8.4.11` |
| DB 이름 | `haedam_portal` |
| 앱 DB 사용자 | `haedam_app` |
| DB 비밀번호 | B의 VM secret 파일에 보관. 앱 계정 비밀번호만 별도 전달하며 문서·Discord 공용 글·Git에 기재하지 않음 |
| 연결 URL 모양 | `mysql+pymysql://haedam_app:<별도 전달값>@10.10.20.10:3306/haedam_portal?charset=utf8mb4` — 그대로 실행할 값이 아닌 형식 안내 |
| 팀 VPN 서버 | `HAEDAM_TEAM_TRANSIT`, UDP `1195` |
| 서버 접속 주소 | 10/20 관찰 `192.168.7.174`. DHCP이므로 B가 내일 주소 재확인 후 프로필 전달 |
| 터널 대역·서버 | `10.250.0.0/24`, 서버 `10.250.0.1` |
| A 전용 프로필 | 예정 사용자명 `team-a`. 현재 미생성·미발급. B가 준비해 A에게 개별 전달 |
| 확인된 시험 | B 사용자 team-b-test의 VPN 접속·서버 Ping, B 관리 호스트의 DB TCP 연결·컨테이너 내부 앱 계정 SQL 조회 |
| 남은 연결 | A Ubuntu VM→B DB, A agent→C Wazuh, A 포털→D Graylog, 포털 외부 접근 경로 |

A에게 B 시험용·D용 프로필이나 DB root 계정을 전달해 재사용하지 않는다. 현재 팀 VPN은 서버 Ping 뒤 기본 차단이고 내부 서비스 경로도 미설정이다. Windows VPN 연결 성공만으로 Ubuntu VM의 DB 연결이 가능하다고 가정하지 않는다. B가 VPN 종단·왕복 경로·허용 출발지를 정하고 실제로 확인한다.

## 5. 해담포털에 맞춰 바꿀 환경값

실제 변수명은 확인한 백엔드 소스·`.env.example` 기준이다. 값이 정해지지 않은 항목은 추측해서 채우지 않는다.

| 변수 | A의 준비·수정 내용 | 연결 담당 |
| --- | --- | --- |
| `DATABASE_URL` | 위 MySQL 주소·DB·앱 계정과 별도 비밀번호 적용. 실제 프로세스에서 적용됐는지 확인 | B |
| `FRONTEND_DIST` | 빌드 결과 `dist`의 실제 절대 경로. 컨테이너 사용 시 컨테이너 경로와 호스트 마운트 경로를 함께 기록 | A·C |
| `EVENT_LOG_PATH` | JSONL이 보존되는 실제 경로·권한·볼륨 확인 | A·D |
| `ASSET_ID` | 기본 `haedam-portal`. C·D와 같은 자산을 식별할 값으로 맞춤 | A·C·D |
| `GELF_ENABLED`, `GELF_HOST`, `GELF_PORT` | D의 실제 수신 주소·입력 준비 후 사용. 포털이 다른 PC/VM이면 `127.0.0.1`은 D가 아님. 기존 예시 포트 12201/UDP의 실제 입력 확인 | D·B |
| `RESPONSE_API_KEY`, `RESPONSE_ALLOWED_CIDRS` | n8n의 실제 관측 출발지·대응 계약을 맞춘 뒤 설정. 현재 터널 대역 전체를 그대로 허용하면 차단 보호 대상도 넓어지므로 관리 호출자 범위를 별도 결정 | B·D |
| `DASHBOARD_URL` | C의 프로젝트 대시보드 준비 후 관리자 링크로 사용. Wazuh 제품 화면과 구분 | C |
| `COOKIE_SECURE` | 실제 HTTP/HTTPS 접속 방식과 맞춤. 현재 예시 0을 HTTPS 확정값으로 간주하지 않음 | B |

DB 비밀번호·자동화 키는 프론트 빌드 변수에 넣지 않는다. 현재 코드는 전달 헤더를 신뢰하지 않으므로 NAT·프록시를 바꿀 때 실제 앱 로그의 출발지를 반드시 확인한다.

## 6. A가 먼저 보내주면 좋은 점검 결과

아래는 **Ubuntu VM 안**에서 실행하는 읽기 점검이다. 없는 명령의 오류는 해당 도구가 없다는 정보로 전달하면 된다. 환경변수 전체·비밀 파일·VPN 프로필 원문은 출력하지 않는다.

```bash
hostnamectl
ip -br address
ip route
python3 --version
node --version
npm --version
docker --version
docker compose version
systemctl is-active ssh
free -h
df -h /
```

함께 전달할 항목: VMware VM 이름, RAM·CPU·디스크, Network Adapter 모드(NAT/Bridged/Custom), 위 결과, 사용할 코드 커밋, 실제 `dist` 절대 경로. Windows 유선 IP는 Windows `ipconfig` 결과에서 별도로 확인한다.

## 7. B가 추가로 제공·보완할 것과 완료 기준

- B 제공: A 전용 VPN 계정·인증서·프로필, 확인된 접속 주소, 앱 DB 비밀번호의 개별 전달, A VM까지 왕복 경로·필요 방화벽 규칙.
- B·A 보완: 실제 Linux 실행/컨테이너 배포 설정, 비밀값 주입·로그 보존 방법, 실제 웹 서비스 접속 주소·바인딩. Windows용 실행 예제를 외부 공개 설정으로 바로 바꾸지 않는다.
- C 제공: 실제 agent 등록 대상·방법, 웹 루트 감시·기준본·원복 절차. D 제공: Graylog 입력·n8n 호출자 정보.
- 인수 확인: A의 실제 앱 실행 환경에서 DB 인증·마이그레이션 확인 → 로그인·민원 저장·재시작 유지 → C에서 agent Active·파일 변경 경보 → D에서 원본 이벤트 ID 수신 대조. 단계별 미완료는 따로 기록한다.

현재 이 문서로 완료한 것은 코드·환경 요구사항 대조와 인수인계 준비다. A VM 배포·새 VPN 발급·원격 DB 연결·자동 대응·복원 시험은 실행하지 않았다.
