# 정량평가 설명서

> 시험은 각자 돌리고 결과 값만 보내 주세요. [정량평가 리포트](정량평가_리포트.md) 입력은 whiteclover0542가 합니다.

---

## 1. 왜 필요한가

공지의 평가 기준은 "기능 개수보다 구현 완성도와 실측 검증"입니다. "탐지됩니다, 차단됩니다"라고 말하는 것만으로는 점수가 되지 않고, "5번 공격해서 5번 탐지, 40초 만에 차단, 정상 사용자 영향 0건"처럼 숫자로 증명해야 합니다. 발표 PPT의 근거도 결국 이 숫자입니다.

---

## 2. 왜 검문소 방식인가

공격 한 번은 로그 수집 → Graylog 탐지 → n8n 대응 → 티켓 → 복구 순서로 지나갑니다. 마지막 결과만 보면 두 가지 문제가 생깁니다.

**가짜 성공을 걸러내지 못합니다.**
n8n 실행 기록에 "성공"이 떠도 같은 IP로 다시 공격하면 뚫릴 수 있습니다. 그래서 "n8n 성공"이 아니라 "다시 공격했더니 403이 나왔다"를 성공으로 봅니다.

**실패했을 때 어디를 고칠지 모릅니다.**
"안 됐다"만으로는 원인을 알 수 없습니다. 단계마다 따로 확인하면 끊긴 곳이 바로 보입니다.

| 증상 | 원인 | 분류 |
| --- | --- | --- |
| 로그가 Graylog에 안 왔다 | 로그 송신 설정 | 미관측 |
| 로그는 왔는데 규칙이 안 울렸다 | 규칙 조건 | 미탐 |
| 울렸는데 n8n이 안 돌았다 | 워크플로 | 조치 실패 |
| n8n은 돌았는데 공격이 계속 통한다 | 차단 위치 | 효과 검증 실패 |

그래서 단계마다 서로 다른 곳(원본 로그, Graylog, n8n, 재공격 결과, 헬스체크)에서 확인합니다.

## 3. 용어

| 용어 | 뜻 |
| --- | --- |
| 탐지율 | 공격했을 때 규칙이 울린 비율. 5번 공격해서 5번 울리면 5/5 |
| 오탐 | 공격이 없는데 울린 경우. 정상 업무만 흘렸는데 울리면 오탐 |
| 미탐 | 공격했는데 안 울린 경우. 탐지율이 떨어지는 것으로 드러남 |
| MTTD | 공격 조건이 채워진 뒤 탐지될 때까지 걸린 시간 |
| MTTR | 탐지된 뒤 실제로 막히고 서비스가 회복될 때까지 걸린 시간 |
| 보강 전 / 후 | 로그 수집은 연결됐지만 내 케이스의 탐지 규칙·n8n 대응을 넣기 전 / 넣은 뒤 |

## 4. 어떻게 실행하나

> 아래 명령과 화면 위치는 **S1(저속 브루트포스) 예시**입니다. 로그인 API(`POST /api/v1/auth/login`)는 계약에만 있고 아직 구현 전이며, 재현 스크립트(`scripts/replay/S01.sh` 등)도 아직 없습니다. 구현되면 이 예시를 실제 명령으로 바꿉니다. 내 케이스가 S1이 아니면 "공격 입력"만 내 케이스에 맞게 바꾸고 나머지 순서는 같습니다.

### 4-1. 전체 흐름 한눈에 보기

```
① 환경 준비          VM 켜기, 시간 맞추기, 앱·Graylog 로그 들어오는지 확인
        ↓
② 보강 전 시험 1번    ★ 내 규칙을 넣기 전에! 진짜 공격 1번 → "공격 성공, 아무도 모름" 캡처
        ↓
③ 보강               내 Graylog 이벤트 정의·n8n 워크플로 만들기 (평소 개발 작업)
        ↓
④ 보강 후 시험 9~10번 진짜 공격 5번 + 경계·혼합·정상 시험
        ↓
⑤ 결과 보내기         시험 1번당 한 줄 (5장 형식)
```

②를 놓치면 다시 할 수 없습니다. 규칙을 한 번 넣으면 "규칙 없는 상태"로 돌아가기 어렵기 때문입니다. 헷갈리면 **규칙 만들기 시작하기 전날 ②부터** 하면 됩니다.

### 4-2. 보강 전 시험 체크리스트

**언제:** Graylog에서 내 케이스의 로그가 검색되기 시작한 뒤, 내 케이스의 이벤트 정의를 만들기 전.

**지금이 보강 전이 맞는지 확인 (셋 다 O여야 함)**

- [ ] Graylog **Search**에서 내 케이스 로그가 보인다 (예: 로그인 실패를 한 번 해 보고 `username:zz_officer01` 검색 → 1건 나옴)
- [ ] Graylog **Alerts → Event Definitions**에 내 케이스 규칙이 없다 (있으면 꺼져 있다)
- [ ] n8n **Workflows**에서 내 케이스 대응 워크플로가 없거나 비활성(Inactive)이다

**하기 전에**

- [ ] VM 스냅샷 찍기 (이름 예: `S01-before`). 문제 생기면 이 상태로 되돌립니다.

**할 것:** 4-4의 "진짜 공격"을 1번 실행하고, 4-5의 1~3단계까지만 확인합니다. 규칙이 없으니 4단계부터는 "울리지 않음, 대응 없음, 티켓 없음"이 정상 결과입니다.

**캡처할 것 (3장)**

1. `01-attack.png` 공격 명령과 결과 (마지막에 로그인 성공 또는 공격 성공 화면)
2. `02-graylog.png` Graylog 검색에 공격 로그가 쌓인 화면
3. `03-no-event.png` Alerts 화면에 이벤트가 없는 화면

**보낼 것:** `보강 전 / 진짜 공격 / X / 해당 없음 / 없음 / 0 / 해당 없음 / 조건 충족 시각만 / -`

### 4-3. 시험 종류

**보강 전은 진짜 공격 1번만** 돌립니다. 나머지는 보강 후에만 돌립니다.

| 시험 | 보강 전 | 보강 후 | 무엇을 바꾸나 (S1 예: 30분 안에 실패 9번이면 울림) | 기대 결과 (보강 후) |
| --- | --- | --- | --- | --- |
| 진짜 공격 | 1 | 5 | 실패 9번을 30분 안에 | 울리고, 막히고, 티켓 1건 |
| 임계값 바로 아래 | — | 1 | 실패 **8번**만 | 안 울림 |
| 집계 시간 밖 | — | 1 | 실패 9번을 **30분보다 길게** 나눠서 (예: 4번 → 35분 쉬고 → 5번) | 안 울림 |
| 섞기 (혼합) | — | 1 | 계정 A에 5번 + 계정 B에 5번 (합치면 10번이지만 각자는 9번 미만) | 안 울림. 계정별로 따로 센다 |
| 정상 업무만 30분 | — | 1 | 공격 없이 정상 로그인·민원 조회만 | 안 울림, 정상 사용자 문제없음 |
| 조건 하나만 채우기 | — | 1 | 조건이 두 개 이상 겹치는 케이스만 (예: S12에서 요청 수만 넘기고 응답시간은 정상) | 안 울림. S12는 Graylog 요청 수 이벤트가 생겨도 정상이고, n8n이 헬스체크 뒤 대응하지 않아야 함 |

합계: 케이스 ID당 10번, 조건이 겹치는 케이스(S4·S7·S8·S10·S12)는 11번입니다. 필수는 자리별 4종이지만 케이스 ID로는 6개(A S1·S4, B S8·S10, C S7, D S12)라서, **A·B는 두 ID를 각각** 돌립니다.

임계값을 고쳐서 오탐을 줄였다면, 고치기 전과 후의 "임계값 바로 아래"·"정상 업무" 결과를 둘 다 보내 주세요. 오탐 개선 근거가 됩니다.

### 4-4. 공격 입력 예시 (S1)

Kali에서 실행합니다. `<포털IP>`는 VM 배치가 정해지면 채웁니다. **비밀번호는 아무 값이나 틀린 값**을 쓰고, 그 값을 결과에 적지 않습니다.

진짜 공격 (실패 9번, 1분 간격):

```bash
for i in $(seq 1 9); do
  date '+%H:%M:%S'                                   # 몇 번째가 언제 갔는지 기록
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST http://<포털IP>/api/v1/auth/login \
    -H 'Content-Type: application/json' \
    -d '{"username":"zz_officer01","password":"wrong"}'
  sleep 60
done
```

- 임계값 바로 아래: `seq 1 9`를 `seq 1 8`로
- 집계 시간 밖: 4번 돌리고 35분 기다린 뒤 5번
- 섞기: `zz_officer02`, `zz_officer03`으로 5번씩

**9번째 줄에 찍힌 시각이 "조건 충족 시각"입니다.** 화면을 캡처하거나 복사해 두세요.

### 4-5. 한 번 돌릴 때 순서 (어디서 무엇을 보나)

| 단계 | 할 일 | 어디서 | 적을 것 |
| --- | --- | --- | --- |
| 1. 시작 전 상태 | 시험 계정이 잠겨 있지 않은지, 내 IP가 차단돼 있지 않은지 확인 | 정상 로그인 1번 → 성공해야 함 | 이상 없음 |
| 2. 공격 | 4-4 명령 실행 | Kali | **조건 충족 시각** (마지막 요청 시각) |
| 3. 로그 도착 | 공격 로그가 Graylog에 들어왔는지 | Graylog Search: `username:zz_officer01` | 보낸 횟수만큼 왔나 |
| 4. 규칙 발동 | 이벤트가 생겼는지 | Graylog Alerts & Events | **탐지 시각** (이벤트 시각) |
| 5. 대응 | n8n이 돌았는지, 실제로 막혔는지 | n8n Executions → Kali(같은 공격 IP)에서 새 요청 → 403이면 막힘. 앱 차단 목록에 그 IP가 있는지는 **관제 PC**에서 봅니다(n8n 실행 결과의 `GET /response/ips` 응답. 대응 키·관리망이 필요해 Kali에서는 못 부름). 같은 계정을 **다른 정상 IP**에서 로그인 → 성공해야 함 (S1은 계정을 잠그지 않습니다. 401이 나오고 관리자 화면에서 계정이 "잠김"이면 "정상 업무 영향") | **조치 완료 시각** (n8n 실행 끝난 시각), **복구 확인 시각** (403 확인한 시각, `date`로 찍기) |
| 6. 티켓 | 티켓이 1건만 생겼는지 | 인시던트 화면 (위치는 구현 후 안내) | 티켓 수 |
| 7. 원복 | 출발지 IP 차단 해제 | 해제 방법은 구현 후 안내 | — |
| 8. 원복 확인 | Kali IP가 차단 목록에서 빠졌는지(관제 PC), 그 IP에서 정상 로그인 → 성공 | 관제 PC, 앱 | O·X |
| 9. 보내기 | 5장 형식으로 한 줄 | 팀 채팅 | — |

**"안 울림"이 기대인 시험** (임계값 바로 아래·집계 시간 밖·섞기·정상)은 2~4단계만 하고, 마지막 요청 뒤 아래 시간이 지날 때까지 Alerts를 지켜본 뒤 이벤트가 없는지 봅니다. Graylog가 집계 창 안의 신호를 일정 주기로 검사하므로 일찍 끝내면 늦게 울린 이벤트를 놓칩니다.

> 관측 종료 = 마지막 요청 시각 + **내 케이스의 가장 긴 집계 창** + Graylog 검색 주기 + 수집 지연
> 예: S1은 집계 창이 30분이라 30분 + 검색 주기 + 수집 지연이 지나야 끝납니다. 관측 종료 시각도 결과에 적어 주세요.

**막혔을 때:** 3단계에서 로그가 안 보이면 "미관측", 4단계에서 이벤트가 없으면 "미탐", 5단계에서 n8n이 안 돌았으면 "조치 실패", n8n은 돌았는데 같은 IP 요청이 계속 통하면 "효과 검증 실패"라고 적어 보내 주세요. 고치는 건 같이 합니다.

### 4-6. 주의할 점

- **다음 시험 때 계정을 바꿔 주세요** (`zz_officer01` → `02` → `03` …). S1은 계정 + 출발지 IP별로 30분 동안 횟수를 세기 때문에 같은 계정·IP로 바로 다시 하면 앞 시험 횟수가 섞입니다. 앞 시험의 IP 차단은 원복한 뒤 시작합니다.
- **시작 전에 모든 VM 시간을 맞춰 주세요.** 각 VM에서 `date`를 쳐서 1초 넘게 차이 나면 알려 주세요. 시간이 어긋나면 탐지 시간 계산이 틀립니다.
- 테스트 계정은 `zz_`로만 만들고, 캡처에 비밀번호·개인정보가 보이면 가려 주세요.
- 시험은 랩 내부망(VMnet) 안에서만, 우리 VM에만 합니다.
- 실제로 돌린 결과만 보내 주세요. 예상값은 안 됩니다. 실패해도 그대로 보내면 됩니다.

### 4-7. Claude Code에 맡길 때

Claude Code에 이 설명서를 주고 시험을 도와 달라고 할 수 있습니다. 다만 **전부 맡기지는 말고**, 아래처럼 나눕니다.

| 맡겨도 되는 것 | 사람이 직접 하는 것 |
| --- | --- |
| 공격 명령 실행과 시각 기록 | **지금이 보강 전인지 확인** (4-2 체크리스트) |
| 같은 IP로 다시 시도해 403 확인 (S4 잠금은 401이라 관리자 화면 "잠김"으로 사람이 확인) | VM 스냅샷 찍기 |
| Graylog·n8n API로 로그·이벤트·실행 기록 조회 | 캡처 (Graylog·n8n 화면) |
| 보낼 한 줄(5장 형식) 만들기와 분류 판정 | 받은 한 줄을 화면·실행 기록과 대조한 뒤 보내기 |

**어디서 실행하나.** 공격은 **Kali에서** 나가야 합니다. 팀원 PC(Windows)에서 Claude Code가 직접 curl을 쏘면 출발지 IP가 Kali와 달라져서 IP 기준 규칙(S5·S6·S8·S10·S12)의 결과가 틀립니다. Kali에서 Claude Code를 쓰거나, Claude Code에는 명령만 만들게 하고 Kali에서 직접 실행합니다.

**토큰 넘기는 법.** Graylog·n8n API 토큰은 **채팅에 붙여 넣지 않습니다.** 터미널에서 환경 변수로 넣고, Claude Code에는 변수 이름만 알려 줍니다.

```bash
export GRAYLOG_TOKEN='...'   # 직접 입력, 채팅에 쓰지 않기
export N8N_API_KEY='...'
```

**붙여 넣을 지시 예시**

```
team_docs/정량평가_설명서.md를 읽고 내 케이스 시험을 도와줘.
- 케이스: S1, 보강 후, 시험 종류: 임계값 바로 아래, 계정: zz_officer02
- 4-5 순서대로 진행하고, 단계마다 실제 명령 출력을 보여 줘.
- Graylog·n8n 토큰은 환경 변수 GRAYLOG_TOKEN, N8N_API_KEY에 있어. 값을 출력하지 마.
- 실제로 확인하지 못한 값은 추측하지 말고 "미확인"으로 적어.
- 마지막에 5장 형식 한 줄과, 그 줄의 근거(명령 출력·이벤트 ID·n8n 실행 ID)를 같이 보여 줘.
- 보강 전 시험이면 시작하지 말고 4-2 체크리스트를 내가 확인했는지 먼저 물어봐.
- 4-7 표의 "사람이 직접 하는 것"(스냅샷·캡처·대조)에 닿으면 멈추고, 무엇을 어디서 할지(캡처 파일 이름 포함) 안내한 뒤 내가 "완료"라고 할 때까지 기다려.
```
