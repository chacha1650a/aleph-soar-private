# 팀 프로젝트 진행 제안사항

팀 프로젝트를 시작하기 전에, 이전 프로젝트에서 써 보고 효과가 좋았던 방식을 정리했습니다.
참고 예시는 모두 [Rainbow-Bridge](https://github.com/mosejong/Rainbow-Bridge/tree/dev/docs) 레포에 있습니다.

| 구분 | 항목 | 핵심 효과 |
|---|---|---|
| 🔴 중요도 높음 | PROGRESS 파일 관리 | 전체 작업 현황과 팀원 현황을 한눈에 파악 |
| 🔴 중요도 높음 | 개인 개발 일지 | 팀원별 세부 진행 상황 파악, 강사님께 브리핑할 때 편함 |
| 🔴 중요도 높음 | 모닝 미팅 | 팀원끼리 서로의 작업 현황 공유 |
| 🔴 중요도 높음 | 평가지표 작성 | 시스템 수준과 신뢰도를 수치로 증명 |
| 🟡 중요도 낮음 | 아키텍처 문서 | 복잡한 구조를 따로 정리해서 쉽게 확인 |
| 🟡 중요도 낮음 | 협업 규칙 | 혼자 머지하거나 방향이 갈라지는 상황 방지 |

---

## 🔴 중요도 높음

### 1. PROGRESS 파일 관리

> 예시: [docs/PROGRESS.md](https://github.com/mosejong/Rainbow-Bridge/blob/dev/docs/PROGRESS.md)

- 전체 작업 현황과 팀원별 현황을 **한 파일**에서 한눈에 볼 수 있습니다.
- 진행 중 / 완료 / 예정 작업이 정리되어 있어서 일정 관리가 쉬워집니다.

### 2. 각자의 개발 일지

> 예시: [docs/devlog/members/반소람.md](https://github.com/mosejong/Rainbow-Bridge/blob/dev/docs/devlog/members/%EB%B0%98%EC%86%8C%EB%9E%8C.md)

- **최신 날짜가 위로** 오도록 작성합니다.
- 날짜마다 아래 내용을 정리합니다.
  - 오늘의 목표
  - 할 일 (작업 세부 사항)
  - 다음 할 일
- 업데이트 시점은 자유지만, **하루 작업을 마칠 때는 반드시 업데이트**합니다.
- 팀장님이 팀원들 상황을 파악하고 **강사님께 브리핑하기 편해집니다.**

### 3. 모닝 미팅

- 아침마다 각자 아래 내용을 짧게 브리핑합니다.
  - 지금 하고 있는 작업
  - 오늘 할 작업
  - 마무리한 작업
- 대면이 아니어도 괜찮습니다. **디스코드로 진행해도 됩니다.**
- 개발 일지나 PROGRESS로도 현황을 알 수 있지만, 사실 팀장님 말고는 서로의 현황을 찾아보지 않습니다.
  → 그래서 **간단하게라도 직접 공유하는 자리**가 필요합니다.

### 4. 평가지표 작성

> 예시: [docs/AI휴먼_정량평가_리포트.md](https://github.com/mosejong/Rainbow-Bridge/blob/dev/docs/AI%ED%9C%B4%EB%A8%BC_%EC%A0%95%EB%9F%89%ED%8F%89%EA%B0%80_%EB%A6%AC%ED%8F%AC%ED%8A%B8.md)

- 위 예시는 AI 개발 프로젝트라서 평가 항목이 보안 프로젝트와는 많이 다릅니다.
  하지만 **방식은 비슷하게** 가져가면 됩니다.
- 늦어도 **발표 준비 전에는** 우리 시스템 평가를 진행합니다.
- "잘 만들었어요!"라고 말로만 하는 것보다, 우리 시스템의 **수준이 어느 정도이고 얼마나 믿을 만한지** 가장 쉽게 보여주는 방법입니다.
- 개인적으로는 어떤 프로젝트든 꼭 진행하는 편입니다.

#### 보안 프로젝트에 적용한다면 (예시)

탐지 룰처럼 **잡았다 / 못 잡았다**로 결과가 갈리는 시스템은 오히려 정량평가를 하기 좋습니다.

**쓸 수 있는 지표**

| 지표 | 의미 | 측정 방법 |
|---|---|---|
| 탐지율 (Recall) | 실제 공격 중 몇 %를 잡았나 | 공격 시나리오 N회 재현 → 알람이 몇 번 떴는지 |
| 오탐률 (FP Rate) | 정상 행위를 공격으로 잘못 잡은 비율 | 정상 로그만 흘려보내고 알람이 몇 번 뜨는지 |
| 정밀도 (Precision) | 뜬 알람 중 진짜 공격의 비율 | 진짜 공격 알람 수 / 전체 알람 수 |
| 탐지 지연 (MTTD) | 공격 시작부터 알람까지 걸린 시간 | 공격 로그 시각과 알람 시각의 차이 |
| 커버리지 | 공격 기법을 얼마나 덮었나 | MITRE ATT&CK 기법에 룰을 매핑한 수 |
| 처리 성능 (EPS) | 초당 처리할 수 있는 이벤트 수 | 로그를 부하로 넣어서 측정 |

**진행 방식**

1. **공격 재현 스크립트**: 탐지 룰마다 공격을 재현하는 스크립트를 만듭니다. (예: 30초 안에 로그인 실패 9회 이상, 관리자 API 10회 호출)
2. **경계값 테스트**: 임계값 바로 아래와 바로 위를 각각 넣어 봅니다. 아래일 때는 안 뜨고 위일 때만 뜨는지 확인하면 룰 정확도를 보여줄 수 있습니다.
3. **정상 트래픽 테스트**: 정상 사용자 로그를 몇 시간 흘려보내 오탐을 셉니다. 심야 로그인처럼 오탐이 많이 날 만한 룰을 집중적으로 봅니다.
4. **결과 정리**: 아래처럼 표로 정리합니다.

| 룰 | 시도 | 탐지 | 탐지율 | 오탐 | 평균 지연 |
|---|---|---|---|---|---|
| S1 저속 브루트포스 | 20 | 20 | 100% | 0 | 1.2s |
| S2 심야 로그인 성공 | 20 | 20 | 100% | 3 | 0.8s |
| ... | | | | | |

> 위 수치는 형식을 보여주기 위한 예시입니다.

**발표에서 강조하기 좋은 포인트**

- "전체 탐지율 ○○%, 오탐 ○건"처럼 한 줄 요약
- 공격이 여러 단계로 이어지는 연계 룰(스캐너 → 브루트포스 등)이 시나리오 전체를 잡아내는지
- 오탐이 났던 룰을 임계값 조정으로 개선한 **전후 비교** (신뢰도를 보여주기 제일 좋습니다)

## 🟡 중요도 낮음

### 1. 아키텍처 문서

> 예시: [docs/ARCHITECTURE.md](https://github.com/mosejong/Rainbow-Bridge/blob/dev/docs/ARCHITECTURE.md)

- 기획서에도 들어가는 내용이지만, 아키텍처가 길어지거나 복잡해지면 **따로 정리해 두는 게 확인하기 편합니다.**

### 2. 협업 규칙

> 예시: [docs/CONTRIBUTING.md](https://github.com/mosejong/Rainbow-Bridge/blob/dev/docs/CONTRIBUTING.md), [docs/GIT_GUIDE.md](https://github.com/mosejong/Rainbow-Bridge/blob/dev/docs/GIT_GUIDE.md)

- 보통 AI가 이 규칙을 지키도록 하려고 작성합니다.
- 누군가 갑자기 혼자 머지하거나 작업이 엉뚱한 방향으로 뻗어 나가는 걸 막는 용도입니다.
- 다만 **필수는 아니라고 생각합니다.**
