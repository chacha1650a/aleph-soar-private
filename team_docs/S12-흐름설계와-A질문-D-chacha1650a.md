# S12 자동 대응 흐름 설계안과 A에게 물을 질문 (D · chacha1650a)

- 상태: **설계안, 미구현·미시험.** Graylog 이벤트 정의·알림과 S12 자동 대응 워크플로는 만들지 않았다(정량평가 "보강 전" 상태 유지). n8n에는 수신 확인 `haedam-00`(PR #42)만 병합되었고 결과 기록 초안 `haedam-10`(PR #43)은 티켓 저장소가 자리표시인 초안이다.
- 기준: [S12 진행계획](S12-진행계획-D-chacha1650a.md), [대응 호출 방식 초안](2026-10-20%20대응호출방식-초안-A-whiteclover0542.md), B→D 인수인계(10/22) 6절. 숫자 값(N, 기준선, 기한)은 단계 0 측정 뒤에 정한다. 아래 값은 모두 자리표시다.

## 흐름

```text
A 포털 web.request ─GELF→ Graylog ─(후보 이벤트: 출발지별 요청 수 > N / 1분 / 묶기 src_ip)→ n8n Webhook
  → ① 중복 확인 (result-log check: 같은 S12·src_ip의 열린 티켓)
  → ② 보호 대상 확인 (관제·관리 출발지면 중단)
  → ③ 헬스체크 K회 연속 → 지연 판정
        기준선 안 → 대응 없음, 실행 기록에 측정값만 (티켓 없음, 기본안)
        기준선 초과/시간 초과 ↓
  → ④ 출발지 차단 (112, 차단만·속도 제한 없음)
  → ⑤ 반영 확인 (applied_verified)
  → ⑥ 티켓 (114) + 알림 (113)         ← result-log record
  → ⑦ 회복 확인 (정상 출발지 응답시간이 기준선 안 K회, effect_verified, 116)
  → ⑧ 사람이 확인한 뒤 해제 (자동 만료 없음) → 해제 뒤 상태 재측정 → 티켓 닫기
```

| 단계 | 내용 | 근거·메모 |
| --- | --- | --- |
| 후보 이벤트 | 요청 수는 **`web.request`만** 센다. `web.file_access`·인증 이벤트까지 합치면 한 요청이 중복 집계된다 | B 인수인계 5절. `/assets/`·`/favicon.svg`는 `web.request`에서 제외되므로 실제 집계 범위를 기록 |
| Webhook 수신 | 원본 `event_id`·`asset_id`·`src_ip` 유지, n8n 실행 ID와 연결 | 결과 기록 설계서 |
| 헬스체크 | 판정에는 DB를 읽는 경로를 쓴다. 보고 커밋 `47be008`의 `/api/v1/health`는 민원 테이블을 조회한다고 B가 적었다 | **직접 확인하지 않음.** S12 진행계획의 "DB 없는 스켈레톤" 서술은 별도 앱의 과거 상태일 수 있어 A 배포 커밋 확인 필요 |
| 두 측정 분리 | 판정(D 관리 경로)과 회복 측정(정상 사용자 공개 경로)을 따로 남긴다 | B 인수인계 6절 5번 |
| 차단 | 출발지 차단만. 계정 잠금·속도 제한 없음 | 초안 6절 3번(D 확인 대기 → 이 설계는 "차단만"으로 가정, 확인 필요) |
| 해제 | 사람이 한다. 자동 만료는 S1 기준이므로 S12에 자동 복사하지 않는다 | B 인수인계 6절 말미 |
| 자기 차단 방지 | 관제·관리 IP는 대상에서 제외. 포털도 허용 대역 주소 차단을 403으로 거부 | 초안 2절 |

## 시험 입력별 기대 (S12 진행계획 단계 2 표와 동일)

정상·경계 아래·창 밖은 미발동. 요청 수만 초과는 발동하지만 헬스체크가 기준선 안이면 대응 없음. 전체 충족은 차단·티켓 1건.

## 아직 정할 수 없는 것

탐지 임계 N, 헬스체크 주기·연속 횟수·시간 초과, 기준선, 요청률은 **실측 전**이라 값을 정하지 않았다. 차단 지점(앱 403 vs pfSense)은 A·B 사전 시험 뒤에 정한다. 앱 403은 요청이 여전히 Flask까지 오므로 폭주 중 응답시간이 돌아오지 않을 수 있다(S12 진행계획).

## A에게 물을 질문 (가정하지 않음)

초안 2·3절은 A 문서 기준이며 **실제 배포된 포털에서 확인된 것이 아니다.** 아래는 배포 기준 확인이 필요하다.

1. 배포된 포털(VM, 실제 실행 커밋)에 `POST /api/v1/response/ips/block`·`unblock`, `GET /response/ips`가 있는가? backend #2(IP 차단)는 Draft·미병합이라고 적혀 있다.
2. 인증: `X-Response-Key`와 허용 대역(`RESPONSE_ALLOWED_CIDRS`)의 실제 값 방식. 키는 어떻게 전달받는가(n8n 자격 증명에만 넣을 수 있게 채팅·저장소가 아닌 경로)?
3. 허용 호출 출발지: 포털이 보는 n8n의 발신 주소는 무엇이어야 하는가? D PC가 팀 VPN(`team-d`) 주소로 나가면 포털에는 그 터널 주소로 보이는가, B pfSense를 거쳐 다른 주소로 보이는가? (Docker 내부 주소나 VPN 전체 대역을 추측해 허용하지 않기 위해, D가 연결한 뒤 A·B가 포털 로그의 `remote_addr`로 확인)
4. 포털은 현재 `remote_addr`만 보고 `X-Forwarded-For`를 무시한다고 한다. pfSense 목적지 NAT(`203.0.113.1:80` → A VM) 뒤에서도 `remote_addr`가 Kali의 `203.0.113.10`으로 보이는가? (10/21 17:05 요청에 대한 A 로그 대조 답변이 대기 중) 보이지 않으면 `src_ip`가 pfSense 주소가 되어 출발지별 집계와 차단이 모두 무의미해진다.
5. 응답 형식: 성공 `{success, data:{ip, blocked, changed, expires_at}}`, 실패 `{success:false, error:{code,message}}`와 상태 코드표(초안 2절)가 배포 기준과 같은가? 404·관리자 대상 응답 코드는?
6. `Idempotency-Key` 규칙 확정(10/24 API-CONTRACT 반영 예정)과 재시도(5초 시간 초과, 5xx·409는 같은 키 1회)가 배포에 구현되어 있는가?
7. 헬스체크 경로: `/api/v1/health`가 배포 커밋에서 DB를 읽는가? D 관리 경로(인증 없이 부를 수 있는가)와 정상 사용자 공개 경로 중 어느 것을 판정에 써야 하는가?
8. 차단된 IP의 요청도 `web.request`로 GELF에 남는가(403 `IP_BLOCKED`)? 남으면 차단 뒤에도 후보 이벤트가 계속 발동하므로 중복 방지가 필요하다.
9. S12 속도 제한은 "처음엔 차단만"으로 확정인가(초안 6절 3번, D 확인 대기). D 의견: 차단만 진행.
10. `GET /response/ips`는 대응 키가 필요하고 허용 대역에서만 부를 수 있다. D PC가 그 허용 대역에 들어가는가(초안은 관제 PC `10.10.30.10`, 계획값)?
11. 부하 시험: 정상 출발지와 공격 출발지를 각각 어느 주소로 둘 것인가, B와 함께 중단 기준을 정할 수 있는가?

B에게 따로: 팀 VPN `team-d` 프로필 전달, D PC에서 n8n으로 향하는 호출이 지나갈 경로(아웃바운드)의 pfSense 규칙. C에게: 티켓 저장소 API(열린 티켓 조회 포함).

## 10/22 오후 갱신 (A 답변·D 확인)

위 질문 중 아래는 이후 확인되었다. 나머지(5·6·7·8·9·11)는 아직 열려 있다.

| 질문 | 확인된 내용 | 근거 |
| --- | --- | --- |
| 1 배포 여부 | 배포 커밋은 `47be008`(`claude/portal-ip-block-file-key`)이고 `block`·`unblock`·`GET /response/ips`가 코드에 있다. 인증 없이 `GET /api/v1/response/ips`를 보내면 403 | A 답변, D가 코드를 읽고 1회 호출 |
| 2 인증 | `RESPONSE_ALLOWED_CIDRS`가 비어 있어 지금은 누구든 403, `RESPONSE_API_KEY`는 미설정. A가 키를 만들고 D 자리에서 n8n 자격 증명에 직접 입력(채팅·메신저 사용 안 함) | A 답변 |
| 3 호출 출발지 | n8n 컨테이너에서 보낸 `GET /api/v1/health`가 포털에 `src_ip 10.250.0.100`으로 찍혔다. A가 `10.250.0.100/32`만 허용 예정(VPN 대역 전체 아님). D가 재접속해 주소가 바뀌면 다시 맞춰야 함 | D가 요청 1회로 확인, A 답변 |
| 4 `remote_addr` | Kali의 `GET /login`이 `src_ip 203.0.113.10`으로 보였다(pfSense NAT 뒤에서도 Kali 주소가 유지됨). 포털은 `X-Forwarded-For`를 보지 않음 | D Graylog 수신, A 답변 |
| 10 허용 대역 | 위 3과 같다. 허용 주소는 차단 대상에서도 제외됨 | A 답변 |

키와 허용 대역은 A가 S7 동결 해제 뒤 반영·재시작한다고 했으므로 차단·해제 시험은 그 뒤다.
