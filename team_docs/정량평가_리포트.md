# 보안 관제·자동 대응 정량평가 리포트

> 상태: **부분 측정(11/03 기준, A 갱신)**. 보강 후 실제 회차는 S1 2회(조건 충족 4건)·S4 1회·S8 2회(LIVE01 실패 포함)·S10 1회·S12 1회(no_action)뿐이고(PF 단독 인수 ACCEPT01·02는 참고 줄) S7 실제 회차와 정상 30분·경계 시험은 없다. 3·7장 수치는 이 표본만으로 계산했다. (이전 상태: 측정 전 틀.) 지표 정의와 목표는 [기획서 ⑤](기획서.md)와 [기획서 합의본 5.5](기획서_합의본.md)를 따르고, 팀 추가 지표(★)는 합의 전 제안이다.
> 결과 칸은 실제로 돌린 값만 적는다. 측정 전에는 `⬜ 미측정`으로 둔다. 목표값은 10/20 회의 뒤 확정한다.

## 1. 개요

"검문소" 방식으로 공격 한 번이 지나가는 단계마다 독립된 출처(원본 로그·Graylog·n8n·대상 상태·헬스체크)로 채점한다. n8n 실행 성공만으로 대응 성공을 판정하지 않는다.

```
Kali 공격 / 정상 업무 트래픽 (재현 스크립트, run_id)
   ↓
[원본 로그]  Flask GELF · pfSense filterlog/OpenVPN · Suricata eve · Wazuh
   ↓ ──► (검문소 A) Graylog 도착        → 신호 도착률, 수집 지연
[Graylog 이벤트 정의 / Wazuh 규칙]
   ↓ ──► (검문소 B) 이벤트 판정         → 탐지율, 오탐, MTTD
[n8n 대응 봇 108·111~116]
   ↓ ──► (검문소 C) 대상 상태·재공격     → 자동 대응 성공률, 차단 효과, 정상 업무 영향
[인시던트 티켓]
   ↓ ──► (검문소 D) 티켓·묶기           → 사건 묶기 정확도, 통지 처리율
[헬스체크 svc-health / 원복]
   ↓ ──► (검문소 E) 회복·원복           → MTTR, 원복 성공률, 가용성
[증적 폴더]
     ──► (검문소 F) 증적 점검           → 증적 완비율, 민감정보 노출
```

## 2. 테스트셋

필수 4종은 자리별 시나리오 4개이고, 측정 대상 케이스 ID는 6개다: A S1·S4, B S8·S10, C S7, D S12 ([합의본 ②](기획서_합의본.md)). A·B는 두 ID를 따로 측정하고 결과도 ID별로 낸다. 이 6개를 우선 측정하고, 나머지 S1~S12는 구현된 것만 같은 절차로 추가한다. 모든 시험은 격리 VMnet 안에서 `zz_` 테스트 계정과 랩 주소만 쓴다.

**보강 전/후 기준.** 보강 전은 로그 수집은 연결됐지만 그 케이스의 탐지 규칙(Graylog 이벤트 정의·Wazuh 규칙)과 n8n 대응을 아직 넣지 않은 상태다. VM 스냅샷·설정 버전으로 고정한다. 보강 후는 규칙과 대응을 넣은 상태다.

보강 전에는 규칙이 없어 결과가 미탐·티켓 없음으로 정해져 있으므로, **전체 조건 충족 1회만** 돌려 "공격은 성공하고 로그는 남았지만 아무도 모른다"를 증적으로 남긴다. 나머지 시험은 보강 후에만 돌린다. 이 1회는 규칙을 넣기 전에 먼저 해야 하며, 나중에 다시 할 수 없다.

| 입력 종류 | 보강 전 | 보강 후 | 기대 (보강 후) | 용도 |
| --- | --- | --- | --- | --- |
| 전체 조건 충족 | 1회 | 5회 | 발동 1건 → 대응 → 티켓 1건 | 탐지율, MTTD·MTTR, 대응 성공률, 보강 전후 비교 |
| 경계 바로 아래 | — | 1회 | 미발동 | 경계 오탐 |
| 조건 일부만 충족 | — | 1회 | 미발동 (S12는 최종 판정 기준, 아래 예시) | 경계 오탐 (결합 조건 케이스 S4·S7·S8·S9·S10·S12만) |
| 시간 창 밖 | — | 1회 | 미발동 | 경계 오탐 |
| 혼합 | — | 1회 | 주체별 따로 판정 | 사건 묶기 정확도 |
| 정상 업무 | — | 30분 1회 | 이벤트 0건, 정상 요청 성공 | 정상 업무 오탐, 정상 업무 영향 |

| 규모 | 시험 수 |
| --- | --- |
| 케이스 ID 1개 | 10회 (결합 조건 케이스 11회) |
| 필수 케이스 ID 6개 | 65회 (S1 10 + S4·S8·S10·S7·S12 각 11) + A·B 연쇄 확인 2회(앞 단계 자동 차단을 끈 시험, 합의본 ②) = **67회** (보강 전 6 + 보강 후 61, 통합 스토리라인 제외, #20) |
| (참고) 보강 전 1회를 안 쓰면 | 보강 전 N=5회로 ID마다 +5회 → 98회. #20에서 **보강 전 1회**를 채택해 67회로 확정 |

- 보강 전 1회는 #20에서 채택됐다(67회, 통합 스토리라인 제외). 목표값은 합의 전 제안이다.
- 순서 조건(S4·S8)을 요구하기로 정하면 해당 ID에 "순서 반대" 1회가 더해진다([합의본 5.9](기획서_합의본.md)).

- 임계값·묶기 키를 고쳐 오탐을 줄인 케이스는 고치기 전과 후의 경계·정상 시험 결과를 따로 한 줄씩 남긴다(4-6).

- 표본이 작으므로 비율은 항상 횟수와 함께 적는다(5회 중 1회 실패 = 4/5, 80%).
- 집계 창이 긴 케이스(S1 30분 등)는 실행마다 테스트 계정·출발지 IP를 바꿔 앞 실행의 집계가 남지 않게 한다.

### 예시 시험 (기획서 S1 기준)

**[전체 조건 충족] 입력:** 한 출발지 IP에서 `zz_officer01` 계정에 30분 안에 로그인 실패 9회 (`count()>8 · 30분 · username + src_ip`)

→ 기대 동작: `login-bruteforce` 이벤트 1건(묶기 필드에 공격 IP) → n8n 112 출발지 차단 → 같은 공격 IP의 새 요청 403 `IP_BLOCKED` + 앱 차단 목록(`GET /response/ips`, 관제 PC에서 조회)에 그 IP → 같은 계정을 다른 정상 IP에서 로그인 성공 → 114 티켓 1건 → IP 차단 해제 후 사전 상태와 같음

S1은 계정 잠금(111)을 쓰지 않는다. 포털은 잠긴 계정도 비밀번호 오류와 같은 401을 주므로([PORTAL-API](https://github.com/NoBugs-Aleph/aleph-soar-capstone/blob/claude/portal-ip-block-file-key-contract/docs/haedam/PORTAL-API.md)), 정상 IP 로그인이 401이고 관리자 화면에서 계정이 "잠김"이면 정상 사용자를 막은 것이므로 "정상 업무 영향"으로 판정한다.

**[경계 바로 아래] 입력:** 같은 조건에서 실패 8회

→ 기대 동작: 신호 8건 도착, 이벤트 0건, 대응 0건

**[S12 조건 일부만 충족] 입력:** 한 출발지 요청 수만 임계 초과, 응답시간은 기준선 이내

→ 기대 동작: Graylog 요청 수 후보 이벤트 1건(정상, 오탐 아님) → n8n 헬스체크가 기준선 안으로 판정 → 대응 0건·티켓 0건 → **케이스 미발동** (요청 수와 응답시간이 **둘 다** 넘어야 발동, [합의본 5.2](기획서_합의본.md)). 이 시험에서 n8n이 대응하면 오탐이다.

### 4-2. 탐지

| 지표 | 계산 | 값의 출처 | 3대 원칙 |
| --- | --- | --- | --- |

- S12의 "발동"은 Graylog 요청 수 후보 이벤트가 아니라 후보 이벤트 + n8n 헬스체크 판정을 합친 최종 판정이다. 탐지율·오탐(정상·경계)은 최종 판정으로 세고, 후보 이벤트만 생기고 n8n이 대응하지 않은 경우는 오탐이 아니다.
- 오탐은 공격이 없는데 발동한 경우, 미탐은 공격 조건을 채웠는데 발동하지 않은 경우다. 미탐은 탐지율의 분모에 남아 탐지율로 드러난다.
- 조건 충족 시각은 창·묶기·순서를 포함한 전체 조건을 처음 충족한 원본 신호의 시각이다. 저속 브루트포스의 공격 시간이 탐지 지연에 섞이지 않게 한다.
- 오탐(정상 업무)은 정상 요청 수·종류·동시 사용자와 관측 종료 시점을 함께 적고, 0건이면 "이 조건의 T분에서 0건"으로 보고한다.

### 4-9. 공통 측정 규칙

- 시각은 네 개를 따로 남긴다: 조건 충족 → 이벤트 생성 → 조치 완료 → 효과·회복 확인. S12는 탐지를 Graylog 후보 이벤트 시각과 n8n 판정 시각으로 나눠 다섯 개를 남긴다. 첫 공격 시각도 보존한다.
- 판정 기한([합의본 5.9](기획서_합의본.md)): 발동 기대 시험은 조건 충족 뒤 검색 주기 + 수집 지연 + 여유, 미발동 기대 시험은 마지막 입력 뒤 **그 케이스의 가장 긴 집계 창 + 검색 주기 + 수집 지연**까지 관측한다(S1은 30분 + 검색 주기 + 수집 지연). 관측 종료 시각을 결과와 함께 적는다.
- 시간 지표는 평균이 아니라 **중앙값 · 최댓값**으로 적고, 형식은 `중앙값 ○초 · 최댓값 ○초 · 성공 ○/N · 미탐 ○ · 시간 초과 ○`.
- Graylog 이벤트 검색 주기와 헬스체크 주기를 결과와 함께 적는다. 시간 지표의 해상도가 이 주기에 묶인다.
- 비율은 횟수를 함께 적는다(예: 5/5).

### 6-2. 탐지 (탐지율·오탐·MTTD)

- 사전 관측(결과표 아님): S1·S4 이벤트 정의를 1분 실행으로 재현하면 첫 발동이 조건 성립 뒤 최대 60초 늦고(53초), 조건이 유지되는 동안 같은 키로 반복 발동한다(S1 6회·S4 2회). 알림 억제(grace)를 창과 같게 두어 n8n 호출은 키당 1회. 실측 MTTD는 Graylog `timestamp_processing`으로 잰다.
- 시각 기준 정리(11/03, C·D 확정): Graylog `timestamp`(`condition_met_at`)는 1분 평가 창 끝이라 조건 충족 순간이 아니다. S4 LIVE01에서 창 끝 15:45:03.089와 처리 15:45:08.691이 5.6초 벌어졌고, 대시보드 "MTTD 5.602초"는 이 간격이라 공격→탐지 시간이 아니다. 이 리포트의 MTTD는 포털 원본 조건 충족 → `timestamp_processing`이다.

### 6-3. 대응 (자동 대응 성공률·정상 업무 영향)

- 미달 1건: S8 LIVE01은 Graylog 탐지·알림 발송까지 정상이었고 n8n 웹훅이 등록돼 있지 않아 끊겼다(검문소: 알림 → n8n). 포털 원본·DB로 요청이 포털에 오지 않았음을 먼저 확인해 원인을 좁혔고, D 복구 뒤 20분 만에 LIVE02 통과. 개선: 회차 전 웹훅 수신 시험(키 없는 요청 403·키 있는 요청 수신)을 사전 확인에 넣는다.
- PF 경계 차단은 S10 본 시험(S10-20261103-LIVE01)에서 실제 티켓 T-20261103-0003과 함께 포털·PF 이중 자동 차단으로 확인했고, 자동 대응 7/8 분모에 1회로 들어간다. 이와 별도로 PF 도구 단독 인수는 ACCEPT01에서 block·unblock 모두 결과 불일치로 B 수동 복구, 도구 r2 배포 뒤 ACCEPT02에서 자동 block·unblock 각 1회 성공·잔여 없음. 단독 인수는 티켓이 없어 분모에 넣지 않는다.
- 탐지 뒤 조치 완료는 S1 0.55~5.9초·S4 0.979초·S8 1.9초로 짧다. 종단 시간의 대부분은 Graylog 1분 평가 주기와 시험자 확인 대기다.

### 6-4. 사건 (묶기 정확도)

- 실제 회차마다 티켓 1건이었다: S1 `.11`·`.13`(같은 계정)은 T-20261028-0002 한 건, 해제 뒤 재공격은 정책(#62)대로 새 T-20261028-0003, S1-after-02 T-20261029-0001, S8 T-20261103-0001, S4 T-20261103-0002. 같은 키 반복 발동(S1 이벤트 16건)은 n8n 실행 1회로 억제됐다(grace).
- 미시험: n8n 재전송·동시 실행, S8과 S10이 같은 출발지로 함께 발동할 때 한 티켓으로 묶이는지(통합 스토리라인).

### 6-5. 회복·원복 (MTTR·가용성·원복)

- 원복 7/7은 모두 사람이 연결한 해제다(S1·S8 D haedam-12 수동 실행, S4 A 비밀번호 재설정 + D unlock 기록, S10 PF 해제 → 포털 해제 단계별 수동). 승인 해제 워크플로(haedam-50)는 `dry_run` 고정이다. 원복 소요시간 중앙값 79.2초(7건, 3장)는 시험자 재접근 대기를 포함해 목표 60초와 바로 비교할 수 없다.
- 티켓 화면 MTTR(S4 346.0초)은 효과 확인을 사람이 기록한 시각까지라 실제 효과 시각(148.6초)보다 길다. 발표에서는 두 값을 함께 적는다.

- S12 (S12-20261103-LIVE01): 판정용 health(D n8n, 탐지 직후 6초 동안 3회)는 28~39ms로 정상이었지만, 정상 사용자 `/login`(부하 시작~종료 후 포함 전체 480초, 240건)은 p95 46.4 → 582.2ms, max 1,300 → 2,152ms로 느려졌다. 막힌 요청은 없어 대응 없음이 기준대로의 결과이나, health 측정 시점·경로가 사용자 체감 지연을 반영하는지는 다시 볼 과제다(D, 원인 미확정). 부하는 B 송신 4,399 = 포털 원본 4,399로 송신·수신 요청 총건수 일치, 40 req/s 단계는 송신 2,299건(95.79%, 부족 101).
