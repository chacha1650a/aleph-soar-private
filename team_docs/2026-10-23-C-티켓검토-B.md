## 2. C 수정 요청

### 2-1. [P1] 자리 간 해제 보류 조회는 사건 묶기 키와 조치 대상을 분리

- 위치: `services/ticket-store/ticket_store/core.py:45~60`, 설계 1-1·2-1④·3-1①.
- 재현: A/S1은 `group_key=zz_review_user`, D/S12는 `group_key=203.0.113.31`로 각 티켓을 만들고, 두 티켓 모두 `bot=112, via=portal, action=block, target=203.0.113.31`을 기록한다.
- 실제: `GET /api/v1/tickets/open?group_key=203.0.113.31`의 `tickets`에는 D만 나온다. A의 활성 차단은 존재하지만 조회에서 빠진다.
- 영향: D가 자기 차단을 풀기 전에 다른 자리의 차단 유무를 확인해도 A를 놓쳐, 공유된 포털 IP 차단을 해제할 수 있다.
- 요청: 티켓 묶기용 `group_key`는 유지하되, 자리 간 원복 보류는 조치의 대상·집행 위치 등 실제 자원 식별자로 조회할 수 있게 한다. API 계약·응답 예시와 D result-log의 조회 인자를 함께 맞춘다.
- 확인 조건: A의 username 묶음과 D의 IP 묶음이 달라도 같은 자원에 걸린 두 조치가 조회되고, 다른 자원이면 섞이지 않아야 한다.

### 2-2. [P2] 해제된 조치는 새 차단의 중복 근거에서 제외

- 위치: `services/ticket-store/ticket_store/core.py:165~171`.
- 재현: D 티켓에서 applied(block) → released(unblock) → **새 event_id·새 Idempotency-Key**로 applied(block)을 기록한다. 기존 티켓은 restored이지만 아직 closed는 아니다.
- 실제: 마지막 응답은 `duplicate:true, status:restored`, `check.applied_actions=[]`다. 새 조치는 actions에 중복 줄로 저장돼 활성 조회에서 빠진다.
- 영향: 실제 다시 걸린 차단의 소유·효과·원복 기록이 사라지고, D가 차단을 반복 호출하거나 해제 필요성을 놓칠 수 있다.
- 요청: 중복은 현재 활성 조치에 대해서 판단한다. 새 조치를 같은 티켓의 새 주기로 기록할지, 기존 티켓 종료 후 새 티켓으로 만들지 상태 정책을 먼저 정하고 D와 맞춘다. 현재의 단방향 상태 정책을 조용히 바꾸지 않는다.
- 확인 조건: 새 조치가 활성 목록에 나타나며, 이전 released·새 applied가 원본 순서대로 보존돼야 한다. 같은 요청의 재전송은 여전히 중복을 만들지 않아야 한다.

### 2-3. [P2] 포털 차단과 pfSense 차단을 다른 조치로 식별

- 위치: `services/ticket-store/ticket_store/core.py:23~42,149~177`, 설계 3-1①과 응답 스키마의 조치 참조.
- 재현: B/S10의 같은 열린 티켓에 `bot=112, action=block, target=203.0.113.31`을 두 번 기록하되, 첫 번째는 `via=portal`, 두 번째는 `via=pfsense`로 보낸다.
- 실제: pfSense 줄이 `duplicate:true`로 저장되고, 자리 지정 check의 `applied_actions`에는 `via`도 없어 두 집행 위치를 구분할 수 없다.
- 영향: 포털만 차단됐는데 경계 차단까지 된 것으로 오해하거나, 한 집행 위치의 원복 기록으로 다른 위치의 활성 차단까지 지울 수 있다.
- 요청: 조치 중복·효과 갱신·원복·조회에서 집행 위치를 일관되게 식별한다(예: `bot + via + action + target`). 해제 동사가 block→unblock으로 달라지는 대응 관계도 계약에 적는다. `ticket-response.schema.json`과 D의 check 소비자도 함께 맞춘다.
- 확인 조건: 포털·pfSense 차단이 각각 활성 조치로 보이며 한쪽만 해제해도 다른 쪽은 활성으로 남아야 한다.
