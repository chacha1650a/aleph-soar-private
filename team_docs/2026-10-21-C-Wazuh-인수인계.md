# 김상혁(C) Wazuh·S7 인수인계

작성: 김명준(B)·Codex / 2026-10-20, Asia/Seoul. C가 기존 수업 환경을 해담포털에 맞춰 수정할 때 필요한 연결 정보·설정·확인 순서를 정리한다. **C PC에 실제 적용하거나 S7을 검증한 결과는 아니다.** C의 책임은 S7 홈페이지 변조, Wazuh와 프로젝트 보안 대시보드·티켓이다.

## 1. 내일 시작할 순서

1. C의 기존 Wazuh manager·indexer·dashboard 버전, Compose 위치·볼륨·공개 포트·자원 사용량을 확인한다. 수업 데이터와 기존 설정을 보존한다.
2. B와 C의 VPN 종단·주소·agent 수집 경로를 맞추고 A의 Ubuntu agent를 등록한다. A의 실제 agent가 Active인지 확인한다.
3. A에게 실제 배포 웹 루트·마운트·자산 정보를 받아 realtime FIM을 맞춘다. 승인한 시험 파일 하나를 변경·복원하고 경보를 확인한다.
4. D와 Wazuh 경보 전달·필드 정규화·S7 상관 조건을 맞춘다. 이후 원본 복구·새 파일 격리·티켓·원복을 단계별로 붙인다.

첫 공동 목표는 **A agent의 파일 변경 경보를 C가 실제로 받는 것**이다. S7 전체 완료는 같은 파일 웹 접근과의 상관·대응·티켓·효과·원복 확인까지 포함한다. [A·C 작업계획](2026-10-21-A-C-작업계획.md), [A VM 인수인계](2026-10-21-A-VM-인수인계.md)를 함께 확인한다.

다음은 B PC의 [10/20 관제 사전 점검 기록](https://github.com/NoBugs-Aleph/aleph-soar-capstone/blob/46ad042eb7819457fb385e2c3f78bac47da3068a/work-log/2026-10-20-monitoring-preflight.md) 기준이다. C·D의 실제 버전·설정은 별도로 확인한다.

| B의 관찰 | C·D 분산 시 확인·수정 |
| --- | --- |
| Wazuh manager·indexer·dashboard 4.9.0 | C 버전을 먼저 확인하고 A agent와의 호환성을 맞춤. 최신 태그로 바로 재설치·업그레이드하지 않음 |

| Graylog Syslog UDP 1514는 pfSense용 | Wazuh agent 연결 기본 TCP 1514와 구분. 숫자가 같아도 목적지·프로토콜·역할이 다름 |
| FIM용 실습 규칙 100220~100222와 `wazuh_file` 필드가 있음 | 이 ID는 기존 수업 사용자 정의다. C에 같은 규칙이 존재하는지 확인하고 새 기본 규칙이라고 가정하지 않음 |
| `wazuh_file`은 절대 경로, 포털은 `file_key`를 보냄. 같은 파일 접근과 묶는 S7 정의는 미구성 | 아래 자산·파일 키 정규화와 D의 상관 규칙을 보완 |
| B에서 여러 스택 실행 시 호스트 메모리 여유가 매우 적었음 | C에서 실측. Wazuh 기동과 프로젝트 대시보드의 동시 자원을 확인하며 B의 수치를 C 성능으로 사용하지 않음 |

## 3. B에게 받을 팀 연결과 필요한 포트

| 항목 | 현재 기준 |
| --- | --- |
| C Windows 유선 주소 | 사용자 전달 `192.168.3.5`. 내일 실제 값 재확인. Wazuh 서비스의 터널 주소와는 별개 |
| 팀 VPN | `HAEDAM_TEAM_TRANSIT`, UDP 1195, 10/20 서버 관찰 주소 `192.168.7.174`(DHCP) |
| 터널 | `10.250.0.0/24`, 서버 `10.250.0.1` |
| C 전용 계정·프로필 | 예정 `team-c`. 현재 미생성·미발급. B가 개별 준비 |
| 현재 규칙 | 팀 터널→서버 Ping 허용 후 기본 차단. 내부 서비스 경로·A↔C 통신은 미설정·미검증 |

Windows에 VPN이 연결됐다는 사실만으로 A VM이나 C Docker 서비스가 연결되지는 않는다. B가 VPN 종단·왕복 경로·관측 출발지와 필요한 규칙을 정하고 C는 실제 포트 게시·Windows 방화벽·서비스 수신 주소를 맞춘다. 과거 물리안의 `10.10.30.11`을 C에 먼저 적용하지 않는다.

다음은 [Wazuh 공식 기본 포트](https://documentation.wazuh.com/current/getting-started/architecture.html)다. 실제 C의 Compose 호스트 게시 포트와 프로토콜을 확인한 뒤 B에게 전달한다.

| 통신 | 기본 포트·역할 | 필요한 조율 |
| --- | --- | --- |
| A agent → C manager | TCP 1514, 이벤트 수집 | 실제 A 발신 주소만 허용할 경로·게시 포트 확인 |
| A agent → C manager | TCP 1515, agent 등록 | 사용하는 등록 방식과 인증·필요 연결 확인 |
| D n8n → C manager API | TCP 55000, Wazuh API | 대응 단계에서 실제 호출자·API 자격 증명·권한 확인 |
| C Wazuh → D Graylog | 입력 방식·프로토콜·포트 결정 필요 | 수업 예시 UDP 5140을 확정값으로 사용하지 않음 |

Wazuh 제품 dashboard·indexer와 프로젝트 대시보드·티켓의 웹/API 연결은 별도다. 로컬 제품 화면 확인을 위해 다른 PC에 모든 내부 포트를 개방하지 않는다. VPN 파일·등록 비밀값·API 비밀번호는 Git·공용 글에 남기지 않는다.

## 4. A에게 받아야 할 값과 FIM 수정

| A에게 받을 값 | C가 할 일 |
| --- | --- |
| Ubuntu agent 이름·ID·버전·실제 주소 | C manager 등록 대상·연결 상태 확인 |
| 앱의 `ASSET_ID` | agent 식별자와 포털 자산 식별자의 대응을 D와 맞춤. 기본 앱 값은 `haedam-portal` |
| 실제 빌드 `dist` 절대 경로 | 소스 `src`나 수업 예제 폴더 대신 실제 서비스 파일 감시 |
| 컨테이너 사용 시 호스트/컨테이너 마운트 대응 | A VM의 호스트 agent가 보는 경로를 FIM에 사용 |
| 기준본·해시 목록·배포 방식 | 정상 배포 갱신과 변조 시험·복구의 기준을 구분 |
| 시험 파일·실제 접근 URL | 경보 파일과 포털이 실제로 제공한 파일을 같은 대상으로 대조 |

[공식 FIM 안내](https://documentation.wazuh.com/current/user-manual/capabilities/file-integrity/basic-settings.html)에 따라 존재하는 디렉터리에 realtime 감시를 설정한다. 아래는 **A의 실제 경로 확인 후 수정할 예시**다. 기존 `/var/ossec/etc/ossec.conf`를 보존하고 기존 syscheck 설정에 항목을 병합한다. 설정 적용은 A와 조율하며 agent 재시작 후 연결·경보를 확인한다.

```xml
<directories realtime="yes">/srv/haedam/frontend/dist</directories>
```

기준본·해시 목록·격리 위치는 웹 루트 밖에 두고 웹 계정이 기준본을 바꾸지 못하게 한다. 전체 OS·DB·비밀 파일을 감시/복구 대상으로 넓히지 않는다. A 배포 전이면 승인한 시험 디렉터리로 agent·FIM 경로만 먼저 확인하고 실제 포털 연동과 구분한다.

## 5. D와 맞출 S7의 자산·파일 키

S7은 **같은 자산·같은 파일의 FIM 변경/생성 + 실제 웹 접근**을 연결하는 계획이다. 기획서 기준 집계 창은 10분이다. 수업 FIM 경보 하나만으로 전체 S7 완료 처리하지 않는다.

예시 경로(실제 배포값 아님):

| 관측 위치 | 예시 값 |
| --- | --- |
| A 호스트 FIM 경로 | `/srv/haedam/frontend/dist/assets/s7-proof.txt` |
| 앱 컨테이너 `FRONTEND_DIST` | `/app/frontend/dist` |
| 포털이 제공한 URL | `/assets/s7-proof.txt` |
| 공통 `file_key` | `assets/s7-proof.txt` |

FIM 경로에서는 **호스트 웹 루트**를 제거한다. 컨테이너의 `FRONTEND_DIST`와 호스트 경로가 다르면 마운트 대응을 이용한다. 앱 이벤트는 `web.file_access`의 `details.file_key`(GELF `file_key`)를 사용한다. 두 값은 자산도 일치해야 하며 agent 이름을 앱 자산 ID로 자동 간주하지 않는다.

파일 키 규칙은 [기존 포털 계약](https://github.com/NoBugs-Aleph/aleph-soar-capstone/blob/46ad042eb7819457fb385e2c3f78bac47da3068a/docs/haedam/PORTAL-API.md)을 따른다. 웹 루트 기준 상대 경로·`/` 구분이며 `..`·빈 세그먼트 등 잘못된 값은 제외한다. 여기서 새 필드를 계약으로 확정하지 않는다.

C는 D에게 비밀값 없는 경보 샘플의 rule.id, agent 식별자, syscheck.path, 변경 유형·해시·시각을 전달하고 D와 자산·파일 키 매핑 및 수신 결과를 대조한다. B 기록의 level 5 이상 전송 필터에 시험 경보가 걸리는지도 확인한다. 정상 배포의 기준본·해시 갱신과 복구 후 FIM 재경보로 인한 중복 티켓·반복 대응을 따로 다룬다.

## 6. 파일 복구·격리와 티켓의 후속 작업

- 변경된 파일은 검증한 기준본으로 복구하고 해시와 실제 웹 응답을 확인한다. 새 시험 파일은 웹 루트 밖으로 격리한 뒤 원래 URL이 404인지 확인한다.
- Wazuh FIM 탐지와 자동 파일 복구는 별도 구현이다. 기본 경보가 복구까지 해주지는 않는다. 기획서의 117은 가칭이며 명령·대상·권한·응답 계약은 확정·구현 여부부터 확인한다.
- 1안은 D n8n이 C의 Wazuh API를 통해 A agent의 custom active response를 요청하는 방식이다. [공식 실행 입력](https://documentation.wazuh.com/current/user-manual/capabilities/active-response/custom-active-response-scripts.html)과 설치 버전을 확인해 구현하고, A에서 실제 실행·해시 변화·실패 기록까지 검증한다. 외부 입력의 경로·셸 명령을 그대로 실행하지 않는다.
- 자동화 연결 전 C·A가 승인한 시험 파일로 수동 복구·격리를 먼저 확인한다. 자동화 시험은 D와 조율해 기존 수업 워크플로의 실제 대상을 확인한 뒤 실행한다.
- Wazuh 제품 dashboard는 agent·경보 확인 화면이다. 프로젝트의 사건·티켓 저장/조회 화면은 별도 작업이며 D와 API·인증·대응/원복 상태를 맞춘다. 기존 샘플 화면은 실제 사건으로 표시하지 않는다.

## 7. C가 먼저 공유할 점검 결과

C의 **Windows PowerShell**에서 실행하는 읽기 점검이다. Compose 파일 원문·전체 환경변수·비밀값 포함 로그를 그대로 올리지 않는다.

```powershell
docker version --format '{{.Server.Version}}'
docker compose version
docker compose ls
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}\t{{.Status}}'
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}'
Get-NetIPAddress -AddressFamily IPv4 | Select-Object InterfaceAlias,IPAddress,PrefixLength
```

함께 공유: Wazuh 버전, Compose 경로, 볼륨 위치, 실제 manager 호스트 게시 포트, agent 목록·대상 agent 상태, 제품 화면 주소, RAM 사용량, B에게 필요한 연결. 화면 로그인 정보와 API 비밀번호는 별도 보관한다.
