# 티켓 저장소 API 초안 (C · shk12170-dev)

> **10/23 이후 기준은 [C 티켓 저장소 설계](../docs/C-티켓저장소-설계.md)입니다.** 이 파일은 D에게 질문할 때 쓴 10/22 초안으로 남겨 둡니다. D 답을 반영하면서 위치(D PC → C PC), `bot` 형식(문자열), `asset_id`(`haedam-portal`), `Idempotency-Key`(단계별), 응답 모양(D 확인 중)이 바뀌었습니다.

결정 1 (스키마): 새로 만든다 (contracts/ticket.schema.json) — 이유: 기존 incident.schema.json은 username이 필수라서 username이 없는 S7·S12 티켓을 담을 수 없고, 상태도 3개(open·contained·resolved)뿐이라 5단계 흐름(open→responding→verified→restored→closed)과 맞지 않는다. 기존 스키마를 고치면 이미 있는 예시·테스트가 같이 흔들리므로, 티켓은 새 스키마로 두고 incident와의 대응은 계약 변경(PROGRESS 1-3) 때 맞춘다.

결정 2 (30분 창): 열린 티켓이 있으면 계속 덧붙인다 — 이유: 같은 자리·같은 group_key의 열린 티켓은 하나만 두는 유일 제약(합의본 427행)만으로 중복을 막을 수 있어 구현이 단순하다. 30분 기준으로 나누면 "마지막 기록 시각" 계산과 경계 시각 처리가 더 필요하고, S7 복구가 FIM 경보를 다시 내는 경우 새 티켓이 생겨 같은 복구를 또 실행할 위험이 있다. 사건이 끝나면 사람이 티켓을 닫고(closed), 그 뒤 들어온 경보는 새 티켓이 된다.

결정 3 (읽기 키): 쓰기만 키 필요 (record에 X-Response-Key + Idempotency-Key) — 이유: 쓰기는 다른 PC의 n8n이 부르므로 포털 대응 API와 같은 두 겹 인증(허용 대역 + 키)이 필요하다. 읽기(목록·상세·대시보드 화면)는 합의본 265행대로 127.0.0.1에만 열어 관제 PC 브라우저에서만 보므로 출발지 제한으로 충분하고, 브라우저에 키를 넣지 않아도 된다. 단, check(GET /tickets/open)는 n8n이 다른 PC에서 부르면 쓰기와 같은 키를 요구한다.

결정 4 (위치): D PC (D 확인 필요) — 이유: 티켓 저장소를 가장 많이 부르는 쪽이 D PC의 n8n이라, 같은 PC·같은 Docker 네트워크에 두면 PC 사이 경로·VPN 규칙·Windows 방화벽 예외가 필요 없어 연결 실패 지점이 줄어든다. 또 C PC는 Wazuh 전체·수업 Graylog·n8n·MySQL로 이미 약 5.2/7.7GiB를 쓰고 있다. 대신 C가 D PC에 컨테이너를 배포해야 하므로 D와 배포 방법을 정하고, D PC에서 docker stats로 여유 메모리를 먼저 확인한다(대시보드+티켓 저장소는 Flask+SQLite 수준의 가벼운 컨테이너 하나 예상, 미측정). D PC 메모리가 모자라면 C PC에 두고 D→C 포트 1개(B VPN 규칙·C 방화벽)를 연다.

========================================================================
5단계 · 경로 4개의 요청·응답 예시 (초안, 미구현)
========================================================================

[공통 규칙] 포털 대응 API(A 초안 2절)와 같게 맞춘다.
- 주소: http://<티켓 저장소 주소>:<포트>/api/v1  (주소·포트는 결정 4 확정 뒤)
- 응답 모양: 성공 {"success": true, "data": {...}} / 실패 {"success": false, "error": {"code": "...", "message": "..."}}
- 시각: 한국 시간 + 시간대 표시 (예: 2026-10-24T14:05:31+09:00)
- 키(X-Response-Key): check·record만 필요. 목록·상세는 127.0.0.1 전용이라 키 없음(결정 3)
- 티켓에 넣지 않는 것: 키, 비밀번호, 요청 본문 원문, 세션 값
- 값 제한: seat = A|B|C|D, case_id = S1|S4|S7|S8|S10|S12,
           status = open|responding|verified|restored|closed,
           result = applied|already_applied|failed|rejected|released (D 설계와 같음)
- group_key(묶기 키) 만드는 법: A = username, B·D = src_ip, C = "{asset_id}:{파일 경로}"

------------------------------------------------------------------------
① check · GET /api/v1/tickets/open   (호출: D의 n8n, 키 필요)
------------------------------------------------------------------------
용도: "같은 사건의 열린 티켓이 있나? 이 조치는 이미 했나?"

요청
  GET /api/v1/tickets/open?seat=C&group_key=haedam-portal-vm%3A%2Fhome%2Fhaedam%2Fhaedam-portal-frontend%2Fdist%2Findex.html
  X-Response-Key: <대시보드 키>

응답 200 (열린 티켓 있음)
{"success": true, "data": {
  "exists": true,
  "ticket_id": "T-20261024-0001",
  "status": "responding",
  "applied_actions": [
    {"bot": 117, "action": "restore", "target": "/home/haedam/haedam-portal-frontend/dist/index.html", "result": "applied"}
  ]
}}

응답 200 (열린 티켓 없음)  ← 404가 아니라 200 + exists:false
{"success": true, "data": {"exists": false, "ticket_id": null, "status": null, "applied_actions": []}}

메모: applied_actions에는 result가 applied·already_applied인 조치만 담는다.
      n8n은 여기에 같은 (bot, action, target)이 있으면 대응을 다시 부르지 않는다.

------------------------------------------------------------------------
② record · POST /api/v1/tickets/record   (호출: D의 n8n, 키 필요)
------------------------------------------------------------------------
용도: 열린 티켓이 없으면 새로 만들고, 있으면 조치 결과 한 줄을 덧붙인다(한 번에 처리).

요청 헤더
  X-Response-Key: <대시보드 키>
  Idempotency-Key: <n8n 실행 ID>-record      (8~100자. n8n 재시도 때 같은 값)
  Content-Type: application/json

요청 본문
{
  "seat": "C",
  "case_id": "S7",
  "group_key": "haedam-portal-vm:/home/haedam/haedam-portal-frontend/dist/index.html",
  "title": "웹 루트 파일 변조 (index.html)",
  "asset_id": "haedam-portal-vm",
  "src_ip": null,
  "username": null,
  "event_ids": ["<Graylog 메시지 ID>"],
  "action": {
    "bot": 117, "target": "/home/haedam/haedam-portal-frontend/dist/index.html",
    "via": "wazuh", "action": "restore",
    "result": "applied", "applied_verified": true, "effect_verified": null,
    "requested_at": "2026-10-24T14:05:31+09:00", "finished_at": "2026-10-24T14:05:34+09:00",
    "n8n_execution_id": "1234", "detail": "sha256 matches baseline"
  }
}
  - action은 null이어도 된다(탐지만 기록하고 대응 전인 경우).

응답 201 (새 티켓을 만듦)
{"success": true, "data": {"ticket_id": "T-20261024-0001", "created": true, "duplicate": false, "status": "responding"}}

응답 200 (열린 티켓에 덧붙임)
{"success": true, "data": {"ticket_id": "T-20261024-0001", "created": false, "duplicate": false, "status": "verified"}}

응답 200 (같은 조치가 이미 applied → 한 줄은 남기되 중복 표시)
{"success": true, "data": {"ticket_id": "T-20261024-0001", "created": false, "duplicate": true, "status": "verified"}}

같은 Idempotency-Key로 다시 보내면: 처음 응답을 그대로 돌려준다(새 줄 없음).

티켓 상태는 저장소가 정한다(n8n이 status를 보내지 않음):
  action 없음                        → open
  result = applied·already_applied   → responding
  effect_verified = true             → verified
  result = released                  → restored
  closed                             → 사람이 닫을 때만(확장: 상태 변경 경로)

연습 1 · S12 record 요청 본문 (D 자리)

요청 헤더는 ② record와 같다(X-Response-Key, Idempotency-Key: <n8n 실행 ID>-record).

{
  "seat": "D",
  "case_id": "S12",
  "group_key": "203.0.113.11",
  "title": "포털 요청 폭주로 응답 지연",
  "asset_id": "haedam-portal-vm",
  "src_ip": "203.0.113.11",
  "username": null,
  "event_ids": ["<Graylog 메시지 ID>"],
  "action": {
    "bot": 112, "target": "203.0.113.11",
    "via": "portal", "action": "block",
    "result": "applied", "applied_verified": true, "effect_verified": null,
    "requested_at": "2026-10-24T15:00:00+09:00", "finished_at": "2026-10-24T15:00:02+09:00",
    "n8n_execution_id": "5678", "detail": "portal changed:true"
  }
}

메모:
- D는 group_key = src_ip라서 group_key와 src_ip가 같은 값이다.
- effect_verified는 아직 null이다. n8n이 헬스체크로 응답시간 회복을 확인한 뒤 다시 record를 부를 때
  true가 되고, 그때 티켓 상태가 responding → verified로 바뀐다.
- 기준선 안이라 대응하지 않은 경우("요청 수만 초과")는 S12 설계 기본안대로 record를 부르지 않는다
  (티켓 없음, n8n 실행 기록에만 남김). (팀 확인)

- message에는 어떤 필드가 틀렸는지만 쓰고, 받은 값 전체나 키는 넣지 않는다.
