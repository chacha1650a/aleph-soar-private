# 10/21 반소람(A)·김상혁(C) 작업 계획

작성 기준: 2026-10-20 채팅 실측과 사용자 분산 배치 결정. 아래는 내일 실행할 계획이며 팀원 PC 작업 완료 기록이 아니다. 기존 케이스 책임과 김명준·Codex의 React/Flask 코드 구현 책임은 유지한다.

## 현재 출발점

- 사용자 확인: 전원이 같은 수업을 들어 Docker와 기본 도구를 보유한다. 기본 도구 신규 설치를 공통 선행 작업으로 두지 않고 기존 구성의 재사용·프로젝트 연결부터 진행한다. B의 Docker Desktop 화면에서 n8n·wazuh-lab·9_graylog·7_test_class 실행을 확인했으며, 다른 팀원 PC의 실제 버전·기동 상태는 내일 확인한다.
- Windows Docker Desktop과 포털 Linux VM 안의 Docker는 실행 환경이 다르다. 기존 Linux VM·Docker·agent를 먼저 확인하고, 프로젝트에 필요한 구성만 추가한다. 수업용 데이터·볼륨은 보존한다.
- B의 pfSense 팀 VPN(TRANSIT UDP 1195, 터널 10.250.0.0/24)은 B 호스트의 team-b-test 접속·10.250.0.1 Ping 성공을 확인했다. 다른 PC 접속은 아직 시험하지 않았다.
- B의 DB VM은 10.10.20.10에서 MySQL 8.4.11을 실행한다. 앱 계정의 DB 조회와 B 관리 호스트의 TCP 3306 연결을 확인했다. A 포털에서의 DB 연결·데이터 보존은 미시험이다.
- 팀 VPN은 현재 터널 서버 Ping 허용 뒤 팀 대역 기본 차단이다. 내부 서비스용 경로·허용 규칙은 추가 확인이 필요하다.
- 과거 물리 분산안의 10.10.10.10·10.10.30.x를 다른 PC에 입력하는 것만으로 연결되지 않는다. 실제 주소·VPN 종단·왕복 경로를 B와 확인한 뒤 적용한다.

## 해담포털에 맞춰 수정할 설정

기존 도구 보유는 준비의 출발점이다. 담당자는 현재 설정과 아래 요구를 대조하고, 다른 부분은 프로젝트용 설정으로 수정한 뒤 실제 동작을 확인한다. 아래 항목은 수정 계획이며 팀원 PC에 적용한 결과가 아니다. 수업 설정·데이터를 먼저 보존하고 프로젝트용 Compose 설정·볼륨·로그 구분을 정한다.

| 담당 | 프로젝트에 맞춰 수정할 것 | 확인할 결과 |
| --- | --- | --- |
| A · 포털 배포 | 프론트 빌드와 Flask 실행 설정, MySQL 연결·마이그레이션, 비밀값 보관, FRONTEND_DIST와 호스트 마운트, JSONL 로그 보존·GELF 수신 대상 | 실제 포털 화면·API·DB 저장이 동작하고 재시작 후 데이터가 유지됨. 앱 로그의 출발지와 실제 시험 출발지 대조 |
| A·C · 파일 감시 | 수업 예제 경로를 실제 포털 웹 루트로 변경. realtime FIM, 원본·해시 보관 위치, 정상 배포 갱신 절차와 복구·격리 대상을 맞춤 | 시험 파일 변경·복원을 탐지. 정상 배포와 변조를 구분. 복구·격리는 승인 경로와 시험 파일에서 별도 검증 |
| C·D · 로그와 탐지 | 포털 이벤트 계약에 맞춰 Wazuh→Graylog 전달·필드 매핑·탐지 조건 수정. S7은 자산과 웹 루트 기준 파일 키로 FIM·접근 이벤트를 연결 | 실제 원본 이벤트가 수신되고 같은 자산·같은 파일끼리 연결됨. 수업 예제 이벤트만 잡히는 상태와 구분 |
| C·D · 대응·티켓 | 실제 대상 주소·허용 출발지·인증과 티켓 연결을 맞춤. 기존 계약과 A의 미합의 초안 간 차이는 먼저 합의하고, 계약 변경이 필요하면 원본·소비자를 함께 갱신 | 조치 요청·실제 효과·티켓 저장·원복을 각각 확인. 경로·키를 추측해 워크플로에 넣지 않음 |
| B · 망과 관측 | VPN·라우팅·NAT·방화벽과 Suricata 감시 인터페이스를 실제 포털 배치에 맞춤 | 정상 출발지 유지, 시험 출발지 식별, 필요한 연결 허용과 불필요한 연결 차단을 확인 |

공통 계약·망 문서 취합은 B가 맡고, 각 담당은 자기 설정 변경 목록과 검증 결과를 전달한다. 포털 코드 수정은 기존 김명준·Codex 담당을 유지한다. 미완료 항목은 내일 결과에 다음 작업으로 명시하고, 도구 실행만으로 프로젝트 설정 완료 처리하지 않는다.

## A 반소람 — 포털 배포 기반과 S1·S4 준비

VM 준비 경험, 실제 코드 브랜치·커밋, DB/VPN 정보와 미제공 항목은 [A VM 인수인계](2026-10-21-A-VM-인수인계.md)를 먼저 확인한다.

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| A1 | 기존 수업 Ubuntu VM·Docker·Compose·SSH 구성을 확인해 포털 배포에 재사용할 환경을 정한다. 필요한 경우 별도 복제본을 준비하고 없는 구성만 추가 | 사용할 VM 이름, OS·Docker 버전, 실제 메모리·디스크 사용량, SSH 접속 결과 기록 |
| A2 | 김명준에게 배포할 프론트·백 저장소의 브랜치·커밋과 실행 방법 받기. 해담포털용 실행·환경·볼륨·로그 설정으로 맞춰 VM에 배포하며 프론트 빌드 파일의 실제 호스트 경로를 C에게 전달 | 사용 커밋, 실행 명령, 화면 URL, 변경 설정 목록, 호스트 웹 루트와 컨테이너 마운트 대응 기록. 미배포면 준비까지만 표시 |
| A3 | B와 VM의 팀 VPN 연결 방식·주소·DB까지의 왕복 경로 확인 후 포털 → B MySQL 연결 | 포털 실행 환경에서 앱 계정 DB 조회 성공. 그 뒤 로그인 → 민원 작성·조회 → 앱 재시작 후 저장 유지 확인. TCP 성공만으로 DB 인증 완료 처리하지 않음 |
| A4 | Ubuntu VM의 기존 Wazuh agent 유무·등록 대상을 확인하고 C의 프로젝트용 manager에 연결. agent가 없는 경우에만 추가한다. S1·S4 시험용 정상·공격 대상 계정을 구분하고 로컬 앱 이벤트 위치 확인 | C 화면에서 agent Active, 시험 계정 목록과 정상 로그인·실패 로그 확인. 비밀번호는 증적에 남기지 않음 |

포털 코드 수정이 필요하면 김명준에게 재현 절차·로그를 전달한다. A가 새 포털을 별도로 구현하는 작업은 아니다. 배포 코드·DB 경로가 늦어지면 A1과 VM의 시험 디렉터리·agent 준비를 먼저 진행한다.

## C 김상혁 — Wazuh 기동과 S7 파일 감시

기존 Wazuh 구성, A에게 받을 웹 루트·agent 정보, D와 맞출 필드·대응은 [C Wazuh·S7 인수인계](2026-10-21-C-Wazuh-인수인계.md)를 먼저 확인한다.

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| C1 | 기존 수업 Wazuh 스택을 재사용해 구성·버전·데이터 보존 위치 확인. manager·indexer·dashboard의 현재 동작과 자원 사용량 확인 | 제품 화면 로그인, 컨테이너/서비스 상태, RAM 사용량·재시작 여부 기록. 실행 중이면 재설치·재기동 없이 상태부터 확인 |
| C2 | B와 C의 VPN 종단·주소·수집 포트·허용 출발지를 정하고 A agent를 등록 | A agent가 실제로 Active. Windows VPN 성공과 Linux VM agent 연결 성공을 각각 기록 |
| C3 | 수업용 감시 경로를 A가 전달한 실제 포털 호스트 웹 루트로 맞추고 realtime FIM 설정. 원본·해시를 별도 보관한 시험 파일 하나 변경 후 복원 | 변경 설정 목록, 변경·복원 시각, agent/자산 식별자, 파일 경로·해시와 Wazuh 경보 확보. 포털 배포 전이면 시험 디렉터리 검증으로 표시 |
| C4 | D와 Wazuh 경보 → Graylog 전달 방식을 맞추고, A와 웹 접근 이벤트의 파일 키를 대조 | 같은 자산·같은 파일의 FIM/접근 로그를 연결할 수 있는지 확인. D 준비 전이면 전달 설정·필요 정보만 정리 |

Wazuh 제품 dashboard와 프로젝트의 인시던트·티켓 화면은 별개다. 내일 우선 목표는 A agent의 파일 변경 경보 수신이다. 여유가 생기면 기존 API 계약과 A의 대응 호출 초안을 검토해 티켓 연결의 미합의 항목을 목록으로 남긴다. 샘플 화면을 실제 탐지·자동 대응 성공으로 표시하지 않는다.

## B 김명준이 먼저 준비할 연결

1. A·C의 현재 학원 유선 주소를 다시 확인하고, 개인별 VPN 사용자·인증서·프로필을 준비한다. 예정 이름 team-a·team-c는 아직 생성 완료가 아니다.
2. pfSense TRANSIT DHCP 주소를 확인한다. 현재 관찰 주소 192.168.7.174가 바뀌면 접속 프로필의 목적지를 갱신한다.
3. 서비스가 실행되는 Linux VM·Docker와 VPN 사이의 실제 경로를 정한다. Windows에 VPN을 켠 사실만으로 VM의 서비스가 연결됐다고 가정하지 않는다. 주소 안정성·왕복 경로·관측 출발지를 확인한다.
4. A→DB TCP 3306, A agent→C manager의 필요한 수집·등록 포트 등 연결별로 허용 규칙을 기본 차단 위에 추가한다. A↔C 통신은 현재 꺼진 inter-client 통신 설정도 함께 검토하고 실제 통과·차단 대조로 확인한다.
5. 기존 포털 NAT 목적지 10.10.10.10은 A VM의 실제 배치·라우팅과 맞는지 확인한 뒤 시험한다. A가 원격 PC라는 이유만으로 기존 NAT가 작동한다고 처리하지 않는다.

## 함께 진행할 순서와 내일 최소 목표

1. 각자 기존 수업 환경의 버전·기동 상태·실제 PC 자원 확인. 기본 도구 설치를 반복하지 않는다. A1·C1은 연결 시험을 기다리지 않고 진행한다.
2. B와 A·C의 VPN 및 서비스 경로 확인. D의 team-d 접속 시험도 별도로 진행한다.
3. A 포털 → B DB 정상 연결, A agent → C Wazuh 경보를 각각 시험한다.
4. D가 준비되면 로그 전달을 붙인다. 자동 복구·n8n 대응·티켓 생성은 추가 검증 항목으로 남긴다.

내일 최소 목표는 **A의 기존 환경에 포털 배포 준비, C의 기존 Wazuh 정상 동작 확인, A agent의 파일 변경 경보 1건 확인**이다. DB 연결·포털 배포까지 성공하면 별도로 증거를 남긴다. 정상 배포와 변조를 구분하는 기준본·해시 관리, 같은 파일 웹 접근과의 S7 상관, 자동 복구·격리·원복은 후속 필수 작업이다.

기록할 것: 담당, 시각, 사용 커밋/버전, 실제 주소·경로, 실행 명령, 기대/실제 결과, 캡처 위치, 막힌 지점·다음 입력. 비밀번호·자동화 키·인증서 개인 키는 넣지 않는다.
