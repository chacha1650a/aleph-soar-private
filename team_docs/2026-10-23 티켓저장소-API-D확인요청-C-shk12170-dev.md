## 1. 한눈에 보기

D의 result-log 서브워크플로가 부를 티켓 저장소 API를 아래처럼 잡았다. 인증·응답 모양·오류 코드는 포털 대응 API(A 초안 2절)와 같게 맞췄다.

| 경로 | 용도 | 부르는 쪽 | 키 |
| --- | --- | --- | --- |
| `GET /api/v1/tickets/open?seat=&group_key=` | check: 열린 티켓·이미 실행한 조치 조회 | D n8n | `X-Response-Key` |
| `POST /api/v1/tickets/record` | record: 없으면 생성, 있으면 조치 결과 덧붙임(한 번에 처리) | D n8n | `X-Response-Key` + `Idempotency-Key` |
| `GET /api/v1/tickets` | 대시보드 목록 | 대시보드 화면 | 없음(127.0.0.1 전용) |
| `GET /api/v1/tickets/{ticket_id}` | 대시보드 상세 | 대시보드 화면 | 없음(127.0.0.1 전용) |

- 응답(10/23 D 확정): 성공 `{"ok": true, "ticket_id", "created", "duplicate", "status"}`, 실패 `{"ok": false, "error": {"code", "message"}}`. D haedam-10이 이미 쓰는 모양
- 티켓 상태(`open → responding → verified → restored → closed`)는 **저장소가 결과 값으로 정한다.** n8n은 `status`를 보내지 않는다.
- `action` 한 줄은 D 설계의 출력 형식(`bot`·`target`·`via`·`action`·`result`·`applied_verified`·`effect_verified`·`requested_at`·`finished_at`·`n8n_execution_id`·`detail`)을 그대로 쓴다.

## 2. D 설계와 달라지는 점

| 항목 | D 설계 | C 초안 | 이유 |

| 열린 티켓 찾는 기준 | `dedup_key = {case_id}-{src_ip}-{bot}-{action}` | `(seat, group_key)`의 열린 티켓 1건. group_key는 A `username`, B·D `src_ip`, C `{asset_id}:{파일 경로}` | S7은 src_ip가 없고 "자산+파일"로 묶는다(합의본 426행). dedup_key는 조치 단위라 티켓 단위와 층이 다르다 |
