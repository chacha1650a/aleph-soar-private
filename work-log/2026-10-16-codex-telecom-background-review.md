## 2. 최종 판정: 통신 전환

**통신사 운영 환경을 배경으로 한 외주 원격접속 대응·복귀 검증 랩으로 전환할 것을 권고한다.** R06의 접속 통제와 효과 검증을 중심에 두고, 통신 특화는 비인가 외부 통신·로그 수집 공백 관측 및 보고 초안으로 제한하는 조건이다. Open5GS·UERANSIM과 실제 기관 연계는 핵심 완료 조건에서 제외한다.

추천 이유는 사용자가 통신 분야를 제안하려는 현재 방향과 맞고, 공식 사고 조사에서 확인된 계정·장비 인증·접근 경계·로그 확보·보고 문제를 학습 목표로 구체화할 수 있기 때문이다. 인증·망 경계·조치 승인·실제 접근 거부·정상 작업 지속·복귀라는 R06의 뼈대를 재사용하므로, 통신 프로토콜 구현을 추가하지 않아도 일관된 시연을 구성할 수 있다.

이는 **현재 요청에 대한 설계 적합성 판단**이다. 과정 이름에 SK가 들어간다고 SKT가 주제 채택·취업·민관 업무 연계를 보장하지 않는다. 통신이 금융보다 네트워크 역량이나 채용·공방전 성적에서 본질적으로 우월하다는 근거도 없다. 금융안은 직접적인 외주 통제 조항을 문제 배경으로 삼기 좋고, 통신안은 이번 사용자의 관심과 사고 유형을 통한 설명에 맞는다. 스마트팩토리안의 운영 연속성 검증도 재사용할 수 있지만 새 후보 투표를 시작할 필요는 없다.

## 3. 우선순위별 지적과 구체 수정안

### P1 · ‘기반시설 지정 범위 확대’를 완료 사실로 단정하면 안 된다

**위치·주장:** docs/20 §2.3의 “서버·관리망으로 넓어졌고, HSS가 새로 포함됐다”.

**이유:** 직접 읽은 [뉴시스 2025-08-18 보도](https://www.newsis.com/view/NISX20250818_0003293604)는 확대 결정·협의와 전망을 설명한다. 정부의 지정 고시나 완료 범위 원문을 확인한 것은 아니다. 기반시설은 법정 지정 절차를 거치는 것이므로 기사에 나온 기술 구성요소를 모두 지정 완료 자산으로 취급할 수 없다.

**수정안:** “통신 분야의 중요 서버·관리 영역으로 기반시설 보호 범위를 확대한다는 보도가 있었다. 정부 원문과 지정 완료 범위는 추가 확인이 필요하다”로 낮춘다. 정부 원문을 확보하기 전에는 “2025년 8월 HSS 지정 완료”를 발표 근거로 사용하지 않는다. 지정되지 않은 교육용 랩의 일부 점검을 법정 기반시설 평가 완료로 표현하지도 않는다.

### P1 · 신고 시한을 최초 경보 시각·사건 생성 시각과 동일하게 계산하면 안 된다

**위치·주장:** docs/20 §3 민관 협력 층의 “탐지 시각부터 24시간 신고 시한까지”.

**이유:** 현행법의 기준은 침해사고 발생 사실을 알게 된 때이다. 원시 경보, 사실을 알게 된 시각, 사건 생성, 승인·조치 시각은 서로 다를 수 있다. 담당자의 확인·승인 완료를 기다리며 기산을 임의로 늦출 수도 없다. [정보통신망법 제48조의3 제1항, 2026-10-02 시행](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1025111303)

**수정안:** 발생 추정 시각·최초 경보·발생 사실 인지 시각과 근거·초안 작성·모의 승인·실제 제출 여부를 별도로 기록한다. 시한은 인지 시각을 기준으로 산정하고 변경 이력을 남긴다. 완전한 분석 결과가 나올 때까지 초안을 묶어 두지 않으며, 미확인 원인·피해는 미확인으로 표시한다. 파일 생성은 실제 신고 완료가 아니다. 추가로 확인한 사실의 신고도 별도로 다룬다. 현재 시행령의 정확한 조문은 4절 참조.

### P1 · S4의 VPN 인증서 폐기와 KT 장비 인증 실패는 다른 통제다

**위치·주장:** docs/20 S4를 “KT 펨토셀 인증서 관리 실패 유형”에 연결하는 부분.

**이유:** 공식 조사에는 제조사 공통 인증서, KT 인증서 발급, 긴 유효기간, 장비 형상정보 검증 문제가 함께 등장한다. 개인별 VPN 인증서 하나의 CRL 차단 시험으로 이 장비 등록·발급 체계 전체를 재현하거나 방어했다고 할 수 없다. [과기정통부 KT 최종 조사 브리핑, ‘펨토셀 관리체계’ 부분](https://www.korea.kr/briefing/policyBriefingView.do?newsId=156737260)

**수정안:** “실제 장비 인증 사고에서 도출한 인증 수단의 개별 관리·회수·재사용 방지 원칙을 VPN에서 검증한다”로 쓴다. 장비 고유 등록·발급 정책 검증은 별도의 장비 모사 확장으로 둔다. 복사된 유효 인증서는 유효한 동안에는 인증서만으로 복제본을 구분하기 어렵다는 한계도 적는다. CRL은 이미 열린 연결 종료를 대신하지 않는다.

### P1 · T1을 BPFDoor 탐지나 로그 삭제 탐지로 표현할 근거가 부족하다

**위치·주장:** docs/20 T1의 “비정상 외부 통신과 로그 공백을 pfSense·Wazuh로 탐지”, 후보 T1205·T1070.

**이유:** 외부 통신 하나는 신호 패킷을 통한 은닉 기능 활성화의 증거가 아니며, 로그 공백은 삭제 외에도 무활동·전송 실패·수집 지연·보관 기간 종료로 생긴다. 백도어를 재현하지 않는 현재 T1에 두 기술을 확정 매핑하면 시험보다 주장이 커진다.

**수정안:** T1-a ‘정책 밖 외부 목적지 통신 시도’와 T1-b ‘기대 로그의 수집 공백’으로 나눈다. 목적지·포트·방향·규칙과 생성/수신 시각·순번·에이전트 상태를 기록한다. 공백 동안에는 효과를 미확인으로 표시한다. BPFDoor 탐지·로그 삭제 입증·정보유출 확인이라는 이름을 붙이지 않는다. 매핑 판단은 5절에 정리했다.

### P1 · 민관 협력의 산출물과 실제 기관 연계를 구분해야 한다

**위치·주장:** docs/20 §2.3과 §3의 신고 보고서·위협 목록·점검 체크리스트를 “민관 협력 층”으로 묶는 부분.

**이유:** 이 산출물은 협력 업무를 연습할 수 있지만 외부 기관 수신·피드백·조치를 실행하지 않으면 실제 협력 체계 구현은 아니다. SK 관계자가 수행한다는 업무도 미확인이다.

**수정안:** 이름을 “모의 신고·공유·점검 증적 묶음”으로 두고 한 사건에서 재사용하는 파일 출력으로 구현 범위를 제한한다. 실제 기관 제출·메시지 발송·망 연결은 포함하지 않는다. 팀 내부 모의 수신 역할을 둘 경우에도 교육용 역할임을 표시한다. 평가에 필요한지는 과정 기준 확인 전 판단 보류한다.

### P2 · 사고 규모·외주 인력 수가 취업 기회의 크기를 증명하지 않는다

**위치·주장:** docs/20 §2.2의 피해 규모, §2.4의 공시 인력 수에서 “진입이 넓다”로 이어지는 부분.

**수정안:** 사고 수치는 출처·발표일·단위를 붙인 문제 배경으로만 사용한다. IMSI 건수를 고유 피해자 수로 바꾸지 않는다. 공시의 인력 수·환산 방식 원문을 확인하기 전에는 정밀 수치를 핵심 근거에서 빼고, 외주 비중을 신규 채용 수·신입 진입 가능성으로 환산하지 않는다. 목표 직무와 채용 공고를 따로 조사해야 한다. T05 센터 사례도 정부 원문 확인 전에는 언론 소개 수준으로 남긴다.

### P2 · ‘가입자 서버·과금’을 기능명만 바꾼 통신 시스템으로 보이게 하지 않아야 한다

**위치·주장:** docs/20 §3의 가입자 정보 서버·망 관리 서버, 가상 개통·과금 작업.

**수정안:** “운영 대상 A: 합성 가입자 레코드 조회 API”, “운영 대상 B: 합성 작업 처리·결과 저장 API”처럼 실제 동작을 적는다. 개통 요청·상태 조회 작업 중 하나만 선택해 독립 작업 ID로 측정하고, 과금·정산·결제 기능은 추가하지 않는다. 실제 HSS·UDM·OSS/BSS 기능이나 통화·서비스 품질을 구현했다고 쓰지 않는다. 키·실가입자 식별자·실제 과금 정보는 사용하지 않는다.

## 5. S1·S3·S4·T1과 모의 신고·공유·점검의 수정안

### 핵심 시나리오와 R06의 공통 수정

| 항목 | 수정안·인수 기준 |
| --- | --- |
| S1 외주 자격 증명 악용 | 인증서+비밀번호 등 실제 선택한 방식에 맞춰 탈취 가정을 선언한다. VPN 사용자·인증서·접속 시각·터널 IP를 방화벽·호스트 로그와 연결하고, 담당 외 탐색 → 사건 → 승인 → 접속 회수 → 효과 재시험으로 구성한다. IP 하나만으로 사용자를 확정하지 않는다. |
| S3 조치와 실제 효과 불일치 | 조치 API 응답만 성공이거나 이전 연결이 남는 상황을 별도 주입한다. 인증 수단·활성 VPN·관련 state·업무 세션을 각각 확인한다. 실패와 관측 불가를 구분하고 성공 종결·자동 복귀를 막는다. |
| S4 복귀 후 이전 수단 | 이전 인증서+현재 비밀번호, 현재 인증서+이전 비밀번호, 이전 두 수단, 새 두 수단을 대조한다. CRL 적용 서버·인증서 일련번호와 시험 시각을 남긴다. 이미 열린 연결과 이전 앱 세션도 확인한다. A 폐기 때 B 인증서는 유효해야 한다. |
| 정상 업무 | 정상 B의 기존·신규 접근, 독립 생성기의 발행 작업 ID와 처리 결과를 대조한다. 예정/발행/수락/완료/실패/미완료/중복·지연·내용 일치를 기준선·대응 중·복귀 후에 비교한다. 성공 순번만 연속이라는 결과로 연속성을 입증하지 않는다. |
| 조치 운영 | 승인 대상·정책·유효기간·적용 전 상태를 명시하고 중복 요청을 같은 조치로 처리한다. 전체 state 삭제·VPN 서버 재시작은 정상적인 계정 단위 대응으로 쓰지 않는다. 복귀에는 자격 증명 회수뿐 아니라 원인 확인·호스트 점검·권한 재확인 등 이번 범위의 조건을 명시한다. |

인증 방식과 개인별 인증서·CRL 구성의 문서 근거는 [Netgate OpenVPN 공식 예시의 Server Mode·Certificate Revocation 부분](https://docs.netgate.com/pfsense/en/latest/recipes/openvpn-ra.html)이다. 문서 기능 확인과 실제 환경에서의 폐기·종료 성공은 별도다. R06에서 요구한 망 경로·허용표·Docker 우회 경로 검증, 주체가 불명확하면 자동 조치 중단, 조치 상태와 효과 상태 분리는 그대로 적용한다.

### T1은 두 가지 작은 관측 시험으로 나눈다

**T1-a: 정책 밖 외부 통신 시도.** 운영 대상에서 랩의 통제된 시험 수신지로 합성 요청을 발생시키는 시험을 설계한다. pfSense에서 출발지·목적지·포트·허용/거부·규칙 ID를 확인하고, 필요하면 호스트의 실행 근거와 연결한다. 방화벽 거부 로그는 통신 시도의 증거이고 유출 성공이나 백도어 감염의 증거가 아니다. 기본 정책이 이미 거부한다면 탐지 후 새로 차단했다고 보고하지 않는다. 정상 DNS·시간 동기화·로그 전송 경로는 허용표에 반영한다.

**T1-b: 기대 로그의 수집 공백.** 각 시험 호스트에서 일정한 순번의 표식 이벤트가 생성되고 중앙 수집까지 도달하는지를 관측한다. 생성 시각·수신 시각·마지막 순번·에이전트 상태·수집기 상태를 구분하고, 소스 중단·전송 중단·수신 지연을 따로 주입한다. Wazuh의 연결 상태만으로 모든 업무 로그의 수집을 보장하지 않는다. 공백 중 실제 접근 결과를 못 봤다면 “차단 성공”이 아니라 “미확인”이다. [Wazuh 공식 에이전트 연결 상태 문서](https://documentation.wazuh.com/current/user-manual/agent/agent-management/agent-connection.html)

보관 기간 만료에 따른 과거 로그 부재와 실시간 수집 공백도 다른 문제다. 짧은 heartbeat 시험으로 장기 보존·복구 가능성을 검증했다고 하지 않는다. 2주 가정이라면 S1·S3·S4 연결 이후 T1의 한 가지 실패 주입부터 선택하고, BPFDoor·루트킷·악성코드 샘플·실제 유출은 추가하지 않는다.

| 모의 신고 초안 | 사건 ID, 발생 추정·인지·경보 시각, 인지 근거, 확인된/미확인 피해, 조치·증적 참조, 담당 역할, 초안 버전, 신고 기한을 담는다. 항상 “교육용 초안·미제출”을 표시하고 실제 접수번호를 만들지 않는다. 추가 사실·수정 이력도 분리한다. |
| 위협 관측 목록 | 랩 주소·관측 구간·수법 후보·근거 ID·판단 확신도·공유 범위·유효기간을 JSON/CSV로 내보낸다. 사설 IP 단독을 전 세계 차단용 IoC로 쓰지 않고 관측과 악성 판단을 구분한다. |
| 선택 통제 점검표 | 개인별 인증 수단, 승인된 경로, 담당 외 거부, 자격 증명 폐기, 기존 연결 회수, 로그 수집·보존 설정, 정상 업무 지속 등 선택 항목에 절차·기대/실제 결과·증적·미점검을 적는다. 이름은 “기반시설 보호 관점의 교육용 선택 통제 점검”으로 둔다. |

신고 양식은 현행 법령의 필수 정보 범주를 반영하면 된다. 이번 확인만으로 특정 기관의 현재 제출 화면·서식과 일치하는 공식 신고서라고 부르지는 않는다. 불명확한 정보는 꾸며 채우지 않는다.

STIX는 초기 필수 조건으로 권하지 않는다. 단순 목록은 “자체 JSON/CSV 관측 목록”으로 표시하고 STIX 호환이라고 쓰지 않는다. 확장한다면 [OASIS STIX 2.1 §4.14 Observed Data와 관련 객체](https://docs.oasis-open.org/cti/stix/v2.1/os/stix-v2.1-os.html)를 참고해 관측 데이터·위협 지표의 의미를 나누고 형식 검증과 수신 측 해석을 확인해야 한다. STIX 파일 생성과 실제 기관의 정보 교환 연동도 다르다. 실제 민관 수신자의 요구가 확인되면 그 규격을 우선한다.

## 6. Open5GS·UERANSIM 확장과 사고 사례 표현 기준

### 선택 확장 판정: 핵심 흐름 완료 후, 기간·자원 확인 시 검토

Open5GS와 UERANSIM의 조합은 합성 가입자의 등록·세션 및 통신 경로를 보여주는 선택 확장으로 타당하다. 다만 외주 유지보수 인증과 UE/기지국·가입자 인증은 다른 평면의 문제다. 이 조합을 켰다는 사실만으로 S4의 VPN 인증서 시험이 펨토셀 사고 재현이 되지는 않는다.

[Open5GS 공식 Quickstart §4~5](https://open5gs.org/open5gs/docs/guide/01-quickstart/)는 가입자 DB·네트워크 기능 설정, 주소·라우팅/NAT, SCTP 기반 연결 등을 설명한다. [UERANSIM 공식 저장소](https://github.com/aligungr/UERANSIM)는 5G SA UE·gNodeB 시뮬레이터이며 무선 물리계층 전체를 제공하지 않고 UDP로 일부를 모사한다고 명시한다. 따라서 실제 무선망·상용 통신망 재현이라고 부르지 않는다.

필요한 자원·환경은 다음을 먼저 확인해야 한다.

- Linux 실행 환경과 SCTP 지원, 코어·시뮬레이터·관제 간 실제 연결 경로. [UERANSIM 공식 설치 문서](https://github.com/aligungr/UERANSIM/wiki/Installation)는 Windows 지원 및 WSL·NAT 관련 제약을 안내하므로, 현재 Windows PC에서 Docker만 실행하면 된다고 가정하지 않는다. Linux VM/호스트를 우선 후보로 검증한다.
- 코어 기능·가입자 DB와 gNodeB/UE 프로세스, 사용자 평면용 TUN·라우팅/NAT 및 컨테이너 사용 시 필요한 장치·권한. 단순 웹 컨테이너와 요구가 다르다.
- 선택 버전에 맞는 제어·사용자 평면 포트와 주소 설정. 공식 예시의 NGAP/SCTP 38412, GTP-U 2152 등을 출발점으로 삼되 모두 외부 공개할 포트로 취급하지 않는다. UPF 경로가 pfSense를 우회하는지도 별도 확인한다.
- Wazuh·Graylog의 저장·인덱싱과 다른 VM이 사용할 CPU·메모리·디스크·로그 보관량. 이번 자료에서 전체 구성의 검증된 최소 RAM/CPU 수치를 확보하지 못했으므로 숫자를 보장하지 않는다. 시험 UE 1개·최소 작업 부하로 관측한 뒤 자원표를 확정한다.

Docker 사용 가능성은 패키지·이미지 출처·버전 조합·호스트 커널·망 구성 확인 전의 후보이다. 이번에 이미지 설치·호환성 시험은 하지 않았다. 공식 예시의 방화벽 완화·인터넷 연결 설정을 공방전 환경에 그대로 복사하지 말고 프로젝트 허용표에 맞춰야 한다.

확장 착수 조건은 핵심 S1·S3·S4의 반복 재현, 정상 업무 기준선, 관측 공백의 미확인 처리, 재시작 후 복구 절차가 먼저 갖춰지는 것이다. 확장의 첫 완료 조건은 UE 1개의 등록·세션·통신 확인과 관련 로그 연결 정도로 제한한다. 프로토콜 취약점·펨토셀·RF 공격까지 넣을지는 기간과 공방전 규칙 확정 후 별도 판단한다.

### SKT·KT 사고를 다루는 표현 기준

1. **조사 기관·발표일·확인 범위를 함께 적는다.** “과기정통부의 2025년 최종 조사 발표에 따르면…”처럼 쓴다. 당시 발표의 과실·미신고 지적을 숨길 필요는 없지만, 현재까지의 법적 결론이나 개인 책임으로 확대하지 않는다.
2. **확인 사실·팀 해석·랩에서 시험한 항목을 나눈다.** KT의 장비 등록·인증 문제에서 인증 수단 회수 원칙을 가져왔다는 설명은 가능하다. VPN CRL 시험으로 그 사고 전체를 재현·예방했다고 쓰는 것은 부정확하다.
3. **로그가 없다는 사실로 삭제·유출·무피해를 단정하지 않는다.** “해당 구간은 확인 불가”라는 조사 한계를 그대로 유지한다. 현재 랩의 관측 공백도 동일하게 미확인으로 처리한다.
4. **확인되지 않은 최초 침투 경로와 사고 간 인과를 만들지 않는다.** 외주 계정 탈취는 우리 위협 가정이지 두 사고 모두의 확정 원인이 아니다. SKT의 계정 관리 문제와 별도의 공급망 발견, KT의 펨토셀과 서버 악성코드 문제를 구별한다.
5. **교육 과정·기업의 승인이나 연계를 암시하지 않는다.** SK 과정명은 주제 관심의 맥락일 뿐이다. 실제 회사망을 닮았다는 도식·로고·공식 공동 연구 표현은 근거 없이 쓰지 않는다. 과정의 사례 활용 허용 범위는 확인 전 판단 보류로 남긴다.

권하는 발표 문장은 “공개 조사에서 드러난 운영 통제 문제를 학습 목표로 정해, 자체 구성한 격리 랩에서 선택 통제의 효과와 한계를 확인한다”이다. 실제 시험 전 문서에서는 마지막 부분을 “확인할 계획이다”로 쓴다.

## 7. 채택 시 재작업·추천 주제·최소 시연·남은 결정

### 재작업 순서

1. **범위·기준 확정:** 팀이 통신 배경 채택 여부, 실제 기간·목표 직무·평가 기준을 결정한다. 핵심은 외주 접속 회수·효과·복귀이고, 통신망 구현·실제 기관 연계는 선택 확장임을 기록한다.
2. **자산·경로·정상 업무 정의:** 외부 시험 구역 → VPN 접속 구역 → 운영 대상 A/B, 관리·관제 구역의 허용표를 정한다. 포털·합성 레코드·작업 처리의 실제 기능과 미구현 통신 기능을 명시하고 Docker·호스트 우회를 점검할 계획을 세운다.
3. **R06 지적 반영 확인:** 인증 방식, VPN 주체 연결, 네 가지 조치 대상, 기존 연결 잔존 실패, 작업 ID 대조, 승인·재시도 안전성과 복귀 조건을 계약·예시·소비자에 대조한다. 배경 이름만 바꾸고 계약 영향이 없다고 가정하지 않는다.
4. **통신안의 새 보완:** T1을 외부 통신 정책 위반·수집 공백으로 나누고 근거 없는 ATT&CK ID를 제거한다. 신고의 법적 기산점·현재 조문·추가 사실 갱신·미제출 표시를 정의한다. 지정 확대의 완료 단정을 정정하고 선택 점검의 범위를 밝힌다.
5. **문서·계획 연결:** docs/07·14·18·19·20, 백로그·역할·작업 계획, 필요 시 API 계약·스키마·예시를 새 결정과 맞춘다. R06은 과거 검토 기록으로 보존한다. 금융·제조업 시장 자료는 해당 배경의 조사로 남기고 통신 수요 자료로 바꿔 인용하지 않는다. 이번 회신에서는 이 작업들을 실행하지 않았다.
6. **핵심부터 구현·시험:** 정상 A/B 접속과 로그 전달 기준선 → S1·S3·S4 → T1의 작은 관측 시험 → 같은 사건에서 모의 신고·공유 출력 순으로 진행한다. 체크리스트는 이 시험 증적을 재사용한다. 새 관제 플랫폼이나 별도 공유 서버를 먼저 만들지 않는다.
7. **선택 확장 판단:** 기간·배치·공방전 진입점이 정해지고 핵심 흐름이 반복 재현된 뒤 Open5GS·UERANSIM 및 공유 표준 연계를 선택한다. 규칙상 VPN 자격 증명이 제공되지 않으면 S1은 자체 시험이며 상대 팀의 실제 공격 진입점은 별도로 정한다.

**추천하는 한 문장 주제:** “통신사 운영 환경을 모사한 랩에서 외주 유지보수 계정의 이상 접근을 탐지하고, 승인된 접속 회수의 실제 효과·정상 합성 업무 유지·안전한 업무 복귀를 검증한다.”

짧은 이름은 **“통신 운영망 외주 원격접속 대응·복귀 검증 랩”**을 제안한다. 여기서 운영망은 실제 통신 프로토콜망 전체가 아니라 운영용 서버·유지보수 접속 경계를 단순화한 환경이라고 첫 화면과 발표에 표시한다.

**최소 시연 흐름:** 정상 B와 합성 작업을 계속 실행 → A의 담당 외 탐색을 VPN 주체와 연결 → 사건과 승인 → A의 인증 수단·기존 연결 회수 → 기존/신규 접근 거부와 B·합성 작업 유지 확인 → 한 차례 조치 실패 또는 관측 공백을 미확인/효과 불일치로 표시 → 복귀 승인 후 이전 수단 거부·새 수단의 담당 대상 접근 확인 → 같은 사건의 모의 신고 초안과 관측 목록을 저장한다. T1-a/b 전체와 5G 코어는 최소 시연 완료 후 확장할 수 있다.

**남은 결정:** 실제 기간(2주 여부), 팀 채택, 목표 직무, 제품 버전·CPU/RAM/디스크·망 배치, 승인·적용의 수동/자동 경계, 합성 업무 허용 실패·지연 기준, 공방전 시작점·제공 자격 증명·허용 기법·채점, SK 측 민관 업무 내용과 사고 사례 활용 허용 범위다. 이를 다시 확인된 조건처럼 쓰거나 빈칸을 임의로 확정하지 않는다.

**인수인계:** 이번 변경은 이 회신 파일 신규 작성뿐이며 계약·동작 변경, 커밋·푸시·PR·메시지 발송은 없다. 실제 확인은 저장소 문서 열람·공식 웹 자료 대조와 회신 형식 점검이다. 제품 연동·공격·복구는 미실행이다. 다음 담당의 첫 작업은 회신의 전환 권고, P1 수정 조건, 공식 확인/언론 확인/미확인을 구분하여 docs/20에 Claude 후속 판단을 적는 것이다.
