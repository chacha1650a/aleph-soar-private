## 2. 판정: 수정 권고

**R08의 방향과 대부분의 경계 정의는 수용합니다.** 4계층을 엣지–네트워크–앱–데이터로 세고 Wazuh·Graylog·n8n을 계층으로 세지 않은 점, 계층별 "미도달·미조회"를 정상으로 구분한 점, DB 증거 네 종류를 나눈 점, 세션 거부와 TCP/VPN 종료를 다른 시험으로 둔 점은 그대로 유지해야 합니다.

수정 권고인 이유는 네 가지입니다.

1. **WAF 차단의 증거 단위가 부족합니다.** CRS의 실제 차단은 개별 탐지 규칙이 아니라 이상 점수 평가 규칙(949110)으로 결정되고, 기여 규칙 기록이 누락된 보고가 있습니다. "앱 미도달"을 시간대만으로 대조하면 약하고, WAF 거래 ID를 앱까지 전달하는 설정은 공식 이미지 문서에 없습니다.
2. **DB-02의 "금지 조회 거부 + DB 감사"는 아직 문서로 뒷받침되지 않습니다.** 공식 로그 형식 문서는 권한 거부 질의의 기록 여부를 말하지 않습니다. 공식 Docker 이미지의 플러그인 포함 여부도 확인되지 않았습니다.
3. **망 분리의 실제 배치가 가장 큰 위험인데 결정 시점과 대안이 열려 있습니다.** Docker bridge 위주 배치에서는 구역 간 통신이 pfSense를 지나지 않을 가능성이 높습니다.
4. **로그 운반이 UDP 중심입니다.** pfSense 기본 syslog와 Wazuh syslog 출력은 UDP라 유실이 생길 수 있는데, 수집 공백 시험(DB-04)은 DB만 다룹니다.

모두 G1 위험 확인 단계에서 작은 시험으로 판정할 수 있는 항목이라, 판단 보류가 아니라 수정 권고로 봅니다.

## 3. 우선순위별 지적

### P1 · TEL-E01의 "규칙 ID·앱 미도달" 증거 단위를 정해야 한다

**위치:** 4절 엣지 행, 6절 TEL-E01, 7절 증적 묶음.

**문제:** CRS 기본 설정은 이상 점수 방식이라 차단 결정은 949110(Inbound Anomaly Score Exceeded)으로 기록되고, 실제 탐지 규칙(예: SQLi 계열)은 그 앞에 기여 규칙으로 남습니다. 기여 규칙이 감사 로그에서 빠진 사례가 보고돼 있습니다(검색 요약). 또 차단 403이 기록됐는데 요청이 백엔드로 전달된 보고([#3509](https://github.com/owasp-modsecurity/ModSecurity/issues/3509))가 있었으므로, "차단 기록 = 앱 미도달"로 가정할 수 없습니다. 공식 이미지는 감사 로그를 기본으로 stdout에 JSON으로 내보내며, WAF 거래 ID를 앱으로 넘기는 설정은 문서화되어 있지 않습니다([CRS Docker README](https://github.com/coreruleset/modsecurity-crs-docker)).

**수정안:**
- 증거 필드를 "차단 결정 규칙(949110 등)·총점·기여 규칙 ID 목록·엔진 모드(On/DetectionOnly)·클라이언트가 실제로 받은 상태 코드"로 나눕니다. 기여 규칙이 비면 "기여 규칙 미확인"으로 표시합니다.
- WAF가 생성한 거래 ID를 요청 헤더로 앱에 전달하고, 클라이언트가 보낸 같은 이름의 헤더는 WAF에서 덮어씁니다. 앱은 이 값을 `request_id`로 기록합니다. Apache 계열이면 `UNIQUE_ID`를 헤더로 싣는 방식이 후보입니다(일반 설계 판단, 이미지에서 시험 필요).
- "앱 미도달"은 차단된 거래 ID가 앱 로그에 없음으로 판정하고, 같은 시각의 정상 거래 ID는 앱 로그에 있음을 함께 보여 줍니다. ID 전달이 불가능하면 시간창 대조로 낮추고 "제한된 추정"으로 표시합니다.
- 감사 로그 출력 위치(stdout 또는 파일)와 수집 경로를 G1에서 고정합니다.

### P1 · DB-02의 권한 거부 기록 여부를 G1의 통과 조건으로 올려야 한다

**위치:** 4절 데이터 행, 5절 DB-02, 6절 TEL-D01.

**문제:** [MariaDB 로그 형식](https://mariadb.com/docs/server/reference/plugins/mariadb-audit-plugin/mariadb-audit-plugin-log-format) 문서는 QUERY에 retcode가 있다는 것만 보여 주고, 권한 부족으로 실패한 SELECT가 QUERY 이벤트로 남는지, 남는다면 어떤 retcode인지 말하지 않습니다. TABLE 이벤트(READ 등)는 템플릿에 retcode가 없으므로 성공·실패 판단에 쓸 수 없습니다. 공식 Docker 이미지에 `server_audit` 플러그인 파일이 들어 있는지도 확인되지 않았습니다(검색 요약).

**수정안:**
- G1 체크리스트에 "선택 버전·이미지에서 플러그인 로드 확인, 허용 SELECT·권한 거부 SELECT·존재하지 않는 테이블 질의를 각각 실행해 QUERY/TABLE 기록과 retcode를 실제 줄로 확인"을 넣습니다.
- 권한 거부가 기록되지 않으면 DB-02의 거부 증거는 "클라이언트 오류 + DB 권한 설정 확인"으로 바꾸고, "DB 감사로 거부를 확인"이라는 표현은 쓰지 않습니다.
- 플러그인 설정이 재시작 후에도 유지되는지 확인합니다(옵션 파일 방식 권장, 검색 요약 기준).
- 이벤트 필터는 처음에 CONNECT·QUERY·TABLE로 두고, 줄이는 것은 기준선 측정 뒤에 정합니다.

### P1 · 망 분리 배치를 G1에서 둘 중 하나로 고정해야 한다

**위치:** 3절 "구역 간 통신은 pfSense를 경유하도록 실제 라우팅을 검증", 8절 G1.

**문제:** 문서는 우회 위험을 정확히 적었지만, 구역을 무엇으로 나눌지(VM, Docker 네트워크, 다른 PC)를 정하지 않았습니다. 한 호스트의 Docker bridge 여러 개는 기본적으로 호스트 내부에서 라우팅되어 pfSense를 지나지 않습니다(일반 설계 판단). 이 결정이 늦어지면 네트워크 계층과 TEL-P01·DB-03 전체가 막힙니다.

**수정안:**
- 후보 A: 구역마다 VM을 두고 pfSense VM의 여러 NIC를 하이퍼바이저 내부 네트워크에 연결합니다. 각 VM 안에서 Docker를 씁니다. 가장 확실하지만 메모리가 많이 듭니다.
- 후보 B: 최소한 "WAF·앱"과 "DB"를 서로 다른 VM에 두고 그 사이만 pfSense를 경유시킵니다. 관제 구역은 별도 VM에 둡니다.
- G1 통과 조건은 "앱 VM에서 DB로 가는 패킷이 pfSense 로그에 나타나고, pfSense 규칙을 끄면 연결이 끊기는 것"입니다. 호스트에서 DB 포트로 직접 붙어 보는 부정 시험도 포함합니다.
- 어느 쪽도 불가능하면 네트워크 계층은 "미완료"로 표시하고 Docker 네트워크 분리를 대신 증거로 쓰지 않습니다. 문서의 기존 원칙과 같습니다.

### P1 · 앱 요청과 DB 감사 줄의 연결 방법을 구체화해야 한다

**위치:** 5절 "앱 경로의 연결은 서버가 생성한 request_id와 DB 호출 전후의 connectionid·시간·대상·결과 매핑".

**문제:** connectionid와 시간만으로는 연결 풀의 동시 요청에서 질의를 유일하게 대응시키기 어렵다는 점을 문서가 인정하지만, 대응을 강하게 만드는 방법은 제시하지 않았습니다.

**수정안 (일반 설계 판단, 시험 필요):**
- 연결을 풀에서 빌릴 때마다, 업무 질의 전에 서버가 만든 표식 질의를 같은 연결에서 실행합니다. 예: `SET @aleph_request_id = '<서버 생성 request_id>'`. 감사 플러그인이 QUERY를 기록하면 이 줄이 같은 connectionid에 남습니다. 풀에서 빌린 연결은 반납 전까지 한 요청이 독점하므로, 다음 표식 전까지의 질의를 그 요청에 귀속할 수 있습니다.
- 표식 값은 서버가 생성한 ID만 쓰고, 사용자 입력·비밀값을 넣지 않습니다. 문서의 "SQL 주석·외부 입력 ID만으로 사용자를 확정하지 않는다" 원칙과 충돌하지 않습니다.
- 그래도 DB 사용자는 `portal_app`입니다. 웹 사용자 귀속은 "앱 로그의 request_id → 웹 사용자"와 "DB 감사의 표식 → request_id"를 이어서 얻는 2단계 추론임을 증적에 적습니다.
- 표식 질의는 요청마다 왕복 1회가 늘어납니다. 시험 범위에서만 켤지 정합니다.

### P2 · 로그 운반의 유실을 모든 계층에서 관측해야 한다

**위치:** 4절 로그 운반, 5절 DB-04.

**문제:** pfSense 기본 원격 syslog는 UDP만 지원하고 평문입니다([pfSense 원격 로그](https://docs.netgate.com/pfsense/en/latest/monitoring/logs/remote.html)). Wazuh syslog 출력도 기본 UDP입니다(검색 요약). 공방전 중에는 부하로 유실이 생기거나, 같은 구간에 있는 상대가 로그를 엿볼 수 있습니다.

**수정안:**
- DB-04의 표식 이벤트 시험을 WAF·pfSense·앱·DB·Wazuh 모두로 넓혀 "계층별 수집 기준선"으로 만듭니다.
- 증거로 쓸 원본은 소스 쪽 파일에도 남기고, 중앙 수신 누락이 보이면 "미확인"으로 표시합니다.
- 로그 전송은 관리망 안에서만 하고, 공방전 대상 구간을 지나지 않게 허용표에 적습니다. TCP가 필요하면 syslog-ng 패키지나 파일 전달기를 검토합니다.

### P2 · 진행 중·대기 중 작업의 처리 정책을 정해야 한다

**위치:** 2절 "이미 처리 중인 요청·작업의 종료 경계와 잔여 영향도 시험에서 따로 기록", 6절 계정 회수 효과의 경계.

**문제:** 기록하겠다는 원칙은 있지만 정책이 없어서 TEL-A02의 기대 결과를 미리 적을 수 없습니다.

**수정안 (P01에서 결정할 기본안):**
- 조치 적용 기준 시각은 앱 DB에 계정 잠금·세션 버전 증가가 커밋된 시각으로 정의합니다.
- A의 승인 대기·실행 대기 작업은 조치 시 "보안 조치로 취소"로 바꿉니다.
- 실행 중인 작업은 끝까지 수행하되, 결과 저장 직전에 계정·승인 상태를 다시 확인하고 조치된 계정이면 결과를 보류합니다.
- 조치 전에 시작해 조치 후에 끝난 HTTP 요청은 "잔여 요청"으로 따로 기록합니다.
- B의 작업은 어느 경우에도 영향을 받지 않아야 합니다.

### P2 · 계약 충돌을 P01 변경 목록으로 확정해야 한다

**위치:** 9절 계약 표.

**문제:** 문서가 지적한 충돌은 맞습니다. 구체 필드가 없어 P01에서 다시 설계해야 합니다. 상세 제안은 6절에 있습니다. 이번 리뷰에서 계약은 바꾸지 않았습니다.

### P2 · 4인 분담에서 망·엣지·수집 담당에 일이 몰린다

**위치:** 9절 작업 묶음.

**문제:** 한 사람이 pfSense, WAF, 라우팅, 모든 소스의 전달 경로까지 맡습니다. G1 위험 대부분이 이 사람에게 몰립니다.

**수정안:** 소스별 전달은 소스 담당이 소유합니다. DB 감사 설정과 DB 로그 전달은 업무 앱·DB 담당, Wazuh 에이전트와 경보 전달은 탐지·대응 담당이 맡습니다. 망·엣지 담당은 pfSense·WAF·배치와 Graylog 입력만 소유합니다.

### P3 · 정상 B 트래픽도 WAF를 거쳐야 한다

**위치:** 2절 정상 업무, 6절 TEL-N01.

**문제:** CRS는 정상 요청을 오탐으로 막을 수 있습니다. B 생성기가 WAF를 우회해 앱에 직접 붙으면, 가용성 채점이 있을 때 정상 업무 영향을 보지 못합니다.

**수정안:** B의 독립 생성기는 WAF를 거쳐 접속하게 하고, 기준선에서 B 요청의 WAF 오탐 건수를 기록합니다.

### P3 · 보안 조치 승인자와 복귀 승인자를 기록으로 나누기

**위치:** 2절 보안 담당자 역할.

**문제:** 한 역할이 대응 승인과 복귀 승인을 모두 맡습니다. 4인 랩에서는 불가피하지만, 기록에서 두 승인이 구분되지 않으면 승인 절차를 보여 주기 어렵습니다.

**수정안:** 같은 사람이 맡더라도 다른 계정으로 승인하고, 사건 이력에 조치 승인과 복귀 승인을 별도 항목으로 남깁니다.

### 추가 의존성과 비용

WAF 컨테이너, MariaDB, 로그 전달기가 늘고, 원래 도구 중에서도 Graylog(검색 엔진·MongoDB 포함)와 Wazuh(인덱서 포함)가 각각 검색 엔진을 씁니다. 장비 사양을 모르는 상태에서 가장 큰 비용은 메모리입니다(일반 설계 판단). Wazuh는 관리자만 두고 경보를 Graylog로 보내는 구성을 축소 후보로 G1에서 함께 시험할 것을 권합니다. 이 구성의 지원 범위는 Wazuh 공식 문서로 다시 확인해야 합니다.

### 축소 순서 (문서 8절 보완)

1. 5G 코어·공유 표준·별도 보고 시스템·VPN 신규 기능 (문서와 같음)
2. 추가 탐지 규칙과 복잡한 화면 (문서와 같음)
3. Wazuh 대시보드·인덱서 → 관리자만 남기기
4. DB-02 직접 시험의 거부 기록 → 플러그인이 기록하지 않으면 클라이언트 결과와 권한 설정 증거로 낮추기
5. 망 분리 → 배치 B(앱–DB 구간만 경유)

WAF·DB 감사·pfSense 경유가 강사 필수로 확인되면 3~5는 축소 대상에서 빼고 범위를 다시 나눕니다. 실패한 계층을 샘플이나 앱 로그로 대신하지 않는다는 문서의 원칙은 그대로 유지합니다.

**가장 먼저 확인할 위험:** (1) 구역 배치에서 pfSense 경유가 성립하는지, (2) MariaDB 감사가 선택 이미지에서 로드되고 권한 거부를 기록하는지, (3) WAF 차단 요청이 정말 앱에 도달하지 않는지를 거래 ID로 판정할 수 있는지. 세 가지 모두 G1에서 작은 입력으로 판정할 수 있습니다.

### 수정한 최소 시연

1. **기준선:** A·B 정상 업무가 WAF→앱→DB로 처리되고 B 생성기가 계속 돈다. 모든 소스의 표식 이벤트가 Graylog에 도착한다.
2. **엣지:** 통제 요청 1건이 WAF에서 403을 받는다. 감사 로그에 949110과 기여 규칙이 있고, 그 거래 ID는 앱 로그에 없다. 같은 시각 정상 거래 ID는 앱 로그에 있다.
3. **네트워크:** 시험 클라이언트가 앱 원본 포트와 DB 포트에 직접 붙지 못하고, pfSense 거부 로그가 남는다.
4. **앱 공격:** A 세션이 B 작업 ID를 반복 요청해 모두 거부되고 자료가 반환되지 않는다. 규칙이 사건을 만든다.
5. **대응:** 승인 → n8n → 내부 회수 API. 커밋 시각 이후 A의 이전 쿠키·신규 로그인·새 작업 요청이 거부되고, A의 대기 작업은 취소된다. B 작업은 계속된다. DB 감사에서 적용 시각 이후 A 요청에 귀속된 업무 질의가 없다(표식 연결 기준).
6. **실패 대조:** 세션 회수를 빠뜨린 실행에서 "효과 불일치"가 표시되고 사건 종결과 복귀가 막힌다.
7. **복귀:** 별도 승인 후 새 자격 증명으로 A만 A 자료에 접근하고, 이전 수단은 거부된다.
8. **데이터 직접 감사(가산점 대비):** 제한 계정의 허용 뷰 조회와 금지 조회 결과, 그리고 G1에서 확인된 범위의 감사 기록을 증적 묶음에 넣는다.

### 완료 조건

- 각 시험에 기대값을 먼저 적고 실제값·판정(성공/실패/효과 불일치/미확인)·원본 키를 남긴다.
- 4계층 각각에 실제 제어 증거가 있거나, 없으면 "미완료"로 표시돼 있다. 샘플·앱 로그로 대신한 계층이 없다.
- 연결 근거가 정확·제한된 추정·연결 불가로 표시돼 있다.
- 다른 팀원이 같은 절차로 한 번 이상 재현했다.
