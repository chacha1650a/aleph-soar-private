# R09 독립 검토 · 팀원 제안과 Codex 핵심 범위 축소안

파일은 수정하지 않았습니다. 참고로 요청 문서의 경계를 읽기 전에 `git fetch`·`git status`·`git log`와 요청 문서 `cat`을 한 번 실행했습니다. 그 뒤에는 읽기 도구로만 자료를 확인했습니다.

## 1. 판정: 수정 권고

"대표 흐름 하나를 먼저 완주하자"는 방향은 맞습니다. 다만 이 문구를 그대로 보내면 팀원 제안을 기존 안으로 바꾸려는 것처럼 읽힐 수 있습니다.

1. **두 서비스가 섞여 있습니다.** 문구는 "통신사 업무 포털"에서 "고객정보"에 접근한다고 합니다. 그런데 기존 외주 유지보수 포털에는 고객정보가 없습니다. docs/24가 정한 보호 자산은 업체별 작업·결과이고, 실제 가입자 정보는 넣지 않는다고 했습니다. 고객정보는 MockTel의 자산입니다. 어느 서비스로 갈지는 팀 결정 사항인데, 문구가 이를 이미 정한 것처럼 흐립니다.
2. **팀원 제안의 핵심 질문이 빠졌습니다.** 팀원 안의 중심은 "기본 설정만으로는 무엇을 놓치고, 무엇을 추가해야 잡히는가"와, 같은 공격을 보강 전후로 비교하는 것입니다. Codex 문구는 기존 안의 차단·복구 흐름으로 중심을 옮겼고, 이 질문을 언급하지 않습니다. 팀원이 3분 시연으로 잡은 INC-01도 아무 말 없이 빠졌습니다.
3. **대표 흐름 하나에 직접 걸리는 제약을 반영하지 않았습니다.**
   - 웹서버 두 대가 각자 SQLite를 쓰므로, 한쪽에서 계정을 잠가도 다른 쪽에는 적용되지 않습니다.
   - VM 메모리 합 15GB를 RAM 16GB PC에 그대로 올릴 수 없습니다.
   - 팀원 안에는 별도 "데이터 영역"이 없습니다. SQLite가 웹서버 안에 있기 때문입니다.
   - "호스트 로그 분석"이 웹 계정 악용에서 호스트 이상이 생긴다는 뜻으로 읽힐 수 있습니다.

## 2. 팀원 원안의 장점을 살리는지

**절반만 살립니다.**
- **살리는 것:** 실제 사고를 참고한다는 방향, MockTel의 고객 조회 API(INC-04), 티켓, 정상 사용자 영향 확인.
- **바꾸는 것:**
  - 질문이 "탐지 공백→보강"에서 "차단·복구 검증"으로 바뀝니다.
  - 네트워크가 단일 /24에서 사용자·웹·데이터·관리 영역 구분으로 바뀝니다. 이건 docs/24의 구역 설계를 가져온 것입니다.
  - 가용성(INC-06)과 호스트 탐지 축(INC-01~03)이 빠집니다.

결과적으로 기존 Codex 안에 가까워집니다. 두 장점을 모두 살리려면, 대표 흐름 안에 "기본 탐지 vs 보강 탐지" 비교를 남기고, 그 뒤에 "티켓→승인→차단→복구"를 잇는 구성이 필요합니다.

**추천 대표 흐름: INC-04형 "고객 조회 API 계정 악용"**

정상 고객 업무 → 일반 계정으로 타 고객 객체 조회(저속·대량) → 기본 탐지(보강 전) 결과 기록 → 보강 규칙 → 티켓·승인 → 계정 잠금·세션 무효화 → 자격 증명 재설정과 정상 사용자 재확인 → `SECURE_MODE=1`에서 같은 입력 재시험.

추천하는 이유는 이렇습니다.
- 6개 티켓 중 정상 업무, 앱·네트워크·호스트 수집 로그, 계정 대응, 복구, 보강 전후 비교가 모두 들어가는 유일한 티켓입니다.
- rogue VM이나 k6 부하 없이 웹서버 한 대로 할 수 있습니다.
- 사고 연결 문구에 주의가 필요합니다. 팀원 문서는 이 유형을 KT 2012·2014(대량 조회, 객체 권한 검사 부재)에 연결했고, 출처는 언론 보도입니다. 그래서 "KT 사례 유형을 참고한 교육용 합성 시나리오"로 표시해야 합니다. 웹 계정 악용이나 IDOR을 SKT의 침투 경로로 연결하면 안 됩니다. SKT는 탐지·로그·평문 계정 관리라는 교훈의 근거로만 쓰는 것이 맞습니다.

**대안: INC-01형 "호스트 은신 행위"**

웹서버에서 BPFDoor를 흉내 낸 무해한 행위를 하고, Wazuh 보강 탐지 → 격리·증거 보존 → baseline 복원·재검증으로 이어지는 흐름입니다.
- **장점:** SKT 공개 교훈(탐지·로그 공백)과 가장 직접 연결되고, 팀원이 시연 중심으로 잡은 장면입니다.
- **단점:** 정상 사용자 업무와 복귀를 보여주기 약하고, 네트워크 역할이 작습니다.
- 팀이 SKT 연결과 HIDS를 더 중요하게 보면 이쪽이 낫습니다. 다만 "BPFDoor 일부 행위의 무해한 모사"라는 한계는 그대로 밝혀야 합니다.

## 4. 최소 완료 조건

1. **정상 기준선**
   - 조건: 정상 사용자 2명이 공격과 다른 출발지에서 본인 조회·검색을 정해진 횟수만큼 성공합니다. 정해진 시간 동안 경보 수를 기록합니다.
   - 증거: 정상 생성기 결과(응답 본문·권한 확인), 앱 인가 로그, 해당 시간의 Wazuh 경보 수(오탐 기준선).
2. **이상 접근 탐지와 미탐·미관측 구분**
   - 조건: 빠른 대량 조회와 저속 타 고객 조회를 각각 입력합니다. 보강 전과 후에 어떤 신호(NIDS·앱 로그 규칙)가 잡았고 무엇을 놓쳤는지 기록합니다. 센서가 패킷을 못 본 경우는 미탐이 아니라 "미관측"으로 따로 둡니다.
   - 증거: 입력 실행 ID와 경보의 대조표, Suricata eve.json→Wazuh 수신 기록, 앱 인가 로그.
3. **티켓과 승인**
   - 조건: 경보 근거 ID로 티켓을 만들고, 승인자·시각을 남긴 뒤에만 조치합니다.
   - 증거: ticket.md, 경보 ID, 승인·조치 타임스탬프.
4. **차단 효과와 정상 사용자 피해**
   - 조건: 잠금 후 신규 로그인과 기존 세션이 모두 거부됩니다. 정상 사용자 업무는 유지되며, 오차단이 있으면 건수를 기록합니다.
   - 증거: 재시험 HTTP 응답과 앱 로그, 같은 시간대의 정상 생성기 결과. IP 차단을 쓰면 정상 출발지 영향도 함께 기록합니다.
5. **복구와 보강 전후 비교**
   - 조건: 자격 증명을 재설정한 뒤 원래 업무만 허용되고, 이전 세션과 이전 비밀번호는 거부됩니다. `SECURE_MODE=1`에서 같은 입력이 거부됩니다.
   - 증거: 복구 재시험 결과, 시작·종료 기준을 적은 탐지 시간·복구 시간 표.

## 5. 팀원에게 보낼 메시지 초안

> 제안서 꼼꼼히 봤어요. 실제 통신사 사고를 근거로 MockTel, 탐지 축별 역할, 보강 전후 비교까지 잡아 주셔서 논의하기가 훨씬 수월해졌어요. 다만 4명이 짧은 기간에 PC 자원도 빠듯해서, 티켓 여섯 개를 같은 비중으로 하면 각각 탐지 확인에서 끝날까 봐 조금 걱정돼요. 그래서 대표 흐름 하나를 끝까지 먼저 완성하고 나머지를 붙여 가는 순서는 어떨까 싶어요. 예를 들면 INC-04처럼 고객 조회 API를 계정으로 악용하는 상황을 정상 업무 → 이상 접근 → 기본·보강 탐지 비교 → 티켓 → 승인 후 차단 → 복구와 정상 사용자 확인까지 이어 보는 거예요. 이렇게 하면 '기본 설정이 무엇을 놓치나'라는 핵심 질문도 그대로 살릴 수 있을 것 같아요. INC-01처럼 호스트 쪽을 대표 흐름으로 하는 게 더 낫다고 보시면 그 방향도 좋아요. 정상 서비스를 MockTel로 할지 기존 외주 포털로 할지, 처음 띄울 VM 구성은 같이 정했으면 해요. 편하실 때 의견 주세요!
