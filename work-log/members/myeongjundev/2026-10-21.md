## A 전용 VPN 발급·WSL에서 DB 연결 확인

- 사용자 수동 작업을 화면과 결과로 확인했다. `team-a` 사용자와 팀 CA의 사용자 인증서를 만들고 전용 프로필을 내보냈다. 사용자는 프로필과 비밀번호를 A에게 개인 전달했다고 보고했다. 프로필·비밀번호 원문은 이 일지에 포함하지 않는다.
- TRANSIT에 `HAEDAM_TEAM_VPN_A`: IPv4 UDP, 출발지 `192.168.3.7`, 목적지 TRANSIT address, 목적지 포트 1195, 로그 사용 규칙을 추가·적용한 화면을 확인했다.
- `HAEDAM_TEAM_TRANSIT`의 터널 `10.250.0.0/24`는 유지하고 IPv4 Local networks에 DB 호스트 경로 `10.10.20.10/32`를 설정했다. 사용자 화면의 Status/OpenVPN에서 `team-a`, 실제 출발지 `192.168.3.7:54463`, VPN 주소 `10.250.0.2` 연결을 확인했다.
- OpenVPN에 `HAEDAM_TEAM_VPN_A_DB`: 출발지 `10.250.0.2`, 목적지 `10.10.20.10`, TCP 3306 허용·로그 규칙을 팀 기본 차단보다 위에 둔 화면을 확인했다. 이 주소는 현재 동적 할당이며 개인별 고정 주소와 동적 풀 분리는 미설정이다.
- A의 VPN 종단은 Windows 호스트가 아니라 WSL Ubuntu였다. Windows의 TCP 실패를 WSL의 실패로 해석하지 않도록 검사 위치를 수정했다. A 결과 화면의 `ip route get`은 `via 10.250.0.1 dev tun0 src 10.250.0.2`를 보였고, `nc` 첫 시도는 timeout, 재시도는 TCP 3306 접속 성공이었다. DB ICMP 허용 규칙을 만들지 않았으므로 DB ping 무응답으로 TCP 실패를 판정하지 않았다.
- A의 MySQL 로그인에서 1045 인증 거절이 보고됐다. DB 컨테이너 `haedam-mysql` / 서비스 `mysql` / 이미지 `mysql:8.4` 기동과 포트 바인딩을 사용자 출력으로 확인했다. 관리자 조회 결과 앱 계정은 `haedam_app@%`, plugin `caching_sha2_password`, 잠금·만료 모두 N, `haedam_portal` DB 전체 권한이었다. VPN 전용 계정이나 추가 GRANT는 만들지 않았다.
- DB VM에서 앱 비밀번호를 사용한 컨테이너 내부 TCP 로그인 결과 `DATABASE()=haedam_portal`, `CURRENT_USER()=haedam_app@%`를 확인했다. 이는 DB 로컬 인증 결과이며 A WSL의 인증 성공을 대신하지 않는다. 사용자는 A가 문제없이 작업을 이어가고 있다고 보고했지만, A의 재로그인 쿼리·포털 저장·재시작 유지 결과는 별도로 받지 않았다. 비밀번호 불일치라는 원인은 아직 확정하지 않는다.

- 전달할 답변 초안을 준비했다. B는 C 전용 사용자·팀 CA 인증서·프로필과 C 유선 출발지의 UDP 1195 허용을 준비하고, C의 실제 VPN 종단과 manager 게시 포트를 받은 뒤 A 실제 agent 출발지→C manager의 TCP 1514/1515만 기본 차단 위에 허용하는 순서다. Wazuh 수집 TCP 1514와 등록 TCP 1515를 구분하고 전체 VPN 대역·다른 내부 포트를 일괄 개방하지 않는다.

- A↔C는 동일 서버의 VPN 클라이언트 간 경로이므로 B DB로의 라우팅과 구분한다. 현재 inter-client 설정·pfSense 통과 경로·Windows/WSL/Docker 수신 및 반환 경로를 확인해 최소 포트만 통제한다. 광범위한 client-to-client 설정을 단순 활성화해 해결 완료로 처리하지 않는다.
- 현재 결과는 답변 준비이며 C에게 메시지 발송·프로필 발급·포트 허용·agent Active 확인 완료가 아니다. 다음 B 첫 행동은 pfSense User Manager에서 `team-c`와 팀 CA 사용자 인증서를 준비하는 것이다.

## C VPN 접속 확인 후 Kali 준비 재개

- C의 초기 VPN timeout에 대해 TRANSIT UDP 1195 접속 규칙(출발지 `192.168.3.5`, 목적지 TRANSIT address)을 안내했고 입력 화면을 확인했다. 이후 사용자 Status/OpenVPN 화면에서 `team-c` 접속 성공, 실제 출발지 `192.168.3.5:64518`, VPN 주소 `10.250.0.3`을 확인했다. 같은 화면의 A 주소는 `10.250.0.2`다. 개인별 고정 주소 검증은 아니다.
- C가 전달한 출력은 `wazuh/wazuh-manager:4.9.0`의 호스트 TCP 1514~1515 게시·컨테이너 Up 상태다. C의 VPN 종단과 Docker 실행 위치 일치 여부, Windows 수신 방화벽, 실제 A agent 등록은 아직 별도 확인이 필요하다.
- `HAEDAM_A_TO_C_WAZUH`: IPv4 TCP, A `10.250.0.2`→C `10.250.0.3`, 목적지 포트 1514~1515, 로그 사용 입력 화면을 확인하고 DEFAULT_BLOCK 위 배치·저장·적용 및 A WSL의 두 포트 nc 시험을 안내했다. 저장·적용 후 목록과 두 시험 결과는 아직 받지 않았으므로 연결 완료로 기록하지 않는다.
- 사용자가 Kali 준비 재개를 지시했다. 로컬 VMX에서 실제 저장된 설정은 RAM 2048MB, 총 vCPU 2, 코어/소켓 2, custom VMnet5다. 파일 잠금 항목이 있어 `vmrun -T ws list`로 별도 확인했으며 실행 중인 VM은 Haedam-pfSense와 Haedam-DB 두 개뿐이었다. Kali는 부팅 전이다.
- 호스트 여유 RAM은 약 2.39GiB로 재관찰했고 B 수업 컨테이너는 계속 실행 중이다. 이 점검에서 VM·컨테이너 전원을 변경하지 않았다. 다음은 사용자 VMware에서 Kali 첫 부팅·로그인과 게스트 실제 NIC·주소·경로 확인이다.
- 후속으로 사용자가 A의 WSL(`root@DESKTOP-B4KEDI4`)에서 `nc -vz -w 5 10.250.0.3 1514`와 같은 목적지 1515 검사가 모두 `succeeded`인 결과를 전달했다. 이로써 해당 WSL→C VPN 주소의 두 TCP 포트 연결을 확인했다. 이는 실제 Wazuh 프로토콜 인증·agent 등록/Active·FIM 탐지 완료와 구분하며, agent가 다른 VM에서 실행된다면 그 환경의 경로도 별도 검증해야 한다. 다음 A·C 작업은 실제 agent의 manager 대상·등록 설정을 맞추고 C에서 agent Active와 이벤트 수신을 확인하는 것이다.
