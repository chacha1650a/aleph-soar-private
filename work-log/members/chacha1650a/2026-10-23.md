## 문제와 해결

- 증상·원인: 재부팅 직후 Graylog가 내려가 있었고, 수업 `gl-graylog`와 `flask_mysql`(`0.0.0.0:3306`)이 자동으로 다시 올라와 있었다. `.env`의 `BIND_IP`가 팀 VPN 주소라 VPN 주소가 없으면 컨테이너 포트 바인딩이 실패한다.
- 수정 내용·재확인 결과: 수업 컨테이너 둘을 `docker stop`하고(삭제 없음), MongoDB·OpenSearch만 먼저 시작한 뒤 VPN 연결 뒤에 Graylog를 시작했다. 입력 5개 RUNNING 확인. 재부팅하면 수업 컨테이너가 다시 올라올 수 있다.
- 증상·원인: 처음 합성 로그 검색이 0건이었다. GELF 추가 필드의 밑줄(`_ztest`)이 색인 필드에서는 `ztest`로 저장되는데 밑줄 이름으로 검색했다.
- 수정 내용·재확인 결과: `ztest:` 필드로 검색해 800건을 확인했다.
- 증상·원인: n8n 화면 세션이 만료되어 API가 401을 돌려줬다.
- 수정 내용·재확인 결과: D가 다시 로그인했고 화면에서 목록을 확인한 뒤 삭제했다.

## 미완료·미검증·필요한 도움

- **포털 GELF 유실 원인 미확정:** 도착률 88.6%이고 10:44:46 한 건이 없다. D 로컬 시험은 유실이 없었으므로 A→pfSense→팀 VPN 구간이나 A의 송신 쪽일 가능성이 있으나 확정하지 못했다. A→D TCP 12201은 pfSense 규칙이 UDP만 허용해 막혀 있다고 A가 보고했다. B의 규칙 추가가 필요하다.
- **시간 차이 원인 미확정:** 11:27 시험에서 D 스트림 시각이 A 로그보다 약 2.5초 늦었다. D 시계 오차와 방향이 같지만 같은 원인인지 확인하지 못했다. 포털 GELF에 시각 필드가 있는지 A에게 확인을 요청했다.
- **정상 출발지(`.100~.109`)·공격 출발지(`.41~.49`)의 `src_ip` 보존 미확인:** B 몫인 `.21`이 보존되는 것만 보고로 확인했다.
- **정상 출발지 → pfSense → 포털 경로 기준선 미측정.** 대응 판정(VPN 경로)과 회복 판정(정상 출발지 경로)의 임계값을 따로 둘지는 두 번째 측정 뒤에 정한다.
- **판정 식 미확정:** 기획서 잠정 식은 이번 결과에서 사실상 시간 초과만 잡는다. 임시안은 "응답 2,000ms 이상 또는 실패가 연속 3회"이며 PR #49에는 아직 반영하지 않았다.
- **`haedam-10`이 활성(Published)인 이유 미확인.** 티켓 저장소가 자리표시인 초안이고 Webhook은 `127.0.0.1`에만 열려 있다. 티켓 저장소 API(C)가 정해지기 전에는 비활성으로 두는 편이 안전해 보이나 아직 바꾸지 않았다.
- **`haedam-soc` 스트림 오염:** D 로컬 UDP 시험 800건(`host=zz-d-local`)이 `haedam-portal` 스트림에 있다. 요청 수 집계와 보강 전 증적에서 제외해야 한다.
- 차단·해제 API 호출, S12 이벤트 정의·n8n 대응 워크플로, 보강 전 1회, 티켓 저장소 연동은 하지 않았다.
- pfSense filterlog 출발지 필드 정규화 미적용(B 세션 보고: 파이프라인 초안 상태).
- 10/22 일지와 PR #38은 10/26에 병합했고, 이 일지의 README 링크는 같은 브랜치에서 추가했다.
