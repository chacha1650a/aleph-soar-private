## 1. 판정: 수정 권고

10종 이상, 4인 분담, 공통 기반 먼저라는 방향은 유지하는 게 맞습니다. docs/29는 "구상과 실제 통과의 구분", "같은 사건의 경보로 개수 채우지 않기", "예방과 탐지 축 분리"를 이미 적어 두었습니다. 다만 아래 5가지는 고쳐야 합니다.

1. **S8과 S10은 같은 공격 실행에서 함께 성립하는 연계 규칙입니다.** S10은 S8(웹 탐색과 인증)에 pfSense 신호를 더한 것입니다. 이 둘을 별개의 "사고 유형"으로 세면 개수가 부풀려집니다. 반대로 포털의 핵심 위협인 **업체 간 객체 접근(권한 변경 없는 권한 밖 조회)**은 12종에 없습니다. docs/21 핵심 방어 1번과 팀원 INC-04에 해당합니다.
2. **PLAN-01(S1)과 PLAN-04(S4)의 대응이 같습니다(승인 잠금·세션 회수).** S1에 계정 잠금을 쓰면, 공격자가 실패를 반복하는 것만으로 피해자 계정을 잠글 수 있습니다(잠금 악용). 대응을 다르게 해야 두 유형의 검증 가치가 갈립니다.
3. **D보다 A가 먼저 병목입니다.** 정상 업무·인증·세션을 담는 포털은 앱 기반 티켓(01~04, 06, 08, 09) 전부의 선행 조건입니다. 그런데 A는 이 기반과 티켓 4종을 함께 맡습니다. D의 부담은 그보다 뒤 단계(5단계)에 몰려 있습니다.
4. **단계 1이 사실상 플랫폼 전체입니다.** 정상 업무, 경계 경유, 수집, 티켓·승인, 효과 확인 경로가 모두 들어 있습니다. 게다가 현재 계약으로는 05·07·10·11·12를 표현할 수 없습니다. 이벤트 종류는 앱 4종뿐이고, `username`·`src_ip`가 필수이며, 사건도 `username`이 필수입니다. 계약 확장을 단계 0·1의 명시적 산출물로 넣어야 합니다.
5. **완료 기준을 더 촘촘히 해야 합니다.** 상태를 "구상 / 합성 통과 / 실제 연동 통과" 세 단계로 나누고, 티켓마다 어떤 축(탐지 개선·예방·조사·복구)이 적용되는지 표시해야 합니다. 12종이 다 끝나지 않을 경우에 대비한 확장 우선순위와 미완료 표기 규칙도 필요합니다.

**대체 후보 1(추천): 빈 자리에 "업체 간 객체 접근"을 넣습니다.** 근거는 앱의 인가 거부, 객체 소유 관계, 저속 조회와 대량 조회의 구분입니다. 정상 대조는 자기 객체 조회입니다. 대응은 조사 후 필요할 때 세션이나 계정을 회수합니다. 주담당은 객체 권한을 가진 C가 맞습니다. 이 유형이 빠지면 포털의 중심 위협이 12종 어디에도 없습니다.

**대체 후보 2: "앱을 우회한 DB 직접 접근."** DB 감사와 경계 거부를 함께 보는 유형으로, docs/26의 NR-07·NR-08에 해당합니다. DB 감사를 증적으로 보강하려 할 때 검토할 만합니다.

## 4. 단계의 현실성

- **단계 1을 나눕니다.**
  - **1a:** 포털 로그인, 경계 한 곳, 수집기 하나, 수동 티켓.
  - **1b:** 단계 3의 첫 티켓들이 요구하는 만큼만 추가(차단 사전 상태, 객체 권한, FIM 경로).
  - 계약 확장도 이 단계 산출물에 넣습니다. 비계정 이벤트, `layer`, 사건 근거 연결, 대응 검증 칸이 필요합니다.
- **단계 3의 준비 순서**
  - 포털과 덜 얽힌 05(WAF와 차단)와 07(FIM과 웹 접근)이 먼저 준비될 수 있습니다.
  - 01·09는 포털이 갖춰진 뒤입니다.
  - 차이가 나면 docs/29 말대로 공개하고 순서를 조정합니다.
- **확장 우선순위를 명시합니다.** 제안 순서는 04 → 06 → 11 → 02·03 → 업체 간 객체 접근 → 10 연계 → 12입니다. 마감 시점에 끝나지 않은 유형은 "구상" 또는 "합성 통과"로 남깁니다.
- **미확인 사항**
  - **가용성:** 부하 도구와 LB는 확정 도구 6종 밖입니다.
  - **NIDS:** docs/29는 NIDS를 요구하지 않습니다. S8의 웹 탐색 신호는 WAF에서 얻는 쪽이 자연스럽습니다. pfSense 패키지나 별도 센서를 쓸지는 미검증입니다.
  - **FIM:** 컨테이너 내부 파일을 감시하려면 호스트 경로를 연결해야 합니다.
  - **DB 감사:** MariaDB 감사 플러그인 동작은 G1-DB로 확인해야 합니다.
  - **관리자 경로:** S6을 위해 관리자 기능을 어디에 노출할지 정해야 합니다.
  - **16GB:** Wazuh 인덱서와 Graylog 저장소가 둘 다 검색 엔진 계열이라 메모리 부담이 겹칠 가능성이 큽니다. MVP의 중앙 저장소를 하나로 할지, PC를 나눌지를 실측 후 정해야 합니다.

## 5. 완료 기준 수정안

- **상태 3단계:** 구상 → 합성 통과(합성 이벤트로 규칙·사건·티켓 흐름 확인) → 실제 연동 통과(실제 소스가 중앙에 도착하고, 다른 담당이 교차 재현까지 마침).
- **티켓별 적용 축:**
  - 탐지 개선: 같은 입력과 같은 앱 정책에서 기본 규칙과 보강 규칙을 비교합니다.
  - 예방: 같은 규칙에서 취약 정책과 수정 정책을 비교합니다.
  - 조사형(02·03): 판정 근거, 승인, 잔여 위험을 남깁니다.
  - 복구형(01·04·06·07·09·12): 조치 → 실제 효과 → 복귀를 확인합니다.
  - 해당하지 않는 축은 "해당 없음"으로 적습니다.
- **실행마다 결과 라벨 하나와 증거 경로:** 미입력 / 미관측(원본 미수신) / 미탐 / 오탐 / 중복 / 조치 실패 / 효과 미관측 / 복구 실패 / 판정 불가(근거 부족). 오탐은 티켓별 정상 기준선 실행으로 셉니다.
- **실제 연동 증거를 티켓마다 지정합니다.** 예를 들어 05는 중앙에 도착한 pfSense 거부 기록, 07은 Wazuh FIM 경보, 09는 앱 인가 로그입니다. DB 감사까지 주장하려면 감사 원본이 필요합니다.

## 6. 차별점 문구와 팀 공유 메시지

**차별점 문구**
> 다른 팀이 어떤 기능을 하는지는 아직 정확히 모릅니다. 저희는 사고 유형마다 탐지에서 멈추지 않고, 승인한 조치가 실제 경계에서 효과가 있었는지, 정상 사용자가 계속 일할 수 있었는지, 복구 뒤 이전 접근이 되살아나지 않는지를 증거로 남기는 것을 목표로 합니다.

**팀 공유 메시지**
> 강사님 말씀의 '4가지 이상'을 최소 기준으로 보고, S1~S10에 추가 후보를 더해 12가지를 구상해 봤어요. 다만 공격 한 번에 함께 걸리는 연계 규칙(S8·S10)은 '사고 유형'과 '연계 검증'으로 나눠 세서 개수를 부풀리지 않으려고 해요. 우리 포털의 핵심 위협인 '다른 업체 자료 조회'도 한 유형으로 넣으면 좋겠어요. 서비스·네트워크·로그·티켓 기반은 같이 만들되, 각자 자기 기반에서 원본 로그가 중앙에 들어오는 것과 조치 하나의 효과 확인까지 먼저 맞추면 좋겠습니다. 그다음 한 유형으로 전체 연결을 확인하고, 네 명이 각자 한 유형씩 끝까지 완주한 뒤 나머지를 늘려 가요. 유형마다 '구상 / 합성 시험 통과 / 실제 연동 통과'를 구분해 기록하고, 다 못 한 건 미완료로 솔직하게 남기려고 해요. 이름별 담당과 장비는 같이 정해요!
